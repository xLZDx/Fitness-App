04How this got closed today — the tooling side

Worth recording because it's genuinely part of why this round finally produced a clean verdict, not a side note. The same day, a live debugging session on pm-bridge (the Claude↔GPT automation bridge used to run this whole review loop) found and fixed two real root-cause defects in its Playwright transport:

  • Stale-tab reuse. The browser-automation layer was silently reusing a half-alive tab that Chrome's own session-restore had handed back — same URL, but a page that never finished loading. Confirmed live: the message-turn selector matched zero elements anywhere in a 662 KB page dump on the stale tab, and 5 real turns immediately after a forced fresh navigation on the exact same conversation.
  • A same-day regression in that very fix. Forcing a fresh navigation on every call was correct once per browser session — but doing it on every call meant the reply-waiting step was discarding the very page the send step had just typed into, reloading seconds into GPT's response. That is very likely what was visible on screen as ChatGPT's own "Analysis paused" state and behind this session's earlier turn-count anomalies. Caught live by the operator watching the browser window; fixed the same day.

The round-4 verdict above was captured moments after both fixes landed, from a genuine new reply in the same long-running conversation.

06Open question: when to write per-gate AC/DoD

The operator raised a process question right after consensus: should full, structured Acceptance Criteria / Definition of Done (the same format P6.G0 already uses — Purpose / Inputs / Deliverables / Verification / Required review / Exit / Rollback) be written for every gate in the v4.4 plan now, in one upfront pass before implementation starts — or just-in-time, right before each specific gate opens. Context: production stays blocked behind P0.G0–P6.G3, and most P0–P5 gates currently just say "unchanged from v4.2," without the same AC/DoD rigor v4.3/v4.4 gave P6.G0.

GPT-PM's verdict on AC/DoD timing

Writing full, detailed AC/DoD for all of P0–P6 right now is not advisable — on this project it would almost certainly produce a stale spec and rework, since real constraints keep getting clarified as earlier gates are actually passed (P0.G0 and P6.G1's own history already proved this). But deferring every future gate's definition entirely to the day it opens isn't right either — a gate can turn out, too late, to need data or an architectural hook that should have been laid down phases earlier.

Two-tier scheme adopted:

  1. Now — a lightweight Gate Contract for every gate P0–P6: Purpose, prerequisites/dependencies, what the gate blocks, high-level deliverables/evidence classes, required reviewer roles, a high-level exit condition, a rollback class, and known external dependencies. No exact thresholds, commands, filenames, or evidence structure that depend on results from earlier gates.
  2. Exception — full detail now: P0 and the next actually-executable P1/P2 gate — context-drift risk there is low, and it establishes a working template for the whole program.
  3. Just-in-time for the rest — full structured AC/DoD (the P6.G0 format) authored immediately before each gate opens, checked against the actual repository HEAD and predecessor gates' evidence, plus one short independent pre-flight review (0 BLOCKER/CRITICAL) before the gate is marked OPEN.
  4. Principle: AC/DoD freezes before the work it evaluates begins — never retrofitted afterward to match what was actually built.

Full verbatim reply and reasoning in core/review/SPTR_EQUIPMENT_RECOGNITION_V4_4_ACDOD_TIMING_QUESTION_2026-08-22.md. None of this scheme is implemented yet — not the Gate Contracts, not the full AC/DoD for P0/the next gate; this is the agreed process, pending a separate GO to start it.
