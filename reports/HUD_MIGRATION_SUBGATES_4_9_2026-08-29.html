The status-tint design question (sub-gate 8)

Why this needed a real question, not a unilateral call

A pattern kept recurring: some GlassCard sites use tint: colorScheme.error to paint an async-error card. HudPanel had no fill-color override, so every site was kept as GlassCard under an inline exception comment. By sub-gate 7 that was 6 sites across 5 files — too many to keep deferring.

Sent the proposal to GPT-PM via PM Bridge: reuse HudPanel's own border/glow/shadow recipe and swap only the fill, the same shape HudSheet already uses for an opaque surface.

Verdict: MODIFY. The shape was approved, but GPT-PM caught a real classification error in the framing: one of the six sites (deload_banner.dart) is a recovery-recommendation accent (AppPalette.auroraPeach), not a semantic error state — visually similar, semantically different. The evidenced pattern narrowed to 5 error sites across 4 files. GPT-PM also specified: an enum (HudPanelTone), not a raw color parameter; only .error defined today, no speculative warning/success/info without evidence; tone mutually exclusive with the panel's existing secondary/dense tiers; implement immediately rather than deferring further.

Result: HudPanel(tone: HudPanelTone.error, …), covered by 8 new widget-test assertions pinning fill resolution, recipe parity, and the mutual-exclusion assertion. Two more evidenced sites turned up naturally in sub-gate 9 and slotted onto the same mechanism with no further design discussion needed.

Every sub-gate above: flutter analyze clean on touched files, relevant flutter test suites green (widget tests where they exist; the census doc names exactly which touched files have no dedicated widget test, so that gap is stated rather than implied), committed with an itemized message, and pushed.
