03Раунд 1 — что нашло ревью GPT‑PM

Каждая находка проверена независимо перед исправлением: воспроизведение в Node.js для обхода прототипов, прямое перечитывание кода для дыры в таймауте, git show против родителя для регрессии порядка проверок.

Major · исправлено

Проверка languageCode in LANGUAGE_NAMES обходилась через цепочку прототипов

Оператор in против объектного литерала проходит по ВСЕЙ цепочке прототипов, а не только по собственным ключам: "constructor", "toString", "__proto__" — всё это удовлетворяло проверке и резолвилось в реальные (не строковые) члены Object.prototype, которые затем попадали бы в промпт как function Object() { [native code] }.

Исправлено: прямое строковое равенство (=== "ru" / === "en") — у равенства нет цепочки прототипов для обхода. 5 регрессионных тестов, включая проверку каждого из найденных обходов.

Major · исправлено

Иерархия таймаутов не была структурно закреплена

.timeout() оборачивал только сетевой вызов, а не ресайз фото — так что медленный ресайз плюс легитимный сетевой round-trip вместе могли превысить внешний бюджет контроллера, даже когда собственный подтаймер сети ещё не сработал.

Исправлено (раунд 1): ресайз и сеть объединены в одно составное future под одним .timeout(). Оказалось неполным — см. раунд 2.

Minor · исправлено

Извлечение image_validation.ts не полностью сохраняло поведение

Составной невалидный случай ({mimeType:"image/gif"} без поля изображения) после извлечения получал другое сообщение об ошибке, чем до него.

Исправлено: validateImageInput владеет обеими проверками сырых типов в исходном порядке. Граница уточнялась ещё дважды — раунды 3–4.

Minor · исправлено

Журнал решений отставал; сбит счёт соседних тестовых файлов

Мелкие фактические неточности в записи журнала.

Исправлено: текст скорректирован.

04Раунд 2 — «зомби»-сетевой вызов

Major · исправлено

Future.timeout() не отменяет исходный future

Составное future раунда 1 (ресайз+сеть под одним .timeout()) всё ещё позволяло сетевому вызову стартовать (тратя реальную квоту/стоимость провайдера) уже после того, как describe() сдался и вернул null — потому что Future.timeout() в Dart не отменяет исходное вычисление, а только перестаёт его ждать; вычисление продолжает идти в фоне.

Исправлено: ресайз таймаутится отдельно первым; сетевой вызов вообще не стартует, если после ресайза не осталось бюджета — вместо «стартовать и потом бросить».

В этом же раунде 1 MINOR: порядок вычисления полей объектного литерала в JS/TS — свойства вычисляются в порядке ЗАПИСИ в исходнике, а не в порядке объявления типа, из-за чего дорогая проверка изображения выполнялась раньше дешёвой проверки языка. Исправлено переходом на последовательные const-присваивания вместо литерала с вызовами функций как значениями.

05Раунды 3–4 — уточнение границы «дёшево / дорого»

Три раунда подряд GPT‑PM сверял порядок проверок с ТОЧНЫМ порядком оригинального коммита 6e52bd6 — каждый раунд сужал границу чуть точнее, пока раунд 4 не воспроизвёл её ровно.

  • Раунд 3, MINOR: DateTime.now() не монотонны (синхронизация NTP, переход на летнее время, ручная смена часов пользователем) — заменено на Stopwatch.
  • Раунд 3, MINOR: исправление раунда 2 «язык сначала» перестаралось — проверяло язык раньше даже дешёвых проверок типа полей изображения. Разделено на checkImageFieldTypes / decodeAndValidateImageBytes.
  • Раунд 4, MINOR: граница раунда 3 всё ещё была не там — проверка допустимости MIME-типа и пустой base64-строки должна идти ПОСЛЕ языка, а не до. Переразбито на checkImageFieldsAreStrings (только два «сырых» typeof) и decodeAndValidateImageBytes (всё остальное).

Самостоятельно пойманная регрессия перед отправкой на раунд 4

Тот же более тонкий разрез, применённый наивно, сломал бы у aiEquipmentRecognition.validateImageInput его СОБСТВЕННЫЙ, более грубый порядок проверок (проверка типа и допустимости для каждого поля объединены в одно условие). Поймано прогоном существующего набора image_validation.test.ts до отправки на ревью — один тест упал. Исправлено структурно: общая работа с байтами вынесена в приватное ядро validateImageBytes, а каждый callable получил свою независимо корректную последовательность проверок поверх него.

09Сверка закрытия Rosetta: MAJOR + MINOR, оба разрешены

При закрытии плана (pm_rosetta_close) собственная реконструкция Rosetta ("changed set" из git status в этом общем, параллельно используемом репозитории, а не из диапазона коммитов плана) выдала «27 путей» и «72 негавернед-акта» без объяснения. GPT‑PM, получив эту закрывающую запись, вернул VERDICT: MAJOR findings.

Major · разрешено

«No leakage» противоречило собственному changed-set закрытия

Закрытие утверждало «diff точно совпал с заявленной областью плана, утечки нет», но перечисленные «27 путей» дополнительно включали неродственные маркетинговые/citation-отчёты, которых нет в области этого плана.

Разрешено: git diff --stat по точному диапазону коммитов плана (a6404fb..08820e5, все 7 коммитов) дал ровно 14 файлов — все в заявленной области. Маркетинговые файлы подтверждены как ?? untracked в рабочем дереве, никогда не закоммиченные ни одним из 7 коммитов — наследие параллельных сессий в этом общем репозитории. GPT‑PM независимо перепроверил через собственный доступ к GitHub (ahead_by: 7, behind_by: 0, тот же список из 14 файлов) и подтвердил.

Minor · разрешено, затем уточнено ещё раз

72 негавернед-акта без классификации

Акты разобраны на три категории по сырому журналу Rosetta: часть относится ко второму (уже закрытому) срезу, часть — read-only команды проверки (tsc, jest, flutter test/analyze, git status/diff, grep), которые классификатор Rosetta консервативно помечает как «мутацию», и остаток — реальные правки в переходном окне между черновиком плана v2 и получением GO.

Разрешено (раунд 9): итоговая формулировка журнала решений по ошибке приравняла ВСЕ 72 акта к «долгу» — GPT‑PM поймал это как отдельный MINOR. Исправлено, раунд 10: формулировка сужена до явного подмножества, точный счёт внутри которого не подсчитывался отдельно. VERDICT: APPROVE, PUSH: AUTHORIZED для 44c0a2f.
