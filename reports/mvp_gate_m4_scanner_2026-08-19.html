01

Scanner reskin — narrow scope by design

dafa2d9Scanner rebuilt onto the HUD widget kit via conservative reskin

scanner_page.dart is 1769 lines with ~44 tests pinning safety-critical behavior (AI-coach gating on stated health answers, four distinct camera-denial causes, a double-tap guard against duplicate paid cloud classification calls, the printed-text-vs-classifier-label honesty rule). A structural survey confirmed the screen had already been through an earlier redesign pass and was structurally close to the handoff's Scan block. So this gate is a presentational container swap only, not a rewrite: every Key, onTap, provider read, and safety branch is unchanged.

What changed: GlassCard → HudPanel in six places. Deliberately left on GlassCard: both error states (need a tint parameter HudPanel does not have) and five widgets each with its own documented reason (the top bar, the shutter control, the opaque sheet background over the live camera, the viewfinder banner, the camera-unavailable state — for which the handoff has no equivalent at all).

One real, additive fidelity gain: _HeroMatchCard, a new card for a confident match with a HudRing at the "Scan 78" geometry already reserved for this screen in hud_metric.dart's own doc comment but never wired to a real value until now. The ring is bound directly to VisualMatch.confidence with no renormalisation.

Independent review (flutter-reviewer) found no BLOCKER/MAJOR; one MINOR (a rounding mismatch between the ring's number and the adjacent confidence text) was fixed on the spot. Verified: flutter analyze clean, 44/44 scanner_page_test.dart with no test file changes at all, 47/47 HUD components, full suite 3102/3103 — the same documented flake.

ef8cc34A real collision found and resolved: two independent implementations of the same feature on two branches

The choice was presented to the operator as a structured question; the operator chose take Gate D, retire M3 — and on inspection Gate D's version is objectively stronger: it distinguishes "confirmed never done this" from "not found in the checked window" via a real all-session count, counts by distinct session rather than row, and accounts for AI-generated exercises for equipment with no catalog entry.

Integrated surgically, mobile files only, hand-reconciled at the current (diverged) insertion points — marketing-site files and the claim-governance register were left untouched. M3 (equipment_memory.dart and its provider) was removed after confirming by grep that nothing else referenced it; commit a08f428 remains in history.

03

M4 complete: memory wired into the scan result

9729ab5LastSessionCard wired into the Scanner's confident match — without rewriting Gate D

The surviving implementation (Gate D) was wired into _HeroMatchCard: the confident match card now renders the exact same LastSessionCard widget the equipment detail page already uses — no second implementation of the same idea anywhere in the app. Deliberately not attached to the plain "maybe this" rows — attaching memory to an unresolved candidate would claim the app knows the machine when it has explicitly said it is not sure.

The "what is this and how sure are we" hierarchy (ring + confidence + name) and "what did you log here before" (memory, a different data source) are visually separated, not merged into one row.

Four new tests in scanner_page_test.dart proving the WIRING itself (the arithmetic is already proven by equipment_type_history_test.dart): real history renders correctly; a confirmed-empty history renders no fabricated card; history from a different equipment type does not leak into this match; an unresolved candidate never instantiates a memory card at all. The first draft of one test failed with "0 widgets found" from an unmet async-provider expectation — caught and fixed before it shipped, not after.

Verified: flutter analyze clean, scanner_page_test.dart 48/48 (44 existing + 4 new), full suite 3118/3119 — the same documented flake, not caused by this change.
