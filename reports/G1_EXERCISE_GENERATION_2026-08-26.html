02What changed

The client sends only equipmentId and languageCode — no prompt, no machine name. The server resolves the machine name itself from equipmentId via a real JS Map (not an object literal — see the plan-v1 review in section 03) and decides the prompt language itself. Response parsing (parseResponse, muscle-vocab filtering) stays client-side, unchanged — that part never went over the network.

03Rosetta: the plan went through 3 revisions before GO

GPT‑PM approves the plan, not the operator (per this project's rules); the operator remains the sole approver only for irreversible operations. Plan v1 and v2 were rejected at the GO request stage — each revision answered the specific findings of the prior one.

Plan v1 · rejected — 4 MAJOR + 2 MINOR

Unsafe prototype-chain lookup, no drift guard test, wrong timeout hierarchy

The equipmentId→name lookup wasn't explicitly specified as prototype-safe; no test guarded the id→name map against drift from the live assets; the server timeout was proposed at 25s equal to the client's 25s — recreating a client/server race already fixed twice; decision point 7 proposed deleting the structural regression test along with the dead production file (GPT‑PM ruled: delete the file, repurpose the test); no muscle-vocab guard existed.

Fixed in v2: real Maps instead of an object literal; a live parity test against the assets; client timeout raised to 35s, strictly above the server's 25s; the test kept and repurposed; a muscle-vocab parity test added.

Plan v2 · rejected — 1 MAJOR + 2 MINOR

Russian machine-name semantics would have been silently lost

v2 would have resolved only the English base name regardless of language — behavior would silently change for Russian-speaking users. Verified directly: equipment.ru.json holds 69 genuinely translated entries, not an English copy. Also: the muscle vocabulary was still only checked against two independently hardcoded golden copies that could drift together undetected; ai_gateway.ts still referenced the soon-to-be-deleted provider_safety_settings.dart.

Fixed in v3: two separate Maps (EN/RU) chosen by a validated languageCode; the TS test now reads the ACTUAL Dart source via regex and compares element-for-element instead of a second hardcoded list; the ai_gateway.ts comment updated.

Plan v3 (Fitness_App-2026-08-26T20-00-13-970Z-78ff27) received GO along with an 18-item binding Definition of Done — section 08.

Two defects self-caught before review

The hand-typed equipment map was wrong. The first draft of EQUIPMENT_NAMES_EN/_RU was typed from memory and confused with a separate, differently-sized list, CANONICAL_MACHINES, in another file — several ids were simply wrong or invented. Caught before commit: a one-off Node script was written to read the live JSON assets directly, the map regenerated programmatically, and the hand-typed draft replaced wholesale.

A false positive in the structural guard test. An early version of the "zero direct Gemini calls" check also scanned for the literal string FirebaseAI.googleAI() — which appears verbatim in all four migrated files' own doc comments describing what they NO LONGER do. Caught by running the new test locally before committing — it failed on 4 false matches. Fixed, at that point, by narrowing the scan to generativeModel( (the real constructor call, never appearing in prose) and requiring an import '...'-prefixed match for the package:firebase_ai import check — a single-quote-only pattern that was itself still incomplete: round 1 (section 04) caught that it missed a valid double-quoted import and generalized it to a quote-agnostic regex.
