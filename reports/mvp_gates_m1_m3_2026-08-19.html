M3 — Level-1 equipment-type memory (domain layer)

a08f428equipmentMemoryFor(): what the user last did on this TYPE of machine

A pure, Flutter-independent function (equipment_memory.dart) resolves the most recent matching entry from the real workout history (workoutSessionHistoryProvider) via the exerciseId → ExerciseItem.equipmentId chain — the log entry itself carries no direct equipmentId — reusing the same catalogue-map pattern already used by day_result.dart and session_digest.dart. Wired via equipmentMemoryProvider (Provider.family).

"Type," not "this exact unit" — the whole point of the contract: the equipment id names a machine model, not a physical unit in a specific gym — nothing in this app's data model represents per-instance state, and inventing one would be exactly the kind of claim this gate exists to rule out. Every field is copied verbatim from a real log entry: no progression, no projected next weight — this is recall, not coaching.

Scanner-screen integration is deliberately deferred to M4 (its own handoff-driven rebuild), not skipped: wiring the service into a screen about to be fully rewritten would be thrown-away work. The domain layer itself does not wait on M4, per the mandate's own instruction.

Verified: 8/8 unit tests on the pure function (latest by time, not by list position; unrelated equipment excluded; a deleted/renamed exerciseId is skipped, not guessed at; no history returns null, not a zeroed record) and 3/3 real-provider wiring tests. Full suite 3102/3103 — the same documented flake.

04

Operator rule change: push immediately after every commit

Mid-thread (between M2 and M3) the operator introduced a new mandatory rule for this session: push immediately after every commit and verify remote HEAD equals local HEAD before starting the next unit of work — superseding the prior "PUSH: NO" restriction for this thread only. The cycle is now: implement → test → review/mutation where warranted → fix → commit → push immediately → verify remote → only then the next work. No batching commits.

Attached to that message was a large mandate written for a SIBLING worktree (D:\Repo\Fitness_App on marketing/site-prototype-2026-08-19) — the operator explicitly flagged it as a report from that other tree, specifically so this thread would not start building a second, competing Home/Scanner implementation on top of the marketing branch. That mandate's own worktree-ownership rule ("if the redesign is on formcoach/gates-a-c and this session is on a different branch, do not silently port mobile UI there") and this repo's own "one session, one project" rule agreed: only the operator's own two general statements from that message (MVP-first, push after every commit) were adopted here; everything about Gate F, the marketing site, or claim-governance belongs to a different session on a different tree and was left untouched.
