How it fits together

Finding 1 — the real cause of the report

PAR-Q+ (the standard 7-question pre-exercise readiness screen) blocks starting any workout — a program or a single catalog exercise — until fully completed. The test account had never completed it.

The screen shows text like "the health screen did not clear you," but to a non-technical user who just wants to start a workout, that reads exactly like "the app isn't responding" — which is most likely what got reported as "results aren't saving": the workout could not even start, let alone fail to save.

Completing the screen (7 questions, answering "No" to each) lifted the block immediately, with no app restart needed.

Finding 3 — a real crash found while automating

Porting the same scenario into an automated test (real widget tree, real button, real difficulty sheet) reproducibly hit:

Bad state: Cannot use "ref" after the widget was disposed.
  #4 _MarkCompleteButton.build.onTap (workout_player_page.dart:723)

Cause: the workout screen's list (SmoothScrollList) is an unkeyed ListView.builder. Tapping "Mark complete" starts a rest timer, which inserts a row ABOVE the button, shifting every index below it by one. With no key to follow the widget across that shift, Flutter silently disposes the button's element and rebuilds a fresh one — and the async code still running inside the OLD onTap (awaiting the rating sheet) touches the now-dead reference.

The existing if (!context.mounted) return; guard sat BEFORE the rating sheet opened, but nothing covered the window AFTER it closes — exactly the window the rest-timer insertion opens on every single completion, not a rare race.

In production: most likely silently swallowed as an unhandled error (reported to Crashlytics) rather than a visible crash — but the difficulty rating itself ("Too easy / Just right / Too hard") silently fails to save when this hits, even though the set's own completion had already saved successfully by that point.

First fix (round 1, pre-review): one additional if (!context.mounted) return; right after the rating-sheet await resolves — which GPT-PM's own review then caught as a fresh bug of its own (see below).

GPT-PM review round — three MAJOR findings, all remediated

1. The first fix silently discarded the rating the user had already chosen. The context.mounted guard sat BEFORE the persistence code — so exactly in the reproduced scenario (element disposed while the sheet is open) the code now quietly returned without ever saving the user's choice. The crash was gone; the data loss was not. Real fix: a ProviderContainer is captured at the top of the handler (tied to the whole route, not to any one widget's lifecycle), and the rating is now always persisted through it; context.mounted only gates the SnackBar, never the write.

2. The test itself could not have caught finding 1. Tapping the rating pill was optional (if (...isNotEmpty)), and no assertion ever read the saved difficulty field back — a version of the code that dropped every rating would still pass. The tap is now mandatory, and the test asserts difficulty was actually saved for all three exercises.

3. "Remembered to recalculate next time" was only proven within the same live screen. The test read stats off the SAME ProviderScope it had just written into — proof the write and the read agree with each other, not proof a COLD restart actually recovers the data. Reworked: the repository is now created OUTSIDE the widget tree; the test tears the whole screen down, rebuilds it from scratch (a genuinely new ProviderScope) against the SAME repository, and proves the three previously-saved workouts come back with no re-tapping — then adds two more on top of the recovered state and proves the count grows rather than resets.

A fourth finding — not from GPT-PM, found while verifying my own fix. The same finding #3 also meant the new test file would not actually run "on every run" — CI hard-coded one file name (app_test.dart) instead of the whole folder. Fixing that (running the whole integration_test/ directory in one command) reproduced a separate, previously-latent tooling bug on the real device: the second file's APK build/install began while the first file's device session was still mid-suite, replacing its running process — every remaining test in the first file then failed with "did not complete" instead of a real result. Fixed by switching to a loop that runs each file as its own separate flutter test process — exactly how both files had already run reliably, individually, earlier the same day.

With that fix, both files now reach a clean, deterministic result together — which surfaced yet another, entirely separate finding unrelated to this task: app_test.dart has 3 pre-existing failures (the bottom nav actually renders labels in UPPERCASE — "ГЛАВНАЯ" / "СКАН" — while the test looks for normal case "Главная" / "Скан"). Unrelated to workout saving and not touched in this gate — recorded in core/DECISION_LOG.md as its own open item for a future gate.

Rounds 3-6 — CI/runner scope, not the save path itself

Round 3 — the run_app.ps1 question. GPT-PM initially required the new test to run on literally any device launch, including via run_app.ps1 — an interactive manual-debugging launcher, not a test runner. Pushed back with evidence (wiring a multi-minute automated suite into it would tax every unrelated manual debug session); GPT-PM explicitly withdrew the requirement, agreeing CI + run_tests.ps1 -Integration are the right, sufficient surfaces.

Round 4 — a real defect in round 1's own fix. Both the CI bash loop (set -e) and the PowerShell loop (return on first failure) stopped at the first failing file — and app_test.dart (already known-red) sorts alphabetically before the new test file. So "this test runs on every CI job" was factually false. Fixed: both runners now execute every file regardless of earlier failures and aggregate the result at the end.

Round 5 — a subtler PowerShell scoping bug, also caught by GPT-PM. A direct $LASTEXITCODE = ... assignment inside a scriptblock invoked via & creates a local shadow in a child scope that never reaches the calling Run-Step function — so if the LAST file in the loop happened to pass, an earlier real failure was silently masked. Verified with a standalone PowerShell repro before trusting the finding. Fixed by emitting a real native exit code (cmd /c exit N), which propagates correctly through the scope chain. Proven with a live end-to-end run of the FULL run_tests.ps1 -Integration on device: the known-red app_test.dart ran to completion, the new test then ran and passed 1/1, and the top-level process correctly returned a failing exit code.

Unrelated noise, investigated and ruled out. That same full run also showed analyze FAIL/test FAIL — 16 pre-existing lint findings and golden-image/layout-assertion failures in entirely unrelated files (scanner, Gemini, settings, offline cache), none overlapping this gate's diff. Three representative files were re-run in isolation and passed cleanly — full-suite-only noise (coverage instrumentation, golden-image environment sensitivity), not a regression. GPT-PM confirmed: out of this gate's scope, not to be reopened for it.
