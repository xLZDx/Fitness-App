01 Gate D — Level-1 equipment-type workout memory

2cc271b

Shows a recognized equipment TYPE's prior workout context ("Your last leg press: 45 kg × 10") — never a claim about the exact physical machine. Client-side matching over data already fetched for other screens; zero new Firestore reads, zero schema change.

Reconnaissance corrected mid-gate: D0 initially targeted the legacy workoutLogsProvider path before discovering it stopped receiving writes at F3.3/F3.4; corrected to workoutSessionHistoryProvider before any code was written. Truncated-window honesty was a deliberate design point: a miss inside a full window reads as a confirmed "never done this equipment," a miss inside a truncated window reads as "not found in your recent workouts" — never conflated.

Independent review — flutter-reviewer, type-design-analyzer, silent-failure-hunter (3 parallel, no cross-seeding)

  • BLOCKER/MAJOR

    The truncation check compared exercise-row count against the all-time session count, so a multi-exercise-session user could see a truncated window silently reported as complete.

    Fixed — count distinct sessionIds instead of raw rows.

  • HIGH

    Exercise-id matching only read the vendored catalog; 11 of 48 registry machines have no vendored exercises and fall through to AI generation, so a workout logged under a generated id could never match — permanently, not a race.

    Fixed — union in cached generated-exercise ids.

  • MAJOR

    The card gated only on the totals fetch, not the session stream's own loading state, so it could flash a false "not found" before the stream's first snapshot arrived.

    Fixed — also gate on the stream's AsyncValue.

One MINOR type-hardening applied (private constructor + .found()/.notFound() factories). One MEDIUM finding (an auth-restore-race in a shared totals provider) deliberately deferred as a candidate for a dedicated cross-consumer hardening pass, not widened into this gate.

02 Gate E — shared uncertainty contract (MRD-06)

105f9d4

Answer<T, R> — a Dart 3 sealed, exhaustiveness-checked type formalizing a pattern three independent systems (ScanOutcome, PoseGateVerdict, VideoFailureReason) had each reinvented without referencing one another: a confident value, or a domain-owned closed-set reason for not having one.

A universal numeric confidence score was explicitly rejected on the codebase's own evidence, not just instruction — two existing confidence fields in the same feature are already non-comparable 0..1 scales, one explicitly documented as "not a probability." Contract type shipped standalone; deliberately not retrofitted onto the five mature, individually-calibrated systems it could unify — doing so would mean inventing new reason taxonomies inside safety-adjacent code as an unrequested side effect. Zero existing production files touched.

Independent review — type-design-analyzer (1 specialist, proportionate to a zero-call-site change)

  • MAJOR

    Unbounded T/R let T be instantiated as nullable, reopening the exact ambiguity the type exists to close — Answer<String?, R>.confident(null) became indistinguishable from an uncertain answer through valueOrNull.

    Fixed — Answer<T extends Object, R extends Object>, enforced by the compiler itself; verified with a temporary probe confirming type_argument_not_matching_bounds, then removed.

One MINOR (phantom-R equality/hashCode asymmetry) explicitly deferred per the reviewer's own recommendation — zero call sites today.

03 Gate F — gym identity (MRD-02)

41d5b23

A free-text gymId field on EquipmentAccess, wired into onboarding and the equipment-report Cloud Function call site. Composite with gyms/{gymId}, which already existed server-side as a business/operator-provisioned namespace with a real consumer (reportEquipment's Slack webhook lookup).

Independent review — flutter-reviewer, type-design-analyzer (parallel, no cross-seeding)

  • MAJOR

    The onboarding field trimmed on every keystroke; because GlassTextField is a controlled widget that force-resyncs whenever its value prop disagrees with the displayed text, this silently deleted the space after every word as the user typed — "Iron Temple Gym" became "IronTempleGym."

    Fixed — trim only at the one consumption boundary that needs a normalized value, not inside onChanged. A first version of the regression test (precomputed target-prefix substrings) did not catch this; rewritten to append each character to the field's actual live-displayed text, it reproduced the exact corruption.

One MINOR noted and deliberately left undocumented-in-code: EquipmentAccess.gymId and a dead-code BuddyProfile.gymId share a bare name with no cross-reference — harmless today, deferred to whichever future gate revives BuddyProfile.

04 Gate G — setup-note memory (MRD-03/04/05)

8dabc20

Reconnaissance's own conclusion was "invent new schema/policy" — correct as far as it went, but it weighed only two options. A third was found: compose Gate F's gymId with the equipment catalog's existing TYPE equipmentId into a composite key approximating "physical machine instance," disclosed honestly as type-level (a gym with two identical units shares one note). No new backend schema or rules change — the existing per-user wildcard rule already covered a brand-new subcollection.

Independent review — flutter-reviewer, type-design-analyzer (parallel, no cross-seeding)

  • MAJOR

    Flutter-reviewer: save() never invalidated the read provider — a plain non-autoDispose FutureProvider.family — so a note saved once and the page revisited within the same session showed blank again, defeating the feature's entire purpose and risking a second Save silently overwriting the real note with a stale blank draft.

    Fixed — ref.invalidate(...) after save; reproduced with a test sharing one ProviderContainer across two independently-keyed widget instances (a fresh ProviderScope per pumpWidget would not have caught this).

  • MAJOR

    Type-design-analyzer (2 findings): the model's "gymId never empty" doc comment was unenforced — fromJson's old fallback let a corrupted document silently construct a note with an empty gymId, which the shared id-slug function would then fold into a collision-prone empty-input fallback shared with an unrelated feature.

    Fixed three ways — a constructor assert, the id function itself throwing on blank gymId, fromJson now returning null for a corrupted document; plus a forward-reference doc comment and a pinning test on the shared slug function.

One MINOR (a cosmetic save-confirmation race, no data corruption) left as-is per the reviewer's own not-blocking read.

05 Gate H — contribution-pipeline measurement (MRD-07)

0f3bcf3

Reconnaissance found no reader of MachineCard data anywhere in the codebase despite three doc comments claiming a collection-group read was "possible," no defined audience or cadence for one, and — the strongest reason to stop short — nothing in the shipped app ever writes the status transition a ranking would help trigger. Shipped exactly the read-only slice the evidence supports: scripts/ops/machine_card_contribution_report.py, a hand-run REST collection-group query mirroring an existing migration script's auth pattern, ranking unrecognised equipment by cross-user sighting count. No write path, no schema/rules change, no scheduled job.

Independent review — security-reviewer, python-reviewer (parallel, no cross-seeding)

security-reviewer: clean, no BLOCKER/MAJOR. Two MINOR hardening suggestions applied — narrow the REST query's field selection so free-text/model-guess fields never cross the wire; confirmed direct test coverage of the never-print-uid privacy guarantee.

  • MINOR

    python-reviewer: _decode_value had no timestampValue branch, though the model's own read side documents Firestore-native Timestamps as a real possibility for date fields — such a document would silently decode to null.

    Fixed — added the branch.

  • MINOR

    Date comparison used raw lexicographic string ordering; Dart's toIso8601String() omits the microsecond suffix when zero, so the same instant can appear at two different string widths and sort backwards.

    Fixed — parse into real datetimes first via new _earlier/_later/_parse_iso helpers. A naive/aware datetime hazard in an early draft was caught and avoided before any test run, by re-reading the code.

  • MINOR

    isinstance(times_seen, int) accepted Python booleans (bool is an int subclass) — a hand-edited boolean timesSeen would silently contribute a phantom sighting.

    Fixed — explicit bool exclusion.

  • MINOR

    The fixed-width name column truncated silently — two machines whose names agree for the first 32 characters could print as identical rows with no signal they differ.

    Fixed — visible trailing marker on truncation; ranking still always keys on the untruncated id.

Two defects self-caught before any external review: a tiebreak test that happened to pass against its own mutation because the fixture names sorted correctly by coincidence (renamed to expose it); a resolved/unresolved property with backwards boolean logic, caught while naming its own test.
