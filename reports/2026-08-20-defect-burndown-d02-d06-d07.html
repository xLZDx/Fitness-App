D-06 — Google sign-in crash

Reproduced on-device, root-caused, fixed

fixed (config), verified

On a clean S8 (app data cleared), selecting an account in Google’s native account picker landed on a debug error screen: AuthException: Sign-in cancelled — even though an account was genuinely picked, not cancelled.

Real root cause

The log carried Auth.Api.Credentials: ckln: [8] Unknown error [status=UNREGISTERED_ON_API_CONSOLE]. The debug package variant (com.fitnessapp.fitness_app.sptr.debug) had zero SHA-1 / OAuth clients registered in Firebase, unlike the release variant. The google_sign_in plugin masks this as an ordinary “cancelled”, so the app has no way to surface the real cause.

# Confirmed via google-services.json:
com.fitnessapp.fitness_app.sptr.debug  1:988522745882:android:7c05c915aa42410ec201a3
  (0 Android-type oauth clients)
com.fitnessapp.fitness_app.sptr        1:988522745882:android:b9af40bb887a0388c201a3
  oauth: ...41sj1tona3gg7ijritm2iv89ttnsd64d  (type 1)
  oauth: ...trrolll3uf2enq67ub193ddrtasl805n  (type 1)

Fixed

The debug keystore’s SHA-1 (35:F1:52:13:...:28:DB) was registered against this Android app via the Firebase Management API.

POST https://firebase.googleapis.com/v1beta1/projects/fitness-app-korostelev/
     androidApps/1:988522745882:android:7c05c915aa42410ec201a3/sha
{"shaHash":"35f15213de217919ec66e4e1e14a19e9555628db","certType":"SHA_1"}
→ 200 OK

Verified on-device

After registering: account pick → a real OAuth consent screen → accept → successful sign-in → routed to onboarding. No crash.

Change made in Firebase (project fitness-app-korostelev), not in code — no commit in this repo.

New finding — the “dead” guest sign-in button

Reproduced 4/4 in a row, root cause not established

confirmed open bug

On /login, the top “Continue” button (anonymous sign-in) does not respond to a tap. The “Continue with Google” button right below it, in the same card, works without issue — which rules out the earlier theory of a parent InkWell swallowing the tap.

What is confirmed

  • Tap coordinates precisely match the rendered button (confirmed by measuring the green gradient in the screenshot — segment y≈844–938).
  • Android delivers the touch: ViewRootImpl@...[MainActivity]: ViewPostIme pointer 0/1 and the exact MotionEvent in the log.
  • After the tap — zero new I/flutter lines: no expected screen transition, no error, no change to a “Signing in…” state.
  • Reproduced across 2 fresh app processes (pm clear + cold launch), with a delay before the tap ranging from 2 to 15 seconds — ruling out an in-flight transition animation.

Not finished

A diagnostic build was compiled with debugPrint directly in _GradientButton’s build() and onTap, to see the live isLoading/disabled state and confirm whether the handler fires at all. The first run after installing that build produced no output at all — not even the startup telemetry line (B6: session log armed) — which looks like a log-capture timing gap rather than a new symptom. The diagnostic run was interrupted by the report gate; the instrumentation was reverted and is not present in the working tree.

Working hypothesis (unverified)

This looks like the previously logged D-03 (“dead guest button”), which an earlier pass this session could not reproduce and closed as NOT_REPRODUCED. It now reproduces reliably on a fresh build of current master. The earlier App Check throttling hypothesis remains plausible but unconfirmed.
