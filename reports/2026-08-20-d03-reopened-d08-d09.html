Headline: D-03

Guest "Continue" button on /login

CONFIRMED_OPEN_BUG · reopened

Earlier in this same work session, D-03 was investigated on an instrumented diagnostic build (diag-d03) carrying debug debugPrint markers. Five taps in a row, each issued after confirmed widget-build readiness, gave 5/5 successes. That was written to DECISION_LOG.md and pushed: NOT_A_PRODUCT_BUG, a cold-start timing artifact (commit b1008d1).

Immediately after, on the real canonical (non-instrumented) build, the same tap issued 26 seconds after confirmed screen readiness — failed. That directly contradicts the verdict just written, and per the standing rule to correct wrong claims immediately, it is withdrawn with a new dated entry rather than silently rewritten.

before this report

Canonical build, tap 26s after readiness: failed. Touch reached ViewRootImpl (Android log); zero Flutter-level reaction.
control run
5 clean back-to-back trials (data clear, launch, tap ~4s after readiness): 1 success / 4 failures.
now
Decision log entry corrected. A targeted fix applied (below). On-device verification not yet complete.

Ruled out on the device, with evidence:

  • A third-party accessibility service (kz.sirius.siriuschat, app-limits) — disabled entirely, the bug still reproduced without it.
  • Touch delivery on the device in general — a control tap on the sibling "Continue with Google" button (OutlinedButton) worked every time, on the first touch.
  • Flutter-side hit-test geometry — a render-tree dump over the VM service shows the button's gesture handler correctly sized and opaque.
  • "Just wait longer" — did not hold up: a 26-second margin also failed.

What was applied (a justified but not yet confirmed fix, not a proven one): the custom _GradientButton was a bare InkWell with no Material of its own and no explicit Semantics(button: true) — unlike every other control on this screen and unlike the app's own shared button library. It never showed up as a single node in an accessibility-tree dump. It is now wrapped in its own Material + Semantics(button: true), matching the pattern already established in this codebase (GlassCard). A regression test asserting real button semantics was added and mutation-verified.

A rebuilt APK was being installed on the S8 test device for a repeat 5-trial stress test when the report hook fired. Whether the fix actually lowers the failure rate is not yet known. This is an open question, not a closed gate.

D-08 · Home refusal wording

STALE_TEST

Not a regression. The test expected urgent wording ("this needs medical attention") for a user who simply left screening questions unanswered — but under the actual F017 policy, urgency requires an answered "yes" on chest pain, not merely an unanswered question. Production code was already correct; only the test was fixed, along with the five-test cascade it had been failing.

D-09 · Blank exercise-of-the-day thumbnails

FIXED

A real bug: for an unscreened user, exercise thumbnails on an already-scheduled programme day went blank, despite being a passive preview rather than a tap into a session. The provider was split into a strict variant (for entering an exercise) and a loose variant (for previews), with no duplicated lookup logic, mirroring the app's own existing includeWholePerson: false list-filter pattern. Regression test added and mutation-verified.
