Three layers behind one error

Every recognition attempt tonight failed with the same string, firebase_functions/unauthenticated. It turned out to be three distinct causes wearing one mask: the client SDK returns that same code for genuinely different rejections.

Layer 1 — what the client showed

unauthenticated

It looked like broken auth. The AUTH-DIAG-1 diagnostic proved otherwise: the ID token was valid, aud/iss correct, and Auth and Functions resolved to the same Firebase app.

Layer 2 — what the server said

app: INVALID

Cloud Functions logs showed auth: VALID on every call and an App Check rejection. Both debug tokens registered in the project were dead — proven by exchanging them directly against the API, with no device involved.

Layer 3 — what is left

permission-denied

With a fresh token, App Check and Auth both pass and the request reaches business logic. The refusal is now honest and on-topic: the S8 session is anonymous, and AI features require a real account.

Two mistakes of mine that review caught

GPT-PM caught both, both were verified against the actual source, and both are recorded in the decision log alongside the successes — a log that only records wins stops being evidence.

BLOCKER

A live secret's value went into a plan-closure payload

Closing AUTH-DIAG-1, I pasted the App Check debug token's actual value into the evidence text. The token was already sitting in the repository in plaintext, but I added one more leak channel — the review exchange itself.

Fixed: the value was removed and the re-submitted closure carried none. No token is printed into the log, the reports or any GPT-PM message from here on — verified after every write.

MAJOR

I called signing in “reversible”. It is not

To close R2 autonomously I proposed signing into Google on the S8, arguing it could be undone with the app's own Sign out. GPT-PM rejected it; I checked the source and it is right: linkWithCredential permanently attaches the Google identity to the same UID (mobile/lib/features/auth/data/firebase_auth_repository.dart:155-165), and on credential-already-in-use the guest data is left unreachable (same file, :193-199).

The option was dropped in favour of one manual tap on the device that already has a real account.
