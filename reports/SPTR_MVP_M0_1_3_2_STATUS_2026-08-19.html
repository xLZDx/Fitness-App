01What was actually broken

One defect class, found once, then traced through three layers of the app.

authUserProvider — the stream every reactive surface in this app is built on — genuinely sits in AsyncLoading on every cold start, for every user, until Firebase finishes restoring the persisted session from disk. That is not an edge case or an adversarial timing window; it happens on every real launch. Code that read .valueOrNull during that window collapsed two different truths — "still restoring" and "genuinely signed out" — into the same null, and confidently rendered the signed-out branch as if it were established fact.

Gate M0's recon swept the current working tree against a 10-point north-star flow and found this pattern reachable at three separate layers: the data providers themselves (MVP-1), the screens that render them (scoped as MVP-2), and the router's own navigation decision (MVP-3). Everything else on the north-star checklist — onboarding, the scan→recognition→content path, safety-critical gating, account isolation, buildability, marketing-claim truth — recon'd clean; no other MVP BLOCKER surfaced.

02MVP-1 — provider layer, BLOCKER, closed

Commit f7279ca · pushed, remote SHA verified

Six leaf providers sampled ref.watch(authUserProvider).valueOrNull and returned a hard default the instant it read null — reachable on every cold start with valid, persisted credentials, not just under adversarial timing. A returning user with real history saw it apparently wiped every time they opened the app, for as long as the restore window lasted.

  • workoutSessionsProvider / workoutSessionTotalsProvider — workout_session_providers.dart
  • currentProfileProvider — profile_providers.dart (rendered "Sign in to sync" to an already-signed-in user)
  • programmesProvider — programme_providers.dart
  • generatedPlanProvider — ai_planner_providers.dart
  • scheduledSessionsProvider — scheduled_session_providers.dart (found live only once independent review pushed back on the original recon count)

Fix pattern: await ref.watch(authUserProvider.future) instead of sampling .valueOrNull — already proven three times elsewhere in this exact codebase before this gate. Test-first throughout, per the operator's own "не чинить гипотезу": each provider got a regression test that failed against the live bug (a StreamController that has not yet emitted, modeling the genuine restore gap — the mock repository replays synchronously and cannot reproduce it) before the fix landed.

03MVP-3 — navigation layer, REQUIRED, closed

Commit 68cef87 · pushed, remote SHA verified

Found independently while verifying MVP-1's own review, by neither reviewer: app_router.dart's redirect reads authRepo.currentUser — a synchronous Firebase getter with the identical cold-start ambiguity — not through any resolved-stream contract. A real signed-in user reached before restore completes would have been bounced to /login. Mitigated in practice by the splash screen's fixed 1300ms dwell timer, but not structurally closed.

Fix: SplashPage now races authUserProvider's real first emission against the existing dwell timer (Future.wait, so normal-path timing is unchanged) before ever leaving /splash, bounded by a 5-second safety timeout so a broken or hung auth stream cannot strand the user on a black screen.

A test that lied at first, caught before it was trusted

The first draft of the reproduction test used one large pump(Duration(seconds: 3)) settle call and produced a false pass against the unfixed code — the assertion should have failed (the old timer-based splash should have navigated regardless of auth state) but didn't, because a single large pump doesn't reliably settle a multi-hop async-chain-then-route-transition. Fixed by switching to the same multi-step pump sequence the pre-existing splash test already relied on; re-run then correctly reproduced the bug, and correctly passed once the real fix landed.

Two review findings, both closed

Silent failure path. The timeout/error branches were completely unlogged — inconsistent with this codebase's own boot-time-guard convention. Fixed: both branches now call debugPrint and a defensively try/catch-wrapped FirebaseCrashlytics.instance.recordError(..., fatal: false). Re-verified that calling Crashlytics from a widget does not throw in the test sandbox — an explicitly flagged, previously unverified risk, since no existing test in this codebase called Crashlytics from a widget before this change.

Unverified ordering premise. The fix assumes authRepo.currentUser is already synchronized by the time the stream fires. Verified directly against the pinned firebase_auth_platform_interface 8.1.9 method-channel source rather than left as an assumption: instance.currentUser is always assigned before the corresponding event reaches the stream controller, in both the signed-in and signed-out branches. Recorded as a doc comment on FirebaseAuthRepository.currentUser.

04MVP-2 — reclassified to POST-MVP, not built

Commit e5d462b · pushed, remote SHA verified · no code changed

MVP-2 was scoped during MVP-1's review: roughly 13 screen-level call sites (progress_page.dart, home_dashboard_providers.dart, programme_providers.dart, and others) read the now-correctly-loading providers through .valueOrNull ?? default — a plain synchronous Provider cannot itself represent "loading," so it silently renders the same false default one hop downstream of MVP-1's fix. At the time it was scoped, this was reachable, because the splash screen still navigated on a fixed timer regardless of auth state.

Re-scored after MVP-3 closed, not before. A Riverpod StreamProvider that has emitted once stays AsyncData for the rest of the session — it does not spontaneously re-enter loading. MVP-3 makes /splash wait for the real first emission before /home is ever reached, and the router's redirect only allows past /login once isSignedIn is true. MVP-3's own review confirmed no OS-level deep-link or state-restoration entry point exists anywhere in this app that bypasses /splash.

So the window MVP-2 was required to close — a user reaching these screens while auth is still genuinely restoring — is no longer reachable by any path in the app. What remains at those call sites is ordinary post-auth Firestore-fetch latency: normal loading-flicker every app has, not the auth-restore truthfulness defect the MVP criterion names.

Decision: reclassified POST-MVP. The .isLoading-gating fix (matching the codebase's own existing correct pattern at entitlementStatusProvider) is still worth doing as UX polish — a skeleton beats a flashed zero — but it is not a release blocker. Full call-site list and reasoning preserved in the plan doc, not discarded.

Same call, made once more: questionnaireDraftProvider

Flagged MINOR during the MVP-1 review — same defect shape, but inside a synchronous Notifier.build() where the .future pattern doesn't drop in as-is. Checked directly: /onboarding is itself only reachable once isSignedIn is true, so this provider's build() can never run while auth is genuinely still restoring for a signed-in user. Accepted as mitigated by MVP-3's router gating — not a deferral, the vulnerable window doesn't exist. No code change.
