What happened

A hypothesis checked against the code — and disproven

GPT-PM's prior decision said: extend poseMatchProvider to work in avatar mode by proving target and live pose are compared in one normalised coordinate space. Before writing any code, a background investigation agent was sent to read the real poseMatchScore, PoseTarget, the live-coordinate path, and the relevant DECISION_LOG.md history. Every citation the agent returned was independently re-verified by direct file read, not taken on faith.

Finding

There is no coordinate-space bug at all

PoseTarget.joints and live landmarks already share one isotropic contract (PoseCoordinateNormaliser), and poseMatchScore independently re-normalises each pose again — centring and rescaling to unit RMS radius. Simply deleting the null guard would already produce a number. The real, already-documented (but unconnected to the new decision) blocker is viewpoint invariance: pose_target.dart's own header states plainly that a front view and a side view are different shapes and will score differently. Every authored target is a side view; avatar mode's default stance is face-on by a separate, deliberate design decision made after a real mirrored-arm bug. The exact same failure — a correct rep, wrong angle, scored as failing — already happened for real on the camera path, which is why the coach now explicitly asks users to stand side-on.

An earlier DECISION_LOG.md entry (Gate E, 2026-08-15) had already identified exactly this and deferred it: "viewpoint-independent scoring is a prerequisite for that gate, not a follow-up to it." The later decision that "option (b)" continued from never reconciled with it.

GPT-PM's decision — received, binding

Prior direction withdrawn; this gate closes as option (d)

  • This gate option (d)

    No implementation now. The gate closes as an investigation/architecture correction, not an implementation gate. Do not remove the guard, do not re-enable push-up, do not invent a temporary score.

  • Strategic target option (c)

    A genuinely viewpoint-tolerant judgement mechanism (3D geometry or a learned representation), through the ML/Form-Coach R&D track, not the redesign execution path. The algorithm is deliberately not selected at this stage.

  • Option (a) rejected as the default fix

    Forcing avatar mode into a side-on stance to make today's 2D matcher usable would optimise the UX around an implementation limitation and reverse a deliberate face-on decision made for a real bug.

  • Option (b) rejected as production architecture now

    A face-on companion target library could be a future research baseline, but not before it's proven to reliably separate correct/incorrect technique across body types and angles — otherwise it trades one viewpoint dependence for two.

  • Joint-fault marker

    Stays deferred, now for a sharper reason: no value in the LandmarkType → SilhouetteFigure surgery before a verdict source exists that can name a specific joint at all.
