4. Блокеры — P0

P0.1 — Injury safety работает fail-open

P0 · safety

security + QA/safety · ✓ подтверждено mobile/lib/features/equipment/data/exercise_filter.dart:38

Если у упражнения нет contraindications, оно автоматически считается безопасным:

bool isContraindicated(ExerciseItem exercise, Iterable<Injury> injuries) {
  if (exercise.contraindications.isEmpty) return false; // ← fail-open
  ...
}

В каталоге ранее зафиксировано ~360 таких строк из 1887. Пользователь с травмой может получить упражнение без доказанного safety-тега. Дополнительно:

  • safeFor(null) возвращает весь список, пока профиль ещё не загружен (exercise_filter.dart:290) — fail-open до hydration;
  • recommendation/session-пути и browse-пути фильтруются по-разному (safeCatalogProvider vs forYouExercisesProvider, equipment_providers.dart:434/451);
  • AI-generated упражнения не имеют обычных contraindication-тегов и защищены только в отдельных resolve-путях.
Рекомендация. deny-by-default для injury-sensitive поверхностей; untagged → в карантин; не показывать prescription/session-контент до hydration; CI-gate untagged contraindications == 0 либо signed-off allowlist; integration-тесты на deep links, cache, reminders, scheduled sessions и AI-generated упражнения.
Спорно. Поведение явно закодировано и покрыто тестами — это опасная спецификация, а не случайный баг. Блокер остаётся.

P0.4 — App Check не enforced (fail-open на уровне attestation)

security-reviewer · ✓ подтверждено grep functions/src/index.ts

P0.5 — Donor wall: PII глобально читаемо

P0 · privacy

security + database-reviewer · ✓ подтверждено firestore.rules:236

Public donor wall — намеренное product-behavior (одна запись на донора, opt-in). Но read открыт без аутентификации. Writes корректно server-only (optInDonorWall проверяет активную подписку). Проблема в read: любой неавторизованный клиент перечисляет всех доноров, и если в документе есть PII (имя/аватар/идентифицируемые данные) — это глобальное раскрытие PII без согласия на публичность именно этого поля.

Рекомендация. Либо хранить в donor_wall только псевдоним/инициалы без PII, либо явно получать consent на публичность каждого поля, либо ограничить read request.auth != null. Добавить тест правила на отсутствие PII-полей.

5. Серьёзные — P1

P1.1 — Firestore rules: wildcard-grant антипаттерн

P1 · database/security

database-reviewer · ✓ прочитано firestore.rules:49-66

Per-user wildcard match /users/{uid}/{coll}/{document=**} даёт blanket read/write, а затем каждая carve-out коллекция (usage, receipts, profile, recognised_models, equipment_identity_*) исключается поимённо. Это deny-by-exclusion, а не explicit allowlist. Firestore разрешает запрос, если ЛЮБОЕ matching-правило его разрешает — значит, любая новая коллекция под /users/{uid}/ по умолчанию получает client-write, пока её не добавят в список исключений. Это хрупко: добавили коллекцию → забыли исключить → клиент может писать в серверные данные.

Рекомендация. Переписать на explicit allowlist: перечислить разрешённые клиенту коллекции явно, всё остальное — if false. Это устраняет класс ошибок «забыли исключить».

7. Перспективы по агентам

Architecture / Flutter / Firebase

Зрелая feature-first структура (33 модуля, единый паттерн data/state/widgets), Riverpod + go_router. Сильная сторона — последовательная iOS-портабельность через HealthService seam. Слабые: монолитный index.ts (2140 строк), монолитная route-таблица, второй ProviderContainer. Документация (CODEMAP.md, CONVENTIONS.md) — выше среднего.

QA / ML / safety logic

Покрытие впечатляющее: ~3808 тестов, catalog pytest 210+, functions 601+473, mutation-тестирование, CT-1 content-QA с deterministic dataset-hash проверкой. ML-провенанс ведётся (запрет train-on-machine-output, реестры). Но: safety-фильтр fail-open (P0.1), нестабильность полного suite (P0.2), отсутствие release-level native-ML smoke. Equipment-классификатор намеренно слабее text-anchor (5/18 vs 18/18) — измеренный дизайн, не дефект.

Security / privacy / abuse

Хорошие практики: SSRF-защита gym webhook (https-only + redirect:"manual"), per-user/per-day квота через transaction, секреты через Secret Manager, грамотный .gitleaksignore с обоснованием каждого fingerprint, quota под user-документом (стирается deleteAccount). Слабые: App Check не enforced (P0.4), donor wall PII (P0.5), wildcard-rules (P1.1), 11 moderate npm vuln (P1.6). Stripe в test-mode — нормально для стадии, к production требует перевода и ротации webhook-secret.

Database / Firestore data model

Правила подробно комментированы, carve-out коллекции изолированы серверной записью, канарейка-токен structurally excluded. Но архитектура правил — deny-by-exclusion (P1.1): новый серверный путь под /users/{uid}/ автоматически получает client-write, пока не добавлен в исключения. Explicit allowlist безопаснее. Lifecycle-coverage не полная (P1.5).

Silent-failure hunter

Код демонстрирует осознанную борьбу с silent failures: isDeliverableWebhook логирует отказ поимённо; enforceDailyQuota кидает resource-exhausted; exerciseNameMatcherProvider «fails closed». Однако OCR-путь equipment-identity не имеет явного failure/timeout state (P1.4) — потенциальный silent fallback. Рекомендуется terminal-reporting для retry-путей и explicit state для OCR-timeout.

Build / analyze resolver

flutter analyze — 17 issue-ей (exit 1), все warning/info уровня (0 ошибок): unnecessary_type_check, unused_import, deprecated_member_use. Лечится за один проход. Главная проблема не в analyze, а в отсутствии release-build в CI (P0.3): host widget-tests проходят, но native/release rendering не проверяется.

Docs / l10n / data-governance

Документация обширна и структурна (INDEX/CODEMAP/CONVENTIONS/TECHSTACK/DEBUGGING, decision-log, per-gate reports). Но здесь самый большой дрифт: счётчики тестов устарели в 2 раза, «integration-тестов нет» — ложь, 54 битые ссылки, 2 RU/EN semantic mismatch. Особенно болезненно для проекта с принципом «доки = реальность». mobile/README.md — всё ещё starter template.
