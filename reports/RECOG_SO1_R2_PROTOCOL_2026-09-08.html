01What run #1 was not guarding

104 observations, 46 answered, 58 refused, every failure HTTP 429. Neither of the two limits behind those refusals was the one the 20-second pacing had been computed for.

The decisive arithmetic, measured from the run's own usage blocks: mean prompt 2,153 tokens, maximum 2,198 — not the 1,813 the pacing assumed. A clean pass of 104 observations with zero retries costs 2,153 × 104 = 223,962 input tokens against a 200,000 daily ceiling. The experiment does not fit in one day on this tier at all. 260 requests were made to obtain 104 observations, and no part of the program knew that.

OTPM is a per-request ceiling rather than a rate: Groq estimates output pessimistically from max_completion_tokens and refuses when the estimate exceeds 1,000. Run #1 sent 4,096 and was refused for that reason alone ten times, twice while the daily budget was still intact. Pacing cannot avoid a per-request ceiling. Actual completions were 22–41 tokens.

02The trap the classifier is built around

The daily refusal and the ordinary minute refusal open with identical words:

Rate limit reached for model `qwen/qwen3.8-27b` ... on tokens per day (TPD): Limit 200000, Used 199789, Requested 2495.
Rate limit reached for model `qwen/qwen3.8-27b` ... on tokens per minute (TPM): Limit 7000, Used 6671, Requested 2096.

A classifier keyed on that prefix would read a spent day as a spent minute and retry into it. Classification is therefore on the parenthesised limit code — (TPD), (RPD), (OTPM), (TPM), (RPM) — and anything else stops the run. Both bodies above are verbatim test fixtures.

03One wait authority instead of three signals

Revision 1 had two: the ordinary pacing sleep and pace_after_failure(), which took max(pacing, Retry-After) on the failure path only. A third guard beside them would have left the composition of three signals undefined. In revision 2 pace_after_failure does not exist. One function computes the interval before every transmission, and the runner sleeps once:

wait = 20                                    # the frozen pacing, always the floor
if valid x-ratelimit-remaining-tokens < 3600:
    wait = max(wait, reset + 2)              # the provider's own TPM reset, plus margin
    if reset is absent or malformed:
        wait = max(wait, 60)                 # conservative fallback
if this attempt follows a retryable 429 with a valid Retry-After:
    wait = max(wait, Retry-After)
# a malformed or absent Retry-After contributes NOTHING
sleep ONCE

Maximum, not addition. Each term states when a request may go, so the binding one is the latest. Nine values are frozen and asserted as the total interval before the next transmission, with an injected clock and no real sleeping:

06Run validity precedes every statistic

Revision 1 had the right thresholds in the wrong order: the scorer computed the disagreement rates, the delta, the permutation p and the competence figures, and only then reached the power floor. And that floor counted manifest rows: it reported 26 sources per arm and kind for a run in which 58 of 104 observations had no reply at all.

INVALID_INSTRUMENT is not PASS, FAIL or INCONCLUSIVE. It means the measurement is structurally invalid and the hypothesis statistics are not produced at all — not computed-and-withheld, not reported-with-caveats. There is nothing to caveat.

Proven by instrumentation rather than by reading rendered text: spies substituted for rate, delta_pp, permutation_p and competence raise when called, and an invalid fixture reaches zero of the four. Beside it sits a control on a valid fixture where all four must fire — otherwise the zero-call assertion would pass simply because nothing ever calls them.

The coverage floor counts answers. At least 20 source photographs per kind with a valid parsed answer in both arms. On run #1's shape the difference between rows and answers is 26 against 6.

Round three: the receipt could lie about which request it had tested

run_stress_probes() took the prompt, vocabulary and config as arguments, built the request from them, and then wrote the digests of the files on disk into the receipt regardless of what it had actually been handed. A probe run with a modified prompt would have produced a receipt claiming the frozen prompt's digest; that receipt would have become the eighteenth sealed artefact, passed both checks, and permanently sealed evidence saying the frozen request was tested when a different one was.

My own round-trip test — added as proof that "the writer and the validator agree" — passed the literal string "p" as the prompt and validated. The third time running that a test of mine exhibited the hole while reading as proof of the opposite.

The arguments are gone: the function reads the frozen files itself, once, and the same bytes both build the request and produce the digest. Nothing is left to forge with. Checks: the signature has no prompt, vocabulary or config parameter; the receipt binds the real digests; and a mutation pointing the writer at a decoy prompt produces a receipt binding the decoy, which then fails to clear the frozen request shape.

09What happens next, in order — and why your decision is not first

This section was written wrongly, and the closure review caught it. I named renewed operator consent as the next step. It is not the next step, and asking for it now would have been an error: consent is bound mechanically to the sha256 of the pre-registration document, and the seal block lives inside that same file. Filling the seal changes the bytes, changes the digest — and a consent granted today would no longer bind the experiment that actually gets sealed. The runner would refuse it. The operator would have had to confirm twice.

The correct order:

  1. wait out 24 hours of quiet since the last Qwen request (2.1 hours had elapsed when this gate closed);
  2. run the two synthetic stress probes, one per arm shape. No corpus photograph is involved;
  3. only if they clear — write the final 18-artefact seal including the probe receipt, verify it, commit and push;
  4. only then — one request for operator consent, bound to the digest of the sealed document and to all four manifests;
  5. after consent, the execution gate.

If the probes fail, the document stays unsealed and consent is not requested at all — there would be nothing coherent to consent to.

So that step 4 is not a surprise, here is what it will put forward. The consent recorded before run #1 authorised that manifest once, and run #1 consumed it; a second pass over the same 52 photographs requires a new explicit reaffirmation, and no reviewer approval substitutes for it:

  • the first transmission of 104 observations happened and failed as an instrument;
  • a second pass over the same 52 photographs is proposed, to the same frozen model and endpoint;
  • it will span four partitions at least 24 hours apart, not one day;
  • the provider's Global ZDR remains enabled;
  • an organisation-exclusivity attestation is also required — that no other traffic is spending qwen/qwen3.8-27b under the same organisation. The provider exposes nothing that could verify this mechanically, which is why it is an attestation rather than a check.

Until that confirmation the runner refuses to transmit anything, and today it would refuse regardless, on isolation. Nothing is being asked of the operator right now: the immediate next step is the isolation wait and the probes, which is a pause rather than a decision.

A ninth defect, found after the GO, during implementation

aggregate()/validate_bundle() originally defaulted preregistration_path/ledger_path as literal parameter values. Python binds a default value ONCE, at function-definition time — rebinding the same-named module constant afterward (exactly what the score_r2.main() end-to-end test does) silently has no effect on a call using the default. manifest_paths already used the correct technique (None, resolved inside the function body); preregistration_path and ledger_path did not, and the defect surfaced immediately as a genuine test failure. Caught by the suite itself, not by a reviewer — the same class of defect as all eighteen before it: a claim wider than the check standing behind it.
