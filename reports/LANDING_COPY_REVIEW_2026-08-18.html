The landing copy describes a different app than the one in this repository

The SPTR document sells a category: guided workouts, progress tracking, step-by-step flow. The code sells a mechanism: a photograph of the machine, a rep counter calibrated against 6,160 labelled repetitions, and an injury filter covering 1,528 of 1,887 exercises. Below: what is genuinely distinctive in this project, what in the code proves it, and what currently blocks selling any of it.

VerdictBasis: FACT

The outside critique is right, for the wrong reason

"Swap SPTR for Fitbod and nothing breaks" describes the document exactly. But its conclusion — if there is no mechanism, the landing page cannot save you, change the product — does not apply here: the mechanisms exist, and there are several. They simply never reached the copy, because the copy was written without reading the repository.

The product is stronger than its landing page. That is a rare and pleasant problem — it is fixed with text, not by rebuilding the app.

The second finding is worse: part of the document describes things that do not exist. The "Download SPTR" button, the two store badges and the footer links to App Store and Google Play are, today, untrue on all three counts.

Asset 1Basis: FACT

Photograph the machine instead of picking equipment off a list

The CODEMAP calls this "the core moat feature", and it is not built the way this is usually built. Recognition runs on two anchors, and the first one is not a neural network — it is OCR reading the machine's own printed name.

18 / 18Machine's printed name
5 / 18 · top-3TFLite classifier
69Equipment types in the registry

Measured on 30 real gym photographs the operator shot. The 29-class classifier scores 28 % top-3; the printed name identifies every frame that could be labelled. So the text anchor runs before the classifier and stays silent when it is not certain. It returns a list rather than a single answer — otherwise a cable-station decal listing six exercises reads as a shoulder-press machine.

Source: mobile/lib/features/visual_equipment/data/machine_text_anchor.dart · core/plans/B5b_TEXT_ANCHOR_2026-08-07.md · mobile/assets/models/README.md

Behind that: cloud Gemini via Firebase AI Logic, with an on-device TFLite fallback (4.5 MB in the bundle), a live-stream smoother, and a "my machines" history.

Why it sells. Fitbod, Hevy and JEFIT all require picking equipment from a list by hand. "Photograph the machine — the app reads its name and shows you what to do on it" is a checkable claim about a mechanism, not a promise of "guided workouts". That is the first-screen headline.

Note: QR codes were removed from the product on 2026-07-30 by operator decision and replaced with photo recognition. The pitch deck core/business/PITCH_2026.md still sells QR stickers — the landing page must not be written from it.
Asset 2Basis: FACT

A rep counter that stays silent where it is not accurate

The counter's thresholds are not invented. They come out of the public MM-Fit dataset (Strömbäck, Huang, Radu — IMWUT 2020, CC BY 4.0): 6,160 labelled repetitions across 21 sessions. Each movement stores its exact-match rate on holdout sessions the threshold sweep never saw.

The bar is holdoutExactRate >= 0.80. Below it, counterFor() returns null and the screen shows no number at all. The file states it as a contract: "returning null rather than a counter with guessed thresholds is the whole contract".

Source: mobile/lib/features/form_check/data/measured_rep_configs.dart

On top of that, a dedicated commit labelled the scanner, Form Coach and posture check as experimental, in plain words: recognition can name the wrong machine, the rep counter is a display and not a measurement, and posture cannot produce a defensible number from a single frame.

Why it sells. The category is saturated with "AI form check" that counts badly and never admits it. A landing section that prints the table above in full — including the two rows where the app refuses to show a number — will be the most memorable thing on the site. Nobody else does this, and a competitor can only copy it by repeating the work.

"We show a count where we verified it against 6,160 repetitions. For push-ups it is wrong — so there is no count there."

Asset 3Basis: FACT

Injuries handled in the catalog, not in a promise

1,528 / 1,887Carry contraindication tags
81 %Catalog coverage
1,527Ratchet floor in tests

The filter is a pure function with no Flutter dependency: exact matching against a closed vocabulary of body regions, substring matching only for legacy free text. Coverage is not asserted, it is measured by safetyCoverage() and held by the ratchet test kSafetyCoverageFloor = 1527 — a commit cannot quietly drop it, the suite fails.

Source: mobile/lib/features/equipment/data/exercise_filter.dart · mobile/test/features/equipment/safety_coverage_test.dart

That measurement exists for a reason. The filter was once a total no-op — 0 tags across 1,887 exercises — while eight places in the interface told the user their injuries were being screened for. The number exists so that cannot happen again unnoticed.

Why it sells. Freeletics states outright that its app is not designed to accommodate injuries; Fitbod requires manual skip-and-swap every session; Centr, Sweat, Ladder and NTC ignore the subject. Here there is a 34-step intake with an injury questionnaire and a catalog tagged to match it. The public claim has to be the number: "flag a bad knee once — 1,528 exercises carry contraindication tags, and the ones you must not do simply never appear."

Licence hygiene is part of the asset: a clip-licence audit ran in August, and a separate commit closed the gap where the licensed library had shipped but the catalog was still serving the unlicensed scaffold. For a video-heavy app heading into a store, that is not housekeeping — it is a condition of existing.

Why it sells. Two things a screenshot proves without a word: male and female demonstrations of the same exercise, and a Russian interface. The first genuinely matters to a female audience and almost nobody ships it; the second is a geographic moat, because every strong competitor in the RU/RO market is English-only.

Asset 5Basis: FACT

Two quiet differentiators worth bringing to the surface

Auto-deload

A pure function over training history: the difficulty trend across the last 7 sessions, the share of scheduled sessions completed over 14 days, and — optionally — a drop in 7-day rolling HRV against a 30-day baseline. Two signals out of three are enough to recommend a deload week. HRV is optional precisely because most users have no wearable on day one.

Source: mobile/lib/features/recovery/data/deload_detector.dart

The file's own doc-comment already carries the marketing line, and it is an honest one: the top reviewer complaint about Centr is that it "doesn't adapt to recovery".

"Other apps push you harder. This one knows when to pull you back."

Privacy as a feature, not a footer link

Progress photos are encrypted on device in AES-GCM envelopes; pose estimation runs on the phone through ML Kit, not in the cloud; account deletion and data export are deployed Cloud Functions; the Play Data Safety answers are worked out and the target age group is declared 16+. For an app that asks people to photograph their own body, that is a direct reason to install — and the document does not mention it at all.

Source: mobile/lib/features/progress_photos/data/photo_store.dart · core/PLAY_DATA_SAFETY_2026-08-05.md

BlockersBasis: FACT

Five reasons the landing page cannot be written from this document

1. The app is in no store

The official scope: Android is the only supported tier, shipping through Firebase App Distribution, with Play "later". iOS does not physically exist — there is no mobile/ios directory, no signing, no App Store Connect entry, and IAP is unimplemented; Stripe cannot be used for digital goods on iOS, so a second payment path is required before iOS can ship at all. Wear OS is in the repo and knowingly broken (its release build is debug-signed) and is not advertised as working.

Consequence for the site: no "Download" button, no two badges, no App Store link in the footer. Version one is a closed Android beta signup with a single CTA.

Source: core/PLATFORM_SCOPE.md

2. Payments are in test mode

The tier model is written ($9.99 / $19.99 monthly, $59.99 / $119.99 annual, family plans at 2 and 4 seats) and Stripe runs in test mode. Nobody can actually pay. A pricing section reading "coming soon" is worse here than no section at all — it says "we haven't decided what to charge you". Until the payment path is live: one line saying the beta is free, and nothing more.

3. The product has no settled name

The document says SPTR. The app's appTitle says "Fitness App". The pitch deck still holds the placeholder "[App Name]". The name is unchosen, and the domain, store listing, logo and every line of copy depend on it. That is a blocker before the page is coded, not a detail.

4. The business documents have fallen behind the code

The pitch sells QR stickers on gym machines — a mechanic removed from the product on 2026-07-30. The competitive assessment is dated May. Anyone writing copy from core/business/ will describe an app that does not exist. Those two documents need updating, or an explicit "historical" marker, before site work starts.

5. Language and geography are undecided

The code is fully bilingual (interface and catalog in Russian), the operator sits in Europe/Chisinau, and the landing copy is English aimed at "adults 20–45" — which is a census, not an audience. A Russian-language landing page in a market where Fitbod and Hevy are English-only is the one place where narrow positioning is nearly free.

PlanBasis: DECISION

The page structure the code implies

Eleven sections is indeed about twice what is needed — but not because there is nothing to say. Four sections repeat one idea ("it will feel clear and simple") while everything checkable was left out. The replacement is seven blocks, each with one claim and its own proof.

BlockWhat it claimsWhat proves it on screen
Hero"Photograph the machine — find out what to do on it"A real scanner screenshot with the machine name recognised. One CTA: beta access
MechanismThree steps: photo → name read → exercises on that machineThree real screenshots in sequence, no abstract mockups

On motion

The page-weight critique is fair, but there is a stronger argument than load time. This product's core asset is credibility: measured percentages, a refusal to display an unreliable number, honest "experimental" banners. An AI-generated "person in a gym" clip sitting next to an accuracy table destroys exactly that. One looping screen capture of a real scan is enough (poster frame, preload="none", loaded on scroll) plus CSS transitions. Real footage shot on a phone in a real gym is fair and honest; generation is not.

OpenBasis: UNKNOWN

Decisions needed before the first line of page code

  • Name and domain. Is SPTR a working title or the final one?
  • Landing language. Russian, English, or both? The code is ready for Russian; the competitors are not.
  • Stage. Beta signup — today the only truthful option — or wait for the Play release and build the page for it?
  • Whether to publish the accuracy figures. My recommendation is yes, together with the "no number" rows. It is the one thing separating this from the whole category, and it only works in full.
  • Geography. Moldova/Romania/CIS or an international launch — this decides the language and which machines belong in the screenshots.
