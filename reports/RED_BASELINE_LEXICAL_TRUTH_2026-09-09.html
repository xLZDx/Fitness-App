Why this gate exists

Twelve tests in test_baseline.py and test_deployment_isolation.py were red at ffb0449. They were disclosed at G3 round 7 as carried forward and unowned: neither file imports rights.py, and both were clean at the commit that last touched them.

GPT-PM, as roadmap owner, picked them as the next gate — the only thing that is broken now rather than waiting on a human. It set one condition that shaped the whole gate: do not pre-decide "update the tests" versus "fix the source". The evidence chooses.

The evidence chose: the source violated neither invariant. The checks did — they were reading prose as fact.

One defect class, two symptoms

Both root causes are the same thing: a structural assertion implemented as a raw-substring scan over file text. Such a scan cannot distinguish a dependency from a mention of one.

And a third MAJOR, about the lexer itself

GPT-PM refused a code-versus-comment split with a counterexample this repository could not have answered. With the real call order reversed:

A lexer that paints the whole ${…} span as code sees the mention before the real call and certifies an order that does not exist. Dart interpolation is a recursive state: it can itself contain strings, comments and nested braces, and r'…' does not interpolate at all.

Both refused plans were closed as rejected rather than left pending. The third was approved: VERDICT: APPROVE, 0 BLOCKER / 0 MAJOR.

What was built

  • A recursive four-class Dart lexer. Every character is CODE, STRING, LINE_COMMENT or BLOCK_COMMENT. Interpolation is a state transition, not a span; $identifier is an expression; raw strings never interpolate; block comments nest, as Dart's do. It fails closed on anything it cannot read to the end — reclassifying code as string is the direction that hides a violation. Measured over the real corpus: 697 Dart files, 0 failures.
  • The live-mode guard now fires on CODE or STRING — a string naming a cloud endpoint is a real concept reference — while comment-only mentions pass and are recorded as cloudConceptMentionsInCommentsOnly. A new mention still changes the baseline and forces a deliberate regeneration. "Needs re-deriving, not assuming" survives; it just stopped firing on prose.
  • The ordering and structural body checks consume CODE only. _exact_identity_absent stays on raw text, on GPT-PM's explicit ruling: its contract is lexical by design.
  • Compile isolation as a compiler-resolved graph assertion. tsc --listFilesOnly, every path through realpath/normcase, containment by commonpath over components rather than startswith: functions-equipment-identity-old is a different directory.
  • Project references walked separately, from tsc --showConfig, recursively — because --listFilesOnly provably cannot see them.
  • The source-level checks kept as additional guards, explicitly not claimed exhaustive: a module specifier, a ../ traversal into the package, and a functions/package.json dependency field — a channel never covered before.

The implementation review: two more MAJORs, both mine

GPT-PM reviewed the implementation and returned 2 MAJOR, 0 BLOCKER. Both were verified by measurement against the real code before acceptance. All four constituent claims were fact.

First: the fix reproduced the very defect it was fixing

verify_no_cross_import stripped comments and then matched module-specifier and traversal shapes with regular expressions over the surviving text — which still contains string literals. Measured:

False positive on prose

const note = 'do not import "…"'rejected

Prose read as code — exactly the class of defect that produced the twelve red tests, reintroduced by the remedy for it.

Missed computed paths

Real couplings, invisible to a pattern hunting one contiguous spelling. And in a file under __tests__, step 3b cannot rescue the miss — it excludes them.

Remediated by handing both questions to TypeScript's own parser (ts_dependency_probe.cjs, using the compiler already installed in functions/node_modules). A module specifier is read from the AST node that is a specifier. A runtime path is constant-folded from call arguments: string literals, substitution-free templates, + concatenation, and path.join/path.resolve over constants. A folded value counts as a path only when the whole value is one — its first component is . or ... That is what separates a real path.join from a sentence quoting the same characters.

The hand-written comment stripper was deleted, not kept. Once the parser answered the same questions, nothing distinguished the scanner from its own absence — and its three tests went with it.

That is the repository's own precedent: G3 measured an absolute-path guard against 11,110 strings, found nothing could tell it from not existing, and deleted it. A subsumed check kept in place is not defence in depth; it is a claim.

The bound that remains

Constant folding is limited to the forms listed above, and detection is bound to real sinks. Not detectable: a path assembled at runtime from a variable; a filesystem call through an alias the file never bound from fs; and an inline require("path").join(…). For a file excluded from functions/tsconfig.json, step 3b will not cover those misses either. All of it is recorded in the docstring as named gaps, not as covered cases — which is precisely the discipline this gate was opened to restore.

Round 2: the remediation had two regressions of its own — the same defect again

GPT-PM verified the fixes and returned 2 MAJOR — both direct regressions from that remediation, which is the one thing §17 permits a third round for.

what the probe rejected as a dependencyfive false positives, measured

foo.join("..", "functions-equipment-identity", "x");      → rejected
foo.resolve("..", "functions-equipment-identity", "x");   → rejected
obj.require("../functions-equipment-identity/src/x");     → rejected

The probe was semantic at the AST node but not at the sink: it accepted any property named .join, .resolve or .require, and treated the constant arguments of every call as paths. Data read as behaviour — this gate's own defect for the third time, each time one layer further down: a comment read as code, then a string read as code, now an arbitrary object's method read as node's path.

Remediated by binding the sinks to the modules they claim to be. The probe collects which local names the file actually imported from path and fs — via import * as, a default import, named imports, import x = require(…), const x = require(…) and destructuring — and only then treats path.join/path.resolve as path construction and a method on an fs binding as a filesystem sink. require is the bare identifier; obj.require is an ordinary method call.

The fixtures moved with the contract: they now read through fs.readFileSync(path.join(…)) in six shapes, and five controls assert the non-dependency forms above stay clean. One older fixture calling an unbound readFileSync(…) stopped being detected and was corrected rather than exempted — an unbound identifier is not node's filesystem module, and pretending otherwise is precisely how foo.join(…) became a dependency.

And the second: the extends walk disagreed with TypeScript about a valid chain

It parsed JSONC with TypeScript but resolved bare specifiers with node's require.resolve. Measured on a config package declaring {"main": "index.js", "tsconfig": "base.json"}: tsc accepts it and inherits base.json — exit 0, "strict": true present in the resolved options — while the hand-rolled resolver followed main, landed on JavaScript, and called the chain unreadable. An instrument that fails a valid build is the same defect class as one that passes an invalid one.

The hand-rolled resolver is gone. ts.getParsedCommandLineOfConfigFile now runs with an instrumented host whose readFile records every file consumed, so the chain is by construction exactly what TypeScript read. Diagnostics 5083/6053 still fail the check closed; 18003 ("no inputs") is ignored, because whether a config matches source files says nothing about what it inherits. The added regression first asserts that tsc itself accepts such a package and inherits the option, so it measures a disagreement rather than asserting one.

The remediation is a deletion in both cases, and that is the point

The probe already loads the real TypeScript compiler and already runs inside node. It had no business owning a second, worse copy of either.

  • collectModuleBindings and leftmostIdentifier are gone. makeBindingResolver asks checker.getSymbolAtLocation what an identifier is bound to at this occurrence and reads the declaration it lands on. Parameters, block scope, nested binding patterns and every other scoping rule come free, because TypeScript already implements them.
  • normalizeJoin and normalizeResolve are gone. foldPathCall calls the real path.win32 / path.posix. A binding's flavour comes from its module specifier, and a plain path import is folded under both — this probe runs on Windows while functions deploys to nodejs20 on Linux, so choosing one would silently choose a platform.
  • FS_OBJECT_EXPORTS names promises as the one fs export that is an object carrying the same path-taking API.
  • require is node's only when the identifier is bound to nothing.

Round 5: each round-4 fix was right in one of the two places it had to hold

GPT-PM closed the path-algebra MAJOR and confirmed, on the direct question, that the declared residue is not a blocker — step 3a is a bounded additional guard, step 3b is the isolation proof, and the limits are now stated rather than claimed as covered. Two new MAJOR, 0 BLOCKER.

MAJOR 1 — the checker was consulted in one of the two places require is read

isRequireCall asked isUnbound before treating a bare call as node's loader. moduleOfRequire, which decides that const fs = require("fs") creates an fs binding, checked only the spelling. Measured:

MAJOR 1, second half — the one-program approach leaked script globals between files

A genuine regression introduced by round 4, and the round's most serious finding because it is a miss rather than a false alarm. TypeScript treats a source with no import and no export as a script, whose top-level declarations share one global scope with every other script in the program. Measured:

other.ts   function require(name: string) { ... }        // no import, no export
probe.ts   const mod = require("../<NAME>/src/index");    -> CLEAN, wrongly

A real, unambiguous cross-import read as clean because an unrelated sibling file declared a function of the same name. Node runs each file in its own module wrapper; one program over all of them did not, so one file's isolation answer came to depend on another file's contents. Fixed with moduleDetection: ts.ModuleDetectionKind.Force (TypeScript 5.9.3, presence verified), restoring the per-file scope the runtime actually has.

MAJOR 2 — the chain model introduced a false negative on an API this file already tabulated

fs.realpath.native and fs.realpathSync.native are real callable functions — measured in node, not read off documentation — taking the same pathname in the same position as their parents. Round 4's rule required every intermediate chain segment to be an object export of fs; realpath is a function, so the whole call was discarded as "not a sink". Both read clean. FS_NATIVE_VARIANTS is now a bounded set of exactly those two names, deliberately not a rule like "any .native member", because the point of the chain model is that an arbitrary .foo.bar() is an arbitrary object.

Round 6: a declaration is not a binding

1 MAJOR, 0 BLOCKER — the first round to come back with fewer than two. Both halves of round 5's MAJOR 1 closed, and the .native MAJOR closed with its bounded list and negative control intact.

The remaining MAJOR is the round-5 fix's own regression, and it is the sharpest statement of this gate's subject so far. Round 5 defined "not node's require" as "the checker returned a declaration". But a declaration is not a binding: declare function require(name: string): any; gives the checker a FunctionDeclaration symbol and emits no JavaScript at all — what executes is still node's own module wrapper. Measured on the round-5 code:

declare function require(name: string): any;
const fs = require("fs");
fs.readFileSync("../<NAME>/terms.json");        -> CLEAN, wrongly
require("../<NAME>/src/index");                 -> CLEAN, wrongly

Both channels, because isUnbound feeds the CJS initializer AND the bare-call specifier reader — so this is the "fixed in one of the two places it lives" pattern again, arriving this time through the predicate they share rather than through either caller. declare const require: … behaves the same way; a type-only interface require already read correctly and is kept as a control.

isRuntimeValueDeclaration now decides it: a declaration in a .d.ts, one carrying the declare modifier or sitting in an ambient context, an interface, a type alias, a type parameter, or a type-only import creates no runtime value and therefore shadows nothing. The direction is chosen deliberately and stated rather than left to the reader: treating something as NOT a shadow means treating the call as node's, so a wrong guess that way costs a false alarm and a wrong guess the other way costs a miss. Fail-closed points at "assume it is node's".

Round 7: import type is erased — and a finding two-thirds refuted

1 MAJOR, 0 BLOCKER. The round-6 ambient-declaration fix closed. The remaining MAJOR is its own next layer, but the more useful record is this: two thirds of the finding were refuted by measurement, and the third was real.

The claim: the predicate read declaration.isTypeOnly, the PER-SPECIFIER flag, and therefore missed the whole-clause form import type { Foo as require }, where the specifier's own flag is false and the enclosing clause's is true. The AST shape is exactly as described — measured:

But the predicted behaviour held for only one of the three fixtures:

The reason the first two were already right is worth writing down, because this code did not choose it: checker.getSymbolAtLocation returns no declarations at all for a type-only alias used in a VALUE position, so isUnbound was true by default and the call was correctly read as node's. The namespace form is the one the checker does resolve, and it was the live defect.

So the guard was right for a reason it had not stated — this gate's own defect wearing the opposite face. Relying on that accident would be a check narrower than its claim rather than wider, and just as unearned. Both control mutants for that over-correction are in the harness, and both die.

What the gate actually turned out to be

Eight review rounds found twelve MAJOR, and not one of them was in the project's source. All twelve were in the checks — and nearly all in checks added by the previous round of this same gate. The sequence is worth reading whole:

  1. the check read a comment as code;
  2. the fix read a string literal as code;
  3. the fix read an arbitrary object's method as node's API;
  4. the fix read a name as a binding, and concatenation as path algebra;
  5. the fix asked the checker in one of two places, and leaked globals between files;
  6. the fix treated a declaration as a runtime binding;
  7. the fix read a per-specifier flag instead of the import's semantics.

Every step is the same thing: a claim wider — and once narrower — than what the check actually checks. And every real fix was a deletion: the hand-rolled extends walker, the hand-rolled comment stripper, the hand-rolled binding collector, the hand-rolled path algebra, the hand-rolled type-only test — all removed and replaced by asking the compiler, or node, which were already loaded and already knew.
