How the external review went (GPT-PM)

  • Round 1 (head 3bedcba4): MODIFY, one MAJOR finding. A test of the plan required that after a failed manual "Try again" no automatic retries happen, while the design kept the existing retry ladder (5 s, 15 s, 60 s, 5 min, 5 min). Both cannot hold. I checked the code: the finding is correct.
  • Round 2 (head 27d6dc44): the first finding closed, a second one found: in the test I had rewritten, the "open" and "bind" counters were impossible for the "journal failed to open" state. While verifying I found the root cause: the code has no separate "open attempt"; the journal object is created without touching the disk and binding (which is also the open) is a single call. The "failed to open" state is unreachable in the running app.
  • Independent review before round 3 (read-only reliability reviewer, 9 scenarios checked against the code): 5 MAJOR and 4 MINOR findings, no blocker. All applied: "failed to open" is now a defensive state without retries; a manual attempt has a clear result (started / busy / not applicable); single-flight protection and the timer belong to a "generation" (one sign-in of an account) so a late completion of a former account changes nothing; recovery counts come from an optional interface so the existing retry test stays unchanged.
  • Round 3 (head 59828804): approved, 0 BLOCKER and 0 MAJOR. The approval permits implementation and focused tests under the documented contracts. It does not permit a push to GitHub or a merge: those are possible only after the finished code is reviewed.

What the plan now says, in plain words

  • One owner of the state. For the mode choice there is one "write if not yet present" function; when onboarding finishes, a new user is guaranteed to get the mode chooser and a user of an older version gets a "migrated" record. Before, two independent writes could race each other.
  • A corrupt stored mode value is not overwritten. Before, it was read as "empty" and rewritten.
  • Never show someone else's data and never claim "no activity" falsely. While the journal is binding to the account, the panels show loading, not emptiness; the data of one account cannot appear for another after a switch.
  • Sign-out. If a journal exists but cannot be read, a sheet "we could not check the activity stored on this device" appears with the buttons "Try again" and "Sign out anyway". This refines contract item J10 (the sign-out behaviour); GPT-PM accepted it.
  • Tests are not empty. The side-rail width is tested through a replaceable measurer (tests have no real font); timers are tested on real controllers, not stubs; static checks have an explicit file list.

Accepted deviations and risks (not questions to you, but you may object)

  • A loading window of up to 11 minutes 20 seconds. If binding the journal keeps failing, the panels show a loading indicator until the five automatic retries are exhausted, and only then a message with "Try again". Accepted for S03 because nothing is written to the journal until S05, so there is nothing to show; S05 resolves it with a separate "taking longer than usual" state (a contract change).
  • No "Try again" button in the "journal failed to open" state. This deviates from acceptance criterion AC-PR-2 ("Try again" in the error panel); it is justified because the state is unreachable in the running app and there is nothing to retry.
  • The test plan is 34 percent larger than estimated at design time (458 versus 342 by stories). This is a consequence of the review findings.

What I got wrong, in plain words

  • Two authors invented the same ids for different tests. I started the design and the test plan in parallel without a single owner of the ids. I found it myself when comparing the id sets (83 in the design, 144 in the plan, 5 and 64 unpaired) before any reviewer saw it. Rule now: name one owner of the ids and compare the sets before review.
  • My task wording caused the round-2 error. I wrote "the opener or bind counter equals 1" without separating the paths, and the plan author repeated it. I also sent the retry-machine fix to the external reviewer without an independent review, and that review found what five internal reviewers had missed. Rule now: a state-machine fix gets an independent review before it is sent, and reviewers receive scenarios to work through.
  • The first design draft gave one state several writers and treated the journal as "open" by default; reviewers caught both before any code was written.
