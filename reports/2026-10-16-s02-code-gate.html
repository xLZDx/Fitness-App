What the tests and reviews found, in plain words

ProblemRiskResolution
Streams were never uploadedSummary sync marked an entry done and the uploader only picked up unfinished entries.A dedicated stream-upload marker in the journal.
The on-phone journal was not wiped on account deletionData and key stayed on the device, and sessions of the first account could be pushed into the cloud of the second.Journal wipe on account deletion and an owner guard: on an account switch the journal is wiped first.
A transient read failure deleted dataOne I/O error at start deleted the last committed version or permanently marked a stream as lost.Read errors no longer delete or mark data; retried at the next start.
Aborted account deletionThe account stayed alive but activity writes were refused for good.After 24 hours with no retry and no deletion intent record the fence is cleared automatically; no data is touched.
Timeout and starvation of the stream deletion queueTwenty stuck jobs blocked deletion for everyone else; the reconciler could overrun its time limit.Fair queue by attempt age, a deadline, operator signals.
Memory pressure on stream commitA crafted compressed file could exhaust function memory.1 GiB memory and an element-count pre-check.
Stream upload under another accountOn an account switch an unfinished upload could continue under the new account.The uploader is bound to its account and re-checks it before every network step.
The conflict screen silently went emptyAny refresh error hid conflicts and the Retry button.Loading and error states with retry.

Still needed from the operator

  • Approve the privacy wording. The paragraph about summary sync in public/privacy.html is a draft. Until approved, the cloud path stays off. Consequence: without approval nothing from the cloud can be enabled for users.
  • Three retention answers. What else besides GPS may go to the cloud; whether a "keep forever" option is offered; the default retention (730 days proposed, allowed 90, 365, 730). Does not block the code, blocks enabling.
  • Steps outside the repository before enabling: create the bucket, grant permissions, set up alerts, decide the soft-delete window and a dedicated service account. The tombstone TTL policy is now declared in the repository and deployed with the indexes, so no separate console step is needed for it.
  • Release condition. Before cloud streams are enabled in a production build or GPS recording ships, the heavy processing (compression, hashing) must move off the app's main thread. It is not a problem at the current volume.
  • For S03. Whether the local activity journal opens in the default build regardless of the cloud flag. Recommended: yes, otherwise the activity dashboard cannot show recorded workouts. Described in the S03-D design draft.
