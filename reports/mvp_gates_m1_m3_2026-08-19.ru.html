03

M3 — Память об оборудовании уровня 1 (доменный слой)

a08f428equipmentMemoryFor(): что пользователь последний раз делал на тренажёре ЭТОГО ТИПА

Чистая функция без зависимости от Flutter (equipment_memory.dart) выводит последнюю подходящую запись из реальной истории тренировок (workoutSessionHistoryProvider) через цепочку exerciseId → ExerciseItem.equipmentId (у самой записи истории нет прямого equipmentId) — тот же паттерн построения карты каталога, что уже используют day_result.dart и session_digest.dart. Подключено провайдером equipmentMemoryProvider (Provider.family).

«Тип», а не «этот экземпляр» — весь смысл контракта: идентификатор оборудования называет модель тренажёра, а не физическую единицу в конкретном зале — в модели данных приложения нет состояния на уровне физического экземпляра, и придумывать его было бы ровно той ложью, которую этот гейт обязан не допустить. Каждое поле копируется дословно из реальной записи: без прогресса, без прогнозируемого следующего веса — это память, а не тренерская подсказка.

Интеграция в экран сканера сознательно отложена до M4 (его собственный рескин под хендофф), а не пропущена: подключать сервис к экрану, который через один шаг будет переписан целиком, означало бы выбрасывать работу. Доменный слой при этом не ждёт M4, как и требует мандат.

Проверено: 8/8 модульных тестов чистой функции (порядок по времени, а не по позиции в списке; несвязанное оборудование исключено; удалённый/переименованный exerciseId пропускается, а не угадывается; отсутствие истории — это null, а не обнулённая запись) и 3/3 теста подключения к реальным провайдерам. Полный прогон 3102/3103 — тот же документированный флейк.

04

Операторское правило: пуш немедленно после каждого коммита

В середине потока (между M2 и M3) оператор ввёл для этой сессии новое обязательное правило: после каждого коммита — немедленный пуш и проверка, что remote HEAD равен local HEAD, прежде чем начинать следующую единицу работы; это отменяет прежнее ограничение «ПУШ: НЕТ» именно для этого потока. Цикл теперь: реализация → тесты → ревью/мутации где нужно → фикс → коммит → пуш немедленно → сверка remote → только потом следующая работа. Без пакетной отправки коммитов.

Вместе с этим оператор прислал большой мандат, написанный для СОСЕДНЕГО рабочего дерева (D:\Repo\Fitness_App на marketing/site-prototype-2026-08-19) — и явно указал, что это отчёт из другого дерева, чтобы этот поток не начал строить второй, конкурирующий Home/Scanner поверх маркетинговой ветки. Правило владения рабочим деревом из самого мандата («если редизайн идёт на formcoach/gates-a-c, а сессия — на другой ветке, не переносить мобильный UI туда молча») и правило «одна сессия — один проект» из D:\Repo\CLAUDE.md совпали: из присланного мандата в этот поток взяты только две общие формулировки самого оператора (MVP-first, пуш после каждого коммита), а весь контент про Gate F/маркетинг-сайт/претензии-governance не тронут — это работа другой сессии на другом дереве.
