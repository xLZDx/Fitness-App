1. Enabled the green glow 525e058

Enable live green-glow verdict for squat/hinge in avatar mode

Request

Operator: "I want that green skeleton like in the mockup, but for real, not like now." Before this commit, match scoring in avatar mode was deliberately disabled (a prior gate's decision, Codex-reviewed) — the screen showed "Counted, but not graded" instead of a verdict.

What changed

Re-enabled target scoring in avatar mode (the premise for disabling it — a scale mismatch between the silhouette and the skeleton — had already been resolved earlier). Added a matchScore fallback to avatarVerdictSeverity for squat and hinge: once the match crosses the threshold, the skeleton gets green (severity 0); red/ amber is structurally unreachable through this path.

Verification

408/408 tests, including 5 new for the new logic. A side effect was reviewed and confirmed correct: a rep can now come back "missed", where it used to stay silent.

2. Target outline shoved right and clipped 6677133

Fix target silhouette clipping: authored joints used width-normalised x, not isotropic x

Trigger

The operator sent a video of a real test: the target outline sat pinned to the right edge of the panel and clipped, while the tracked dark figure sat correctly in place.

"tell me, does this look alike??"

Root cause

The target's joint coordinates (squatBottomTarget and others) were authored as a fraction of the frame's width (0..1) — the ordinary convention. But the app draws everything in an isotropic space where x only spans 0..aspectRatio (~0.56 on a 9:16 portrait phone). A point at x=0.5 ("centre of width") landed almost at the right edge of the real 0.56-wide frame — hence the clip.

Fix

An xScale parameter on buildSilhouette converts the authored coordinates into the real frame's space at draw time. Deliberately did not touch poseMatchScore in this commit — judged that changing the calibrated threshold table alongside an urgent visual fix was too risky. That call was revisited the same evening (see below).

Verification — live, on two phones

3. The same bug lived inside the score — and made passing impossible 7c1d123

Fix poseMatchScore: same x-convention bug as the silhouette, but blocking every pass

Trigger

The outline was centred — but the "you haven't reached the silhouette" message stayed. That was the tell that the bug wasn't only visual.

What the math showed before touching code

Verified computationally (reproducing the exact normalisation algorithm poseMatchScore uses): took a landmark set representing a perfect match to the target — a real camera, correctly isotropic coordinates — and scored it without the correction.

Perfect match, uncorrected
0.7376
Passing threshold
0.80

A perfect repetition could not clear the threshold under any circumstances — not a calibration margin, a structural impossibility.

Why no test caught it

Every existing test compared the target against poses derived from the target itself (moved/scaled as a rigid body) — the same wrong coordinate convention carried onto both sides of the comparison, so the absolute x-scale error cancelled out. The bug was invisible to those tests by construction.

Fix

Same principle as the drawing fix: the target's x is multiplied by frame.aspectRatio — now directly inside poseMatchScore, keyed to the live frame's own aspect ratio rather than a constant.

Did the fix invalidate the calibrated threshold table?

Checked, not assumed: re-derived the same calibration-table scenarios synthetically, post-fix.

Verification

417/417 tests (5 new, deliberately using an independent, non-self-referential frame — isotropicPoseOf), including proof the fix didn't flatten discrimination between poses and that it works for more than one aspect ratio (9:16 and 3:4).

What changed in the process

The operator asked to stop distributing release builds via Firebase for intermediate checks — each one required them to record a video just to show what was broken. Now: a debug build (flutter build apk --debug, ~35-75s vs. ~100-220s for release) installs via adb install -r directly on both physical phones (S23 Ultra, S8), and the first-pass check is a screenshot Claude takes itself via adb shell screencap — before asking the operator to test anything.

What's still unverified

  • Needs a real body in frame

    Match scoring is now fixed mathematically and covered by tests, but the live green skeleton on a real tracked body — the thing that opened this whole gate — has not been confirmed on-device: that needs an actual person in front of the camera, which Claude cannot do.

  • Not confirmed as a regression

    The missing "start workout" button — the code governing it (coach_phases.dart) was not touched in any of the three commits. Most likely the quality gate simply hadn't yet accepted the body as fully framed — but without a live retest, a separate, still-undiscovered issue can't be ruled out.

  • Not started

    The full visual target from the operator's two reference screenshots (circular "Reps"/"Technique" gauges, the bottom "Trainer counters" panel, a photorealistic silhouette instead of a line outline) — recorded in project memory; this is the next, considerably larger gate.
