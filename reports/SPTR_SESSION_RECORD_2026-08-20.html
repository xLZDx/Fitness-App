06 · the finding that stopped the gate

06 Stop-the-line: the device pass tested the wrong branch

Mid-panel, the Clinical/Safety reviewer reported it could not find the PAR-Q-style health-screening gate (“Has your doctor ever said you have a heart condition…”, “This needs medical attention, not a workout”) anywhere in mobile/lib — despite that exact content being witnessed live on-device, in both languages, throughout §01–03. Checked directly against git rather than trusting either side.

FACT, git tree comparison — not inference

  • mobile/lib/features/safety/ (data/eligibility.dart, state/eligibility_providers.dart, widgets/eligibility_notice.dart, widgets/safety_refusal_card.dart) exists on origin/master. git ls-tree -r HEAD on this branch finds nothing under features/safety.
  • The feature's origin commits (9c16699, 8bf16d2, 917dc01, 4cfac26, d925940, and others) confirmed not ancestors of this branch's HEAD via git merge-base --is-ancestor.
  • This branch's fork point from master (78b24dc) predates all of them — not a revert; this branch was never in a position to receive that work.

Conclusion: the debug APK on emulator-5554, used for the entire session's real-device evidence, was almost certainly built from master (or a branch carrying its safety-module commits, e.g. formcoach/gates-a-c), not from marketing/site-prototype-2026-08-19. Device metadata (versionCode=14, firstInstallTime=2026-08-19 18:00:39) is consistent with an install predating this session's start. A second real device (ce0417141997e4640c, Samsung SM-G950F) was also found attached mid-session, corroborating a shared, not session-exclusive, environment — consistent with this workspace's own standing note that checkouts and devices are shared across concurrent sessions.

What stands and what doesn't

Stands: every direct source-code citation the reviewers made against this branch's actual working tree — app_router.dart, login_page.dart, auth_providers.dart, firestore.rules, gemini_equipment_service.dart. Read live from this session's real checkout, not from the running app.

Doesn't stand as evidence for this branch: every live behavioral claim in §01–03 — scan outcomes, language-switch screenshots, isolation proof, stuck-on-Welcome reproduction, injury-gate pass/fail behavior. Real observations of a real build doing real things, and the underlying defects (dead Firebase AI Logic config, the silent stuck-navigation bug, the missing Crashlytics call) are very likely still real on this branch too, since the touched code is common ancestry — but “very likely” is not this project's own evidentiary bar for a release-gate closure.

Most urgent open question this raises: it is not yet known whether this branch ships any equivalent injury/safety gate at all. The closure plan's “Existing state” section asserts one is “genuinely enforced and fail closed” for the app being released — that assertion itself may be resting on the wrong branch's code.

Decision and required next steps

MVP release gate is NOT closed. RG-5/RG-6 do not proceed on this evidence. The nine dream-team verdicts already gathered (§05) are preserved for their code-level analysis and reasoning quality; their behavioral premises need re-confirming against a verified-correct build before any BLOCKER / SUFFICIENTLY-COVERED call is treated as final.

  1. Rebuild the debug APK explicitly from this branch's current HEAD, on a device confirmed not shared with a concurrent session mid-test.
  2. Re-run RG-1/RG-2/RG-3, or at minimum spot-check: scan outcomes, language persistence, account isolation, and specifically whether this branch's injury/safety gate resembles the PAR-Q flow described above at all.
  3. Only then resume RG-5 with confirmed-accurate behavioral evidence.
