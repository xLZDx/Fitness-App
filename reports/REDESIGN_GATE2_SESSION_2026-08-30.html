Scope question — before code

Reference vs the real screen: a genuine mismatch

The reference Session screen is minimal: a ring, a done/current/pending set-status list, one dynamic-label CTA. The real workout_player_page.dart is ~970 lines: video demo, muscle map, technique steps, form-coach card, suggested-weight chip, the set timer (already on HudRing), a plate/warm-up tools row, the rest timer, and four sequential action buttons (Mark Complete / Add Another Exercise / Schedule For Later / Add To Programme). None of that richer content has any equivalent in the reference.

GPT-PM's decision (recorded as a standing governance rule for this screen): "Session reference is authoritative for visual language and timer/state presentation where there is a direct semantic mapping. It is not authoritative for removing production functionality or inventing a narrower workout-player information architecture where no mapping exists."

What shipped — within that decision

Two items, both explicitly GO'd by GPT-PM

  • RestTimer → HudRing

    The 56px rest-progress indicator now renders through the same HudRing the set timer already used, instead of the stock CircularProgressIndicator. Same state, same callbacks, same pause/skip/reset, same widget keys.

  • Timer colours → semantic tokens

    SetTimerCard and RestTimer: the five set phases now colour through AppSemanticColors instead of raw AppPalette.aurora* literals. danger is deliberately left unused — none of the five phases carries error meaning.

Explicitly out of scope for this gate: the page's four action buttons stay separate and unchanged; no new done/current/pending set-status list — GPT-PM's reasoning: such a list needs a state model that does not yet exist as a clean read-only projection of engine state.
