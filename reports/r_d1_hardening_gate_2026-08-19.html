01

R-D1-01 – R-D1-04, each closed with evidence

R-D1-01HudRingLabel overflow at large system text scale

Reproduced first: a 78px ring's centre label threw a real RenderFlex overflow — 11px at 2.0x system text scale, 55px at 3.0x. Fixed by bounding the centre child to a fraction of the ring's own drawn diameter (derived per-instance from radius/size, not a flat constant) and wrapping it in FittedBox(fit: BoxFit.scaleDown). At 1.0x every current label already fits, so this is a no-op there.

Regression-tested at 1.0/1.3/1.5/2.0/3.0x using tester.getRect — not tester.getSize, which RenderFittedBox makes tautological, since it lays its child out unconstrained and applies the fit as a pure paint-time transform the reported size never reflects. Mutation-verified: reverting to the pre-fix Center(child: child) makes both new tests fail.

Accessibility trade-off named, not hidden: the bound is fixed in px, not in textScale, so a user requesting a large scale specifically for this ring's own number gets a capped, sub-proportional result once the label exceeds the bound. A real design decision (grow the ring, or move the label outside its geometry) is out of scope for a hardening fix and is left to a future pass — the code's own doc comment says so now, instead of implying the fix is proportional. What is guaranteed and tested: the result never renders smaller than the 1.0x baseline, and never again exceeds the bound that caused the original crash.

R-D1-02Nav bar's real .40→.24 gradient fill, and the lerp bug it exposed

Measured cheap enough to implement rather than accept as a deviation: a gradient fill and a flat fill are the same GPU primitive next to the BackdropFilter already on that surface. Wired in — then a design-fidelity reviewer found a real BLOCKER underneath it.

Confirmed, independently re-verified against the Flutter SDK source, fixed: HudGlass.lerp()'s naive Gradient.lerp(a, b, t) does not do what the name suggests when one side is null — every recipe but the dark nav bar. Read directly from LinearGradient.lerp (Flutter 3.27.1 stable, packages/flutter/lib/src/painting/gradient.dart:495-504): a one-sided-null lerp returns a transparent COPY of the non-null side, never the other side's own flat colour. On a live dark→light theme toggle this painted the nav bar fully transparent at the settled end of the transition — a real defect on every theme switch, not a hypothetical one.

Fixed by snapping fillGradient (and fill, in lockstep, only when a gradient is actually involved) at the transition midpoint — the same pattern brightness already used a few lines away for the identical reason: no meaningful "in between" state. Two new tests pin both transition directions; mutation-verified by reverting to the naive Gradient.lerp call and confirming both fail.

R-D1-03HudScrollFade had no quality kill-switch

Per the mandate's own instruction not to invent a second performance-setting system, HudScrollFade now checks the existing HudQuality.frostedOf toggle and skips its ShaderMask under reduced quality — the exact mechanism HudSurface's own frost toggle already used.

R-D1-04Adaptive veil density per shipped background — and a computed contrast number, not an assumed one

A prior review round measured real brightness across all ten bundled backgrounds and confirmed a near-white worst case is reachable with the app's own shipped assets, deferring a per-image fix as its own design decision. This gate is that decision: HudBackgroundProfile, derived from each scene's measured top-zone 95th-percentile luminance, boosts the veil for the brighter scenes.

The a11y reviewer's MAJOR finding on this residual was sharp and correct: the formula's doc comment pointed to DECISION_LOG.md for its derivation, and nothing was there. Closed by writing the actual evidence — see §04 below — not by softening the claim.

05

MRD-01's premise, re-verified against this tree

Confirmed

The Marketing Decision Pack claims WorkoutLogEntry already carries exerciseId and that 1,384 of 1,887 exercises already carry equipmentId — making Level-1 equipment-type memory "a query, not a migration." Those numbers were computed against a different repository (xLZDx/Fitness-App @ 78b24dc) and were not to be trusted here without re-checking.

Measured directly against this tree's own shipped asset (assets/data/exercises_vendor.json, python3 + json.load, this session): 1,887 rows, 1,384 with a non-null equipmentId — matching the Pack's cited numbers almost exactly. No custom/user-authored exercise concept exists in this codebase, so every exerciseId a log entry can carry resolves to either the vendor catalogue or an AI-generated exercise keyed by equipment id by construction. Weight is stored as a single canonical weightKg, no unit ambiguity to resolve.

Flagged, not silently reconciled

equipment_models.dart's own doc comment states equipmentId is null for "all 1,899" of the purchased library's entries, attributing that to the vendor's free-text-only metadata. That is stale against the measured 1,384/1,887 — either the mapping gate it refers to already ran since that comment was written, or it describes a different, larger snapshot. Not edited this pass (changing it without knowing which explanation is correct risks replacing one stale claim with another); flagged for whoever next touches that file.
