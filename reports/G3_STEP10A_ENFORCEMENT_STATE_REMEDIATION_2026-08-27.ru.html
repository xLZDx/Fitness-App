01 Что построено

Автоматический, задеплоенный на Cloud Scheduler (раз в 6 часов) аналог человеческого скрипта production_manifest.py — четыре живые секции состояния, каждая честно OK либо UNAVAILABLE, никогда не выдуманная.

enforcement_state.ts — четыре секции

Код готов

Functions (инвентарь + состояние), Firestore Rules (активный релиз + ruleset), App Check (режим защиты по сервисам), Identity Toolkit (allowlist полей — секреты вроде signerKey/apiKey никогда не проходят). Пагинация с ограничением в 20 страниц, таймаут на каждый запрос, единый бюджет на весь пробник (45с под платформенным лимитом в 60с), включая получение токена.

5-я политика алертов — независимая проверка "не завис ли планировщик"

Код готов

ENFORCEMENT_STATE_STALENESS_POLICY — не LogMatch, а conditionAbsent на метрике cloudscheduler.googleapis.com/job/execution_count, которую платформа пишет сама вне зависимости от кода этого файла. Первый несобственный (не LogMatch) тип условия алерта в проекте.

Ничего не задеплоено

Ожидает

Ни функция, ни метрика, ни политики не созданы как живые ресурсы GCP — по правилу «ноль живых мутаций до чистого раунда ревью», действующему в проекте с предыдущего Шага 9B.

02 Три раунда до APPROVE

Каждый раунд ремедиации закрывал часть находок одним пакетом — не по одной находке за раунд — и следующий раунд GPT-PM проверял именно закрытие, а не искал новый периметр.

Раунд 1 · 4 MAJOR + 1 MINOR
Доступность API путали с корректностью данных (пустой список — не ошибка). HTTP 200 с битым телом читался как успех. Пагинация не работала вовсе. Устаревание проверки зависело только от собственного лога функции. Плюс: таблица статуса в README сама себе противоречила про App Check.
Ремедиация 1
Отказ закрытым на пустом/битом результате. fetchAllPages() с пагинацией. Независимая политика устаревания через conditionAbsent. Таймаут на каждый запрос. Попутно найдено и исправлено: отсутствовал заголовок X-Goog-User-Project на вызове App Check — не находка GPT-PM, обнаружено прямым curl-пробом вживую.
Раунд 2 · 4 MAJOR (те же 4, глубже)
Сравнение режима защиты App Check со строкой "OFF" — реальный API никогда её не возвращает ("ENFORCED"/"UNENFORCED"), сигнал был мёртв с рождения. Поля строк молча подставлялись как "?" вместо отказа секции. unreachable[] у Cloud Functions v2 отбрасывался молча. Таймаут на один запрос не ограничивал весь пробник целиком.
Ремедиация 2
Сравнение только с "ENFORCED". Список сервисов, которые ЭТОТ проект обязан защищать (firestore.googleapis.com — подтверждено вживую: сейчас реально UNENFORCED в проде). Обязательные поля на уровне строки, не всей секции. Единый бюджет на весь пробник, а не на один запрос.
Раунд 3 · 2 MAJOR (последние два)
Единый бюджет считался ДО получения токена, но получение токена им самим не ограничивалось — зависший вызов мог съесть весь платформенный лимит. Релиз cloud.firestore мог остаться OK без реального updateTime — а DoD Шага 10A требует именно его.
Ремедиация 3 → GPT-PM: APPROVE
Получение токена гонится против ТОГО ЖЕ бюджета (не второго независимого таймера) через новый инъецируемый raceDeadline(), с очисткой таймера в любом исходе. updateTime обязателен для cloud.firestore и для каждой функции. revision сознательно оставлен best-effort — его наличие зависит от поколения (GEN_1/GEN_2), а в проекте нет живого GEN_1 для проверки.

03 Реальные баги, найденные помимо находок GPT-PM

Не для галочки — каждый подтверждён прямой проверкой (curl-проб, живой API-вызов, живой прогон тестов), не предположением.

App Check реально UNENFORCED сейчас в проде

Живой факт

Прямой curl-проб к firebaseappcheck.googleapis.com подтвердил: firestore.googleapis.com сейчас, по-настоящему, UNENFORCED. firestore.rules даёт аутентифицированному клиенту прямой доступ к своей /users/{uid}/... ветке без собственной проверки App Check в самих правилах — значит это единственный контроль, способный требовать аттестацию на этом пути. Раунд-1 код не смог бы это увидеть, даже если бы строка вовсе отсутствовала.

Собственный баг в новом тесте на пагинацию

Найдено тестами

Четыре секции проверки идут параллельно (Promise.all) — позиционная цепочка моков в тесте ломалась из-за перемешивания первых вызовов до того, как хоть один резолвится. npm run build прошёл чисто, npx jest поймал сразу (count 1 вместо 2). Переписано на диспетчеризацию по URL — устойчиво независимо от порядка.

04 Чек-пойнт: живой деплой требует отдельного решения оператора

GPT-PM выдал полный APPROVE и явное «GO: proceed to Step 10A live activation» + «PUSH: AUTHORIZED under the current Gate policy». Тем не менее реальный firebase deploy --only functions:runEnforcementStateCheck создаёт живой ресурс в боевом проекте Firebase. §4 глобального контракта резервирует «production migrations» за оператором отдельно — «even if a broader GO exists» — явно включая одобрение делегированного ревьюера вроде GPT-PM. Поэтому сессия не деплоит сама, а фиксирует этот чек-пойнт как решение, которое должен принять оператор.

Следующий шаг после решения — по формулировке самого GPT-PM: целевой (не blanket) деплой, живой санитизированный снепшот состояния, подтверждённый ID job'а Scheduler, позитивное доказательство исполнения, контролируемое доказательство деградации/ fail-closed, независимое доказательство политики устаревания, подтверждение что 4 колбэка AI Gateway остаются НЕ задеплоенными.
