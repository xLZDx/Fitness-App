02 Rounds 4–10: every finding batch closed whole

The project's rule held: remediation closes a round in one batch, and the next round verifies exactly that closure rather than sweeping a new perimeter.

Round 4 · MAJOR: Identity Toolkit extraction depth
Verified against real Google documentation (not just live, empty-at-the-time data). Plus: the staleness policy did not scope to real 2xx traffic — added metric.labels.response_code_class="2xx", live PATCH confirmed by SHA-256 source==live.
Round 5 · MAJOR: fail-open on malformed fields
extractIdentityToolkitState/extractSmsRegionPolicy accepted any present value with no type check — a string where a boolean was expected silently passed through as real state. Fixed via a discriminated Extracted<T> result: any malformed field fails the whole section closed to UNAVAILABLE. Round 6 · MAJOR: the same gap one level up
Round 5 validated leaf fields but not the container objects above them: multiTenant: "corrupt" (a string, not an object) makes raw?.multiTenant?.allowTenants resolve to undefined via optional chaining through a primitive — indistinguishable from genuine absence. Added isPlainObject() validation at every container boundary. Plus MINOR: my own DECISION_LOG entry claimed a mathematically impossible 510→517 test-count delta — corrected via a new append-only entry backed by the real git diff.
Round 7 · clean APPROVE, first push
No new findings. First push under the standing GPT-PM push delegation.
Round 8 · MAJOR: the failure alert's match path never fired
The most significant discovery this segment. firebase-functions/logger unconditionally rewrites jsonPayload.message into "Error: EVENT\n<stack>" for ERROR severity whenever none of the passed arguments is already an Error instance — confirmed by reading the library's own source directly, not inferred. That means the exact-equality messageEquals filter never matched the function's real log line — the checker was genuinely fail-closed, but the alert meant to page someone about it could not fire.
Remediation 8 → the eventEquals mechanism
Added LogMatchFilterSpec.eventEquals, matching the metadata's own jsonPayload.event field, which the logger never rewrites. Applied only to Step 10A's own alert — a second live proof-only cycle confirmed the semantics live, live policy PATCH confirmed by SHA-256 source==live.

04 Near-miss: a premature "closed," caught on a retry

Round 9 first returned a clean APPROVE and the text "Step 10A: CLOSED" — that entry turned out to be premature. Not edited after the fact, but corrected with a new append-only "CORRECTION" entry in DECISION_LOG.md, per the project's own evidence discipline.

What happened

Live gap

The live alert policy had already been PATCHed for the new jsonPayload.event field (round 8), but the real deployed runEnforcementStateCheck function was never redeployed across the whole remediation cycle — it remained on its original build, 2026-08-27T18:40:09Z, revision runenforcementstatecheck-00001-caj, even though enforcement_state.ts and enforcement_state_schedule.ts changed substantially across rounds 4–8. At that moment the live alert was actually worse than before round 8's fix: the old code could never produce the field the policy now required.

How it was caught

--final retry

The first attempt to send the --final receipt left no trace in the send log — verified via pm_bridge_status, the send genuinely never went out. A retry landed and triggered a fresh, independent adversarial re-review — not a rubber stamp of the prior verdict, but a real re-check of live state that caught the gap.
