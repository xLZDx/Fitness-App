02 Three rounds to APPROVE

Each remediation round closed a batch of findings at once -- never one finding per round -- and the next round verified exactly that closure rather than hunting for a new perimeter.

Round 1 · 4 MAJOR + 1 MINOR
Reachability was mistaken for correctness (an empty list wasn't an error). A malformed HTTP 200 body read as success. Pagination didn't exist. Staleness detection depended entirely on the function's own log. Plus: the README's own status table contradicted itself about App Check.
Remediation 1
Fail closed on empty/malformed results. fetchAllPages() with pagination. An independent staleness policy via conditionAbsent. A timeout on every request. Found and fixed along the way: a missing X-Goog-User-Project header on the App Check call -- not a GPT-PM finding, caught by a direct live curl probe.
Round 2 · 4 MAJOR (the same 4, deeper)
App Check's enforcement-mode comparison used the literal string "OFF" -- the real API never returns it ("ENFORCED"/"UNENFORCED"), so the signal was dead on arrival. Row fields silently defaulted to "?" instead of failing the section. Cloud Functions v2's unreachable[] was silently discarded. A per-request timeout didn't bound the whole probe.
Remediation 2
Comparison against "ENFORCED" only. A named list of services THIS project actually needs enforced (firestore.googleapis.com -- live-confirmed currently, actually UNENFORCED in production). Required fields at the row level, not just the envelope. One shared budget for the whole probe, not per request.
Round 3 · 2 MAJOR (the last two)
The shared budget was computed before token acquisition but never actually applied to it -- a hung call could still exhaust the whole platform timeout. A cloud.firestore release could stay OK with no real updateTime -- Step 10A's own DoD requires exactly that field.
Remediation 3 → GPT-PM: APPROVE
Token acquisition now races against the SAME budget (never a second, independent timer) via a new injectable raceDeadline(), clearing its timer on either outcome. updateTime is required for cloud.firestore and for every function. revision was deliberately left best-effort -- its presence is generation-dependent (GEN_1/GEN_2), and the project has no live GEN_1 deployment to verify that against.

03 Real bugs found beyond GPT-PM's own findings

Not for show -- each one confirmed by a direct check (a curl probe, a live API call, a live test run), not an assumption.

App Check is genuinely UNENFORCED right now, in production

Live fact

A direct curl probe against firebaseappcheck.googleapis.com confirmed: firestore.googleapis.com is currently, actually UNENFORCED. firestore.rules grants an authenticated client direct access to its own /users/{uid}/... subtree with no App-Check gate in the rules themselves -- making this the ONLY control that can require attestation on that path. Round-1 code could not have surfaced this even if the row had been entirely absent.

A real bug in the new pagination test itself

Caught by tests

The four check sections run concurrently (Promise.all) -- a positional mock chain in the test broke because the sections' first calls interleave before any of them resolves. npm run build was clean, npx jest caught it immediately (count 1 instead of 2). Rewritten to dispatch on the request URL instead, stable regardless of call order.

04 Checkpoint: live deploy needs a separate operator decision

GPT-PM issued a full APPROVE plus explicit "GO: proceed to Step 10A live activation" and "PUSH: AUTHORIZED under the current Gate policy." Even so, the actual firebase deploy --only functions:runEnforcementStateCheck command creates a real, live resource in the production Firebase project. The global operating contract §4 reserves "production migrations" for the operator's own separate confirmation -- "even if a broader GO exists" -- explicitly including a delegated reviewer's own GO. So this session did not deploy on its own; it records this checkpoint as the decision the operator needs to make.

The next step once decided, in GPT-PM's own words: a targeted (not blanket) deploy, a live sanitized state snapshot, a confirmed Scheduler job identity, positive execution proof, a controlled degradation/fail-closed proof, an independent staleness-policy proof, and confirmation that the four AI Gateway callables remain undeployed.
