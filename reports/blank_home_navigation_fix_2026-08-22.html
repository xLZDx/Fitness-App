Blank Home after the PAR-Q block screen — root cause found, fix verified on-device

The block screen's "Check my health answers" button dropped users on a blank Home instead of the questionnaire. Cause: a GoRouter redirect, not an engine hang.

Summary

The operator recorded a video: on the Library tab, with the health screening (PAR-Q) unanswered, tapping an exercise shows the "This exercise is on hold" block screen. Tapping its one button — "Check my health answers" — left a blank Home instead of the questionnaire: only the background photo, no content, often no bottom nav either. The effect did not self-heal and persisted across tabs.

Root cause is not a Flutter engine hang but the router: push('/onboarding') for an already-onboarded user is silently rewritten by a redirect to /home — exactly the state every account that reaches this screen is in (onboarding done, PAR-Q not). Fix: the same button now pushes /onboarding/edit, a route already built to survive that redirect. Verified live on S8: the questionnaire opens, and back navigation returns correctly.

How the cause was found

  1. Operator's video: Workouts → Library → PAR-Q block → Back → Home is blank; the same blank screen persists after switching to Progress.
  2. Checked the debug traces: the operator pushed back — "if debug doesn't catch it, it's broken." Confirmed in code: kDebugMode traces are compiled out of release builds entirely by Dart, so their silence proves nothing. The bug was reproduced separately on a debug build from current HEAD to confirm the trigger isn't release-specific.
  3. Live logcat on S23 (release 1.0.0 / 2656): the operator reconnected the device and reproduced the bug live ("exactly like the video"). ~48 minutes of capture, the app process alive and foregrounded the whole time — and not one line from the app itself: no exception, no ANR in com.fitnessapp..., no Choreographer/Davey warning. This ruled out a caught exception, a system-detected ANR, and ordinary frame jitter as the cause.
  4. The operator described the repro in words: "the banner appears, I agree, and everything disappears, only the wallpaper remains" — one tap on the block screen's button, no Back involved.
  5. Re-walked the video frames (2 fps): frame 16-17 is the block screen with its one button, "Check my health answers"; frame 18 (0.5s later) is already a blank Home. This pinned the trigger to that specific onPressed, not to Back.

Root cause FACT — direct code read

The button calls:

onReviewProfile: () => GoRouter.of(context).push('/onboarding'),

And the router has a guard against bouncing an already-onboarded user back into first-run onboarding via a stale link or the back button:

// app_router.dart:108-110
if (isSignedIn && isOnboarded && location == '/onboarding') {
  return '/home';
}

isOnboarded is a coarse "finished the onboarding wizard once" flag, independent of whether the PAR-Q step within it was actually answered. An account can be isOnboarded == true and still have a completely empty health questionnaire — exactly what the block screen shows. So the button that exists specifically for "questionnaire incomplete" almost always fires from a state where this redirect guard is active, and its tap silently turns into a navigation to /home.

/home is a child of the app's single ShellRoute (the shared shell with the bottom nav), while the block screen itself is a separate page on the root navigator, outside that shell. HYPOTHESIS — not proven by a trace, but consistent with every observation: pushing a ShellRoute-nested location from a route outside the shell, while the original shell instance is still mounted lower in the stack, is the likely mechanism behind "blank content with zero logged errors," rather than a genuine thread hang.

Where else the "blank content, no background/nav" pattern showed up

After the operator unlocked the phone, a second screenshot caught the same symptom family: the "Training → Programs" tab with visible content but a fully black background (no usual HUD photo), no bottom nav, and "Start program" buttons that looked inactive — visually consistent with the operator's separate complaint that no exercise could be launched at all.

The fix

All six places where the "Check my health answers" button called push('/onboarding') now call push('/onboarding/edit') — a route that already exists and was explicitly built as "a way in that survives the redirect" for an already-onboarded user (the same pattern Profile's own "edit answers" tile already relies on).

FileSite
exercise_reference.dartline 1215 — "exercise withheld" block
workouts_page.dartline 512 — whole-Library-tab block
workouts_page.dartline 1345 — programme-enrolment refusal
ai_planner_page.dartline 66 — AI planner refusal
workout_player_page.dartline 228 — block inside the player
home_page.dartline 168 — block in Home's suggestions

Checked that the swap is safe for not-yet-onboarded users too (the QR-scan path, which also reaches exercise_reference.dart without onboarding): such a user pushing /onboarding/edit just takes one extra redirect hop to /onboarding — same questionnaire screen, no loss of function.

Verification

A debug build (GIT_SHA=onboarding-redirect-fix) was installed on S8 (ce0417141997e4640c) — S23's release install was left untouched on purpose, to keep its pre-fix bug state intact. Reproduced the exact scenario from the operator's video: Library → an exercise with PAR-Q unanswered → block screen → "Check my health answers". Open items

1. S23's release build

The fix is verified on a debug build on S8 only. S23 still runs release 1.0.0 (2656) with the bug present — a full check there needs a new build and reinstall on that device.

2. The "blank content" mechanism is not fully proven

HYPOTHESIS: shell state tearing (ShellRoute / GlobalKey) from a push landing on top of an already-mounted shell instance. The fix removes the trigger itself (the redirect no longer swaps the target), so the mechanism is no longer reachable to confirm directly with a trace — left as an unconfirmed hypothesis, not a fact.

3. Operator's request: confine this messaging to onboarding only

"...the text on the banner is unreadable, and I don't understand why it even appears there — it should only be part of onboarding, and afterward there should be no mentions of it anywhere else..."

Not actioned as part of this fix. The unreadable text in the screenshot was most likely a symptom of this exact bug (black background instead of the HUD photo — see the section above), not an independent contrast defect in the banner itself. But the broader ask — show this message only during onboarding — is a bigger scope than the navigation bug: the code (eligibility_notice.dart, the F017/N01 comments in workouts_page.dart) deliberately makes this block cross-cutting — it is meant to appear on every surface that could hand out an exercise (Workouts, programme enrolment, the AI planner, deep links), not only onboarding, specifically to catch a person who left PAR-Q incomplete and comes back later. That is its own product decision with an existing rationale already recorded in the code — it needs the operator's own explicit call, not a silent change bundled into this fix.
