Headline finding

This confirms the concern you raised: the live recognition path is not reliable enough today to be shown as trustworthy to real users without a mitigation. A user scanning a "rotary torso machine" had a measured 0% chance of a correct match in this sample — while the card would have shown 85% confidence.

Model confidence does not reliably separate right from wrong

Average self-reported confidence on correct predictions was 95.0%. On wrong predictions it was 87.7%. There is a real gap, but a small one: in absolute terms a wrong answer shows the user nearly the same confidence (88%) as a correct one (95%). This is exactly the number the user sees today in the UI (ScanMatchCard) — a percentage ring with no visual distinction between a "trust it" and a "don't trust it" range.

Methodology

Photos
33 real gym photos (out of 62 the operator supplied), hand-labeled against the CANONICAL_MACHINES catalog (70 categories). 5 photos were excluded as personal/people-dominant (including one showing a minor) — never sent to any external API.
Model & config
Vertex AI gemini-3.6-flash, location global, temperature 0, JSON mode, thinking disabled, maxOutputTokens 256 — an exact replica of what the production path functions/src/ai_equipment_recognition.ts / ai_gateway.ts uses, including the prompt text and the full category list, verbatim.
What was NOT tested
The Firebase Callable wrapper (auth/quota/App Check) — a separate, already-closed MVP1.G4 gate. What was tested is the model call itself, exactly as production code makes it.
Sample limitation
n=33 (27 at unambiguous ground truth), one gym, one labeler with no cross-check. Sufficient to disprove "recognition is reliable" — one reproducible 0/4 category failure already does that. Not sufficient to claim a precise final number for a production sign-off — a larger, more diverse sample would be needed for that.

Recommendation

  1. Do not represent live recognition as reliable to real users until one of two things happens: (a) build the already-designed fail-closed mechanism (confidence floor / TYPE_ONLY-NEED_MORE_VIEW mode, described in core/design/sptr_equipment_recognition_v4_1/) and re-measure accuracy against this same manifest, or (b) the operator makes a deliberate, risk-accepted decision to ship with the current UI-only mitigation (confirm-before-proceed, visible percentage), with this number in hand rather than in its absence.
  2. When building the fail-closed threshold, use the measured confidence gap (95.0% vs 87.7%) as a starting point but not the only signal — it is too weak on its own.
  3. Separately investigate the rotary torso machine category — 0/4 at HIGH ground-truth confidence is not noise, it is a systematic failure specific to this category; likely a candidate for forced TYPE_ONLY / manual confirmation.
  4. Expand the sample with a second, independent photo set (a different gym, ideally a different labeler) before using the precise 48.5% figure in a production decision.
