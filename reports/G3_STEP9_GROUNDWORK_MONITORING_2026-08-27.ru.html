01 Что построено

Все четыре пункта — только определения. Ни один живой ресурс GCP (метрика, алерт, канал уведомлений) не создан ни разу за всю работу.

Stripe: сбой сверки дублей подписки

Готово

LogMatch‑политика для webhook‑обработчика Stripe: ловит именно два лог‑сообщения об ошибке сверки, а не два соседних лога успеха/предупреждения из того же кода. Область действия — сервис stripewebhook (Cloud Run, не имя функции — см. ниже).

Удаление и экспорт аккаунта: операционные сбои

Готово

Перед объявлением готовности проведён обязательный аудит покрытия сбоев: чтение документа подписки в deleteAccount происходит ДО первого try — ни один из трёх именованных логов ошибки не сработает, если оно упадёт. Найдена и подтверждена реальная страховка платформы: обёртка onCall в самом firebase-functions ловит любое необработанное исключение и логирует "Unhandled error" — но только если это НЕ HttpsError, то есть только для по‑настоящему непредвиденных сбоев. Оба фильтра включают эту страховку.

App Check: доля аттестованных вызовов

Готово · метрика не создана

Видимость уже была построена раньше (найдено при сканировании, не изобретено заново). В этой части — настоящее определение log‑based‑метрики (не просто фильтр) с ограниченной кардинальностью: 17 известных вызовов × 2 значения attested. Список из 17 теперь механически сверяется с реальным списком функций в исходниках отдельным тестом — если появится 18‑й вызов и не попадёт в список, тест упадёт, а не молча пропустит его.

AI Gateway: четыре метрики и семь запросов

Готово

Счётчик вызовов (операция × исход), распределение задержки (границы бакетов подобраны под реальные тайм‑ауты кода — 20/25/45 секунд), распределение расхода токенов (сознательно включает и неуспешные вызовы — токены могли быть потрачены до того, как ответ оказался пустым), и счётчик исчерпания квоты (это отдельное событие — шлюз вообще не видит отказ по квоте, потому что квота проверяется раньше). Плюс семь именованных запросов для ручного разбора в Log Explorer.

02 Шесть раундов, четыре реальных находки

Каждая находка — не придирка: код действительно не работал бы как задумано, если бы дошёл до продакшена в исходном виде.

Раунд 1 · неверная модель ресурса Cloud Logging
Фильтры использовали resource.labels.function_name — это формат первого поколения Cloud Functions. Проект целиком на v2 (Cloud Run): реальные логи несут resource.type="cloud_run_revision" и resource.labels.service_name. С исходным фильтром монитор совпадал бы ровно с нулём реальных записей — «зелёный» монитор во время настоящего сбоя.
Раунд 1 · не настоящая политика алерта
Определения выдавали только строку фильтра, а не полный JSON AlertPolicy (нужны combiner, conditionMatchedLog, alertStrategy с ограничением частоты уведомлений, список каналов).
Исправлено · раунд 1
Добавлена функция вывода реального имени Cloud Run‑сервиса из имени экспорта TypeScript. Добавлен полный рендер AlertPolicy с пустым списком каналов — оба поля сверены с официальной REST‑документацией Google перед написанием кода, а не угаданы.
Раунд 2 · не настоящая исчерпывающая защита от дрейфа
Список из 4 операций AI Gateway был проверен только через satisfies — это доказывает, что каждое значение массива корректно, но НЕ что каждое значение типа присутствует в массиве. Добавь 5‑ю операцию — код всё ещё компилируется, а новая операция молча исключена из всех метрик.
Исправлено · раунд 2
Единственный источник истины: массив операций теперь живёт в ai_gateway.ts, а тип выводится ИЗ массива, а не объявляется отдельно. Модуль мониторинга импортирует тот же самый массив — дублирования, которое могло бы разойтись, больше не существует структурно.
Раунд 3 · та же проблема, для App Check
Список из 17 известных вызовов для App Check — обычная строка, не тип TypeScript, так что то же структурное решение неприменимо. Список требовал ручного сопровождения без какой‑либо механической защиты.
Исправлено · финальное одобрение
Существующий тест scaling.test.ts, который сканирует реальные исходники на предмет всех вызываемых функций, вынесен в переиспользуемый помощник. Новый тест сверяет список из 17 с этим реальным списком в обе стороны: пропущенный вызов — тест падает, устаревшая запись — тест падает.

03 Что честно не активировано

DECISION FA-D1 — кто владеет боевыми алертами (on‑call) — решение оператора, всё ещё ожидается. Ни один канал уведомлений не создан.
Стоимость живой метрики App Check — у сессии нет доступа к реальным данным биллинга GCP, чтобы подтвердить нулевую дополнительную стоимость; можно только структурно ограничить кардинальность (максимум ~34 временных ряда).
Настоящий Web API‑ключ Firebase для зонда‑канарейки из Шага 9A — тот же пробел, что и в прошлом отчёте: без реальных учётных данных GCP зонд не может подключиться к боевому Auth и корректно отказывается от небезопасного запуска.

GPT‑PM, дословно: «Это не значит, что мониторинг в реальном времени АКТИВЕН... Следующий значимый переход — фаза активации, когда решатся вопросы владения, конфигурации и стоимости».
