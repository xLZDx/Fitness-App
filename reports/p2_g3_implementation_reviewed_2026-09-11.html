This gate's architectural center: a two-phase admit/finalize lifecycle fenced by claimId

Rounds 3–5 rewrote the session/quota atomicity mechanism from scratch — not a patch on the old "pin at the end" model, but a genuine two-phase design.

admitSessionClaim 1 transaction

Linearizes, in ONE Firestore transaction: session ownership, latest-scan ordering, and quota admission — before the expensive pipeline runs, not only at the end. Transaction commit order is itself a real total order: a brand-new claim is always, by construction, the most recently admitted scan for this uid.

Bounded lease + lazy reclaim, no sweeper subsystem

A hung/crashed request never permanently wedges (uid, scanId): any later call to admitSessionClaim notices an expired lease (30s) and reclaims the slot itself — but only for a genuine retry of the SAME request (matching fingerprint) and only while the session is still latest.

claimId/generation fencing (round-4 finding, round-5 closure)

Every successful admission/reclaim mints a fresh, immutable claimId. finalizeSessionOutcome requires an exact generation match — a genuinely still-alive (merely slow, not crashed) original owner whose lease expired and was reclaimed by a fresher attempt presents its own stale claimId and observes ABANDONED, never overwriting the reclaimer's live claim.

finalizeSessionOutcome RESOLVED / SUPERSEDED / ABANDONED

Re-verifies "am I still latest?" at the very END, inside the same transaction that writes the outcome — a scan superseded while it was still running discovers this at finalize and never emits a stale MATCH.
