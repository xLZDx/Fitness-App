01What we're building

Today the app's scanner can tell a user “this is a leg press” — a generic functional category, one of ten trained classes. It can't tell them whose leg press it is, which matters more than it sounds: seat position, pulley ratio, handle adjustment and safety warnings are all specific to the exact model, not the category. We're adding a second, additive layer on top of the existing scanner: exact equipment identity — brand, product line, and model — built from a licensed, rights-cleared knowledge base instead of guesswork.

The generic scanner keeps working exactly as it does today. Exact identity is enrichment that arrives a moment later, in parallel, and only ever adds detail — it never blocks a workout, and it never overrides an existing safety rule.

02Why the current scanner isn't enough

This isn't a hunch — it's measured. A 30-photo real-gym evaluation set (recorded and frozen as historical evidence) showed the bundled 10-class model gets zero out of thirty correct on real equipment it wasn't trained on, and it does so confidently — it doesn't say “I don't know,” it reports a wrong class with up to 90% confidence. That's the actual failure mode a confidence threshold can't fix: the model isn't unsure, it's sure and wrong, because the real machine simply isn't one of its ten classes.

Correct guidance

Seat height, pulley ratio and handle position differ by exact model — a generic “leg press” answer can't give correct setup instructions.

Safety

Warnings and adjustment ranges come from the manufacturer's own documentation for that specific model, not a generic category guess.

Trust

A confidently wrong answer is worse than an honest “I'm not sure” — it's the single failure mode this whole design is built to eliminate.

Product depth

Exact-model history, verified setup pages and gym-specific memory are only possible once identity goes beyond “it's some kind of leg press.”

03The five layers underneath identity

The design is deliberately layered so exact-model work can never quietly change what the app already relies on for exercises and safety.

AEquipment TypeThe existing functional category (“leg press”) that exercises, safety and programmes already run on — untouched, immutable semantics.
BBrand / ModelManufacturer identity — every exact model maps back to a Type, it never replaces one.
CRecognition evidencePhotos, embeddings and matching policy — improves confidence in an identity guess, never redefines the ontology.
DPhysical machine instance“This specific unit at my gym” — private, optional memory, always downstream of the model, never proof by itself.
EExercise knowledge graphThe existing verified exercise/safety catalog, plus read-only enrichment from external sources — the one thing exact identity is never allowed to bypass.

04How it plays out for the user

The generic answer never waits on the exact one. Exact identity resolves in the background and only ever adds — the user is never blocked and never given a silently wrong model.

Every recognition ends in one of a small set of honest outcomes — there is no state that means “probably right, shown as certain”:

EXACT_MODEL PRODUCT_LINE BRAND+TYPE TYPE_ONLY NEED_MORE_VIEW UNKNOWN

The one rule that never bends: exact model identity can only ever select from the app's existing, vetted exercise and safety catalog — it can never generate new exercises or safety guidance on its own. An AI model may rephrase an already-verified setup fact for readability; it may not invent one.

One decision already made along the way

P0.G5 asked whether visual (camera-image) recognition could start now. The honest answer, checked against the real infrastructure rather than assumed: there is currently no safe non-production environment to test it in without risking the live app. Rather than test on production or guess, that path is explicitly deferred — text-based identity (reading the machine's own printed model code, phase P2) ships first, since it needs no image-matching infrastructure at all and is the cheaper, more precise path regardless.

Where things stand: P0 closed today with a full evidence trail (six gates, independent review, a final cross-phase audit that caught and fixed one real defect before sign-off). P1 — the knowledge base that everything downstream depends on — is authorized to begin but needs its own dedicated kickoff, per the phase-boundary review process this program follows.
