02The first-tap investigation (D-03 / D-05B / MainShell)

An intermittent bug where the first tap on three unrelated screens (guest sign-in, Form Coach entry, bottom-nav) did nothing — investigated to a directly-observed root cause, not a guess.

Self-correction on the record. An earlier commit in this pass claimed all three paths showed zero defects, without cross-referencing this same session's own prior findings (a 30% failure rate over 20 trials for one path, 3/3 failure for the other two) and without re-testing under the actual repro conditions. Caught before being reported as final, retracted in an honest follow-up entry, and re-investigated properly.

Re-investigation, properly conducted

All three paths re-run under their exact historical repro conditions: 30/30 clean trials. Two harness artifacts were found and fixed along the way, not folded silently into the result:

  • Fixed-wait taps are not proof a screen is ready. A screenshot taken at a 12-second mark showed the splash screen still visually painted, despite the app having logically navigated ~3.5 seconds earlier — the compositor lagged the widget tree under device load. Fixed by switching to visual-confirmation-before-tap: screenshot first, confirm the target is actually rendered, only then tap.
  • debugPrint does not reliably flush inside a short capture window. One trial showed a trace line missing from a logcat dump, which read as "the callback never ran" — a screenshot taken at the same checkpoint proved the navigation had, in fact, already happened. The visible outcome was treated as ground truth over trace-line presence from that point on.

One anomaly during separate, unrelated manual smoke testing (a messy blind 9-tap sequence, followed by an unexpected launcher exit) did not reproduce under the controlled protocol and is logged honestly as unreproduced — neither folded into the 30/30 clean result nor dismissed.

Working hypothesis, not yet proven

Disabling Impeller/Vulkan rendering (EnableImpeller=false in AndroidManifest.xml) — originally added for an unrelated S23 Ultra crash — correlates in time with the bug no longer reproducing on the S8. This is INFERENCE, not FACT: no controlled A/B test (re-enable Impeller, confirm the bug returns) has been run. The S23 has been disconnected for the entire pass, so its own verification is also outstanding. Both are recorded as known open items below, not silently treated as proven.

03Gates closed this pass: M7, Form Coach reskin, M8, M9

M7 — reduced motion

A new HudMotionX extension reads the real OS accessibility signal (MediaQuery.disableAnimations) and exposes context.reduceMotion / context.hudMotionDuration(normal, reduced:). Applied across ten animated HUD surfaces in eleven files — background crossfade, toggles, buttons, the login CTA, onboarding entrance animations, the progress chart, the set-timer ring, and two continuous-loop controllers stopped rather than merely shortened. Global page-route transitions were deliberately left for a dedicated follow-up, given their app-wide blast radius.

Form Coach HUD reskin

The last remaining un-reskinned screen (besides Light theme) moved onto the same HudPanel container system as M1–M6: nine GlassCard → HudPanel swaps across form_check_page.dart and coach_intro_cards.dart. A HudQuality(frostedGlass: false) opt-out was added around the live-camera body only — reasoned explicitly against its tens-of-Hz per-frame rebuild cadence, worse than any prior reskin's own repaint load — while the pre-camera intro cards correctly kept full frosted glass. Device-verified on the S8: intro card, preparation card, and the live-camera body all render correctly.

M8 — deterministic golden-image tests

13 golden-image regression tests now cover the five low-churn HUD primitives (HudPanel, HudButton, HudChip, HudToggle, HudNavBar) in both themes where the visual delta is real. Font rendering is made deterministic by loading the app's own real bundled fonts through the same pubspec.yaml-driven helper an existing test already used, so the font list can never drift into two copies.

Open, honestly documented: the 13 checked-in baseline images were generated on this session's Windows host; CI runs on Linux. Cross-OS pixel parity is unverified — the next CI run is the real test, and a red result there means regenerating the baselines from Linux, not loosening the comparator.

M9 — adversarial falsification review

Three independent specialist reviewers (silent-failure-hunter, security-reviewer, flutter-reviewer) reviewed the current tree cold, each instructed to actively try to falsify robustness rather than confirm it.

Fixed — silent write-failure on difficulty ratingFixed & verified

mobile/lib/features/equipment/workout_player_page.dart:723

The difficulty-rating write path was the one of three near-identical log() call sites in this file that did not check for a write error before updating local state — a failed save would silently vanish with no feedback. Fixed to match its two sibling call sites exactly. Verified: analyzer clean, 448/448 equipment tests pass, no regression.

Dismissed — hypothesis did not hold upInvestigated, not a defect

mobile/lib/features/form_check/state/form_check_providers.dart:779

Flagged as a possible missing observation-ratio gate on the real-time rep verdict. Direct read of the surrounding code showed the gate is applied one line earlier in the same getter, guarding the flagged line correctly. No fix needed.

Flagged, not fixed — AI Coach has no server-side rate limitMAJOR · needs its own gate

mobile/lib/features/ai_coach/ai_coach_service.dart:28

Calls the Firebase AI model directly from the client with no Cloud Functions intermediary and no quota, unlike every other billable surface in this app's own backend. A misbehaving or compromised client could run up the project's AI billing directly with no server-side backstop. Closing this needs a Cloud Functions (TypeScript) change and a redeploy — a different stack and materially higher blast radius than this pass's Flutter-only work, and it deliberately was not folded in.

Flagged, not fixed — navigation defect is wider than previously knownMAJOR · needs its own gate

mobile/lib/core/router/app_router.dart:333

The already-known "pop lands on /home, not the tab you came from" defect (root cause: several routes are top-level GoRoutes that are siblings of the shell, rather than children of it, so the router's declarative pop can't recover the true origin) is not limited to the two routes previously on record. /subscription — the app's primary monetization surface, with 11+ push origins across the app — shares the identical defect, making this the highest-impact instance found so far. /photos and several lower-traffic routes share it too, at lower severity. The correct fix (a shell migration, or explicit location capture at every push site) touches a dozen-plus files on the app's highest-revenue screens and needs its own dedicated gate with real device testing, not a patch layered onto an already-long pass.

Tempered — PAR-Q safety gate is client-side onlyMINOR · no action needed

Both the security and silent-failure reviews independently confirmed the gate's own logic is genuinely fail-closed on its loading/error edge cases. There is no backend plan-generation path today for a server-side check to sit in front of, and a bypass only lets someone mislead themselves — there is no other party the gate protects. No action needed until a plan-generation backend exists.
