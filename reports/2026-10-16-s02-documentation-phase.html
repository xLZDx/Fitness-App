What the external review fixed in the design

TopicWhat was wrong in plain wordsResolution
Account deletionA phone with queued writes could recreate activity data after the account was deleted.The guard is part of the Firestore access rules themselves: while an account deletion runs, writes are refused.
Two edits from two devicesOne device could silently overwrite the edit of another.Three-way merge per field; the same field with different values stays a visible conflict with a user choice.
Journal on the phoneA crash in the middle of a write could lose the previous confirmed version.Each version is written to its own directory and committed by a COMMIT marker; recovery selects only committed versions.
Values adopted from another deviceAn adopted value could roll back on the next recomputation, on a formula update or on a user edit.Adopted values are kept as overrides with rules: passive change, explicit user edit and automatic recalculation are separated; a recalculation never replaces an adopted value by itself and is offered to the user.
Edit historyUnbounded history could make the cloud write impossible (the counter exceeded its allowed range).The canonical value is stored separately, the history is capped at 64 entries and the counter never exceeds 64.
Test planTest data requirements contradicted each other, one test asserted the opposite, the story to test map was out of sync.Valid and deliberately corrupted data are separated, tests fixed, the map checked against the plan (all 239 tests belong to a story).
