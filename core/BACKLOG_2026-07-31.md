## E3 — Defects, verified now (highest priority: these are live on the operator's phone)

### E3.1 English leaking into the Russian UI of "Тренер по технике" — VERIFIED

| Symptom | Source |
|---|---|
| `Half-rep. Lighten the bar and hit depth.` spoken + shown | `lib/features/form_check/data/form_classifier.dart:57-146` — 9 cue strings, hardcoded English |
| `Ошибки: squat.depth, deadlift.back_angle, pushup.alignment` | `form_classifier.dart:38,81,118` — internal rule ids rendered as user text |
| `Free of $2,500 hardware. Works on your phone...` | `form_check_page.dart:373` |

**Why the round-4 guard missed it:** `test/l10n/no_untranslated_strings_test.dart` scans for English
literals inside `Text(...)` calls. These are values of a `cue:` field on a data class and an
identifier getter — structurally invisible to that test. The guard needs a second rule: no English
sentence in any string field that reaches a `VoiceCoach` or a UI label, and rule ids must never be
rendered.

### E3.2 The coach scores a face — VERIFIED symptom, HYPOTHESIS cause

Screenshot: `0 чисто — 6 с ошибками (всего 6)` produced from a front-camera selfie of a face at
arm's length. No squat, no full body in frame.

Hypothesis (to confirm on the gate, not asserted): nothing gates classification on landmark
visibility or on the body being in frame, so ML Kit's low-confidence landmarks for a face-only frame
are fed to `SquatDepthClassifier` / `DeadliftBackAngleClassifier` / `PushupAlignmentClassifier`
anyway. `CueGate` then behaves exactly as designed — severity ≥ 2 repeats every `interruptGapMs`
(1200 ms) while the "error" persists (`voice_coach.dart`, the interrupt branch) — which is what the
operator experienced as "завис, повторяет одни и те же слова".

Fix shape: an in-frame / visibility gate BEFORE classification, and a visible "поставьте телефон
так, чтобы было видно всё тело" state instead of scoring garbage. This is also the precondition for
E2 — a virtual trainer that scores a face is worse than no trainer.

### E3.3 Scan latency — NEEDS OPERATOR INPUT

Operator reports 65–180 s. Code has a hard 20 s deadline with on-device fallback
(`gemini_equipment_service.dart:37`, shipped in 1.0.0+8). **Blocked on: which build was tested.**
If +8 already, the delay is elsewhere (resize, on-device model load, or network) and needs a
device-side trace, not another timeout.

## E2 — Virtual trainer (the AR ask: items 2, 4, 7, 8, 18)

### What "дополненная реальность" means here

Not ARCore world-anchoring. The value the operator describes — see yourself, see what is wrong,
hear the correction — is delivered by a **skeleton overlay drawn on the live camera preview**, with
per-segment colouring. That is achievable on-device with what is already installed, at a fraction of
the cost, and works on phones ARCore does not support.

### Building blocks already present (verified)

| Piece | Where |
|---|---|
| On-device pose, 33 landmarks | `google_mlkit_pose_detection: ^0.14.0`, `pubspec.yaml:58` |
| Speech out | `flutter_tts: ^4.2.2`, `:62` |
| Speech in | `speech_to_text: ^7.0.0`, `:61` |
| Cue throttling policy (tested, pure) | `form_check/data/voice_coach.dart` — `CueGate` |
| TTS adapter with failure surfacing | `form_check/data/tts_voice_coach.dart` |
| Rep counting | `form_check/data/rep_counter.dart` |
| Muscle atlas, 107 named ids, CC BY 4.0 | `assets/anatomy/muscle_front.svg`, `muscle_back.svg` |
| 192 exercises with 2 stills each | `assets/data/exercises.json` |

### The reference-form problem

To say "your arm is wrong" the app needs an **эталон** to compare against. Proposal: extract joint
angles offline (build-time `mediapipe` script, same model family as ML Kit) from the two catalog
stills per exercise → a start-pose and end-pose joint-angle vector → the reference envelope.

**Honest limitation, stated up front:** two stills give the two endpoints of a rep, not the path
between them. That is enough to judge *depth, alignment and end positions*, and not enough to judge
*tempo or mid-path deviation*. Anything stronger needs real reference video, which we do not have a
free licensed source for. This limitation must be visible in the product, not hidden — the app
should say what it is checking.

### Single RGB camera, no depth — named failure modes

| Failure | Detection instead of garbage |
|---|---|
| Camera angle wrong (front view for a squat) | per-exercise required view; detect shoulder/hip width ratio and ask the user to turn the phone |
| Partial body in frame | landmark visibility gate (E3.2) |
| Torso rotation ambiguity | flag low confidence, drop to "cannot judge this rep" rather than scoring |

### Gate breakdown

| Gate | Content |
|---|---|
| **V0** | E3.1 + E3.2 — localise cues, hide rule ids, gate on visibility. Prerequisite for everything below |
| **V1** | Offline `mediapipe` extraction → `assets/data/pose_reference.json` (start/end joint angles per exercise) |
| **V2** | Live skeleton overlay on the camera preview, per-segment colour (ok / drift / danger) |
| **V3** | Segment-level Russian cues through the existing `CueGate` — "разверни локоть", "колено внутрь" |
| **V4** | Session recording + post-workout replay with error markers on a timeline |
| **V5** | Per-exercise technique score, history, and the challenge/leaderboard layer (item 8b) |

**V4 carries a promise conflict — must be resolved before it is built.** The app currently tells the
user, on that exact screen: *«Кадры никуда не загружаются — камера остаётся приватной»*. Recording
workouts and/or sending them for cloud analysis contradicts that sentence. Options: keep recordings
strictly on-device (promise survives), or change the promise and add an explicit consent step. This
is an operator decision, not a technical one.

## E1 — Personalisation (items note, 3, 11, 12, 13, 14, 15, 20)

Requirement, condensed: the home screen leads with **the user's goal and distance to it**; content is
ranked by **gender, level/intensity, and location (home / gym / outdoor)**; a detailed questionnaire
(10 mandatory + unlimited optional) feeds the ranking; ranking, not hard filtering.

Open design questions the operator already raised himself, kept verbatim in intent:

1. What ranking applies if the user skips the questionnaire?
2. How is priority split on multi-select (Home + Outdoor)?
3. What happens to the feed when preferences change a month later?
4. Hard filter (100 % chosen location) or proportional mixing (e.g. 80/20) for discovery?

**Known blocker:** the catalog has no location, intensity or gender tags today — ranking cannot be
built before the 192 exercises + 48 machines carry them. Sizing that is part of the architecture
review running now.

Gender segmentation additionally needs a **female anatomy variant** of the atlas; the current
`muscle_front.svg` / `muscle_back.svg` is a single body.

## E4 — Content (items 19, 22)

**19 — ready-made programmes** for weight loss, posture, balance, endurance, strength, flexibility,
suggested from the questionnaire.

Two corrections to the ask, stated plainly:
- "100 % эффективные" — no training programme is 100 % effective for everyone; the honest version is

### E7.2 SHA-256 ключа Play App Signing — НЕВОЗМОЖНО ДО ЗАГРУЗКИ

**Verified:** upload-ключ зарегистрирован в App Check; enforcement включён
(гейт F0·6).

**Blocks:** ключ Play App Signing физически не существует до первой загрузки
бандла. Google переподписывает APK своим ключом, поэтому без второго
отпечатка App Check начнёт отвергать запросы настоящих пользователей из
магазина. Порядок жёсткий: загрузить `app-release.aab` -> Play Console ->
Setup -> App signing -> скопировать SHA-256 -> добавить **вторым**, не
заменяя upload-ключ.

**Внешняя блокировка:** аккаунт разработчика на проверке личности у Google
(со слов оператора, 2026-08-05, «may take a few days»).
