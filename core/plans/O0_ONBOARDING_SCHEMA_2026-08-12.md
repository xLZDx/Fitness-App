**Это документ, а не код.** Спека требует именно такой остановки дословно: *«Use existing profile

## Метод

оператора и из реализации прототипа (`App.tsx:2387-2409`, `TOTAL_OB_STEPS = 9` на `:1202`), а не

## Главный результат: половина «нового» уже есть, и не там, где ожидалось

**Закрытый словарь зон тела уже существует.** `InjuryRegion` — восемь регионов
(`profile_models.dart:61-70`), и его док прямо объясняет, почему свободный текст был неверен, и
называет виновника: `step_health.dart:64-82`. Диаграмма тела из фигмовского 4/9 ложится на него
без единого нового поля. Онбординг просто никогда в него не писал — заполняется только
`Injury.bodyPart` (строка), а `Injury.region` остаётся null.

**Правила Firestore менять не нужно.** `firestore.rules:12` — шаблон
`match /users/{uid}/{coll}/{document=**}` без валидации полей. Новые поля проходят как есть.

## Предлагаемая минимальная схема

Принцип: ничего не переименовывать, ничего не удалять. Старые поля остаются либо как есть, либо
становятся вычисляемыми — чтобы существующие читатели не переписывались.

### 1. `PersonalInfo` — год рождения

```dart
final int? birthYear;              // новое, пишется онбордингом
int? get age => birthYear == null  // вычисляемое, читатели не меняются
    ? null : DateTime.now().year - birthYear!;
```

Миграция в единственной точке чтения (`firestore_profile_repository.dart:44`):
`birthYear ??= текущий год − age`. Приблизительно на ±1 год — месяц рождения неизвестен и никогда
не спрашивался. Это подписывается в интерфейсе, а не замалчивается.

### 2. Главная цель — расширить `ProgrammeGoal`, а не заводить второе перечисление

`ProgrammeGoal { strength, muscle, weightLoss, form, comeback }`
(`features/programmes/data/programme.dart:30`) — пять значений, и они почти совпадают с
фигмовскими шестью. Не хватает `endurance`.

```dart
enum ProgrammeGoal { strength, muscle, weightLoss, form, comeback, endurance }
// + FitnessGoals.primary — ProgrammeGoal?, единственный выбор
```

**Зачем именно это:** ответ пользователя становится напрямую пригоден для подбора программы,
вместо таблицы соответствия между двумя перечислениями, которую никто не будет поддерживать.

**Цена, названная честно:** три места получают новую ветку — `_goalHue`
(`workouts_page.dart:850-856`), подписи целей в `CatalogLabels`, и `AppPalette` получает шестой
оттенок. Все три — исчерпывающие `switch`, то есть компилятор укажет на них сам.

Шесть булевых `FitnessGoals` **остаются**: фигмовский 1/9 спрашивает главную цель, а наш нынешний
шаг 3 позволяет отметить несколько. Одно не заменяет другое.

### 3. Уровень — четвёртое значение

```dart
enum FitnessTier { never, beginner, intermediate, advanced }
```

`never` первым, чтобы порядок читался как возрастающий. Затрагивает четыре файла
(`exercise_filter.dart`, `step_level.dart`, `firestore_profile_repository.dart`,
`set_timer_providers.dart`).

### 4. Место и оборудование

```dart
enum TrainingLocation { gym, home, outdoor, mixed }
enum EquipmentKind {
  fullGym, machines, dumbbells, barbell, kettlebells, bands, bodyweight, cameraScan
}

// в EquipmentAccess:
final TrainingLocation? location;        // новое
final List<EquipmentKind> available;     // новое
bool? get hasGymAccess =>                // вычисляемое, читатели не меняются
    location == null ? null
    : location == TrainingLocation.gym || location == TrainingLocation.mixed;
```

`homeEquipment` (свободный текст) **остаётся** для того, что не влезло в закрытый набор — тот же
принцип, что у `Injury.note`: неподходящее хранится, но не участвует в сопоставлении, и это
честнее, чем впихнуть его в ближайшую категорию.

`cameraScan` — не оборудование, а намерение («буду распознавать камерой»). Живёт в том же наборе,
потому что на экране это такой же чип; читателям, подбирающим упражнения, его надо игнорировать.

### 5. График — новая под-модель, НЕ переиспользование `frequencyPerWeek`

```dart
class TrainingSchedule {
  final int? daysPerWeek;              // 2..6
  final int? sessionMinutes;           // 30/45/60/75/90
  final List<int> preferredWeekdays;   // DateTime.monday..sunday
}
// UserProfile получает поле schedule
```

**Почему не `FitnessLevel.frequencyPerWeek`:** там записано, сколько человек тренируется **сейчас**
(текущий шаг 4, «Тренировок в неделю»). Слить это с «сколько планирую» — уничтожить единственную
базовую точку, от которой генератор плана может считать нагрузку.

`MotivationPrefs.preferredDuration` остаётся вычисляемым из `sessionMinutes`, чтобы существующие
читатели корзин не переписывались.

### 6. Приоритетные зоны и барьеры

```dart
enum FocusZone { chest, back, shoulders, arms, core, glutes, legs, fullBody }
enum TrainingBarrier {
  exerciseChoice, machineUse, techniqueDoubt, time, consistency, discomfort, none
}
```

Обе — множественный выбор. `FocusZone` намеренно **не** переиспользует `InjuryRegion`: одно
отвечает «что тренировать», другое «что обходить», списки не совпадают (у приоритетов есть
«всё тело» и «пресс», у ограничений — «запястье» и «голеностоп»), и объединение их дало бы
перечисление, где половина значений бессмысленна с каждой стороны.

### 7. Ограничения — новых полей НЕТ

Онбординг начинает заполнять `Injury.region`. Тип уже есть, словарь уже есть, тег для
сопоставления с каталогом уже есть (`InjuryRegionTag.tag`, `:72-96`).

## Решения оператора, которые схема принять не может

1. **«Верх спины» против `neck`.** Фигмовский 4/9 предлагает восемь зон: плечо, локоть, запястье,
   **верх спины**, поясница, тазобедренный, колено, голеностоп. Наш `InjuryRegion` — те же восемь,
   но вместо «верха спины» стоит `neck` (шея). Семь из восьми совпадают точно.
   Это не косметика: перечисление есть словарь тегов, которым S3b собирается разметить 1 887
   упражнений, и обе стороны обязаны говорить одними словами.
   Варианты: (A) оставить `neck`, на экране подписать «шея и верх спины»; (B) добавить девятый
   регион `upperBack`; (C) переименовать `neck` → `upperBack` и потерять шею.
   **Рекомендую A** — ноль изменений в словаре, который ещё не начали использовать по назначению.

2. **Куда «Образ жизни»** (питание, курение, алкоголь; текущий шаг 5). Фигмовского дома нет.
   Раскрывающийся блок в 4/9 рядом с медицинским, отдельный экран (тогда экранов восемь), или
   перенос в профиль. **Рекомендую перенос в профиль** — это не то, что нужно знать до первой
   тренировки.

3. **Health Connect (8/9).** Шов `HealthService` есть, интеграции нет. Заглушка с честным текстом,
   полноценная интеграция отдельным гейтом, или шаг убрать.

## Чего в этом предложении намеренно нет

- **Полей под «генерацию» и «превью плана».** Спека запрещает фальшивый прогресс и требует
  настоящего генератора (`:382-383`, `:388`). Заводить под это поля, пока генератора нет, — значит
  готовить место для фикстуры, которую спека запрещает.
- **Отдельного перечисления целей онбординга.** Отвергнуто в пользу расширения `ProgrammeGoal` —
  см. §2.
- **Переименований и удалений.** Ни одно существующее поле не исчезает; несовместимые становятся
  вычисляемыми.

## Оценка объёма после утверждения

Три новых перечисления (`TrainingLocation`, `EquipmentKind`, `FocusZone`, `TrainingBarrier` — 
четыре), два расширения существующих (`ProgrammeGoal`, `FitnessTier`), одна новая под-модель
(`TrainingSchedule`), четыре новых поля в существующих моделях, два поля становятся вычисляемыми,
одна миграция чтения. Правила Firestore не трогаются.
