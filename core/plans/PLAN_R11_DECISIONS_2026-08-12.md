## Конфликт, который надо разрешить до P5

Фигма-спека §8 (`LATEST_DEV_SINGLE_FILE_MASTER_PROMPT_EN.md:351-384`) задаёт **18 экранов** и
первым же требованием ставит «one primary question per screen». Наш поток — **7**.

«Оставить 7 шагов» и «всё остальное как в Фигме» несовместимы буквально: применение фигмовского
потока и есть превращение 7 в 18.

**Рабочее прочтение (принято для P1-P4, требует подтверждения для P5):** замораживаем
**структуру** (7 экранов, объединения не разбиваем), берём из Фигмы **контролы и оформление** —
линейки и колёса, диаграмму тела, карточки выбора. «One primary question per screen» тем самым
сознательно отвергается, и это записано здесь, а не подразумевается.

Побочное следствие: у Фигмы есть экраны, которых у нас нет вообще — Value proposition, Training
location, Schedule, Target areas, Main obstacle, Health Connect, Generating, Plan Preview, Account,
Contextual notification permission. При замороженной структуре они либо не появляются, либо
вкладываются в существующие семь. Это решение P5, не P1-P4.

## Разведка (измерено, не предположено)

**Онбординг — 7 шагов** (`onboarding_page.dart:34-40`): Personal, Health, Goals, Level, Lifestyle,
Equipment, Motivation. Индикатор считает `_index + 1` из `_stepCount` (`:121`).

**Шаг 2 = Health** и это худший экран относительно Фигмы: восемь свободных текстовых полей, причём
травмы парсятся из строки «часть тела: тип» через запятую (`step_health.dart:63-82`). Запись без
двоеточия отбрасывается молча (`:72` — `.where((s) => s.contains(':'))`). У прототипа на это
`BodyDiagram:1443` и `ChoiceCard:1218`.

**Шаг 1 = Personal — второй объединённый**: возраст, пол, рост, вес, ИМТ, целевой вес, дельта,
уровень активности на одном экране (`step_personal.dart:21-118`). Линейки уже стоят (R11b частично
сделан), колеса года рождения нет.

**`age` читается в шести местах**, поверхность миграции мала: `profile_models.dart:205,213,223,230,238,545`,
`firestore_profile_repository.dart:44` (чтение), `step_personal.dart:33,37` (запись),
`profile_page.dart:386` (показ).

**`NotificationService` не подходит под месячное напоминание как есть**
(`core/notifications/notification_service.dart:7-51`): единственный планировщик —
`scheduleReminder(ScheduledSession session, ...)`, привязанный к тренировке, и
`cancelReminder(String sessionId)`. Фото — не `ScheduledSession`.

**Конвейер подсчёта имеет чистый шов для паузы**: `RepSessionController._onFrame` (`:583`) —
единственная точка, где кадр превращается в счёт; `resetSet()` (`:775`) — единственный публичный
мутатор.

## Под-гейты

Разбито по правилу A3 (>2ч / 15+ файлов / 350+ строк спеки → дробить). Порядок — от независимого к
зависимому.

### P1 — ВЫПОЛНЕН (2026-08-12)

1. **Privacy gate и экспорт закрыты решениями, а не кодом.** Постоянная полоса
   (`progress_photos_page.dart:396-419`) сильнее одноразовой карточки; экспорт остаётся
   запрещённым по записанному решению (`local_progress_photos_repository.dart:68-72`).
2. **Месячное напоминание построено.** `NotificationService.scheduleAt(id, fireAt, ...)` —
   общая форма; `scheduleReminder` теперь выражен через неё, поэтому правило «время уже прошло →
   отменить» существует в одном месте вместо двух. Якорь — сохранение снимка: один общий id
   (`kProgressPhotoReminderId`), каждое сохранение сдвигает единственное ожидающее напоминание.
3. **Обещание показывается ДО запроса разрешения** — строка в листе метаданных, и только когда
   уведомления включены, иначе это было бы обещание, которое приложение уже решило не держать.

Найдено при этом: `NotificationService` умел планировать только от `ScheduledSession`, а
две тестовые подделки реализуют интерфейс через `implements` — тот же урок, что в C1: тела не
наследуются, метод пришлось добавить в обе.

### P1 — исходный замысел (сохранено)

1. **Privacy gate и экспорт — кода нет, только запись решений.** Обновить
   `PLAN_REDESIGN_REMAINDER_2026-08-12.md` и `DECISION_LOG.md`: пункты закрыты решением, а не
   реализацией. Экспорт — отказ подтверждён, ссылка на `local_progress_photos_repository.dart:68-72`.
2. **Месячное напоминание.** `NotificationService` получает второй планировщик, не привязанный к
   `ScheduledSession`. Якорь — момент сохранения снимка: при `save()` ставится напоминание на
   +30 дней, предыдущее снимается. Самокорректируется и не требует фонового джоба.
   Затрагивает: `notification_service.dart` (+реализация), провайдер-слушатель на сохранение,
   строки l10n, тесты. Тумблер в настройках — **не** делаю: `settings.notifications_enabled` уже
   существует и должен гасить всё.

**Риск:** низкий. Новый метод рядом с существующим, ничего не переписывается.

### P2 — тренер: active / paused / summary

Фазы уже объявлены, вызывающих нет (`coach_phase_providers.dart`).

1. `paused` останавливает счёт **одним** guard'ом в `RepSessionController._onFrame` — по фазе, а не
   по флагу в контроллере, чтобы источник истины остался один (тот же принцип, что в R11h).
2. Камера продолжает работать (решение оператора): `_openCamera`/`_startDetector` не трогаются.
3. `finish()` → фаза `summary`, полноэкранные итоги подхода из уже существующего
   `_SetSummaryCard`, кнопка «Новый подход» → `resetSet()` + фаза `active`.
4. Кнопки паузы/возобновления/завершения над превью.

**Риск:** средний — трогает конвейер подсчёта. Тест обязан доказать, что на паузе счётчик не
растёт при поступающих кадрах, а не только что кнопка перекрашивается.

**Не входит:** `calibration`. Сигнала «детектор устоялся» нет; предложу порог N подряд пригодных
кадров отдельной запиской, когда P2 закроется.

### P3 — год рождения вместо возраста

1. `ProfilePersonal` получает `birthYear`; `age` становится **вычисляемым** геттером, чтобы
   `profile_page.dart:386` и проверки полноты не переписывались.
2. Миграция в единственной точке чтения (`firestore_profile_repository.dart:44`):
   `birthYear ??= текущий год − age`. Запись всегда `birthYear`.
3. `WheelYear` по §9.1: колесо + прямой ввод + ± контролы + крупный текст. Гаптика — если
   `HapticFeedback` доступен без нового пакета.
4. `step_personal.dart` меняет числовое поле возраста на колесо.

**Риск:** средний — данные существующих пользователей. Миграция односторонняя и приблизительная
(±1 год, так как месяц рождения неизвестен); это записывается в UI как подпись под колесом при
первом открытии, а не замалчивается.

### P4 — ОТМЕНЁН оператором (2026-08-12)

Предлагался перевод шага 2 «Здоровье» на фигмовские `BodyDiagram` и `ChoiceCard`. Оператор,
увидев, какой именно это экран: *«нет экран на шаге 2 не трогать он щас очень удобный»*.

Записано как решение, а не как невыполненная работа: восемь свободных полей заполняются быстрее
любой таксономии, и это законный аргумент, который фигмовский вариант проигрывает.

**Открытым остаётся, какой экран оператор изначально хотел «сделать как в фигме».** Исходная
формулировка называла «шаг 2», но после уточнения, что шаг 2 — это «Здоровье», решение сменилось
на противоположное. Наиболее вероятный кандидат — шаг 1 «Личное», второй объединённый экран, и
именно его затрагивает P3 (колесо года рождения по §9.1 BodyMetricPicker). Не додумывать: спрошено
отдельно.

### P4-lite — молчаливая потеря травм (не оформление, а дефект)

Переживает отмену P4, потому что к виду экрана отношения не имеет.

`step_health.dart:72` — `.where((s) => s.contains(':'))` — отбрасывает всё, что не подошло под
формат «часть тела: тип». Пользователь пишет «колено болит», поле выглядит заполненным, в профиль
не уходит ничего. Молчаливая потеря данных о травме.

Правка внутри нынешнего экрана, вид не меняется: неразобранная запись сохраняется как травма с
пустым типом вместо выбрасывания.

**Честно о пользе:** на сегодняшнее поведение безопасности это НЕ влияет —
`exercise_filter.dart` фильтрует 0 из 1 887 упражнений, потому что тегов противопоказаний в
каталоге нет (записано в `CLAUDE.md`). Правка делает данные пригодными к моменту, когда теги
появятся. Продавать её как «теперь безопаснее» нельзя.

**Риск:** низкий, одна функция разбора и тест на неё.

## Целевой поток (7 экранов)

Прототип (`App.tsx:2387-2409`) против нашего текущего (`onboarding_page.dart:34-40`):

| Фигма | Содержание | Наш текущий источник |
|---|---|---|
| 1/9 | Цель + Уровень | шаги 3 «Цели» и 4 «Уровень» — оператор: «объединить 3 и 4» |
| 2/9 | Место + Оборудование | шаг 6 «Оборудование»; «где тренируешься» — новое |
| 3/9 | График: дней/неделю, длительность, предпочитаемые дни | нового нет |
| 4/9 | Тело: вкладки Ограничения ↔ Приоритеты, диаграмма тела | шаг 2 «Здоровье» уходит сюда |
| 5/9 | Барьеры («что обычно мешает») | частично шаг 7 «Мотивация» |
| 6/9 | Год рождения + Рост | \} вместе это наш шаг 1 «О себе» |
| 7/9 | Вес + Целевой вес | \} |
| 8/9 | Health Connect | нового нет |
| 9, вне счёта | Генерация, превью плана, аккаунт | нового нет |

**Применяем принцип оператора** («объедини как ты сделал для первого шага»): фигмовские 6/9 и 7/9
сливаются в один экран «О себе» — ровно то, что текущий билд уже делает, плюс пол и уровень
активности, которых в фигмовском списке нет вообще.

Итог: **7 экранов**, оформление фигмовское.

## Медицинские данные — по указанию оператора

*«добавь контрол типа дополнительные сведения со списком из шага 2 в фигма шаг 4 ограничения»*.

Раскрывающийся блок «Дополнительные сведения» внутри 4/9 на вкладке «Ограничения», под диаграммой
тела и чипами. Содержимое — нынешний шаг 2 без изменений: состояния, аллергии, лекарства, травмы,
ограничения, операции, давление, прочее.

Это разрешает противоречие между двумя указаниями оператора: экран здоровья «очень удобный» и его
не трогать — он и не трогается, только переезжает под шторку. Свободный ввод сохраняется.

## Что в фигмовском потоке отсутствует, а у нас есть

- **Пол.** В списке §8 его нет. Нужен: `missingBodyAnswersProvider` требует его для силуэта
  тренера. Уходит в «О себе».
- **Образ жизни** (питание, курение, алкоголь — текущий шаг 5). Фигмовского дома нет. **Решение
  оператора требуется:** сложить вторым раскрывающимся блоком в 4/9, оставить отдельным экраном
  (тогда 8), или убрать из онбординга в профиль.
