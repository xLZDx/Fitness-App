# Bulk-delete fence and straggler pass (GPT-PM MAJOR-02)

- What: `manageBodyScanData` `deleteAllScans` / `deleteAllPhotos` now (1) raise a per-user fence document on the first page and refresh it on every continuation page, (2) run a bounded straggler pass on the final page, and (3) clear the fence when the final page completes. `createBodyScan` reads the fence inside its transaction and refuses with `failed-precondition: delete-in-progress` while it is active.
- Why: the walk is in document-id order with `startAfter(cursor)`. A scan created between pages with a client UUID id sorting before the cursor was never visited, so the last page returned "done" while a live scan survived (privacy-deletion hole).
- Design:
  - Fence document: `body_scan_purge_state/delete_fence_<first 32 hex of sha256(uid)>` with `{startedAtMs, activeUntilMs, action}`. This collection is already deny-all for clients and carries no uid, so no rules change was needed (the id is a hash, not the uid). `activeUntilMs = now + 15 min` (`DELETE_FENCE_MS`), refreshed per page; an abandoned delete therefore unblocks creation after at most 15 minutes.
  - `createBodyScan`: inside the existing transaction, for every outcome except the terminal replays (`done`, `cancelled`), the fence is read; active fence -> decision `deleting` -> quota refunded -> `delete-in-progress`. Creating, resetting a `failed` scan and re-issuing upload URLs are all refused (an upload slot opened behind a finished walk would survive it). `done` replay and `cancelled` answers behave as before. Because the fence is read in the transaction, a fence written after that read forces a retry.
  - Straggler pass (final page only): query `body_scans where createdAt >= windowStart orderBy createdAt` (single-field index, no new composite), filter in code (`status != cancelled` for scans, `photosState` not `deleted`/`none` for photos), process with the same per-scan logic (`processScan`, extracted from the walk). Window start = fence start - 15 min on a first-page run (covers creates that started before the fence), = stored `startedAtMs` - 15 min on a resumed run, = 0 (full re-check) when a resumed run finds its fence lapsed. At most 3 passes; work still found after the third pass throws `aborted: delete-incomplete` and leaves the fence in place (it expires) rather than reporting done.
  - `estimateBodyScan` is unchanged: it cannot create a scan, already answers `scan-cancelled` for tombstones, and a scan created after the fence start cannot exist.
  - Mobile: `delete-in-progress` added to the retriable slug set in `body_scan_api.dart` (no other client change; unknown slugs already map safely).
- Contracts: new closed slugs `delete-in-progress` (failed-precondition, create) and `delete-incomplete` (aborted, manage); new server-only document family under `body_scan_purge_state`. Response shapes unchanged (`processed` on the final page includes straggler scans).
- Paths: `functions/src/body_scan/{shared,create,manage}.ts`, `functions/src/__tests__/body_scan/{manage,create}.test.ts`, `mobile/lib/features/body_scan/state/body_scan_api.dart`.

New cases: fence raised/refreshed/cleared and uid-free id; straggler tombstoned for `deleteAllScans` and photos deleted for `deleteAllPhotos` (id before cursor, created between pages); lapsed-fence resume; cap -> `delete-incomplete`; create refused during fence (new, re-issue, failed reset) with refund and no URLs; done replay unaffected; cleared fence allows create; expiry boundary at `activeUntilMs`; another user's fence ignored.
