# Late sweep: compare-and-delete and an honest contract (GPT-PM round 3)

- What: (1) the late sweep deletes its record only through a transaction that re-reads it and deletes iff `rev` and `dueAtMs` equal what the run read before sweeping; (2) the "17 minutes" statement is now a target, not a bound.
- Why (1): `completeFence()` of a newer bulk delete B rewrites the shared per-user `late_sweep_<hash>` record (later `dueAtMs`) while the scheduler may be processing the older state A. A's unconditional `delete()` then erased B's pending sweep, so B's late PUT would never be swept.
- Design (1): `completeFence` writes `{uid, action, dueAtMs, rev}` with a fresh random 64-bit `rev` on every write. `runLateSweep` remembers `{rev, dueAtMs}` from the query snapshot, sweeps, then runs a transaction: re-read; if the doc is gone or `rev`/`dueAtMs` differ it is kept (counted as not completed), otherwise deleted. A kept record is picked up by the next 5-minute run once due. A racing write between the transaction read and its commit makes the transaction retry and re-compare. Legacy records without `rev` compare as equal to themselves.
- Contract (2): runbooks/body_scan_bucket.md section 9, the `purge.ts` header comment, `firestore.rules` comment (comment text only, no rule change), `core/DATA_INVENTORY_2026-08-11.md` row 197 now say: target removal within about 17 minutes of completion under normal operation; a record that cannot finish (page cap 20 x 500 objects per user per run, storage error, outage) is kept and retried every 5 minutes until it succeeds; there is no hard upper bound; the uid-bearing record lives until the sweep has deleted it. Earlier change records (2026-10-15-fence-ownership-late-sweep.md, 2026-10-15-fence-ownership-tests.md) keep their original "at most 17 minutes" wording as history; THIS record supersedes it. Load limits (schedule, 90 s budget, page caps) are unchanged.
