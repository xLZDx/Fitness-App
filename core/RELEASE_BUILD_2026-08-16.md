# Android release build — 2026-08-16 (gate G2)

The project has claimed release readiness for a while without ever having produced a release
artifact. This is the first one, and the point of the gate is that a release build is the only thing
that can answer questions a test suite cannot: does the signing config actually resolve, is the
result actually a release, and how big is it.

Not in `core/PRODUCTION_MANIFEST.md` deliberately: that file is generated by
`scripts/dev/production_manifest.py` from live Firebase and GCP APIs and says in its own header not
to hand-edit it. A local build artifact is a different kind of fact and does not belong in a file
about what is deployed.

## The artifacts are releases, not debug builds dressed as one

This was checked rather than assumed, because "it said release on the command line" is not evidence.

| Check | Result |
|---|---|
| Signing certificate | `CN=Ivan Korostelev, OU=Ivan Korostelev II, O=Ivan Korostelev II, L=Chisinau, ST=Chisinau, C=MD` |
| Certificate SHA-256 | `77da5eedd3ce1ce2128ed9040cda91168f4a9454c0f26bae126d23cee5b310b7` |
| Key | RSA 2048, SHA256withRSA |
| Contrast: the debug APK in the same output directory | `C=US, O=Android, CN=Android Debug` — a different certificate |
| `android:debuggable` | absent from the release manifest (i.e. false) |
| Package id | `...sptr`, without the `.debug` suffix `applicationIdSuffix` adds to debug builds |
| Bundle signature | `jarsigner -verify` passes with the same certificate |
| APK signature schemes | v2 ✅, v1 ✗, v3 ✗ |

The certificate fingerprint is recorded because it is public information — Play displays it, and an
app's signing identity is meant to be checkable. `android/key.properties` holds the keystore path and
passwords; it is untracked and matched by `android/.gitignore:17`, verified, and **nothing from it
appears in this document or anywhere in the repository**.

One observation on the signature schemes: only v2 is present. v3 adds key rotation support. With
`minSdk 26` this changes nothing about installability and is not a blocker; it is worth a line
because "signed" is often assumed to mean "signed with every current scheme".

Eight native libraries ship per ABI. The four largest in `arm64-v8a`: `libxeno_native.so` 20.60 MB,
`libapp.so` 11.94 MB (the Dart AOT snapshot), `libmlkit_google_ocr_pipeline.so` 10.55 MB,
`libmlkitcommonpipeline.so` 10.48 MB, `libflutter.so` 10.31 MB. ML Kit is roughly half the native
weight; the pose and OCR pipelines are what the Form Coach and the machine scanner are built on, so
this is the cost of two shipped features rather than accidental bloat.

Largest assets: `pose_landmark_detector_full_f16_inf.tflite` 6.14 MB, `equipment_v1.tflite` 4.29 MB,
and the two vendor catalogues at 3.06 MB (RU) and 3.05 MB (EN).

### Against Play's actual limits

Verified against
[Play Console — download size limits](https://support.google.com/googleplay/android-developer/answer/9859372):
the base module limit is **500 MB compressed download size**, with a user-facing warning about
mobile data above **200 MB**. An arm64 device downloads roughly what the arm64 split APK weighs,
107.2 MB, so the app is **comfortably inside both** — under a third of the hard limit and about half
the warning threshold.

The 263.4 MB fat APK is not a submission route and does not need to be; it exists because
`flutter build apk` produces it, and Play takes the bundle.

## BLOCKER — `targetSdk` 35 is below what Play will accept in 15 days

**Basis: FACT.** The built artifact reports `targetSdkVersion:'35'`.

[Play's target API level requirements](https://support.google.com/googleplay/android-developer/answer/11926878)
require **Android 16 (API 36)** for new apps and updates from **31 August 2026**. Today is
2026-08-16. This app has never been submitted, so it would be a new app, and the deadline lands
before any realistic submission date. An extension to 1 November 2026 can be requested, which is a
delay, not an exemption.

`compileSdk` is already 36, so the code is compiled against the API 36 surface and the change itself
is one line: replace `targetSdk = flutter.targetSdkVersion` with an explicit `targetSdk = 36` in
`android/app/build.gradle:126` — Flutter 3.27.1's `flutter.targetSdkVersion` is 35 and pinning is the
same reasoning already written above `compileSdk = 36` in that file.

**It was deliberately not changed here.** `targetSdk` is the one SDK knob that changes runtime
behaviour rather than API availability — API 36 enforces edge-to-edge display, and this app's layouts
have never been opened on an Android 16 device. Bumping it in a gate that cannot run on a device
would produce a build that compiles, passes every test, and is visually broken for users, which is
precisely the "helper functions exist, therefore the feature works" claim this project's contract
forbids. The required change is one line; the verification it needs is a device.
