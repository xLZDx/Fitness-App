# Decision: `N-04` (gym-association authority, and its two sub-questions P-1/P-2)

**Decision: defer both. Leave the gym-association code path as dormant, undecided, inactive.**

## P-2 — who is the customer for an equipment report?

**Not decided. Deliberately left open.** The code is built as though the customer is the gym
(routed work-order, gym identity load-bearing, webhook dispatch); it behaves as though the
customer is the user (no `gymId` is ever supplied, nothing is routed anywhere); the UI claims the
first. `core/review/N04_EQUIPMENT_REPORT_AUTHORITY.md`'s own text: *"Nothing in this repository can
settle that, and it is the question that decides whether N-04 ever comes back."*

Operator's own words, from a live session, 2026-09-17: *"Пока не знаю, оставить как временно
неактивный код"* ("don't know yet, leave it as temporarily inactive code"). This is a genuine
decision, not a non-answer: it is a deliberate choice to defer rather than force a premature
product call, and it is a valid closure of the row because the code path this question gates is
already unreachable in practice — `gyms/` has no writer anywhere in this repository, so no
equipment report is ever actually routed to a gym today regardless of which way P-2 eventually
resolves.

## P-1 — is a gym's maintenance webhook a disclosed processor?

**Not decided, and moot for now as a direct consequence of P-2's deferral.** `app_en.arb`'s privacy
body names exactly two processors (Google, Stripe); a gym-controlled `maintenanceWebhookUrl` would
be a third recipient once it actually fires — but it does not and cannot fire today, because no
`gyms/` document exists for it to route to. There is nothing live to disclose or fail to disclose
while P-2 stays undecided and the webhook stays unreachable. This is not a resolution of P-1 either
way (disclose vs. remove) — it is a statement that the question has no live consequence yet.

## The trigger this deferral depends on

`core/review/N04_EQUIPMENT_REPORT_AUTHORITY.md`'s own recorded gap: the deferral's trigger
("revisit when `gyms/` gains a writer") is inert — no test, CI check, or runtime guard is keyed to
it, and every webhook test primes the gym document itself, so nothing turns red on the day a real
writer ships. `RESIDUAL[N-04-gym-association]` names the cheapest fix (a test that fails when
`reportEquipment` can reach a populated `gyms/` with no association check) but it is deliberately
not built here — building a guard for a decision nobody has taken would be exactly the "engineering
performed to look busy" this project has already flagged elsewhere. If this deferral stands for
long enough that gym onboarding becomes real roadmap work, building that guard becomes due at that
point, not before.

## What this closes and what it does not

This closes the `N-04-gym-association` row in `core/CURRENT_STATE.md` as an operator decision to
defer, not as a product resolution — P-1 and P-2 remain genuinely open questions, revisited only
if gym onboarding becomes real roadmap work. Nothing in the shipped code changes as a result of
this decision; the webhook dispatch code and the association-authority code both stay exactly as
they are, dormant.
