01Почему это отменяет прежний APPROVE

Раунды R1–R3 самого документа выполнял один непрерывный ревьюер (GPT), проигрывающий разные роли в одном чате, и сам себя свёл к APPROVE. Этот вердикт — первый проход, который (а) сверил claims дизайна с реальным деревом Fitness_App, а не с текстом самого документа, и (б) прогнал два по-настоящему независимых метода ревью и свёл их результат, а не принял один проход за финальный.

Два из четырёх подтверждённых BLOCKER — это факты из репозитория, противоречащие обязательным инвариантам самого дизайна, а не design-level пробелы:

  • Дизайн требует enforceAppCheck=true как security exit condition (§8.5, §11, P2.G3). App Check enforcement сейчас глобально выключен в репозитории (functions/src/scaling.ts:113-124), заблокирован на отдельной инфраструктурной миграции (текущие тестовые билды через Firebase App Distribution не аттестуются).
  • firestore.rules:24-35 — wildcard users/{uid}/{coll}/{document=**} даёт клиенту полную запись в любую не исключённую подколлекцию. recognised_models (exact-model history, P5.G3) не входит в список исключений — модифицированный клиент может подделать identityLevel: EXACT_MODEL с произвольным catalogVersion/modelId, что ломает все claims дизайна про server authority.

02Подтверждённые BLOCKER (4)

BLOCKER B-01App Check global-off
Enforcement выключен глобально, зависит от несвязанной платформенной миграции; P2.G3/P6 security exit не может честно закрыться.
Источник: Claude Architecture (repo-grounded) — принято GPT без rebuttal. Требуется: новый prerequisite-гейт (P0.G0/PLATFORM-AC-01) со статусами BLOCKED_EXTERNAL_PLATFORM_MIGRATION / READY_FOR_SHADOW / READY_FOR_PRODUCTION; явное разделение shadow vs production identity; запрет production promotion пока APP_CHECK_ENFORCED != true.
BLOCKER B-02Firestore wildcard client write
recognised_models подделывается клиентом через wildcard-правило users/{uid}/**.
Источник: Claude Architecture (repo-grounded) — GPT назвал это "хуже, чем просто отсутствующая rules-запись". Требуется: firestore.rules + firestore.indexes.json становятся обязательными deliverables P1/P5; deny-by-default/server-authoritative правила для exact history; emulator mutation-тесты (client CREATE/UPDATE authority fields → DENY, server/admin write → ALLOW, чужой аккаунт → DENY).
BLOCKER B-03P6 shadow ошибочно optional
P6.G1 (shadow deployment) классифицирован как OPTIONAL / NOT A P6 PREREQUISITE — буквальный copy-paste классификации P5.G4.
Источник: GPT B-01, независимо воспроизведено Claude Architecture другим методом (обнаружение copy-paste). Требуется: реклассифицировать P6.G1 как RELEASE-BLOCKING PREREQUISITE; определить минимальный shadow volume/время, полноту terminal outcomes, SLO на App Check/rate-limit ошибки до promotion.
BLOCKER B-04Sealed-test reuse / multiple comparisons
Переиспользование sealed-test для per-model promotion (P6.G3) создаёт post-selection bias, который единый глобальный confidence bound не покрывает.
Источник: GPT B-02, независимо воспроизведено Claude ML/Data Science. Требуется: pre-register per-model критерии promotion и фиксированный candidate set до sealed-прогона, с поправкой на множественность сравнений (напр. Bonferroni на K моделей) либо явная иерархическая/partial-pooling статистическая модель — запрещено выбирать "прошедшие" модели после просмотра sealed-результатов.

04Находки только Claude, принятые GPT при сведении

Всё ниже — ACCEPT от GPT в финальном раунде, без rebuttal:

  • Региональная привязка (europe-west1/eur3) завязана на стабильность URL Stripe webhook (scaling.ts:65-68); P0.G5 не должен считать регион открытым архитектурным выбором — смена региона рискует окном "платежи никуда не долетают".
  • Дублирующийся rate limiter: rate_limit.ts (§12.3) дублирует уже работающий транзакционный abuse_guard.ts. Сначала расширить существующий; новый limiter — только после gap-анализа.
  • Provider не autoDispose, нет scanId-lifecycle: visualEquipmentControllerProvider — глобальный NotifierProvider, не autoDispose/family; async-invariant §7.1 сейчас — проза без Riverpod-механизма. Нужен family по scanId/recognitionSessionId + autoDispose + guard текущей сессии.
  • Client-readable equipment_models vs server authority — ACCEPT WITH REFINEMENT: читать display-метаданные можно; нарушение — если клиент сам решает "эта модель VERIFIED, значит exact/setup авторизован" по кэшированным полям вместо живой server-проверки policy.
  • Не назван статистический метод: числа (~100/~299 при нуле ошибок) совпадают с точной односторонней границей Clopper-Pearson, но метод нигде не назван явно — implementer может взять Wald-приближение, которое вырождается при нуле ошибок. Явно зафиксировать Clopper-Pearson.
  • Исчерпание round-cap без исхода: неразрешённый BLOCKER/CRITICAL на раунде 5 должен означать GATE REMAINS OPEN / NO PROMOTION / ESCALATE TO OPERATOR, а не молчаливый проход по исчерпанию раундов.
  • Не переиспользована существующая ML CI-machinery: scripts/ml/lifecycle.py + test_ml_contracts.py, подключённые к .github/workflows/flutter.yml, уже механически проверяют claims MODEL_REGISTRY.json против реального дерева ассетов. Новая promotion-machinery дизайна должна идти через этот контракт, а не строить параллельный, непроверяемый CI.
  • 15 новых файлов Cloud Functions заходят в единственный существующий codebase без scaling/deploy-изоляции от stripeWebhook — принято как MAJOR, но GPT не согласился, что "отдельный codebase" — единственное решение; нужен evidence-driven выбор.
  • Схема MODEL_REGISTRY.json плохо ложится на equipment_identity_embedding/gemini_equipment_verifier как новые записи models[] — в реестре уже есть категория vendor_models (используется для текущей записи gemini), которая подходит лучше.
  • Retrieval-specific утечка: ассет, использованный для построения retrieval-индекса equipment_model_exemplars, может попасть и в CALIBRATION_SET — pHash-only правило split этого не ловит.
  • Названные роли ревьюеров в §10 (R2 "Provenance/legal", R5 "Release reviewer") не имеют соответствующего agent-файла в Fitness_App/.claude/agents/, хотя роли R1/R3/R4 — существуют реально. Отдельно: механизм R5 "GPT review" сейчас глобально отключён (ENABLED_REPO_ROOTS = []).
  • Опциональный verifier (P4.G4, POST_MVP) может незаметно выпасть из decision-пути без отдельного сигнала, что EXACT_MODEL выдан без адъюдикации Gemini.

UNSUPPORTED MODEL is not UNKNOWN EQUIPMENT. CLIENT CANCEL is not BACKEND TIMEOUT. POLICY REVOCATION is not HISTORICAL EXACT IDENTITY.

06Что пережило оба ревью без изменений

Не переоткрывать

  • Additive-архитектура вокруг equipmentId: exact model никогда не заменяет функциональную онтологию и не обходит safety/exercise-фильтрацию.
  • Denoising в machine_text_anchor.dart остаётся нетронутым; отдельный IdentityTextParser — верное структурное решение.
  • Переиспользование core/ml/MODEL_REGISTRY.json вместо второго ML lifecycle — верно (с уточнением: категория vendor_models, а не models[], для новых hosted-моделей).
  • Rights-модель (§4.4) действительно fail-closed и многомерна.
  • Реклассификация 30 фото в legacy regression и OCR-first "resolve via text before image upload" — обоснованы.
  • Отказ P0.G5 доверять emulator parity для vector search — верен для этого репозитория.

07Рекомендованный следующий шаг

По заключению GPT-PM (согласовано Claude): не ещё один полный раунд ревью v4.1, а механическая сборка v4.2 Remediated Review Candidate из этого свода находок, закрывающая минимум перечисленное в §2–§4 этого отчёта, затем один финальный verification pass — что согласованные фиксы реально попали в документ, а не открытое ревью заново.

Заметка о живом тесте PM Bridge. Это ревью одновременно стало первым живым end-to-end тестом Playwright-транспорта PM Bridge после фикса конкурентности в Gate 6. gpt_send прошёл успешно (со второй попытки — гонка гидратации сайдбара при поиске по title, устранена переходом маппинга Fitness_App в config/conversations.md на ID-роутинг, по аналогии с уже сделанным для самого pm-bridge). gpt_await_reply дважды не смог задетектировать реально пришедший ответ (подтверждённый неизменный баг подсчёта turn count, не пропавший ответ — оба раза ответ был полностью на странице). Содержимое ответа получено и залогировано через gpt_ingest_reply как fallback оба раза. Это отдельный нерешённый дефект транспорта, не находка по дизайну — зафиксирован отдельно, не чинился в рамках этой задачи.
