## 0. How to read this document

Every statement is tagged:

- **FACT** - verified in a file of this worktree; the path follows.
- **PROPOSED** - a requirement or default this contract introduces; it becomes binding only after approval. Nothing tagged PROPOSED exists in code.
- **UNVERIFIED** - could not be confirmed in this worktree (listed again in section 11).

Requirement ids are `GPS-PRIV-nnn`. Later sprints cite them in stories, tests and change records. "MUST" means the sprint that builds the feature fails its DoD without it. Source of the sprint and decision ids: `docs/phase2/plan/03_ROADMAP_AND_SPRINTS_2026-10-15.md` (S01 row, section 10 decision register, section 11 matrix).

## 1. Purpose and scope

Purpose: fix, before any location code exists, what location-related data the product may collect, where it may live, who may see it, how long it stays, and how it leaves the system (export, deletion, logs). Location history is the most sensitive data the app will hold (FACT, `docs/phase2/plan/01_PROJECT_REASSESSMENT_2026-10-15.md`, risk R-1 and section "riskiest assumption is GPS").

In scope: raw GPS samples, derived geometry, published routes, previews and thumbnails, caches, route photos, background location, heart-rate streams, friends/social graph, minors. Consumers: S02 (activity persistence), S04-D/S04 (permission and recorder), S05/S06 (EXPLORE, RIDE), S07 (route catalogue), S09 (publication protocol), S10 (sharing UI), S11 (offline), S25 (security and privacy review), S28 (deletion SLA).

Out of scope: tile and route-data licensing (S01 part b), UI baseline (S01 part c), body photos and nutrition (covered in the matrix only as existing-data baseline).

## 3. Data classes and definitions

| Id | Class | Definition |
|---|---|---|
| C1 | Raw GPS samples | Timestamped latitude, longitude, accuracy, optional altitude/speed/bearing as received from the location provider during a recording |
| C2 | Derived geometry (private) | Smoothed track, distance, elevation profile, splits, bounding box computed from C1 and stored with the activity |
| C3 | Published routes | A route entity visible beyond the owner (unlisted, friends, public) |
| C4 | Previews and thumbnails | Rendered images or simplified polylines of C2 or C3 used in lists, cards, share images |
| C5 | Caches | Any derived or fetched copy kept for speed or offline: route cache, map tile cache, previews cache, geocoding results |
| C6 | Route photos | Photos attached to a route or activity, which may carry EXIF including GPS coordinates |
| C7 | Background location | Location delivered while the app is not in the foreground (foreground service or background permission) |
| C8 | Heart-rate streams | Timestamped heart-rate series from a sensor or health platform during an activity |
| C9 | Friends and social graph | Follow/friend edges, groups, membership, buddy requests |
| C10 | Minors | Cross-cutting rules for users under 18 or of unknown age |
| C11 | Privacy zones | Centre and radius of home, work or user-defined areas used to trim and validate shared geometry; location data about the owner (added in review round 2, GPS-PRIV-095; matrix class C11) |

## 4. Principles

- GPS-PRIV-001 (MUST, PROPOSED) Private by default. Every new activity, route, photo and preview is visible only to its owner until the owner takes an explicit publish or share action. No flag, onboarding default or experiment may change this default.
- GPS-PRIV-002 (MUST, PROPOSED) Purpose limitation. Location is collected only while the user is recording an activity or has explicitly invoked a location feature (for example "Find nearby"). It is never collected at launch, during onboarding, or passively.
- GPS-PRIV-003 (MUST, PROPOSED) Least data. Sample rate, precision and fields are the minimum the calculators need (decided in S04-D); precision is not increased for diagnostics.
- GPS-PRIV-004 (MUST, PROPOSED) Every class in section 3 has a row in `DATA_LIFECYCLE_MATRIX.md` and in `scripts/ci/data_lifecycle_policy.json` before its first line of code merges.

## 5. Permission and consent flow

Flow (PROPOSED; screen design belongs to S04-D, which MUST implement these rules):

1. Foreground location is requested only at the moment of the first "Start GPS" or "Find nearby" tap, with a one-line reason shown first. (The same rule is stated in `docs/phase2/plan/04_UI_UX_DIRECTION_2026-10-15.md`, line 52, FACT.)
2. Background location is requested only after foreground is granted, only when a recording is active or about to start, and only on platforms where continuous recording needs it. Foreground-service recording is preferred over background permission wherever the platform allows it.
3. Denial of either permission leaves the app fully usable: manual entry, history, no-GPS walk.
4. Consent is recorded per purpose in the Consent centre (rows: GPS, background location, health import, route visibility; the centre itself is specified in `docs/phase2/plan/04_UI_UX_DIRECTION_2026-10-15.md` line 76, FACT as a plan).

Requirements:

- GPS-PRIV-005 (MUST, PROPOSED) No location permission prompt appears at app launch, on first run before a location feature is chosen, or in onboarding.
- GPS-PRIV-006 (MUST, PROPOSED) Foreground location is requested before background location; the pre-prompt explains in plain words what is recorded, where it is stored and who can see it.
- GPS-PRIV-007 (MUST, PROPOSED) Background location is used only while a recording is active (including paused-by-auto-pause). When the recording ends or is discarded, background collection stops within the same user action. A persistent system notification is shown during background collection.
- GPS-PRIV-008 (MUST, PROPOSED) Revoking a permission (in the app or in system settings) stops collection immediately. A recording in progress is saved up to the moment of revocation and marked "permission revoked"; the user is offered keep, export or delete for that data. The app never re-requests in a loop.
- GPS-PRIV-009 (MUST, PROPOSED) Consent is stored as a record per purpose with timestamp, text version and current state; withdrawing consent is as short as granting it (one switch in the Consent centre) and offers export and delete links for the affected class.
- GPS-PRIV-010 (MUST, PROPOSED) Location privacy text is approved by the operator or counsel before any route can be made visible beyond the owner (roadmap section 7 lists legal review before S09; risk R-1 in `01_PROJECT_REASSESSMENT`, FACT).
- GPS-PRIV-011 (MUST, PROPOSED) The Android manifest and store data-safety forms declare background location only if the final design uses the background permission; the declared set equals the used set (checked in S25).

## 6. Requirements per data class

Retention values marked "per D-16" are open (section 9).

### C1 Raw GPS samples

- Collected: only during a recording (GPS-PRIV-002). Local: crash-safe journal on the device until synced or discarded (PROPOSED, S04). Cloud: PROPOSED private compressed object per activity (roadmap S02: "streams as compressed private objects", FACT as a plan), not a Firestore document and never in a collection readable by anyone but the owner.
- GPS-PRIV-012 (MUST, PROPOSED) Raw samples are never readable by any user other than the owner and never appear in any published, unlisted, friends or public artefact.
- GPS-PRIV-013 (MUST, PROPOSED) Until D-16 is decided and recorded in `core/DECISION_LOG.md`, raw samples stay on the device only; no upload code path is enabled (flag OFF).
- GPS-PRIV-014 (MUST, PROPOSED) The local journal is deleted after a confirmed sync, or on discard, or on sign-out/account deletion. A journal left by a crash is offered for recovery and then follows the same rule.
- GPS-PRIV-015 (MUST, PROPOSED) Retention for cloud raw samples follows the D-16 outcome and is enforced by a mechanism, not a document (object lifecycle rule or scheduled deletion), with a test.
- Export: GPX and FIT (roadmap S02/S06, FACT as plan) containing the full raw series. Deleted: with the activity and with the account.

### C2 Derived geometry (private)

- GPS-PRIV-016 (MUST, PROPOSED) Derived geometry lives and dies with its activity: same owner-only access, deleted in the same operation as the activity and the account. Its upload to the cloud is gated like C1 (GPS-PRIV-072) and it has its own retention row (matrix C2, D-16 sub-choice in section 9).
- GPS-PRIV-017 (MUST, PROPOSED) Derived geometry is recomputable from C1 and is not treated as a safe, anonymised substitute: it carries the same sensitivity as C1.

### C3 Published routes

- GPS-PRIV-018 (MUST, PROPOSED) Visibility is a server-held enum private / unlisted / friends / public, defaulting to private, changed only by an authenticated owner action. Enforcement is server-side (S09), not only in the client.
- GPS-PRIV-019 (MUST, PROPOSED) Publishing requires a preview of the exact geometry that will be visible (after privacy zones and trimming) and an explicit confirm. Unpublish and delete-shared-copy are available from the same screen.
- GPS-PRIV-020 (MUST, PROPOSED) A published route is a separate derived artefact. The raw samples (C1) are never copied into it. It stores only trimmed, simplified geometry.
- GPS-PRIV-021 (MUST, PROPOSED) Trimming is not treated as sufficient protection. Before publication the server runs a re-identification check and refuses or asks for more trimming (roadmap S09, FACT as plan: "trimming alone is not treated as protection"). The check is made testable by GPS-PRIV-073 and GPS-PRIV-074 (inputs, parameters, acceptance criteria).
- GPS-PRIV-022 (MUST, PROPOSED) Unlisted links use unguessable identifiers (at least 128 bits of randomness) and are revocable.
- GPS-PRIV-023 (MUST, PROPOSED) Every published artefact stores a back-reference to its source activity so deletion or unpublish can find every copy (derived-artefact registry, S09). Amended by GPS-PRIV-075: the back-reference lives only in a private server-only registry; the public document never carries owner or source ids.
- GPS-PRIV-024 (MUST, PROPOSED) Report and takedown records exist for published routes; a takedown hides the route for everyone except the owner and moderators (S09).

### C4 Previews and thumbnails

- GPS-PRIV-025 (MUST, PROPOSED) A preview is generated only from geometry already filtered for the target visibility (privacy zones and trimming applied). A preview of a private activity inherits private visibility.
- GPS-PRIV-026 (MUST, PROPOSED) Previews are registered in the derived-artefact registry (GPS-PRIV-023) and deleted or detached whenever their source is deleted, unpublished or re-trimmed. A preview is never kept after its source is gone.
- GPS-PRIV-027 (MUST, PROPOSED) A preview or share image never embeds location metadata (no EXIF/XMP GPS) and never contains street-level base map detail inside a privacy zone.

### C5 Caches

- GPS-PRIV-028 (MUST, PROPOSED) Every cache (route cache, preview cache, tile cache, geocoding results) has a documented maximum size and age, and is cleared on sign-out and on account deletion.
- GPS-PRIV-029 (MUST, PROPOSED) A cache never holds data the owner has deleted or that is outside the viewer's visibility; unpublishing or deleting an activity evicts local caches on the owner's devices on next sync, and the server-side cache (if any) is purged by the same deletion operation. "On next sync" does not work once the account no longer exists; account deletion has its own local wipe rule (GPS-PRIV-085).
- GPS-PRIV-030 (MUST, PROPOSED) Map tiles are cached only as the provider licence allows; no bulk pre-fetch from a provider that forbids it (S01 part b and S11, FACT in roadmap: OSM community tile policy forbids offline pre-fetching).

### C6 Route photos with EXIF

- GPS-PRIV-031 (MUST, PROPOSED) EXIF, XMP and any GPS metadata are stripped on the device before an upload and again verified server-side on receipt; the client-side strip is a first line only. The server never stores in a delivery location, or serves, a file that has not passed the quarantine decode and full re-encode of GPS-PRIV-080; a file that cannot be decoded, or that still carries GPS tags after re-encode, is rejected and deleted, not silently stored (roadmap S09, FACT as plan). Uploads land in quarantine first (GPS-PRIV-080), so "rejected" means "never promoted".
- GPS-PRIV-032 (MUST, PROPOSED) Original unstripped files are never uploaded. Photos are private by default and follow the visibility of their route; making a photo public requires its own explicit confirmation.
- GPS-PRIV-033 (MUST, PROPOSED) Route photos are stored in a private Storage path under the owner's id, covered by `storage.rules` (GPS-PRIV-064), deleted with the route, activity and account, and listed in the export (metadata and the stripped images).
- Note (FACT): existing progress photos are a different class: encrypted on device and never uploaded (`mobile/lib/features/progress_photos/data/aes_photo_cipher.dart`). Route photos do not reuse that promise; the privacy text MUST say they are uploaded.

### C7 Background location

- GPS-PRIV-034 (MUST, PROPOSED) Background location is a collection mode of C1, not a separate store: samples collected in the background have the same classification, retention and deletion as C1.
- GPS-PRIV-035 (MUST, PROPOSED) No location is collected in the background when no recording is active, on boot (`RECEIVE_BOOT_COMPLETED` is declared today for notifications, FACT in the manifest), or after sign-out. Mechanism: all location access goes through one injectable location-service interface; a widget/unit test with a fake service asserts that no subscription exists before a recording starts, after it stops, after sign-out and after boot, and a lint or grep-based check fails the build if location plugin APIs are imported outside that one file.

### C8 Heart-rate streams

- GPS-PRIV-036 (MUST, PROPOSED) Heart-rate streams are health data: consent per source and per datatype, device-only by default, uploaded only after D-16 and only with that consent, never shown in a published, unlisted or friends artefact, and never included in a public preview or share image.
- GPS-PRIV-037 (MUST, PROPOSED) Platform reads (Health Connect, HealthKit) are read-only and use the minimum granular permission; a new datatype means a new manifest permission, a new consent row and a new matrix entry. Today only resting heart rate and HRV reads are declared (FACT, manifest).
- GPS-PRIV-038 (MUST, PROPOSED) Heart-rate retention, export and deletion mirror C1 (same activity cascade), except that D-16 may set a different retention period for each (section 9).

### C9 Friends and social graph

- GPS-PRIV-039 (MUST, PROPOSED) Social features are opt-in. Edges are visible only to the two parties (and group members for groups). There is no public follower list and no search for people by location. Discovery of routes by the viewer's own location (S07/S08 "Find nearby") is allowed, and is served only from the public index of GPS-PRIV-075 built from trimmed geometry; it never queries raw or private data and never returns owner identity. The viewer's own position used for such a query is not stored (GPS-PRIV-048, GPS-PRIV-082, GPS-PRIV-096).
- GPS-PRIV-040 (MUST, PROPOSED) Friends visibility follows the D-17 outcome and is enforced server-side. Definitions (GPS-PRIV-088): "known adult" = server-held birth year with `birthYear <= currentYear - 19`; "known minor" = server-held birth year that is not known adult and not in the future; "unknown age" = no server-held year or an invalid one. Under register default and D-17 option A: friends visibility is available only to a known adult, or to a known minor on a mutual-accept edge with the stated guardian-guidance copy; unknown age is refused. Under option B: refused for known minors and unknown age. Under option C: not applicable (no location data below the gate). Adult-to-minor edges: the binding default until the operator decides D-17 sub-option E is E1, an adult-to-minor friends edge (an edge between a known adult and a known minor, or involving unknown age) is refused server-side at creation and acceptance, so an adult cannot read a minor's friends-visible routes. Edges between two known minors under option A need mutual accept; E2 and E3 remain open options (section 9). AC: see GPS-PRIV-063 (friends path). Leaving a group or removing a friend takes effect for all future reads immediately.
- GPS-PRIV-041 (MUST, PROPOSED) Account deletion removes the user's edges and group memberships, and replaces the user id in records that are not theirs alone with a tombstone value, following the existing pattern (`DELETED_UID = "deleted_user"`, FACT, `functions/src/index.ts` lines 2080-2087).

### C10 Minors

- GPS-PRIV-042 (MUST, PROPOSED) CONDITIONAL on the D-17 outcome (section 9). Under the register default (D-17 not decided, or option A or B): a user under 18 or of unknown age has no public sharing: public and unlisted visibility are unavailable and every publish endpoint refuses; under option B friends visibility is refused too. Private recording and local use are allowed. Under D-17 option C (block GPS recording for minors) this requirement is superseded: location recording itself is unavailable below the gate and the matrix C10 row changes accordingly.
- GPS-PRIV-043 (MUST, PROPOSED) The sharing gate uses its own function "known adult", not `ageBandFor`. Reason (FACT): `ageBandFor(null)` returns `AgeBand.adult` for an unknown age (`age_policy.dart` line 27 and 52-57), which is right for training heuristics and wrong for sharing; reusing it would let an unknown-age user publish.
- GPS-PRIV-044 (MUST, PROPOSED) The age used by the gate is server-held. The profile document is client-writable (the profile rule only checks the health block, FACT `firestore.rules` lines 194-211), so a client-asserted birth year cannot be trusted by a publish endpoint. S09 MUST read an age field written only by the server or verified by a server function; how that field is obtained is part of D-17.
- Note (FACT): the age data available today is a birth year, and the app resolves the 17/18 boundary on the cautious side; the privacy text sets a minimum account age of 16 (`public/privacy.html` line 99). Users aged 16 and 17 can therefore hold accounts and are minors for this contract.

## 7. Safeguards

- GPS-PRIV-045 (MUST, PROPOSED) Privacy zones (home, work, user-defined) and default start/end trimming apply to every artefact that leaves the owner-only scope (C3, C4, C6 captions, share images). Zones are enabled by default for EXPLORE and RIDE (roadmap S05 DoD, FACT as plan). Zones are applied when deriving the shared artefact, never by editing C1.
- GPS-PRIV-046 (MUST, PROPOSED) Default trim radius and the zone editor are defined in S04-D/S10-D; the value is not fixed in this contract (UNVERIFIED parameter, to be set from a design decision, not invented here).
- GPS-PRIV-047 (MUST, PROPOSED) Zone definitions are themselves location data: stored with the owner only, included in export, deleted with the account, never logged with coordinates.
- The safeguard set also includes, by reference and without new ids: EXIF stripping (GPS-PRIV-031), the re-identification check (GPS-PRIV-021) and the minors rules (GPS-PRIV-042 to GPS-PRIV-044).

## 8. Logging, export, deletion

### Logging

Existing practice (FACT): server log events carry a stable event name and the uid, with an error string (`functions/src/account_export.ts` lines 391-408 using `EXPORT_ACCOUNT_FAILED`).

- GPS-PRIV-048 (MUST, PROPOSED) Logs, metrics, analytics, crash reports and error strings never contain coordinates, geohashes, route geometry, place names, heart-rate values, or photo contents. Allowed: counts, durations, sample counts, byte sizes, activity or route ids, permission state, error codes.
- GPS-PRIV-049 (MUST, PROPOSED) Error strings forwarded to logs are sanitised: an exception message that interpolates a sample or geometry is mapped to a bare code first (precedent: `accountDeletionRetries` stores only a bare error code, FACT, `scripts/ci/data_lifecycle_policy.json`).
- GPS-PRIV-050 (MUST, PROPOSED) The `debug_sessions` telemetry path (FACT: events are not shape-checked beyond count) MUST NOT receive location or heart-rate values; the debug telemetry redaction in `mobile/lib/core/diagnostics/debug_telemetry.dart` is extended and tested for this before any GPS code ships. Enforcement is two-sided: the client event schema contains no location or heart-rate field types, and the rules side is limited to what Firestore rules can express (list size and the top-level key set; they cannot check each list element). Per-element checks belong to the client schema test or a sanitising callable, see GPS-PRIV-098; a modified client can therefore still place values inside event elements unless the sanitising callable is adopted.

### Export

- GPS-PRIV-051 (MUST, PROPOSED) Every class held on the server or the device is exportable on request: C1 and C8 as GPX/FIT or JSON, C2, C3 metadata, C6 stripped images, zone definitions, consent records.
- GPS-PRIV-052 (MUST, PROPOSED) Streams are not placed inside the `exportAccountData` response, which is bounded to about 8 MiB (FACT, `functions/src/account_export.ts` lines 54-58). The export lists them and delivers them through a separate bounded mechanism (for example short-lived download links to private objects). The exact mechanism is chosen in S02; its links are bounded by GPS-PRIV-094.
- GPS-PRIV-053 (MUST, PROPOSED) An incomplete export says so in the file, as `truncated` and `notes` do today (FACT); device-only data excluded from a server export is named in the notes (precedent: progress photo note, FACT).

### Deletion

- GPS-PRIV-054 (MUST, PROPOSED) Deleting an activity deletes in one operation (amended by GPS-PRIV-093: where a trash window applies, the activity is first forced private and all public artefacts removed, and this operation runs at trash expiry or on a permanent-delete action): C1 object, C2, every derived artefact in the registry (previews, published route, shared photos), local journal and caches on the owner's devices (on next sync), and tombstones any friend-visible reference.
- GPS-PRIV-055 (MUST, PROPOSED) Account deletion extends `sweepAccountData` (FACT: `functions/src/index.ts` line 2372) with Storage object removal for C1, C6, C8 and derived artefacts, in the same change that introduces the Storage path, as the existing source comment requires (FACT, lines 2073-2077). The step is idempotent and covered by the existing reconciler (`accountDeletionRetries`).
- GPS-PRIV-056 (MUST, PROPOSED) Published copies are either deleted or detached (owner reference removed and the route anonymised) per the matrix; the default is delete. Detach is allowed only for a route another user has already built a dependency on and only if no coordinates inside a privacy zone remain. The choice per class is fixed in `DATA_LIFECYCLE_MATRIX.md`.
- GPS-PRIV-057 (MUST, PROPOSED) A deletion SLA for location data is published and monitored (owner S28). The number and the per-store erasure windows are an explicit open decision, see GPS-PRIV-078 and GPS-PRIV-079.

## 9. Open decisions (written as options; no decision is taken)

### D-16 Retention of GPS and heart-rate streams

Roadmap context (FACT, `03_ROADMAP` section 10): "design default two years is open"; default if not decided: "Device-only until decided"; blocks S02.

| Option | What it means | Consequence |
|---|---|---|
| A. Device-only (register default) | Raw samples, derived geometry (C2) and HR stay on the phone. Cloud holds only non-geometric summary fields (totals, duration, type; no track, no bounding box, no start/end) per GPS-PRIV-072. | Lowest privacy risk and no cloud cost; loses streams and tracks on device loss or reinstall; no multi-device history of full tracks; contradicts the S02 plan item "streams as compressed private objects" (S02 would implement a different scope); deletion and export are simpler. Publishing is still possible only through the client-supplied-geometry path with weaker server validation (GPS-PRIV-073); a team may prefer to also disable publishing under A. |
| B. Cloud, fixed 24 months | Streams uploaded as private objects and removed by lifecycle rule 24 months after the activity date. | Matches the "design default two years" note; needs an object lifecycle mechanism and tests; users lose old raw tracks unless exported; a fixed period needs a privacy-text change (today: "no separate retention timer", FACT `public/privacy.html` line 91). |
| C. Cloud, user-controlled | Streams uploaded as private objects; retained until the user deletes them or the account; the user can set an automatic expiry (for example 90 days, 1 year, 2 years, never). | Best fit for portability and multi-device; highest stored volume and exposure if an account is compromised; requires a visible setting and a default that must be chosen; privacy text change needed. |
| D. Split | GPS streams cloud per option B or C; heart-rate streams device-only (or shorter retention) because they are health data. | Lower sensitivity for HR; two policies to explain and test; HR features that need history (trends) are limited. |
| E. Client-side encrypted streams | Streams are encrypted on the device with a user-held key before upload; the server stores ciphertext only. | Server cannot read, derive geometry from, or validate the stream (publishing falls back to client-supplied geometry, GPS-PRIV-073); a lost key means lost data (compare progress photos, FACT `photo_key_store.dart`, device-bound key); export must happen on the device; strongest protection against a server or insider breach. |
| F. Downsample then discard | Raw samples are kept for N days, then reduced to a downsampled track (lower rate, rounded coordinates) and the raw series is deleted. | Smaller exposure window and storage; permanently loses precision for later recalculation and some replay tests; N and the downsampling rule are new parameters; the downsampled track is still location history (same sensitivity as C2). |
| Orthogonal 1: retention clock | The retention period counts from the activity date (fixed expiry, simple) or from the upload date (a late upload of an old activity lives longer). | Activity-date clock matches the privacy statement most simply; upload-date clock is easier to implement but can silently extend retention. |
| Orthogonal 2: C2 derived geometry | C2 follows the stream option, or has its own shorter or longer retention. | If C2 is kept longer than C1 the user's tracks outlive their raw data and the contract's deletion cascade must cover both clocks. |

Recommended default (PROPOSED, not a decision): keep option A as the binding default until the operator answers; when the operator decides, recommended target is option D with GPS as in option C and a default expiry shown to the user. Reason: GPS streams are needed for route reuse and device change, HR is health data that the app already treats as device-only unless consented. If D-16 is never answered, option A applies and S02 scope reduces accordingly.

### D-17 Minors, sharing and public routes

Roadmap context (FACT): default if not decided "Under-18 and unknown age: no public sharing"; blocks the contract, S09 and S10.

| Option | What it means | Consequence |
|---|---|---|
| A. No public sharing for under 18 or unknown age; friends and private allowed for known ages only | Public and unlisted unavailable below the gate; friends visibility allowed for known minors with a mutual-accept edge and for known adults; unknown age is refused for public, unlisted AND friends (private only). | Keeps community features for 16-17 year olds; friends visibility of a minor's location is still a safety exposure and needs mutual-accept and parental-guidance copy. |

Binding default until decided: E1. | E1 is safest and easy to test; it splits friend lists by age and blocks real family use (for example a parent following a teenager). Recommended default (PROPOSED, not a decision): option A with age source D1 and "unknown means blocked", because it equals the register default, needs no new personal data, and still allows private recording and friends-only sharing between mutually accepted users; revisit D2 before public beta (G-C). - GPS-PRIV-058 (MUST, PROPOSED) Every new collection or Storage path holding class C1-C9 data has its own explicit block in `firestore.rules` or `storage.rules`. ## 12. Requirements appended after security review (GPS-PRIV-071 to 098)

Numbering of 001-070 is unchanged. Each requirement is MUST and PROPOSED unless marked.

### Rules and storage shape

- GPS-PRIV-071 Shielding from the owner wildcard. The wildcard `users/{uid}/{coll}/{document=**}` grants the owner read and write on any subcollection not excluded, and it lists exclusions separately in its `allow read` and `allow write` clauses (FACT, `firestore.rules` lines 61-82; pattern `recognised_models`, lines 68, 79). Every new subcollection under `users/{uid}` that holds server-authored location data (visibility state, registry, moderation state, derived-artefact records) MUST be added to the exclusion list in BOTH clauses, or the data MUST live outside `users/{uid}` (a top-level collection with an explicit block). The same exclusion in BOTH clauses, plus an explicit block with a key allowlist, type and size checks, is required for every CLIENT-writable location-related subcollection that needs a shape check: the activity summary (`users/{uid}/activities`), privacy zones (GPS-PRIV-095) and consent records. The wildcard cannot enforce shape (any matching rule permits), so a subcollection under it has no allowlist at all. Only a subcollection with no shape requirement may rely on the wildcard, and it is listed as such in the matrix (none is currently proposed). Shielding applies to whole subcollections, not to fields inside one; a field that must be server-only (visibility, moderation state, owner, source id) therefore lives in a server-only subcollection or top-level collection, never as a protected field inside a client-writable document. AC: for each server-authored path, an emulator test performs an owner write, update and delete and expects denial while the wildcard exists; a second test removes the exclusion in a copy of the rules (or a rules-text lint) and shows the first test would fail. For each client-writable shape-checked subcollection a second test sends a forbidden key and expects denial; in particular a write of a geometry key (for example `polyline`, `points`, `bbox`, `startLat`) to `users/{uid}/activities/{id}` while the D-16 flag is OFF is denied, and a write with only allowlisted summary keys succeeds.

### C2 gating

- GPS-PRIV-072 Derived geometry is location history and follows the C1 gate. While D-16 is not decided (or option A is chosen), no private C2 geometry of the owner's track (polyline, points, bounding box, start/end coordinates) is written to the activity summary in Firestore or to Storage, and no C1 is written. This does not restrict published C3 routes, whose trimmed polylines are governed by GPS-PRIV-073 to 075, nor privacy zones, governed by GPS-PRIV-095. Only non-geometric summary fields (distance, duration, elevation totals, activity type, source id) may be in the cloud activity summary. When D-16 enables cloud streams, C2 uploads under the same flag and consent and has its own retention value (matrix C2). AC: with the flag OFF, a saved activity writes a document that contains none of the geometry keys (a unit test on the serializer) and the rules block of `users/{uid}/activities` rejects any key outside the summary allowlist (the test of GPS-PRIV-071).

### Publish validation and re-identification

- GPS-PRIV-073 Origin and validation of published geometry. When cloud streams exist (D-16 B, C, D) the server derives the published geometry from the stored C1/C2 itself; the client sends only the activity id, the visibility and the requested trim. When streams are device-only or client-encrypted (D-16 A, E) the client supplies a candidate geometry; the server then treats it as untrusted, applies the checks below to it and records it as `clientSupplied`. In both cases validation MUST NOT depend on raw samples. Inputs the server holds for that purpose: (a) the owner's privacy-zone list (zone centres and radii, owner-only, stored server-side because the check needs it; this is location data and is governed by GPS-PRIV-095 and matrix class C11, with GPS-PRIV-047); (b) a record of the owner's previous published start and end cells (coarse cells, not coordinates, taken from already-trimmed published geometry only, stored as a field of the owner's rows in the private server-only registry of GPS-PRIV-075 and deleted with them). The zone list is governed by GPS-PRIV-095, including its gating. Required checks: published start and end lie outside every zone by at least the trim distance; the polyline contains no vertex inside a zone; point count, length and speed are plausible; total published length matches the claimed distance within tolerance.
- GPS-PRIV-074 Re-identification check, testable. Parameters are named configuration values with these proposed starting values (PROPOSED, to be set in S09): `zoneMinTrimMeters` (at least the zone radius, default 200), `repeatEndRadiusMeters` (200), `repeatEndCount` (2), `uniqueShapeMinOverlapPercent` (not set here, S09 chooses with a measured corpus). The server refuses publication (or returns the minimal extra trim that passes) when the start or end cell is within `repeatEndRadiusMeters` of at least `repeatEndCount` earlier published starts or ends of the same owner, or when the first or last vertex lies inside a zone. AC: fixtures cover (1) route starting inside a zone, refused or trimmed; (2) third publication from the same doorstep, refused; (3) route starting just outside the zone, accepted; (4) client-supplied geometry whose first vertex is inside a zone, refused; each fixture runs for server-derived and client-supplied paths.

### Public versus private records

- GPS-PRIV-075 Public document and private registry are separate. A public route is a document under its own random public id (not derived from, and not stored next to, the activity id). Its fields are an allowlist: public id, simplified trimmed polyline, distance, elevation gain, surface and activity-type tags, region cell no finer than needed for discovery, creation date rounded to the month, optional display name only if the owner opted in, and the server-set `publiclyReadable` flag. It MUST NOT contain owner uid, source activity id, device id, real timestamps, heart rate, cadence or power, raw sample counts, photo ids of unpublished photos, or any field not on the allowlist. The mapping publicId to owner, source activity and derived artefacts lives in a private server-only registry (GPS-PRIV-071 shielding, client read and write denied). The discovery index is built only from the public document's trimmed geometry. AC: an unauthenticated read of a public route returns exactly the allowlisted keys (test asserts the key set and asserts absence of `ownerUid`, `sourceActivityId` and any timestamp finer than a month); a registry read by any client, including the owner, is denied. This amends the back-reference of GPS-PRIV-023: the back-reference lives in the private registry only.

### Deletion cascade

- GPS-PRIV-076 Sweep map. Account and activity deletion are defined against a written sweep map in `DATA_LIFECYCLE_MATRIX.md` section 3, listing every top-level collection and Storage prefix that holds location data with its sweep step. Existing `sweepAccountData` hardcodes `users/{uid}`, `donor_wall/{uid}`, `coach_listings/{uid}` and three owner-field sweeps (FACT, `functions/src/index.ts` lines 2265-2289, 2372-2379), so top-level location collections (public routes, registry, previews, reports, social edges) are NOT covered until added. The new sweep is driven by the private registry and by owner-id queries (not by a hardcoded id list), is idempotent, paged like `sweepInPages` (FACT, line 2299) and runs under the existing durable retry record. AC: one emulator test per top-level collection and Storage prefix seeds the owner's data plus another user's data and asserts the owner's is gone, the other's remains, and a second run is a no-op.
- GPS-PRIV-077 Non-happy path. The registry entry (intent) for a derived artefact is written BEFORE the artefact is created (public route, preview, photo copy), with state `pending`, so a crash between steps leaves a record that points at the orphan. A scheduled orphan reconciler finds registry entries without artefacts, artefacts without registry entries, and artefacts whose source is gone, and deletes or repairs them (precedent: `reconcileAccountDeletions`, FACT). AC: failure-injection tests kill the process after the registry write and before the artefact write, after the artefact and before registry finalisation, and in the middle of an activity-delete cascade; after the reconciler runs no artefact is readable that the owner has deleted.
- GPS-PRIV-078 Secondary stores and erasure windows. The contract states, per store, whether deleted data lingers and for how long; the number is filled by decision GPS-PRIV-079. Stores to cover: preview and photo delivery (cache headers `Cache-Control` short or `no-store` for private and unlisted paths; CDN or Hosting purge on delete); Cloud Storage soft-delete and object versioning (disabled for location buckets or the window stated); Firestore point-in-time recovery and managed backups (window stated; restore procedure re-applies deletions or restores only into isolation); Cloud Logging retention (bounded, and no location in logs anyway, GPS-PRIV-048); search or discovery indexes. Existing evidence: the privacy text claims "no archive copy kept afterwards" (FACT, `public/privacy.html` line 91); if backups or soft-delete exist for location buckets the text must change. AC: a checklist test in S25 reads the bucket and project settings and fails if soft-delete or versioning is enabled on a location prefix without a documented window.
- GPS-PRIV-079 Deletion SLA, open decision (not decided here). Options: (1) primary stores erased within 30 days of the request, backups and logs within their stated windows (aligned with the existing 30-day TTL of `accountDeletionRetries`, FACT, `scripts/ci/data_lifecycle_policy.json`); (2) primary stores within 72 hours, remainder as stated; (3) immediate for primary stores where technically possible. Recommended default (PROPOSED): option 1, because it matches the existing retry mechanism, with the window per store published. Consequence: a shorter number needs the reconciler and monitoring to meet it and raises on-call load; a longer one weakens the "erased" promise. This is an operator decision (owner S28 monitors it) and has no id in the roadmap register; it is proposed to be recorded as a new register entry.

### Photos

- GPS-PRIV-080 EXIF quarantine and full re-encode. Uploads land first in a quarantine Storage prefix that no client can read or list (rules: create only, no read, no list). A function validates the file and writes a NEW file by decoding and re-encoding the pixels, which drops all metadata, not only the GPS tags: EXIF including embedded thumbnail, XMP, IPTC, MakerNotes, device serial and model, timestamps, orientation-derived or ICC-embedded extras. Only the re-encoded file is promoted to the delivery prefix; the quarantine copy is deleted after promotion or after a short TTL. A file that cannot be decoded is rejected and deleted. AC: fixtures with GPS EXIF, thumbnail with its own GPS, XMP location, MakerNotes and a device serial yield a promoted file that contains none of them (checked by re-reading all metadata blocks); a client read or list of quarantine is denied; a non-image or oversize file is rejected.
- GPS-PRIV-081 Photos taken inside a privacy zone. When the capture position (read from EXIF on the device before stripping, never uploaded) or the photo's timestamp falls inside a privacy zone, the app warns before attaching and excludes the photo from any non-private visibility by default; the owner may still keep it private. AC: widget test with a fake zone and a fixture photo inside it shows the warning and defaults to excluded; the upload payload for a public route contains no excluded photo.

### Third-party egress

- GPS-PRIV-082 Egress of coordinates. Coordinates leave the app only to a provider on an allowlist recorded in the repository (map tile provider per D-6, geocoding provider if any), each with its terms checked in S01 part b. No reverse geocoding of raw sample points; at most coarse labels for published start and end cells computed server-side. Tile requests use tile indices, never the user's coordinates in clear form beyond what the tile index implies, and are not issued for areas inside the user's privacy zone at street zoom when the zone is private. The privacy text discloses each provider and what it receives. The client never logs full request URLs (they contain coordinates or tile paths) and error handling strips query strings and path segments before logging. AC: a test with a fake HTTP client asserts the request destinations are on the allowlist, that no request carries a raw sample coordinate pair outside the tile index, and that captured logs contain none of the URL's path or query parts.

### Device exposure

- GPS-PRIV-083 Backup exclusion. The GPS journal, route and preview caches, tile cache and zone definitions are excluded from Android Auto Backup and device transfer in BOTH `mobile/android/app/src/main/res/xml/backup_rules.xml` (Android 11 and below) and `data_extraction_rules.xml` (Android 12+), referenced from the manifest (FACT, `AndroidManifest.xml` lines 41-42). Today only progress photos and three preference files are excluded and "everything else stays backed up" (FACT, `backup_rules.xml` lines 35-43), so a GPS journal in the app documents directory would be uploaded to the user's cloud backup unless excluded. AC: a check parses both XML files and fails if the directories and file names declared for location storage are not excluded in both; the storage paths are defined as constants used by both the code and the check.
- GPS-PRIV-084 At-rest protection. The local GPS journal and caches are either encrypted at rest with a key held in the platform keystore (pattern: `flutter_secure_storage`, already used, FACT in `backup_rules.xml`), or the operator accepts in writing that they rely on OS app sandbox only, recording the residual risk (a rooted or unlocked device, a debug backup). Recommended default (PROPOSED): encrypt the journal and keep caches unencrypted but excluded from backup. AC: a test opens the journal file bytes and finds no plaintext coordinates when encryption is chosen; the decision is recorded in `core/DECISION_LOG.md` otherwise.
- GPS-PRIV-085 Wipe after account deletion. Because "evicted on next sync" cannot run once the account is gone, the client wipes the GPS journal, caches, zones and consent state when (a) the deletion callable returns success, and (b) on the next launch if the app starts with no valid auth session for the stored uid (deletion completed on another device, token revoked) or the auth check returns user-not-found. An unsynced journal in that state is offered export first only if the user is still signed in; otherwise it is deleted. AC: widget/integration test deletes the account on a fake backend, kills the app before the wipe, relaunches with an auth failure, and asserts the journal directory and caches are empty.

### Unlisted links

- GPS-PRIV-086 Unlisted access model. Unlisted routes are served by get-by-id only; list and query on the route collection are denied to everyone (public documents carry no owner field and the owner has no registry read, so the owner's own list comes from the callable of GPS-PRIV-097); the token is at least 128 bits from a cryptographically secure random generator; the same token gates every preview and photo path of that route (no separate guessable paths); responses carry `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`, and pages carry a noindex meta; links never appear in sitemaps or logs. AC: an unauthenticated list query on the collection is denied; get with a wrong token is denied; a preview or photo URL without the route token is denied; response headers are asserted on the delivery endpoint; a revoked token is denied on route, preview and photo paths. The owner's list of active unlisted links is served by a callable (GPS-PRIV-097), not by a client read of the registry.
- GPS-PRIV-087 Revocation and expiry. Revocation takes effect for new requests within a stated latency (proposed: 60 seconds, bounded by cache TTL, which therefore must not exceed it for unlisted paths). Whether unlisted links expire by default is an open sub-decision (options: never; 90 days renewable; 1 year). Recommended default (PROPOSED): never expire by default, with a visible list of active links and one-tap revoke, because silent expiry breaks shared links unexpectedly. AC: after revoke, route, previews and photos return denied within the stated latency in an end-to-end test with the cache layer present.

### Minors gate details

- GPS-PRIV-088 Definition of "known adult". With only a birth year (FACT: `age_policy.dart` documents that the questionnaire stores a year, never a month), a user is a known adult iff a server-held birth year exists and `birthYear <= currentYear - 19` (a person born in year Y is at least 18 in year T only when T - Y - 1 >= 18). Every other state (no year, year in the future, year more recent than that, a conflicting value) is "not known adult". The rule is evaluated at read time with the server clock, so a user only becomes known adult as time passes. "Known minor" is a server-held birth year that is not known adult and not in the future; "unknown age" is everything else. This function is separate from `ageBandFor` (GPS-PRIV-043). AC: table test over year boundaries, including `currentYear - 19`, `currentYear - 18`, null, future and the December-born case.
- GPS-PRIV-089 Mutability of the server age field. The server-held age field is written only by a server function (never by a profile write). It lives in a server-only path outside the client-writable profile document, for example a top-level `userAge/{uid}` collection or a server-only subcollection excluded from both wildcard clauses (placeholder name, GPS-PRIV-071; the profile document is client-writable, so a protected field inside it is not possible). It is set once; after that it can change only toward the more restrictive reading (a later birth year), never toward a more permissive one. A correction toward permissive requires an operator-run support procedure that is logged (no self-service). AC: the callable called twice with a more permissive year leaves the stored value unchanged and returns the stored value; a more restrictive value is accepted; a client attempt to write the field directly is denied.

Users who completed onboarding before this contract have no server age field and are "not known adult" (blocked from public and unlisted sharing) until they set it through the callable. ### Retention of supporting records

- GPS-PRIV-091 Report and takedown evidence. A report record holds route public id, reporter id (or anonymous flag), reason code, moderator action and timestamps; it holds no owner uid and no coordinates, so owner-side cleanup finds reports through the private registry's list of the owner's public ids, and reporter-side cleanup finds them by the reporter field. It holds no coordinates beyond what the public route already shows. It is retained for a stated period after resolution (proposed: 12 months, PROPOSED parameter), and reports about a deleted account's routes are kept only in that reduced form. The reporter's identity is removed on the reporter's account deletion (tombstone, GPS-PRIV-041 pattern). AC: after deleting the route owner's account, the report row contains no owner uid and no geometry; after deleting the reporter's account, the reporter field is the tombstone.
- GPS-PRIV-092 Consent records after deletion. - GPS-PRIV-094 Export links. Any download link for streams or photos in an export is authenticated (the requester's session) or a signed URL with a short life (proposed: 15 minutes, PROPOSED), single purpose, and is not written to logs (the link and its query string are redacted in server and client logs). ### Added in review round 2

- GPS-PRIV-095 Privacy zones are location data and are stored under rules. A zone (centre, radius, no free-text label) is location data about the owner's home or work and is class C11 in the matrix. Locally it is stored with the C1 protections (GPS-PRIV-083, 084). Upload gating: zones are NOT gated by D-16 stream retention, because the safeguard itself needs them server-side (GPS-PRIV-073); this is an explicit, reasoned exemption, subject to a separate consent row "sync privacy zones", OFF by default and required before the first publish. In the cloud, zones live in the client-writable subcollection `users/{uid}/privacy_zones` (placeholder name), excluded from both wildcard clauses with its own block: owner read and write, key allowlist (`id`, `centerLat`, `centerLon`, `radiusMeters`, `updatedAt`), numeric range and count bounds (proposed maximum 20 zones). Zones are exported, deleted with the account, deleted on consent withdrawal, and never logged with values. AC: rules test that a zone write with an extra key, a label, a radius out of bounds or more than the maximum count is denied; owner read and write succeed; another user is denied; with the consent OFF the publish callable refuses; account deletion removes the subcollection (sweep map row) and consent withdrawal empties it.
- GPS-PRIV-096 Viewer position is not retained. The position a viewer supplies for "Find nearby" or any discovery query is used for that request only: it is sent as a coarse cell no finer than needed for the search radius (value set in S08), is not written to any document, index, analytics event or log, and no per-user query history is kept server-side. AC: a test runs a nearby query with a sentinel position and asserts that no Firestore write, log line or telemetry event produced by the request contains it or any finer cell than the allowed one.
- GPS-PRIV-097 Owner link list by callable. Because the private registry is denied to every client including the owner (GPS-PRIV-075), the owner's list of active unlisted links, published routes and their visibility is served by an authenticated callable that reads only `request.auth.uid`'s registry rows and returns the allowlisted public fields plus link state, never other users' rows and never source activity ids beyond the owner's own. Revoke and unpublish are callables too. AC: the callable returns exactly the caller's links; a call as another user returns none of them; a direct client read of the registry stays denied.
- GPS-PRIV-098 Debug event rules-side shape (acceptance criterion for the rules-side part of GPS-PRIV-050). Firestore rules cannot iterate the elements of a list, so the rules side is limited to what they can express: the `events` list size bound (already 500, FACT) and the top-level key set (already allowlisted, FACT, `firestore.rules` lines 299-304). Per-element checking is done elsewhere: in the client event schema (unit test asserting it contains no location or heart-rate types and that the sanitiser drops unknown keys) and, if the operator wants a server guarantee, in a sanitising callable that writes `debug_sessions` instead of the client. AC (rules): a create with `events` longer than 500, or with a top-level key outside the allowlist, is denied; a create within both bounds succeeds. AC (client): the schema test above fails if a location or heart-rate event type is added. This is a bound on shape, not on content; the rules cannot reject a location value inside an element.
