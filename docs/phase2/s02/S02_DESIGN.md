## 3. Data model

### 3.1 Split of `ActivitySession`

PROPOSED: `ActivitySession` stays in `mobile/lib/features/activity/data` (pure, no I/O). Two new pure projections are added there; they only build maps and bytes-free structures:

| Projection | Content | Lives |
|---|---|---|
| `ActivityCloudSummary.fromSession(s)` -> `Map<String, Object>` | Scalars only (table 3.2). No lists, no maps, no geometry, no HR, no friend data | Firestore `users/{uid}/activities/{id}` |
| `ActivityStreamPayload.fromSession(s, allowedKinds)` -> structured payload | Streams of allowed kinds, plus a `meta` section (laps without HR, provenance list, mergeNotes, userEdits) | Private object (section 5); encoding to gzip bytes happens OUTSIDE `activity/data` because `dart:io` is forbidden there (FACT guard) |

PROPOSED (DQ-1, DQ-2): `ActivityStreamPayload.fromSession` HARD-DENIES `heartRate` regardless of `allowedKinds` (a caller passing `heartRate` in `allowedKinds` still gets no HR; unit test), and the server validator rejects it too (defence in depth, 5.1a). By default `allowedKinds` is only `gps`, `altitude`, `speed` (plus time offsets); `cadence`, `power`, `strokeRate` and `temperature` stay device-only until the operator answers the open question in 12.3.

The existing full `toJson` stays as the local journal record format (section 3.4). A unit test asserts that `ActivityCloudSummary` output keys are a subset of the rules allowlist (single constant list shared by a test that parses `firestore.rules`; PROPOSED).

Ordering (PROPOSED, DQ-5, resolved): the summary is ordered by the client-incremented integer `rev` (row above) that rules require to strictly increase on every update, so ordering needs no server stamp on the summary. Stream index rows and settings are ordered by the server `receivedAt` (set by the commit callable and by `setActivityCloudSettings`); the local journal is ordered by the monotonic counter of section 10. Rules do NOT force `updatedAt == request.time`, because queued offline writes would then fail on replay (the Body Scan consent pattern, FACT lines 570-582, is not copied here).

Rev conflict handling (PROPOSED, closing check, revised after GPT-PM round 1 MAJOR-01): a `rev` rejection is routine, not an error state. Two devices editing at rev N both produce N+1; a lost acknowledgement resends the same rev; a fresh device creating a deterministic id that already exists on the server sends an update that rules see as `rev` 1. Premise: the cloud summary is DERIVED from the local record (distance, duration, counts, versions); it is not user-edited, and user edits live in the device-only `userEdits`. The journal entry therefore keeps `baseRev` (the server rev this device last synced) and a `baseSummary` snapshot (the summary map last stored or read from the server). On a rev conflict the client reads the server summary and does a THREE-WAY MERGE per field (base = `baseSummary`, local = the summary now derived from the local record, server = the document just read): only local changed -> local value; only server changed -> server value; both unchanged or both changed to the same value -> that value; the SAME field changed to DIFFERENT values -> NOT synced: the entry stays `sync_conflict`, local data is kept, and the user sees a choice "keep this device / keep cloud" (UI story S02-12, section 11). Nothing is marked `synced` until the merged summary is stored or the user resolved the conflict. Only after a merge (or a user choice) the client writes `rev = max(local, server) + 1`, `baseRev` and `baseSummary` are then replaced by the stored values. Keep-cloud replaces the local derived fields with the server values (local streams, laps, provenance and `userEdits` are never touched); keep-device writes the local values with the next rev. A create for an id that already exists on the server is sent as a read-then-merge-then-update, and a fresh-device sync reads before writing. A second rev conflict during the same retry leaves the entry in `sync_conflict` (retried at the next start, never hot-looped; section 6.2). The required keys in rules are `schema`, `sport`, `startUtc`, `endUtc` and `rev` (the test for required keys, R12, must list `rev`).

Summary overrides and convergence (PROPOSED, GPT-PM round 2 MAJOR-01A): the merge above is correct once, but the summary is re-derived from the local record, so a device that adopted a server-only change would recompute its OLD value from its unchanged record on the next write and re-conflict or overwrite the other device (example: device A changes `distanceM` to 5000; device B holds a stale record that computes 4800, merges correctly to 5000, then recomputes 4800 again). The rule that closes this:

1. `record.json` carries a per-field map `summaryOverrides` of the form `{field: {value, atComputed, atVersions, atRev}}`. An entry is created when a merge adopts a SERVER-only change to a derived field, or when the user chooses "keep cloud" for a field. `value` is the adopted server value, `atComputed` is the value that `recompute(record)` produced for that field AT THAT MOMENT (the stale local value the override masks), `atVersions` is the triple of calculation versions (`formulaVersion`, `metricDefinitionVersion`, `thresholdPolicyVersion`) in force at that moment, `atRev` is the stored rev. The merge itself creates an override ONLY when this device can recompute the field (lead decision on plan question DQ-29); a server-only change to a field this device cannot recompute stays a resolvable `sync_conflict` until the user chooses "keep cloud", which then creates the override with `atComputed` = the value the device holds.
2. The summary a device writes is ALWAYS `effective(record)` = `derive(record)` overlaid first with the latest explicit user-edit value per field from `record.userEdits`, then with the remaining `summaryOverrides` (GPT-PM round 7 MAJOR-01H: an explicit edit is stored in `record.json` in two separate structures (GPT-PM round 8 MAJOR-01K): the canonical `explicitValues` map `{field: {value, atDerived, seq}}` with at most one entry per summary field, which is the ONLY input of the projection, and a separately bounded local history ring `userEdits` (newest 64 entries, oldest dropped, device-only, informational, never read by the projection), so history growth cannot change the effective summary; the projection applies the `explicitValues` entry per field, so the user's chosen value is reproduced after restart without any cloud override; `derive(record)` alone is the RAW recomputation and tests assert both). Everywhere below `recompute(record)[field]` means the value of `effective(record)` before the overrides are applied, i.e. including explicit user edits. The `userEdits` ring stays device-only; only the effect of `explicitValues` on the summary fields is uploaded. The cloud field `userEditCount` is a SATURATING counter stored in the record (number of explicit edit operations since creation, capped at 64; at the cap it stops growing), not the length of any list, so every emitted summary satisfies the rules range 0..64 however many edits occur and synchronisation never becomes impossible; `rev` still advances whenever any summary value changes. Lifetime of an explicit value against newer passive source data (GPT-PM round 8 MAJOR-01J): `atDerived` is the raw `derive(record)[field]` at edit time. The explicit value stays authoritative (a deliberate rule: the user's correction wins until the user reconsiders it). When the raw derivation of that field later differs from `atDerived` (new GPS samples, a corrected import, a calculation upgrade), the explicit value is KEPT, `atDerived` moves to the new raw value, and the new raw value is recorded as a `sourceCandidate` {field, value} shown in the sync-conflict UI as a resolvable entry ("keep my value / use the new computed value"); nothing is written or discarded silently. "Use the new computed value" removes the `explicitValues` entry and the new value is a local change merged three-way against `baseSummary`; "keep my value" clears the candidate. A concurrent cloud change of the same field is adopted through an override above the explicit value as in rule 1 and does not clear the candidate. RESOLUTION IS ONE ATOMIC OPERATION (GPT-PM round 9 MAJOR-01L): resolving a candidate commits, in ONE journal generation, the change of `explicitValues`, `summaryOverrides` and the candidate together, and the chosen value is then compared against the CURRENT last-synced `baseSummary` and the current server revision, never against an older baseline. When an override exists on the field the conflict entry offers three choices, each with this effect: (1) "use the new computed value": remove the `explicitValues` entry, REMOVE the override, clear the candidate; the candidate value is the local value; (2) "keep my value": keep the `explicitValues` entry, REMOVE the override, clear the candidate; the explicit value is the local value (an explicit choice supersedes an adopted cloud value exactly as in kind (ii)); (3) "use the cloud value": remove the `explicitValues` entry, KEEP the override with `atComputed` moved to the current raw value (otherwise the value rule would drop the cloud value at the next load), clear the candidate. When no override exists only choices (1) and (2) are offered. For (1) and (2) the three-way merge then runs: base = current `baseSummary` (after an adoption it already holds the adopted cloud value), server = current server summary; if the server value still equals the base the local value is written; if the server changed again since the base the chosen local value is preserved in `sync_conflict`, an old override is never restored silently and nothing is marked synced. The generation is idempotent: after a restart or a replay of a lost acknowledgement the chosen value is still durable and no removed override reappears. The result is the same whichever happened first, the cloud change or the resolution: resolution first leaves no override and the later cloud change goes through the ordinary three-way merge. `sourceCandidate` and `recalcCandidate` are the same record kind with a reason (`source` or `recalculation`); a calculation upgrade that changes the raw derivation under an explicit value uses reason `source` (the explicit-value path), reason `recalculation` stays for the override path; when the raw derivation later returns to the value `atDerived` had before, the candidate is cleared. The lifecycle is VALUE-BASED (GPT-PM round 5 MAJOR-01D and MAJOR-01E; it replaces the input-revision and dependency-matrix design of revisions 6 and 7, which needed an exhaustive field-to-input classification): an override is dropped when (a) the recomputed value equals the override `value` (converged), or (b) the recomputed value differs from `atComputed`, meaning the local derivation really changed after the merge. While the recomputed value still equals `atComputed` the override stays, however many journal generations were written and whatever else changed, including metadata-only mutations (`synced`, tombstone, `baseRev`, `baseSummary`, queue state, replay of a lost acknowledgement, any new `COMMIT` generation) and changes of inputs that do not alter the field's value (for example a merge note). In case (b) the new recomputed value is a genuine local change and takes part in the next three-way merge, with base = the last synced `baseSummary`: if the server still holds the base value the local value wins, if the other device changed the same field meanwhile it stays a resolvable `sync_conflict`. Three kinds of change are kept apart (GPT-PM round 6 MAJOR-01F and MAJOR-01G). (i) PASSIVE change: any mutation that is not an explicit edit of that field and leaves the version triple equal to `atVersions` is judged only by the value rule above. (ii) EXPLICIT user edit: the edit mutation names its target fields (it cannot be submitted without them), and applying it to a field that has an override drops that override in the same generation, even when the edited value equals `atComputed` or the override `value`; the chosen value is then a local change against `baseSummary` (equal to the override value it converges, otherwise the normal three-way merge applies), it is durable across restart and lost-acknowledgement replay, and an edit followed by a revert before any synchronisation is evaluated as two explicit edits in order, never as "no change". (iii) AUTOMATIC recalculation: when the version triple in force differs from `atVersions` and the recomputed value differs from `atComputed`, the override is KEPT (the adopted cloud value stays authoritative and nothing is written), `atComputed` and `atVersions` are moved to the new values, and the new recomputed value is recorded as a `recalcCandidate` shown in the sync-conflict UI as a resolvable entry ("use recalculated value / keep cloud value"); a second upgrade or a downgrade only refreshes the candidate. A calculation-version change on its own therefore never replaces an adopted value; a version change and an input change inside the same mutation are treated as (iii), the conservative reading. Lead clarifications of the plan's open points: when the version triple changed but the recomputed value equals `atComputed`, the override is kept, `atVersions` moves to the new triple and no candidate is recorded; if the server value of the field also changed in the same sync (another device), that server change is adopted through a new override as in rule 1 and any candidate is recomputed against it, with no `sync_conflict` unless the field cannot be recomputed here; an explicit user edit of a field that carries a `recalcCandidate` drops the override AND clears the candidate (the user's explicit choice supersedes it). VERSION ADVANCEMENT IS MANDATORY AND ATOMIC (GPT-PM round 7 MAJOR-01I): whenever a record is loaded or written under a version triple different from an override's `atVersions`, the version reconciliation step runs BEFORE any other classification and, in the same generation, moves `atVersions` to the triple in force (and, when the value moved, also records the candidate as in (iii)); this happens even when the recomputed value equals `atComputed` and nothing else is written, and it survives restart and lost-acknowledgement replay. Consequently a later passive input change under the new triple (for example a new GPS stream producing 5100 after a V1 to V2 upgrade that left 4800 unchanged) is classified as case (i) and applied through the normal drop-and-merge path, never as a recalculation.
3. A field that cannot be reproduced without recomputing a stream the device does not have (for example a distance derived from a GPS stream held only by the other device) is never declared synced by guessing: it stays a resolvable `sync_conflict` (choice "keep this device / keep cloud").
4. Overrides survive restart: they live in `record.json` inside the committed generation (section 10), not in memory.

Convergence argument: after a merge the written summary equals the server summary field by field (adopted fields come from the override, all others agree or were merged), and `baseSummary` is replaced by it. Restarting and recomputing from the unchanged record yields the same summary because the override is re-applied, so no change is detected and no write or conflict follows. A later edit on either device differs from `baseSummary` only in the fields that device really changed, so the next three-way merge keeps both edits and does not roll either back. Acceptance: after a successful merge, restart, recompute from the stored record, then a new edit on both devices, both earlier edits survive, no repeated conflict occurs and no field is rolled back to an older value. Because the override depends only on observable values, no knowledge of which inputs feed which field is needed and none can be forgotten.

Immutability (PROPOSED, DQ-15): `startUtc` and `sport` are immutable after creation because they feed the deterministic id (`sourceId|start:<epoch ms>`); a user correction goes into `userEdits` (device-only), never into these two fields. Rules enforce that an update leaves `startUtc` and `sport` unchanged (section 4).

Deliberately NOT in the summary (PROPOSED, decision for the operator in 12.3): `avgHrBpm`, `maxHrBpm` (heart-rate derived health data; contract GPS-PRIV-036 allows "at most non-sensitive summary fields chosen in the S02 design"), laps (list, carry HR), provenance list, `userEdits` map, `mergeNotes` list, `extras`, any start/end coordinate, bounding box, place name, friend or visibility field. A forward-compatible reader keeps unknown local keys in `extras` locally; the cloud summary drops them (extras are not uploaded because rules cannot judge them).

PROPOSED (round 1): the summary is owner-only and, in S02, is never exposed to friend or public paths. Exact `startUtc`, `utcOffsetMinutes`, `distanceM` and `sport` together can form a routine or region fingerprint; this is acceptable for owner-only data, and S09 MUST NOT derive any public or friend-visible artefact from summary fields (only from its own privacy-zone pipeline). `startUtc` is additionally range-clamped in rules (section 4) so a forged far-future or far-past date cannot stretch or collapse stream retention.

### 3.2a Why overrides need no field dependency matrix (PROPOSED, GPT-PM round 5)

Revisions 6 and 7 decided override invalidation by per-field input revisions driven by a field-to-input-class matrix. GPT-PM round 5 showed two flaws that no matrix can fix: over-listing a dependency makes a harmless input change drop the override and silently roll back an adopted server value (MAJOR-01D), and a top-level key classification cannot describe containers that mix several input kinds (MAJOR-01E). The value-based rule of 3.2 removes the cause: the override is compared with what the device actually derives. Removed with the matrix: the ten input classes, the digest comparison, the golden dependency fixture and its completeness rules.

Properties pinned by tests (the oracle is a literal fixture in the test plan, independent of production code; GPT-PM round 6 adds explicit-edit and recalculation cases, 3.2 rule 2): a changed input that leaves the recomputed value unchanged keeps the override; a changed input that changes the recomputed value drops it and the new value is merged three-way against `baseSummary`; metadata-only mutations never drop it; an override equal to the recomputed value is dropped; every override survives restart inside the committed `record.json`.

### 3.3 Provenance and schema versioning

- A-5 fields (`formulaVersion`, `metricDefinitionVersion`, `thresholdPolicyVersion`, `sourceTermsSnapshot`) are added to `ActivitySession` as optional strings, written to the journal and summary. Values come from constants in the data layer; where the sprint models carry a model id/version the same string is reused (reconciliation line 160 says they already do; not re-verified, OPEN).
- `schema` today is only a per-document int, loosely checked in rules (FACT `schemaOk`, lines 535-537). PROPOSED: S02 sets `schema = 2` for the persisted form (adds A-5 fields); `schema = 1` records from tests are read as is.
- Tolerant migration (PROPOSED): a `migrate(Map raw) -> Map` chain in the data layer, one step per version, each pure and total; a step never throws, unknown keys are kept in `extras`, a record newer than the app's max schema is read-only with unknown keys preserved and is never rewritten by an older client (no downgrade write). The existing `tryFromJson` is the final stage. Migration is applied on read from the journal and on read from the cloud summary.

Options: (a) add a database package (sqflite/drift): new dependency, native build and review cost, not present today (FACT grep); (b) `shared_preferences`: wrong for hundreds of KB sessions with 100k-point streams; (c) file-based journal in an app-private directory: uses `path_provider` and `dart:io` (both already allowed outside the data layer), follows the existing file-store patterns `photo_store.dart` (AES-GCM) and `offline_video_cache.dart` (S02_CODE_MAP.md). ### 3.5 Authority, sign-out and key loss (PROPOSED, round 1)

- Authority: with `ACTIVITY_CLOUD_STREAMS` off (the default) the DEVICE is the only authority for streams, laps, provenance, edits and heart rate. - Sign-out: laps and provenance never upload and heart rate never uploads, so any non-empty journal holds data that exists only on the device. The rule is therefore simple: sign-out WARNS whenever the journal is non-empty and offers local export (GPX/FIT/JSON, section 7) first; the journal is wiped (GPS-PRIV-085) only after explicit confirmation. An empty journal signs out without a prompt. Account deletion wipes without that prompt (deletion intent is explicit).
- Key loss: if the `flutter_secure_storage` key is missing or decryption of `streams.bin` fails, the repository does NOT crash and does NOT wipe. It marks the record `streamLost = true` in a NEW generation's `record.json` (a tombstone-style state: summary, laps and provenance stay readable, stream unavailable), increments a local counter and surfaces "stream unavailable on this device". There is NO client re-download and no hydrate in S02: a lost key means a lost local stream, even if a cloud copy exists (a restore story is a later sprint, OPEN).
- Tests: sign-out with a non-empty journal requires confirmation and offers export, sign-out with an empty journal does not prompt; simulated key loss yields `streamLost`, no exception, no deletion of other records, no download attempt.

### 5.1a Server validation is a closed schema (PROPOSED, round 1)

"Heart rate never reaches the cloud" is enforced by a server-side closed schema, not by a client strip or a kind-name check alone:

- The commit callable parses the decompressed JSON into typed structures and REJECTS (does not strip) any unknown key at any depth. Closed key sets: top level (`schema`, `kinds`, `meta`), one key set per allowed stream kind (the exact names come from `SampleStream.toJson`; a test pins them), a closed lap schema, a closed provenance-record schema. Numbers must be finite; every string field of the closed lap and provenance schemas (for example `externalId`, `appPackage`, source ids) carries BOTH a length bound AND its own regex (closing check: a length bound alone lets a coordinate-like string through); lists carry a count bound. The closed schemas (key names, regexes, ranges) are written down in the implementation story and REVIEWED BY security-reviewer BEFORE any validator code is written (PROPOSED).
- The object stored in `streams/` is RE-SERIALISED canonically from the parsed structure; the uploaded bytes are never promoted. `storedSha256` is the hash of the re-serialised bytes.
- Honest limit (stated in the runbook and privacy text review): heart-rate values disguised as another numeric stream (for example sent as a series labelled `speed` or `altitude`) cannot be detected by any structural check; the server can only bound shapes and ranges (plausibility ranges per kind are a cheap partial defence, not a guarantee). ACCEPTED RESIDUAL RISK (PROPOSED, DQ-6): HR relabelled as an allowed kind, or smuggled in a counter (telemetry, 8.1), cannot be detected. Mitigations are closed schemas, small explicit counter ranges and sentinel tests; the privacy text and the contract state this limit instead of claiming a guarantee against a modified client.
- Tests: payloads carrying `avgHrBpm`, `hr`, or any unknown key in `meta`, a lap, a provenance record, a stream record or the top level are rejected; a coordinate-like string in each provenance and lap string field is rejected; a clean payload is stored byte-equal to its canonical re-serialisation.

Writer: the client PUTs bytes to a V4 signed URL; the server validates and promotes. 1. `createActivityStreamUpload(activityId, bytes, contentSha256)` (PROPOSED, round 1). In ONE Firestore transaction it reads and checks: the delete fence (`activity_account_state/{uid}` absent, `accountDeletionRetries/{uid}` absent, Auth user exists; section 6.1), the tombstone (absent), the summary document (present), the `cloudStreams` consent (current, not withdrawn), the existing row, and that the session's DERIVED expiry (`startUtc` + current retention, 5.3) is not already due (else bare code `already_expired`, no work and no URL). Otherwise it writes the upload intent with a server-generated `uploadId` and `attempts + 1` (cap 5 per activity per UTC day using `attemptsDay`, which resets the counter when the day changes; then bare code `too_many_attempts`). A row that is `stored` KEEPS `state = stored` and gets `pendingUploadId` and `pendingSince` added (so the purge query, which selects `state == stored`, still sees the old object and expiry cannot be outlived by a re-upload); a row that is not yet stored is written `pending` with `pendingSince`. A new upload supersedes an older pending `uploadId` and deletes that quarantine object. It returns a V4 PUT URL for `quarantine/{uid}/{activityId}/{uploadId}` (TTL 10 min, content type `application/gzip`, length range).
2. `commitActivityStream(activityId, uploadId)` is idempotent (PROPOSED, round 1): (a) transaction 1 re-checks fence (including Auth user existence), tombstone, summary, consent and that `uploadId` is the row's current (`uploadId` or `pendingUploadId`; else bare `superseded`), and that the derived expiry (activity date plus the current setting) is not already due (PROPOSED, lead decision: if due, the commit is refused with bare `expired`, the quarantine object is deleted and `pendingUploadId` is cleared, so a re-upload pending while the stored row is purged for expiry cannot revive the stream); a row already `stored` with the same `contentSha256` returns success. (b) It reads the quarantine object ONCE: metadata first, then the bytes pinned to that object generation (`ifGenerationMatch`), into memory (<= 5 MiB); a changed generation rejects the commit. The SAME in-memory bytes are hashed against `contentSha256`, decompressed, validated (5.1a) and re-serialised, so the validated bytes are exactly the promoted bytes (no overwrite window between check and promotion). Decompression is bounded by an absolute cap (32 MiB), a compression-ratio limit (decompressed/compressed <= 20) and a wall-clock budget (10 s); breaching any aborts the stream. (c) BEFORE promotion, a short transaction writes the INTENDED `storedSha256` (hash of the re-serialised bytes) onto the row as `intendedStoredSha256`; then it writes the object to the uploadId-specific path `streams/<uid>/<activityId>/<uploadId>.json.gz` (5.1). (d) Transaction 2 re-checks fence, tombstone and `uploadId`, then SELECTS that path: it records `objectPath`, `state = stored`, `bytes`, `kinds`, `storedSha256`, `expiresAt` (hint) and `settingsGeneration` read in the same transaction (5.3), and clears `pendingUploadId` and `pendingSince`. The PREVIOUS object (the old `objectPath`, if any) is deleted AFTER transaction 2 commits; a failure of that delete leaves an orphan the reconciler removes (an object under `streams/<uid>/<activityId>/` that is not the row's `objectPath`). If transaction 2 refuses, the callable deletes its own promoted object and the quarantine object (compensation, touching only its own `uploadId` path, so it can never delete another commit's object) and returns a bare code; a crash between (c) and (d) is covered by the late sweep and the reconciler (6.1). Two concurrent commits with different `uploadId` write different paths; exactly one is selected by transaction 2 and the other is compensated, leaving exactly one stored row, one object and no stray quarantine object.
3. Any validation failure deletes the quarantine object, clears `pendingUploadId`/`pendingSince` on a stored row (its state never left `stored`) or removes a never-stored row, and returns a bare code.

### 5.3 Expiry mechanism

A bucket lifecycle rule is by object age, global, and cannot represent a per-user setting; with a "never" option it cannot be used even as a backstop for `streams/` (a backstop shorter than "never" would silently break the setting). PROPOSED (revised in round 1):

- Effective expiry is DERIVED at purge time: `activityDateUtc + current streamRetentionDays` (null setting = never). `activityDateUtc` is taken server-side from the summary `startUtc`, clamped to [2000-01-01, request.time], never from a client parameter. The stored `expiresAt` is only a HINT for the query; it can never extend retention because purge re-derives. This removes the commit-versus-recompute race (a commit that stamped an old retention is corrected by the derivation).
- Row bookkeeping: `expiresAt` (hint), `settingsGeneration`, `purgeAttempts`, `lastErrorCode` (bare code), `lastPurgeAttemptAt`.
- Scheduled `purgeExpiredActivityStreams` (daily, `onSchedule` like `purgeExpiredBodyScanPhotos`, FACT) queries collection group `activity_streams` where `state == stored` and `expiresAt <= now` (composite index 1, section 4), in pages with a run budget (reuse `PAGE` and `PURGE_RUN_BUDGET_MS` from `purge.ts`, FACT constants named by the reviewer). For each candidate a transaction re-reads the row and the settings, re-derives the effective expiry and, if not due, only rewrites the hint. If due: delete the object FIRST (404 = success), then set `state = expired` (row kept so the app can show "stream expired"; summary stays). Failure: `purgeAttempts + 1`, `lastErrorCode` set, next run retries.
- No give-up state: after `MAX_PURGE_ATTEMPTS` the row keeps being retried every run (GPS kept past its expiry is a privacy defect, so a cap may slow alerts but never abandon the row) and the overdue-age signal (6.3) alerts.
- Setting change (`setActivityCloudSettings`): one transaction updates `streamRetentionDays`, increments `settingsGeneration` and resets `recomputeCursor`. The same transaction sets `recomputePending = true` on the settings document. Recompute is resumable and its continuation is run by the EXISTING scheduled purge function `purgeExpiredActivityStreams` (no new scheduler): at the start of each run it queries the collection group `activity_settings` where `recomputePending == true` (index 2 of section 4), takes at most 20 users per run, and for each user processes pages of at most 100 rows ordered by id from `recomputeCursor` within the shared run budget (`PURGE_RUN_BUDGET_MS`), each row rewritten in a transaction (hint and `settingsGeneration`), cursor advanced per page. When the cursor is exhausted a PER-USER final pass queries that user's own `activity_streams` where `state == stored` and `settingsGeneration < current` (a single-collection query with a constant, which works because the comparison value is the user's current generation read from the settings document) to catch rows committed with an older generation; only when that pass finds nothing is `recomputePending` set to `false`. The 5-minute reconciler cadence is not used for this: the purge function runs daily, so a recompute backlog is cleared within a few daily runs for heavy users (stated trade-off: the hint is only a query accelerator and purge re-derives expiry anyway, so a stale hint cannot extend retention). Crash mid-way and rerun is consistent; a purge racing a lengthen leaves the object (re-derivation says not due).
- Shortening makes old streams due at the next purge run (once hints are rewritten); lengthening does not resurrect expired ones (stated in UI copy). Options offered (PROPOSED, contract example list; DQ-7): 90 days, 1 year, 2 years (default, shown), never. OPEN for the operator: whether "never" is offered at all ("never" means indefinite storage of GPS history; the operator chose a user-set expiry, not an unlimited one) and whether 2 years stays the default (12.3).
- Signals: oldest overdue age, count of capped rows and recompute backlog are in the table of 6.3 (counts and ages only, no uid; GPS-PRIV-048 compliant).

### 6.1 Delete fence, ordering and late sweep (PROPOSED, round 1)

Problem: Body Scan reads a delete fence inside its create transaction (reviewer-cited `functions/src/body_scan/create.ts` lines 294-298) and runs a late sweep sized to the URL TTL (`shared.ts` lines 192-194); a stream upload design without both lets a still-valid 10-minute signed URL, or a commit racing a delete, recreate GPS objects after erasure.

Revision 3 (closing check, security N1, FACT from `functions/src/index.ts` lines 2376-2384, 2648, 2671, 2724-2725 and `functions/src/body_scan/shared.ts` line 141): the real `deleteAccount` flow runs `sweepAccountData` twice (Step 2 and Step 4), runs `recursiveDelete` BEFORE the object sweep inside it, writes `accountDeletionRetries/{uid}` only at Step 2b (after the first sweep) and clears it after the Step 4 sweep; Body Scan keeps its fence in a top-level `body_scan_purge_state` document that survives `recursiveDelete`. The revision-2 design (a `deleteFenceAt` field under `users/{uid}` and a late job created as step 6) would lose the fence at the first `recursiveDelete`, would not cover `setActivityCloudSettings` and `deleteActivity`, and would never create the late job if the invocation died after Auth deletion. The redesign:

- Fence and late job document: the top-level server-only `activity_account_state/{uid}` (section 4) holding `fenceAt` and the late-sweep job (`lateSweepAt` = deletion time + signed-URL TTL + margin; with the 10-minute TTL and a 5-minute margin that is 15 minutes, but see the next bullet for how long the fence itself must live). It has no client rule (default deny) and sits outside `users/{uid}`, so `recursiveDelete` cannot remove it.
- Written FIRST among the deletions: `deleteAccount` writes `activity_account_state/{uid}` after the Stripe cancel and token revoke and immediately before the first sweep (section 17), BEFORE the first sweep and before `accountDeletionRetries/{uid}` exists, so a crash at any later point still leaves the job. The write is idempotent (a retry keeps the earliest `fenceAt` and recomputes nothing).
- Every one of the seven callables (5.4) reads `activity_account_state/{uid}` inside its transaction (refuse if it exists) AND checks that the Auth user still exists (refuse if gone). Tokens stay valid for about 1 hour after `deleteUser`, so a live session can still call after Step 4; the Auth-existence check and the fence are the two independent guards. The Firestore CLIENT write of a summary (an offline queue replayed while the ID token is still accepted) cannot be stopped by a callable. GPT-PM round 1 BLOCKER-01 closed this gap: the Firestore RULES for create/update of `users/{uid}/activities/{id}` additionally require `!exists(activity_account_state/{uid})` (section 4 snippet; a rule can read a server-only document regardless of that document's own read rule), so from the moment the fence exists no client summary write is accepted, and the late job's final recursive delete (below) removes anything that slipped in before the fence took effect. The fence document is therefore also a rules input and must live as long as any token that could replay a write.
- Fence lifetime (revised): Step 4's `clearAccountDeletionIntent` removes `accountDeletionRetries/{uid}`, but `activity_account_state/{uid}` is NOT cleared there. The fence is removed only after BOTH `lateSweepDone` AND 70 minutes after the Auth deletion (ID token lifetime 1 h plus margin): `removeFenceAfter = max(lateSweepDone + 1 h, authDeletedAt + 70 min)`. Residual assumption (PROPOSED, lead decision): Firebase Auth assigns random uids and does not re-issue a deleted uid to a new sign-up, and the app does not create users with caller-chosen uids; the removal bounds the fence lifetime even if that assumption were wrong; confirming Auth behaviour against current documentation stays a low-risk item in 12.3. If `authDeletedAt` was never recorded (invocation died between Auth deletion and its write), the late job derives it from Auth user absence at its first run and uses that run time (the later, safe value).
- Account deletion order, numbered, with what each step guarantees:
  1. `deleteAccount` writes `activity_account_state/{uid}` (`fenceAt`, `lateSweepAt`) AFTER the Stripe cancel (Step 1) and the refresh-token revocation and IMMEDIATELY BEFORE the first sweep (Step 1c; correction at build, section 17: a failed Stripe cancel can abort the call for a live account and must never leave it fenced), still BEFORE any sweep and before `accountDeletionRetries/{uid}` exists. Guarantee: from now on the seven callables refuse and the summary rules refuse client writes; a crash at any later point still leaves the late job.
  2. Existing Step 2 `sweepAccountData` with `recursiveDelete(users/{uid})` and `sweepActivityStreamObjects` (both prefixes attempted independently, one bare code on failure). Guarantee: current rows and objects are gone; new ones cannot be created (step 1).
  3. Auth deletion; `authDeletedAt` is recorded on the fence document (Step 3b, non-fatal; the late job derives it from Auth user absence if the write is lost). Guarantee: no new tokens; existing tokens live up to about 1 h.
  4. Existing Step 4 `sweepAccountData` (same activity sweep again, prefix-only). Guarantee: objects PUT through a still-valid signed URL meanwhile are removed.
  5. Late job after `lateSweepAt` (15 minutes): sweeps both prefixes, then a FINAL recursive delete of `users/{uid}/activities` and the other activity collections (`activity_streams`, `activity_settings`, `activity_tombstones`), sets `lateSweepDone`. Guarantee: a write that slipped in before the fence took effect (rules cache or race) does not survive.
  6. The fence document is removed at `removeFenceAfter` (see above). Guarantee: until then the rules and the callables refuse; after it no token issued for the deleted user is valid.
  Removal order is therefore fixed: the fence is created first and removed last; it is never removed while a token could still replay a write.
- Late sweep: a scheduled function (every 5 minutes, pattern of `sweepLateBodyScanUploads`, FACT `purge.ts` line 527) finds `activity_account_state` documents whose `lateSweepAt` is due and not done, deletes `quarantine/<uid>/` and `streams/<uid>/`, ends with the final recursive delete of the activity collections of step 5, sets `lateSweepDone`, and removes the document at `removeFenceAfter`. The document has its own `data_lifecycle_policy.json` row (server-only, client NONE). The destructive part (object sweep, final recursive delete, `lateSweepDone`, fence removal) NEVER runs while the Auth user still exists (an aborted deletion): the job keeps the fence, logs a bare skip slug, counts `skippedLive` and stays armed; a failing Auth lookup fails closed the same way (build correction, test epic 6b).
- Abandoned fence of a live account (remediation A1, binding): an aborted `deleteAccount` (failure at Step 2, 2b or 3) would otherwise leave a live account fenced for ever (rules and callables refuse every write). The fence therefore carries a heartbeat `touchedAt` refreshed by EVERY `writeActivityAccountFence` call, so a retried `deleteAccount` refreshes it. For a job whose Auth user still exists, with no `accountDeletionRetries/{uid}` record and `touchedAt` older than 24 h, the late sweep deletes ONLY the fence document by compare-and-delete on the same `touchedAt` (no resurrection window for a deletion in progress, because the retry refreshes `touchedAt` first), emits slug `fence_cleared_live_account` and never erases data while Auth exists. An old skipped-live job that is not cleared because the intent record exists is counted as `stuck`. Documents written before `touchedAt` existed use `fenceAt`.
- Cleanup invariant (positive, GPT-PM round 1 MAJOR-04): every cleanup of `sweepAccountData` (the Body Scan sweep, the activity object sweep, the late job) is ATTEMPTED INDEPENDENTLY; a failure of one never prevents the attempt of the others; the errors are aggregated into ONE safe bare code; the retry (`reconcileAccountDeletions`, up to `RETRY_MAX_ATTEMPTS`) completes the work that was left unfinished, and each cleanup is idempotent (404 = success). Failure-injection cases: Body Scan cleanup fails -> the activity sweep is still attempted and its fake-bucket state verified; activity sweep fails -> the Body Scan cleanup is still attempted and verified.
- Commit after delete: commit re-checks fence, tombstone and Auth existence in transaction 2 and compensates (5.2), so a commit racing `deleteActivity` or `deleteAccount` promotes nothing that survives the late sweep. Per-activity fence = the tombstone (6.2).
- Tests (BLOCKER-01): replay a queued Firestore summary put after `lateSweepDone` with a still-valid token: rules reject it (fence exists); the fence is NOT removed before both `lateSweepDone` and `authDeletedAt` + 70 minutes; a document that exists only because it was written before the fence took effect is deleted by the final recursive delete. Earlier tests: seed a signed URL, delete the account, PUT afterwards: the object is gone after the late sweep; commit after `deleteActivity` promotes nothing; inject a commit between the Firestore delete and the sweep: after reconcile both prefixes are empty; prefix A fails and B succeeds: the sweep throws one bare code and B is empty. Extensions of F56 and E05 (closing check): a `setActivityCloudSettings` call after the Step 2 `recursiveDelete` is refused and recreates no consent document; the invocation is killed after Auth deletion and the late job document still exists and the late sweep runs; the fence survives Step 4's `clearAccountDeletionIntent`; both existing `sweepAccountData` calls run the activity object sweep.

### 6.2 Resurrection: tombstone, delete wins (PROPOSED, round 1)

Local scope (remediation E1, item 22 of section 17): the local journal is NOT device-wide. Each account uid has its own journal directory and key (scope id = first 32 hex chars of sha256(uid)); ownership is the location, so there is no owner marker and no wipe on account switch. Account deletion wipes only the scope of the deleted uid.

Problem: the summary is client-writable and ids are deterministic (`activityIdFor`), so a queued offline `put` from another device, or a re-sync, recreates a deleted summary (and could re-upload a stream).

Choice: a server tombstone, NOT summary writes behind a callable. Reasons: a callable-only summary write path removes offline-first (the Firestore offline queue is the S02 sync mechanism), and Admin-SDK writes bypass rules so the shape checks of section 4 would have to be duplicated in TypeScript (two validators drifting). With a tombstone, rules stay the single shape gate and cost one `exists()` lookup per summary write. Each summary write now costs two lookups (tombstone and account-deletion fence) against the access-call limit of a batched write, so the repository batches at most 8 summaries (section 4, batch limit; the revision-2 claim "well under the limit" is withdrawn).

- `deleteActivity` creates `users/{uid}/activity_tombstones/{activityId}` (`deletedAt` server time, `expireAt` for the TTL policy) before deleting anything. Rules deny summary create/update for a tombstoned id (section 4); all callables refuse a tombstoned id (bare code `deleted`).
- TTL: proposed 400 days, chosen to exceed any realistic offline replay window (OPEN: operator may change it). The TTL policy on `expireAt` is created by the operator in the console or with gcloud (external step, not in the repository) and is a RELEASE PREREQUISITE; its owner defaults to the operator (OPEN until named). Residual risk after expiry, stated: a very stale queued `put` could recreate a scalar summary (no geometry, no stream: the stream callables would still need a new upload under consent). Accepted because the summary holds no geometry.
- Cross-device rule, DELETE WINS: devices read the owner-readable tombstone ids; on sync, a local journal entry whose id is tombstoned is marked deleted in `record.json` (a tombstone line, 10) and its local data is removed. A permission-denied on a summary write is NOT deletion (closing check: it is routine under the `rev`, immutability, clamp and batch rules). On permission-denied the client reads `activity_tombstones/{id}` and the server summary and then acts: (a) the tombstone exists: local data is deleted (delete wins); (b) no tombstone: the entry is marked `sync_conflict` and the local data is KEPT; it is resolved by read, three-way merge per field (3.2, with `summaryOverrides` so the merged result converges after a recompute) and then write with `rev = max(local, server) + 1` (one retry; a field changed differently on both sides, or a second failure, leaves the entry in `sync_conflict` with a user-visible choice "keep this device / keep cloud", retried at the next start, never deleted and never marked `synced`). A rejection caused by the account-deletion fence is indistinguishable from other rejections (the fence is not client-readable), so it follows (b): the entry stays unsynced, no hot loop, and the account deletion wipe (3.5) removes the local data. A lost acknowledgement (same rev resent) therefore resolves to a no-op or a merged rev bump, and a rejected oversize batch is never read as deletion. Consequence for users: re-importing the same external session (same `sourceId|externalId`) while its tombstone lives is refused; native recordings (new uuid) are unaffected.
- Tests: replay a `put` after `deleteActivity`: no summary, no stream; the other device removes its local copy on sync. Replay of the same rev after a lost acknowledgement, a rev conflict from a second device, a clamp rejection and an oversize batch each leave the local data intact and end in a no-op, a bumped rev or `sync_conflict` (rewrite of I26 and E04); a create for an id that exists on the server becomes an update with the next rev; a fresh device reads before writing.

Crash safety of the local journal (PROPOSED, revised in round 1):

- Write order per mutation (GENERATION DIRECTORIES, GPT-PM round 1 MAJOR-02, commit point per round 2 MAJOR-02A; nothing confirmed is ever overwritten in place): (1) create `journal/<activityId>/g<seq>/` and write `streams.bin` and `record.json` into it (each: temp file, flush, fsync, rename inside the new directory); (2) READ BACK the new generation and verify `streamHash` against the bytes of its own `streams.bin`; (3) write the `COMMIT` marker LAST (temp file, flush, fsync, atomic rename) containing the `seq` and TWO separate checksums, one of `record.json` and one of `streams.bin`: THIS RENAME IS THE COMMIT POINT, and the API acknowledges the caller only after it; "written and verified" is not "committed"; (4) update the `CURRENT` pointer (temp file, flush, fsync, atomic rename) AFTER `COMMIT`; it is only a fast pointer; (5) NO directory fsync: Dart has no directory fsync (FFI is not used), so the design accepts rename atomicity and states the residual limit (a power loss right after a rename may lose that rename; the previous committed generation then remains); (6) append the `index.jsonl` line (append, fsync); (7) the OLD generation directory is deleted only after the next successful verified read of the new generation (for example at the next start or the next read), never in the same step as the commit.
- Recovery on start: choose the HIGHEST generation (`seq`) that has a VALID `COMMIT` marker (the marker parses, its `seq` matches the directory and its `record.json` checksum matches; lead decision on plan question DQ-30: a mismatch of ONLY the `streams.bin` checksum does not invalidate the generation, because rolling back would silently drop acknowledged metadata edits, so that case is recovered as `streamLost`). A generation that was fully written and read back but has NO valid `COMMIT` marker is never activated, even if it is newer and intact: the recovery pass deletes it. If `CURRENT` is missing, corrupt or points elsewhere (including at an uncommitted or invalid generation) it is rebuilt from the highest committed generation. Tombstones, `synced` markers and `summaryOverrides` are part of `record.json` of the committed generation, so they are preserved in every case below. If the committed generation's `streams.bin` fails its hash but its `record.json` is valid, the record is recovered as `streamLost` (3.5) rather than dropped. Uncommitted generation directories are deleted by the recovery pass at once (they were never acknowledged), ALSO when no committed generation exists for that activity (the first generation of a new activity that crashed before `COMMIT` leaves the activity absent from the active journal after restart, even if its `record.json` and `streams.bin` are intact; the `streamLost` recovery applies only to a COMMITTED generation, GPT-PM round 3 MAJOR-02B); other orphan generation directories (older than the committed one) are removed after the bounded age; a directory without any `record.json` is never read as a session. The earlier wordings "take the pair with the larger `seq`", "highest verified generation" and "the CURRENT switch is the commit point" are withdrawn.
- Four crash cases (each a required fault-injection test): (A) crash before `COMMIT` with `CURRENT` intact: the previous committed generation is recovered, the new directory is deleted, the caller was not acknowledged; (B) crash before `COMMIT` with `CURRENT` missing or corrupt: the previous committed generation is recovered and `CURRENT` rebuilt, the uncommitted generation is never activated even though it is newer and intact; (C) crash after `COMMIT` and before the `CURRENT` update: the NEW generation is recovered (it is committed) and `CURRENT` is repaired; the caller was acknowledged only if the acknowledgement was sent before the crash, otherwise the caller retries idempotently (same mutation, same deterministic id and `seq` rule) and no duplicate results; (D) `CURRENT` corrupt after a normal commit: rebuilt from the highest committed generation, no data change.
- The `record.json` of the highest COMMITTED generation is the truth; `index.jsonl` is a rebuildable cache. Delete tombstones and the `synced` state live in that `record.json`, so an index rebuild from the record files loses neither (a rebuilt index must not resurrect deleted ids or re-upload synced ones). On start the repository ignores a torn last index line and deletes orphan temp files.
- Single writer: the repository owns the journal behind an in-process mutex (an async lock); the compute isolate and the S04 recorder submit mutations through it and never touch files directly. Cross-process writers are not supported.
- Full disk and I/O errors: a `FileSystemException` (including disk full and rename failure) aborts the mutation, leaves the previous durable state intact, surfaces a typed error ("storage full") and keeps the recording in memory for retry; it never half-writes a record.
- Ordering and expiry use monotonic counters (a per-journal sequence number in index lines and `record.json`), not wall-clock timestamps, so a device clock change cannot reorder mutations; `updatedAt` stays informational only.
- `synced` markers are written only after the commit callable returned success, so a crash after upload re-uploads idempotently (`already_stored`, 5.2).
- Tests with an injectable fault-injection file system failing at each step (temp write, flush, rename, read-back, `COMMIT` rename, `CURRENT` update, index append, old-generation delete; a crash is injected after EVERY step of the generation write, commit and pointer update) including disk full: in every case the last committed full generation (record AND streams) is recovered, not merely `streamLost` with other sessions intact; the four crash cases above (A-D) each have a test; a fully written, read-back generation without a valid `COMMIT` is never activated and is deleted, also when `CURRENT` is missing; a corrupt or missing `CURRENT` is rebuilt from the highest committed generation; orphan generations are removed; truncate the index at every byte offset of the last line; delete the index and rebuild with tombstones intact; two concurrent writers serialise through the mutex.

## 17. Implementation notes (deviations the build made, 2026-10-16)

21. Bulk deletion propagation (remediation E2, 6.2, 5.4): the local tombstones are durable in the journal record, so the queue survives a restart; E2 adds continuation, observability and capacity. (a) Continuation: after the first round of 8, `syncAll` keeps pushing further rounds of 8 in the same call while the previous round pushed at least one and nothing failed, up to 128 rounds (1024 deletions) per call; a failure in a continuation round, and any quota, unavailable or permission refusal in any round, ends the pass at once (no hot loop); ids that failed earlier in the process are tried last so one poisoned id cannot starve the rest. (b) Observable: `ActivitySyncState.pendingTombstones` (local tombstones not yet confirmed by the server) and `lastTombstonePushError` are emitted through `watch()`. (c) Automatic retry: when tombstones remain after a pass that ended on a failure, an unknown server tombstone list or the round cap, the repository schedules ONE timer with backoff 60 s, 2 min, 4 min, 8 min, 15 min (cap), at most 6 scheduled attempts per app start; `resource-exhausted` uses the longest delay; the timer is cancelled on dispose and sign-out. (d) Quota: `activityDelete` is raised from 100 to 1000 per user per day because each queued deletion is one call and this is privacy-erasure capacity, not an abuse limit (still per user, still refunded on fence refusals; the other quotas are unchanged; the bulk call keeps its own `activityDeleteAll`). (e) Signed URLs: a download URL issued before a deletion lives at most 15 minutes and becomes useless when the backing object is deleted; the object is deleted before the row (6.2), which the sweep and the `deleteActivity` cascade verify.
22. Account-scoped journals (remediation E1, 2026-10-16; 6.2, 7; supersedes the owner-uid guard and the wipe-on-switch of item 18): the single device-wide journal and the `activity.journalOwnerUid` preference marker are removed. Each account uid has its own journal under `<app support>/activity_journal/<scopeId>` (scope id = lowercase hex of the first 32 chars of sha256(uid); the raw uid never appears in a path or key name) with its own secure-storage key (`activity_journal.key.v1.<scopeId>`). `UidScopedActivityJournal` holds no data, is built without I/O at app start and delegates to the journal bound by `bindUid(uid)` (serialized, idempotent, fail closed: false and nothing bound when opening or recovery throws). An always-on listener binds the signed-in uid (anonymous users included) and unbinds on sign-out; cloud sync awaits the same bind first. In plain words: (a) sign-out and account switch never destroy data, they only close the journal; (b) A to B to A keeps A journal intact; (c) account deletion wipes only the deleted uid scope (`wipeForUid`), whoever is bound, including the relaunch path with a pending wipe while another account is bound; a failed wipe is still reported as `activity_journal` and the pending marker stays; (d) an unbound journal returns empty reads and refuses every write with `JournalUnbound`, so no write can land in the wrong account; (e) a missing, corrupt or restored marker cannot exist because there is no marker. `ActivityWipeCoordinator.onSignOut` and `onAuthFailureAtLaunch` work on the bound journal; the app does not call sign-out wipe yet (S03 export offer). No migration: the journal flags are default OFF and S02 is unreleased, so no previous on-disk layout shipped.

23. Sync pass identity, unbound visibility and tombstone retry (remediation F, 2026-10-16; 3.2, 6.2): (a) Every serialized operation of `ActivitySyncRepository` (`syncAll`, `syncEntry`, `syncBatch`, `saveSession`, `resolveConflict`, `resolveCandidate`, `applyExplicitEdit`) runs under a pass identity: the account epoch, the uid the scoped journal was bound to, and the signed-in uid (constructor parameter `String? Function()? authUid`, null in tests), all captured when the operation starts. Before EVERY journal write or delete, and after every await whose result came from the journal, the pass re-checks that the epoch is unchanged and the scoped journal is still bound to the same uid; synchronously immediately before EVERY backend or tombstone-pusher call (no await between check and call) it also re-checks that `authUid()` still equals the starting uid. A stale pass stops with `SyncOutcome.pending` and no further side effect. Reason: activity ids are deterministic, so account A's server tombstones would otherwise delete account B's local copies and a summary could be written under B's Firebase uid. (b) An unbound scoped journal is a visible failure, not an empty one: `refreshState` throws `JournalUnbound` (the state stream errors, the sheet shows its error state with retry), `syncEntry` and `syncBatch` return `pending` and `syncAll` returns an empty map, all without a backend call, and the resolution operations return `unavailable` (reported as failed). `onAccountChanged` also clears the conflict cache and the once-per-process conflict retry marks. (c) The tombstone retry budget is reset by a pass that ends clean; after `kMaxTombstoneRetries` scheduled attempts ONE fallback timer of `kTombstoneFallbackDelay` (60 minutes) remains while deletions are owed (the same single timer slot, never two). An exception in the tombstone phase records its code and schedules a retry; a failed tombstone listing sets `lastTombstonePushError` to `unavailable`; a fully clean pass clears it. (d) `ActivitySyncRepository.requestTombstoneSync()` runs one normal serialized `syncAll` pass for callers that create a local deletion or return to the foreground. S02 has no production local-delete caller (the delete UI belongs to S03), so the method is only added. S03 HANDOFF: the delete flow and the foreground-resume hook must call it. (e) Remediation G1: with a scoped journal and an `authUid` supplier the pass is valid only if the bound journal uid equals the signed-in uid exactly (case-sensitive) at the start and again right before every backend or pusher call; otherwise the pass does nothing (pending / empty, no backend call). `FirebaseAuth.currentUser` flips before the journal rebinds, and without this tie a pass in that gap would write account A's data to account B's cloud.

    ACCEPTED / BACKLOG, stated honestly: (a) Device data of an anonymous account that signs out stays on disk and cannot be reached again; deleting it would repeat the data loss the gate rejected, so it is handled only together with the sign-out export offer in S03. (b) The UI for `pendingTombstones` and `lastTombstonePushError` ("N deletions not yet synced") is S03; the state is already exposed. (c) `main.dart` passes the opened journal to the wipe decorator directly, which keeps `main()` out of widget tests (testability only). (d) A push already in flight at the moment of the switch is bounded by the synchronous `authUid` check right before each call; the call itself cannot be recalled. (e) After a failed journal bind the cloud sync start sequence (bind, uploads resume, `syncAll`, stream upload) is not re-run when the binding provider's retry later succeeds, and after the five bind retries are spent the journal stays unbound for the session; recovery is the next auth event or an app restart. This fails closed with no data leak and no data loss, and it is a secondary mechanism that already had its one fix round (remediation G, accepted, not changed). (f) The conflict presenter's retry only resubscribes to the state stream; it cannot force a journal bind (accepted, not changed). Remediation G2 makes the failed state visible without a tap by republishing on every binding change.
