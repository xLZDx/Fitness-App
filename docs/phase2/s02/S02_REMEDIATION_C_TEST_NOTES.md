# S02 remediation C: test notes (client findings)

One line per item: what a test must assert. FL3, FL4 and FL7 are decided and not implemented.

- FL1: with a fake backend whose `readSummary` throws a generic error (for example a `FirebaseException` permission-denied) for one conflict entry, `watch()` still emits a state in which that conflict has `cloudKnown: false` and no fields; no zone error escapes. With a fake journal whose `list()` throws, `watch()` delivers a stream error (not an uncaught async error), and the presenter ends with `loadFailed: true`, `loaded: false`.
- FL2: before the first emission the sheet shows `activitySync.loading` (a progress indicator) and never `activitySync.empty`; after the first emission with no items it shows `activitySync.empty`; after a stream error it shows `activitySync.error` and `activitySync.retry`; tapping retry re-subscribes (`watch()` called again), clears the error, and a following emission shows the items.
- FL5 (uploader): with an injected `currentUid` supplier, start `runPending`, flip the uid to another value or null before create, before PUT, before commit and before the journal mark: in each case no later network call is made and `markStreamUploaded` / `updateSyncState` are not called (outcome `cancelled`). Two concurrent `runPending` calls return the same future and call `create` once per entry; two concurrent `uploadEntry` for one id run once. Without a supplier the behaviour is unchanged (existing uploader tests stay green).
- FL5 (wiring): changing the auth uid from A to B, or A to null or guest, calls `cancelQueued()` on the uploader; `resume()` is called only after `claimActivityJournal` succeeded for the new uid and the auth uid is still that uid; a failed claim never calls `resume()`, `syncAll` or `runPending`. Flag off: no listener side effects.
- FL6: if `claimActivityJournal`, `ref.read` or any step inside the unawaited closure throws, nothing escapes (no zone error); a `debugPrint` line is produced.
