## 0. Read first: what this document is and is not

1. PLANNED, not run. No test was written, no emulator, device, build, analyzer or test command was run, and nothing was committed while producing this file. Every script below is a specification of a test that does not exist yet. No result, pass rate, latency, battery or accuracy number in this file is a measurement; every number is either copied from the draft/requirements (design target) or marked PROPOSED (a default for reviewers to accept or change).
2. Nothing here authorises implementation. Sprints AI-COACH-01..05 are PLANNED and NOT AUTHORISED (`02_BACKLOG.md` section 0). This plan exists so the later sprints have nothing left to guess.
3. Who will write and run these tests (when a sprint is authorised): `e2e-runner` and `functional-test-reviewer` write the scripts for each epic and run the complete set they wrote after each epic and once more after the last epic (global development rules v4). The coordinator runs no tests. Human-on-device parts are run by an operator-named tester, not by an agent. No mutation runs: each test is justified by what its assertions would observe, not by breaking the code (sections "Breaks if wrong" below are reasoning, not mutation results).
4. Vocabulary. FACT = I opened the cited file. PROPOSED = default for review. OPEN = undecided, tied to an OQ/UQ id with the consequence stated. UNVERIFIED-EXTERNAL = depends on Android/Play/provider/adb behaviour that was not checked against live documentation or a device; the first spike must confirm it. Command lane = deterministic on-device closed-grammar commands (design section 8). Dialogue lane = model conversation through the `liveCoachTurn` callable. Journal = local append-only command journal (design section 6). Replica = Firestore `users/{uid}/live_workout_sessions` (design section 5.3).

### 1.5 Rules every script follows (e2e-testing-contract)

- Wait on an observable condition (event-log entry, widget key, state value), never a fixed sleep. Hermetic tests advance `TestClock`; on-device runs poll with a timeout and, on timeout, dump the on-screen texts and the last 50 event-log entries (same habit as `tapTab`).
- Each test sets up and tears down its own state (own temp journal dir, own uid, own session id). No ordering dependency between tests.
- Assert at each meaningful step, not only at the end.
- Assert on typed codes and keys, never on copy (AICR-066). The only copy assertions are the honesty/forbidden-claim audit (AC-LC-26) and the fixed safety text, and those read the string table, not rendered pixels.
- Independent oracle: expected totals are computed in the test from its own scripted inputs, never read back from the code under test (avoids tautology).
- Flake policy: a new hermetic scenario is repeated 20 times on the same commit before it is called stable (PROPOSED); emulator scenarios 5 times; device scenarios 3 runs per device per scenario (PROPOSED, time-bound). A test that fails some runs is classified flake only after the repeat; quarantine requires a marker, a linked issue and an expiry date, and is listed in the sprint report. Never retry until green, never widen a wait to mask a race.

### E2E-07 App crash: real-device kill-loop (revision 2)

Requirements: AICR-026, 042, 043, 044, 080, 092, 096, 097; NFR-05..07; draft risk "lost workout result". Stories: ACS-002, 025, 074; UI J13, AC-LC-18, AC-LC-38. The physical-device kill-loop (07b) is an EXIT CRITERION of AI-COACH-01, not only of AI-COACH-02 (AICR-097, decision A3.6): the AI-COACH-01 exit cannot be claimed without a recorded result from it. The claim is limited to the test device: it is not a claim about other phones, other OS builds or sudden power loss.

THE ORACLE (one sentence, used by 07a, 07b and S-A4, with no "or"): after every kill and relaunch, every set that the test harness saw ACKNOWLEDGED before the kill is present in the recovered session EXACTLY ONCE, and no set that was not acknowledged is reported to the user as saved. Counted over a whole run this means 0 lost acknowledged sets and 0 duplicated acknowledged sets on the test device. The earlier permissive wording ("present or absent") is removed. An acknowledged command must be present exactly once. A command that was not acknowledged is not required to be present; if the journal happens to hold it (for example a kill between append and acknowledgement), it is counted once and shown in the resume prompt's saved-set count, never twice and never spoken as saved before the user re-confirms.

Metric restatement (D2-5): "lost acknowledged sets = 0" counts sets of a journal that is the live or finished session of its owner. A PARKED journal (the previous owner after a takeover) is not lost, because it stays on the device and is shown, but it is also NOT in History until the user acts (re-add through Review, or export). The kill-loop runs in a single-owner configuration, so this exclusion does not weaken its oracle; any report that quotes "0 lost" over a run that included a takeover (X-18) states the number of parked sets separately. The exit evidence and the metric name say so.

Where the journal lives in these runs: on the TEST DEVICE only (app-support dir `live_coach/<uid>/<sessionId>.journal`, encrypted per AICR-096). The harness keeps its own acknowledgement ledger on the HOST (it records each `acknowledged{command_id, set_id}` line that the debug scenario channel prints), never inside the app's storage, so a kill cannot erase the oracle. The replica is not part of this oracle (it is covered by E2E-12, E2E-21 and X-01); the oracle is L1 only (journal-committed, design 6.4).

- Harness: a host-side orchestrator (PowerShell or Python) drives a debug-only scenario runner in the app. The runner keeps a scripted list of N commands (distinct `record_set` values from a seeded generator, plus `correct_set`, `void_set`, rest commands and `finish_workout` in a fixed mix). The app prints one line per acknowledgement (`ack command_id set_id seq`) to a debug channel that the host reads and appends to the HOST ledger; the host never trusts the app's own state for the oracle.
- Randomised kill points: each iteration draws the kill moment at random from a seeded generator (the seed is printed and stored so a failure can be replayed): either (a) a named kill point Kn announced by the app at a sync point, or (b) a uniformly random delay after the iteration's first command is sent (time-based, between commands and inside a command's append/flush window), executed as `adb shell am force-stop <applicationId>`, `adb shell kill -9 <pid>` through `run-as` on a debug build, or `Process.killPid` from inside (UNVERIFIED on Android). Mix: roughly one third each named point, random delay, kill while the foreground service runs with the screen locked. No fixed sleep decides pass or fail; the relaunch waits for the app's `ready` line.
- Loop and sample: every iteration = run, kill, relaunch, read the recovered session through the debug port (and a `run-as` copy of the journal bytes for the archive), compare with the host ledger. At least 20 distinct randomised kill points x 3 repeats each (PROPOSED) on the S23 and on the low-end device, plus at least 200 consecutive iterations in one loop on the S23 (PROPOSED, time-bound; reported as reduced if shorter, OB-8). Every iteration appends its seed and verdict to a CSV.
- Per iteration oracle (the one sentence above): (1) every acknowledged `set_id` in the host ledger is present exactly once in the recovered session; (2) no recovered set carries a duplicate `set_id` or a duplicate `command_id`; (3) every `void_set`/`correct_set` that was acknowledged is reflected exactly once, and the original record is still in the journal; (4) a torn tail is discarded and nothing before it is lost; (5) the resume prompt appears before Home with Continue / Finish / Not now and no Discard, and does not claim that nothing was lost; (6) the microphone is closed and the voice state is STOPPED after the relaunch; (7) the encrypted file contains no plaintext set value (byte search for the seeded weights and reps).
- Pass rule: ALL iterations pass. One lost or duplicated acknowledged set fails the run and triggers the SQLite fallback decision (below). A failing iteration is replayed from its seed at least 3 times before it is classified (product bug vs harness defect vs flake); a failure that reproduces from the seed is a product bug.
- SQLite fallback trigger (decision A3.6, ADR-005): the file journal is REJECTED, and the work moves to a SQLite implementation behind the same `CommandJournalStore` interface, if (i) any iteration loses or duplicates an acknowledged set, or (ii) a torn or corrupt tail cannot be discarded cleanly, or (iii) flush durability under kill cannot be shown (for example acknowledged records missing after `am force-stop` on either device). The loop is then re-run unchanged against the SQLite store; the exit criterion is the same oracle. A new dependency requires operator approval (ADR-005); until then AI-COACH-01 stays open. Power-loss durability is not claimed either way.
- Low-storage run: see E2E-18 (disk full) and X-11 (`safety_stop` with storage full).
- What the loop does NOT prove: other devices, other Android builds, sudden power loss or battery pull, flash wear, an OS that kills the process during a flush in a way `am force-stop` does not reproduce. The sprint report states the claim as "on <device, build id, N iterations, seed list>".
M (HUMAN-D): swipe the app away from Recents while the foreground service runs; Samsung "Close all"/Device Care "optimise now"; Settings Force stop; battery-saver kill; reboot with an open session (the microphone must not restart after boot, NG-6). Record in each case whether the foreground service survived, whether the notification disappeared, and what the recovery prompt showed.
Limits stated honestly: process kill is tested; sudden power loss (fsync to flash) cannot be simulated without pulling the battery and is NOT claimed. The 07a hermetic run is necessary but not sufficient: it uses a fault-injecting store, so it proves recovery LOGIC only; durability of the real file on the real device is proved only by 07b (SF-13).

### 6.5 Latency P95 sampling method (NFR-01, NFR-02, NFR-03; design 8 C1, 17)

Definitions (design 17 measurement method): start = timestamp of `finalTranscript` (or VAD end of speech); stop = first PCM/TTS sample handed to the audio device; on-device monotonic clock; recorded as `voice_latency_ms` with lane (command / model-mediated), condition and utterance label id. For NFR-02/03 the same pattern with start = command dispatch and stop = journal-commit/timer-state change; these are Runtime micro-benchmarks plus a device trace, no human needed.
Conditions (cells): {Wi-Fi, cellular} x {BT headset, phone mic} x {quiet room, gym}. 8 cells.
Sample size: N >= 100 utterances per cell (matches design 8 C1). 10 commands from FX-UTT x 10 repetitions, random order, at least 8 s apart (no queueing), spread over at least 3 sessions on different days/times. Per-cell exceedance count against 2.0 s is reported.
Statistics: nearest-rank P95 (the 95th smallest of 100), plus median, P90, P99, max, exceedance count, recognition accuracy; all raw samples kept in CSV (labels, no transcripts). Failed recognitions are NOT dropped from latency: no acknowledgement is recorded as a failure (and counted in accuracy), otherwise P95 looks better than reality.
What the numbers can claim: with N=100 the P95 is a point estimate determined by the top five samples, not a confidence statement. A release-grade claim "P95 <= 2.0 s" at 95% confidence needs either 0 exceedances in 59 consecutive samples (since 0.95^59 is about 0.049) or a larger sample (N >= 300 per cell, PROPOSED for AI-COACH-05) with the exceedance count and a binomial upper bound reported. The pass threshold stays the draft's 2 s; the sample-size rule and the lane the 2 s applies to (command lane vs model-mediated) need OQ-12 and OQ-24 decisions.
Other timings sampled the same way: playback-stop time after barge-in (OQ-12 target set from data), reconnect time (30 loss/restore events per network type, PROPOSED), voice session start-to-LISTENING time.

## 11. Failure triage and reporting

When a scenario is red, classify each failure with evidence before touching anything (event-log dump, journal, replica export, logcat, screenshots):
- Product bug: the app violates a stated requirement (for example "saved" spoken before commit). Report it with the requirement id; do not edit the test.
- Test defect: assertion or key no longer matches intended behaviour (for example a renamed key). Fix the test; never weaken an assertion or drop a step to get green.
- Flake: passes and fails on the same commit; prove it with the repeat counts in 1.5 before using the word. Racing an unfinished request, animation timing, shared fixture state and ordering are the usual causes; the hermetic design (fake clock, event-log ordering) removes most.
- Environment: device state, staging data, auth, adb or OS behaviour (for example an OEM battery setting); fix the setup and record the device conditions.
Per-sprint report format: `Suite: PASS|FAIL`, counts per tag (AUTO-H/E/D, SERVER, HUMAN), then per failure: journey, `file:line`, classification, evidence, required action; newly quarantined tests listed separately with issue link, owner and expiry date. Nothing is counted as passed that was skipped, cancelled or not run; items blocked by operator inputs are reported as BLOCKED, not as pass or skip.
