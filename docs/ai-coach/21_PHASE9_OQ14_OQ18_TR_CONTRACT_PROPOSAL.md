## OQ-14 proposed contract

1. **User-visible boundary.** A factual response is a closed envelope `{schemaVersion, locale, templateId, claims[]}`. Every factual sentence shown in that response must be generated solely by the deterministic template renderer from those typed claims. Model-generated free text is never concatenated into a factual envelope. In the initial factual-output scope, model-authored free text is not rendered to the user, including in a supposedly “generic” lane. Non-factual conversation may use only a separately approved closed intent and deterministic localized template; there is no arbitrary-text fallback. A later free-form conversational lane requires a separate product-risk disposition and a falsifiable contract that prevents ungrounded claims. The renderer rejects unknown fields, unknown template IDs, missing claims and untemplated text.
2. **Claim/source schema.** Each claim has a closed `claimKind`, a typed value (including an explicit unit where applicable), and one or more evidence references. Each evidence reference contains `sourceKind`, stable `sourceId`, immutable record identity or source revision/version, `fieldPath`, `capturedAt`, and an integrity/availability state. A versioned allowlist maps each `claimKind` to permitted `(sourceKind, fieldPath, valueType, unit)` tuples; an absent mapping permits no claim. Reason claims use closed typed reason codes. A technique claim requires the specific current Form Coach result and only its allowed typed cue/rep fields; it cannot be generalized into clinical or safety evidence.
3. **Freshness and consistency.** A versioned source policy defines required source versions, freshness limit per mutable source/claim kind, timestamp authority, tolerated clock skew, future-time rejection, and any cross-source maximum skew. `capturedAt` is an absolute UTC instant with an explicit offset or UTC designator; local-time timestamps without an offset are invalid. The policy names the authoritative clock used at response assembly and defines a non-negative tolerance for source-clock error. A capture instant later than the authoritative assembly instant plus that tolerance returns `INVALID_TIMESTAMP` and makes the claim ineligible; the implementation must not clamp it to the assembly time. A claim is eligible only if every required reference is allowlisted, has identity/version and capture time, passes integrity checks, is not revoked/superseded, is no older than the configured limit at response assembly, and satisfies the configured cross-source consistency rule. Missing policy, version, timestamp, limit, clock authority, tolerance or consistency rule makes evidence unavailable; the implementation must not insert a default threshold or treat a digest as proof of freshness. Numeric age limits, populated source mappings, clock authority and tolerance remain open product/technical decisions and are not supplied here.
4. **Normalization and rendering.** Validate canonical typed values before converting to locale presentation. Normalization is deterministic and preserves the source value, normalized value and unit mapping in the rendered claim provenance; rounding/precision and supported locale formatting must be explicit fields of the versioned template/normalization policy, not model choices.
5. **Typed evidence outcomes.** For each required claim, evidence resolution returns exactly one of `AVAILABLE`, `MISSING`, `STALE`, `AMBIGUOUS`, `CONTRADICTORY`, `UNPARSABLE`, `UNSUPPORTED_SOURCE`, `INTEGRITY_INVALID`, or `INVALID_TIMESTAMP`, with source references where available. Any non-`AVAILABLE` required claim prevents the factual envelope from rendering and maps to a deterministic unavailable/refusal/clarification template selected by the product policy. Never repair a failed claim using model inference. Unknown outcome codes fail closed.
6. **Falsifiable acceptance boundary.** For a factual response, acceptance compares the complete user-visible output with the deterministic render of the supplied claim envelope and rejects any extra model-authored characters/content. With no eligible evidence, the factual envelope contains no factual claim. Existing `FT-3006`, `FT-3007`, `FT-3017` and `FT-3018` cover selected number, reason and technique examples but do not establish this complete boundary. The authorized test agents must map the AICR-014/020/052 acceptance cases to the envelope, source allowlist, stale/ambiguous outcomes and negative free-text cases before any implementation gate; this proposal does not edit or execute tests.
7. The current `AiCoachContext`/`AiCoachService.advise` interfaces do not provide this claim/evidence schema or output envelope. OQ-14 stays open until the schema, populated permitted-source map, accepted freshness/consistency policy, validation outcomes, deterministic template coverage and full falsifiable acceptance mapping are specified and reviewed.

## OQ-18 proposed contract

1. A future composer is a pure local function over an immutable copied input snapshot, an explicit schema/policy version, and explicit ordered day slots. The output is a draft only; it is not active or persisted by the composer contract.
2. For each day, apply training-context candidate narrowing and its paired safety-context transformation before calling the existing pure single-day `buildPlan`. Preserve stable day order; every selected exercise must be present in the filtered candidate input. A model cannot choose the schedule, exercise set, weekly volume, sets/reps/rest, progression, or numeric prescriptions. Any user-visible explanation about the draft uses only an approved closed intent with deterministic localized templates and typed OQ-14 claims; model-authored free text is not rendered in the initial scope.
3. Any missing required input/policy or any `PlanRefused` aborts the whole draft with a typed refusal; do not emit or persist a partial plan. The composer never writes planned sets into observed workout history or the volume ledger.
4. **Observed/projected volume (GPT-PM SET VALUE).** For the initial scope, `observed_projected_combination = DISABLED`: no summation, offsetting, deficit adjustment or adaptive feedback from planned sessions into observed history or later days/weeks. The two quantities remain distinct until a separately versioned and approved formula authorizes a specific combination. This is a product restriction, not a selected calculation formula.
5. **Source snapshot and consistency.** The immutable snapshot carries `snapshotSchemaVersion`, `snapshotId`, `assembledAt`, user/profile identity, policy IDs/versions, and a source entry for every required input family: profile, observed workout/history and deficit, scheduled sessions, safety/context, recovery, and equipment. Each entry carries stable source ID, immutable record identity or revision/version, `capturedAt`, and integrity/availability state. `capturedAt` and `assembledAt` are absolute UTC instants with an explicit offset or UTC designator; local-time timestamps without an offset are invalid. A versioned policy specifies freshness limits per mutable source, the authoritative clock used for assembly, tolerated source-clock error, future-time rejection, and maximum permitted cross-source timestamp skew. A timestamp later than the authoritative assembly instant plus the configured tolerance returns a typed `INVALID_TIMESTAMP` refusal; it is not clamped. Missing version/time/policy/clock authority/tolerance, invalidated sources, or a mixed-time snapshot outside configured skew returns a typed refusal for the whole draft. There is no default age/skew/tolerance value here; missing limits refuse rather than silently accepting stale input. Snapshot assembly is not claimed to be one cross-source database transaction.
6. **Recovery coverage.** `RecoveryCoverage` is a typed object bound to the snapshot and draft interval: `{coverageSchemaVersion, policyId, sourceRefs[], windowStart, windowEnd, evaluatedAt, requiredCoverage[], coveredIntervals[], state}`. `state` is one of `COMPLETE`, `PARTIAL`, `EMPTY`, `STALE`, `INVALID`, or `CONTRADICTORY`. `COMPLETE` is valid only when each `requiredCoverage` interval is fully covered by the union of valid `coveredIntervals`, with no gap; every interval references evidence whose identity/version/time passes the snapshot policy. The versioned product policy must state whether recovery judgment is `REQUIRED` and define `requiredCoverage`; it supplies the horizon and freshness rules. Missing policy, absent required coverage, or any state other than `COMPLETE` when judgment is required returns `REFUSE_RECOVERY_EVIDENCE`; `UNKNOWN` cannot map to `RECOVERED`, `no deload`, or an implicit pass. A recovery-independent draft is permitted only when a separate approved product-policy version explicitly marks judgment `NOT_REQUIRED`; absence of that rule refuses. The existing 14-day lookback is source evidence only and is never projected into unsupported future weeks. The current `DeloadVerdict`/`detectDeload` interface does not satisfy this proposed coverage contract. The recovery-dependent `REFUSE`/`UNKNOWN` direction is recorded only in the operator-supplied artifact labelled request `26649707-679f-4962-8d26-e3b2a2ff36b2`; that artifact is not correlated to a PM Bridge turn/reply. This proposal chooses no recovery threshold or clinical rule.
7. **Persistence boundary and concurrency.** The composer is pure and does not implement persistence. A separately owned persistence adapter must provide a linearizable create-if-absent operation for `(userId, generationKey)`, with one atomic record containing canonical input digest, policy/version references, and the complete draft. For concurrent identical key+digest requests, exactly one record is created and every caller receives that committed record. Same key with a different digest returns `GENERATION_CONFLICT` and preserves the first record. A crash before commit leaves no visible partial record and permits retry; a lost acknowledgement is resolved by reading the key and comparing digest; a crash after commit returns the prior record on retry. Client-side check-then-write or multi-step partial write does not satisfy this contract. The actual persistence service/module owner and storage transaction mechanism remain unassigned/unselected; this is a proposal, not a runtime claim.
8. **Canonical generation digest.** Digest input is the normalized tuple of snapshot schema/version, each required source's kind/opaque ID/revision/capture instant in source-kind order, policy IDs/versions, ordered day-slot IDs/dates, normalized typed candidate/policy inputs, and composer schema/version. User identity is supplied by the outer user-scoped persistence key, not included in digest bytes. The schema uses canonical IDs/enums and typed values, not free text. Encode as UTF-8 canonical JSON with no insignificant whitespace; object keys sort by UTF-8 byte order; arrays preserve declared semantic order; instants convert to integer Unix microseconds and serialize as a base-10 integer; calendar dates use `YYYY-MM-DD`; finite decimal values use base-10 notation without exponent, a leading zero before the decimal point, no trailing fractional zeroes or decimal point, and `-0` normalizes to `0`; units are explicit; NaN and infinity are rejected; absent and null remain distinct. Hash the exact bytes with SHA-256. Exclude generated prose, random IDs, and derived output. GPT-PM ACCEPTED this canonical representation as a TR design requirement in request `bafbb0e5-4c6a-47a4-85fa-bd389e685a9e`, subject to exact technical conformance review with the eventual persistence owner. This acceptance does not select a storage engine, prove that a service can satisfy the contract, or identify its owner; implementation must not claim conformance until that review is complete.
9. **Traceability and closure.** Future acceptance must falsify source freshness/skew, recovery-required refusal, recovery-independent policy gating, no partial draft on `PlanRefused`, deterministic day ordering/output, separation of observed/projected volume, and persistence same-key replay/conflict/concurrency/crash/lost-ack behavior. `functional-test-reviewer` and `e2e-runner` own the eventual test matrix and execution; this proposal does not edit or run tests. OQ-18 stays open until per-source policy values, day-slot acquisition, recovery policy, persistence owner/protocol, and exact acceptance mapping are reviewed. Weekly prescription/progression values remain unavailable until OQ-07's approved policy exists.
