The application root overrides the provider with `FirestoreWorkoutSessionRepository` in `mobile/lib/main.dart:434-435`; the provider's fallback is a mock for non-production scopes.
- `mobile/lib/features/workouts/data/workout_session_repository.dart` is the existing persistence interface. `WorkoutSessionExercise.sets` is already a persisted `List<SetCapture>` (`workout_session.dart:29-105`), serialized as a list of records with `weightKg`/`reps`. - `mobile/lib/features/workouts/state/rest_timer_providers.dart` contains the existing `RestTimerController`; the player starts it after a successful save. `mobile/lib/features/workouts/data/set_session.dart` is a timed-set interval model, not a workout-wide session runtime.
- `mobile/lib/features/voice/data/voice_command.dart` contains a pure parser for start/done set, rest, exercise navigation, help, weight and reps intents. It has no production caller; `VoiceCommandKind` has neither `startWorkout` nor `finishWorkout`. `speech_to_text` is declared in `mobile/pubspec.yaml`, but no `SpeechToText`/`speech_to_text` use exists under `mobile/lib`. The `features/voice` directory contains only the parser file.
- `mobile/lib/features/ai_coach/ai_coach_sheet.dart` is a one-shot, machine-specific advice sheet. `ai_coach_service.dart` calls the `aiCoachAdvice` callable and returns one text answer; it does not invoke workout actions.

Conclusion: the operator's requested voice control is NOT IMPLEMENTED. The code has reusable workout UI and persistence, a rest timer, TTS feedback in form check, and an unused command parser, but no microphone-to-command-to-existing-action path. The intent map below completes the source trace for the reviewed touch operations and records the missing whole-workout boundaries. It also identifies the private completion callback that needs a shared action seam before voice can invoke the same operation. The earlier proposed separate authoritative runtime, journal and session collection are not justified by this evidence. If multiple persisted sets are required, extend the existing list writer and preserve or deliberately change its readers; do not create a parallel tracker by default.

The trace did not locate a whole-workout finish/cancel action in the examined `workouts`/`equipment` player and route paths; the player marks its exercise/session record complete as part of logging. The summary route is a day summary, not a workout command API. Treat whole-workout start/finish/cancel mapping as `NOT_FOUND IN THE REVIEWED PATHS` until broader evidence proves otherwise; do not map those intents onto parser labels alone.

**Shared-boundary conclusion:** timer and rest controllers are callable state seams, but starting a timer also has UI setup (load/reps capture). The current writes originate in `_MarkCompleteButton` (set completion plus a possible later rating save) and `_AddExerciseButton` (adding a screened exercise and rating before one save); both call the same `LogSessionAction`, but have different UI/precondition and update semantics. A shared voice boundary must preserve those semantics for any command it supports, not merely wrap `log()`. This is a proposal for a later authorized code sprint, not an implementation. `WorkoutSessionExercise.sets` already serializes a list; the current set-completion writer replaces it with zero/one capture. `asLogEntries()` projects one best set per exercise. `workoutSessionHistoryProvider` consumers use that projection; DayResult, progress/personal-record and weekly-volume readers iterate stored sets. The mobile export also uses `asLogEntries()`, but the account-export callable separately includes raw `users/{uid}/workout_sessions` documents in its `server.workoutSessions` section (`functions/src/account_export.ts:514-520,560-568`), subject to its named `MAX_ROWS`/byte truncation behavior. Do not add a duplicate export path by assumption; preserve the existing raw records and make any cap/read failure visibly incomplete. Source paths for these projections/readers are listed in the row above and below. If actual repeated sets are required, append each confirmed performed set to this existing list, not another store; keep the best-set projection for legacy log consumers unless product changes it. ### Follow-up source sweep for GPT-PM B-01..B-05 / M-01..M-04 (2026-10-19)

The correlated GPT-PM review (`03_DESIGN.md` §0.2) identified additional contracts. These source facts were checked locally against the checkout at `b7f4a6bd`:

- The day completion callback waits for the initial history snapshot when the day row is not yet known; it then assembles a full session from that snapshot. The Firestore repository performs a full-document `set` without a revision/transaction contract (`equipment/workout_player_page.dart:600-635,680-748`; `workouts/data/firestore_workout_session_repository.dart:61-70`). This confirms a stale-snapshot lost-update risk under concurrent writes; cross-device loss is an inferred scenario, not reproduced runtime evidence. A later design must define stale-state detection/conflict handling in the existing store and test it after coding.
- `LogSessionAction.log` returns early only while its own `AsyncValue` is loading; the persisted model has no command/set identity. That prevents some overlapping calls, not replay deduplication or safe retry after an unknown acknowledgement (`workouts/state/workout_session_providers.dart:85-110`; `workouts/data/workout_session.dart:192-219`).
- The first logged exercise sets `status: completed` and `completedAt`. This is existing exercise-log/session behavior, including scheduled-day grouping; it is not a workout-wide “finished” signal (`equipment/workout_player_page.dart:720-725`). Preserve and describe that behavior; do not introduce an implied workout lifecycle.
- After the difficulty sheet returns, the callback creates `rated` from its earlier `entry` snapshot and submits another full-session `log`. If a newer accepted write occurs during that gap, overwriting it is a plausible stale-write risk; it has not been reproduced. A shared action contract must update the selected exercise against current authoritative state (`equipment/workout_player_page.dart:786-818`).
- `weeklyVolume` counts `exercise.sets.length` from every supplied session and does not check `status`; history/export providers filter completed sessions separately. Direct volume/personal-record/day-result readers consume stored sets, while the mobile `workoutLogs` field filters completed records and expands `asLogEntries()`. The full account export separately includes raw `workout_sessions` documents under `server.workoutSessions` when returned; its row/byte caps are reported through `truncated` and there is no continuation cursor. Keep these two representations distinct and do not claim a capped export is complete (`personalisation/data/volume_ledger.dart:96-133`; `progress/data/progress_charts.dart:65-76,151-166`; `workouts/data/day_result.dart:86-129`; `data_export/data_export_providers.dart:80-96,121-124`; `data_export/server_export.dart:8-11,89-110`; `functions/src/account_export.ts:48-53,65-94,514-520,560-568,593-646`).
- The voice parser has no production dispatcher; unsupported or ambiguous intents need a no-mutation/refusal or clarification result. Timer expiry is separate from the completion callback. Scheduled-day route replacement is supported by the reviewed path; single-exercise next/previous and workout-wide start/finish/cancel remain bounded `NOT_FOUND` claims (see the intent table above).
- A scoped `rg` over `mobile/lib` found the two widget-level `LogSessionAction.log` call sites: `_MarkCompleteButton` (completion and its delayed rating resave) and `_AddExerciseButton` (append an eligible exercise, with rating before save). `scheduled_session_providers.dart` and `programme_providers.dart` save the distinct `ScheduledSession` model, not `WorkoutSession` (`workouts/state/scheduled_session_providers.dart:84-100`; `programmes/state/programme_providers.dart:389-403`).
- Export has two views: the mobile `workoutLogs` array is built from completed sessions through `asLogEntries()` (`data_export/data_export_providers.dart:88-96`; `data_export/data_export.dart:34-37,91-96`). The same user export also attaches the server callable result, whose `server.workoutSessions` includes raw Firestore documents (`data_export/data_export_providers.dart:121-124`; `data_export/server_export.dart:8-11,89-110`; `functions/src/account_export.ts:514-520,560-568`). Server output caps each legacy subsection at 2,000 rows and applies a byte-budget fit, naming affected collections in `truncated` (`account_export.ts:48-53,65-94,97-119,593-646`); `workoutSessions` has no continuation cursor. Therefore raw set records are already represented in the export when returned, but a capped export is explicitly incomplete and cannot be called full for users whose workout-session section was truncated.

No `hasPendingWrites`/snapshot metadata handling was found in the reviewed workout state/repository paths (`firestore_workout_session_repository.dart:61-70`; `workout_session_providers.dart:96-110`; `workout_player_page.dart:748-780`). ## Verified facts

- `WorkoutSession` has `id, title, exercises, startedAt, completedAt?, status, durationMinutes?, notes?` (`mobile/lib/features/workouts/data/workout_session.dart:192-219`). No revision, version, owner uid, event list or command id.
- `WorkoutSessionStatus { pending, completed, abandoned }` (`workout_session.dart:11`); nothing writes `pending` or `abandoned`; the player writes `completed` on the first set tap (`mobile/lib/features/equipment/workout_player_page.dart:724-725`). History filters on `completed` (`mobile/lib/features/workouts/state/workout_session_providers.dart:73-76`).
- A set is `SetCapture = ({double? weightKg, int? reps})` (`set_capture.dart:8`); `WorkoutSessionExercise.sets` serializes a list of these records (`workout_session.dart:29-105`). The current completion writer replaces the list with zero or one captured set per exercise (`workout_player_page.dart:671-695`). `SetCaptureSheet` opens before the set on the normal timer path and labels the reps input “Target reps”; the same value is later stored in `SetCapture.reps`, so the current value does not prove performed reps (`set_capture_sheet.dart:50-60,154-185`, `workout_player_page.dart:659-695`). Reader behavior differs: `asLogEntries()` projects one best set (weight, then reps) per exercise for consumers of `workoutSessionHistoryProvider` and data export (`workout_session.dart:339-398`, `workout_session_providers.dart:61-76`, `data_export_providers.dart:80-96`). That provider feeds Home, progress, suggestions, recovery, personalisation and equipment last-session surfaces (`home_dashboard_providers.dart:18-64`, `suggestion_providers.dart:26`, `recovery_providers.dart:14`, `personalisation_providers.dart:14-66`, `last_session_card.dart:22-55`). Day-result, direct progress metrics/personal records and volume-ledger readers iterate/count all persisted sets (`day_result.dart:86-129`, `progress_charts.dart:70-76,151-166`, `volume_ledger.dart:96-133`). A repeated-set implementation must specify which view each existing consumer is meant to expose.
- Persistence: `users/{uid}/workout_sessions/{sessionId}`, plain `doc(id).set(...)` with a 4 s timeout that swallows a late rejection (`firestore_workout_session_repository.dart:20-21,62-70`). No transaction, no revision check, no command ledger; the only double-tap guard is `if (state.isLoading) return;` (`workout_session_providers.dart:96`). A scoped search found no `hasPendingWrites` or snapshot metadata-change handling in the reviewed mobile workout paths; exact recovery/error UX remains to be traced. Offline persistence is the Firestore SDK default; no local journal.
- `set_session.dart` is a clock-free interval timer for timed sets (phases idle, gettingReady, work, rest, done; `:21-38`), not a workout state machine. `RestTimerController` uses a wall-clock `endsAt` with an injectable clock (`rest_timer_providers.dart:53-153`).
- Voice: `mobile/lib/features/voice/data/voice_command.dart` is an English-only substring parser with 12 command kinds and no production caller. `speech_to_text` is declared but never imported; `RECORD_AUDIO` is deliberately absent from `AndroidManifest.xml` (`:30-35`), to be added only with the feature, privacy text and Play declaration. TTS: `TtsVoiceCoach` (`form_check/data/tts_voice_coach.dart:22`), default `ru-RU`.
- Android: no foreground service, no `FOREGROUND_SERVICE*`, no `BLUETOOTH_CONNECT`. Impeller is disabled on the S23 Ultra (`AndroidManifest.xml:98-105`).
- AI path: callables to Vertex AI with Application Default Credentials; no API key in repo or app (`functions/src/ai_gateway.ts:34-43`). `aiCoachAdvice` is one-shot text, 40 per day, 512 output tokens, 45 s timeout (`functions/src/ai_coach_advice.ts`, `abuse_guard.ts:425`). A global server kill switch exists (`abuse_guard.ts:268-324`). No realtime, streaming or ephemeral-token surface exists.
- `features/ai_planner` is a deterministic on-device single-session builder with typed `PlanReason` codes and `PlanRefused` (`ai_planner/data/workout_plan.dart:21-68`). No multi-week plan type exists.
- Safety: `SafetyContext`, `evaluateExercise`, `allowsAnyTraining`, fail-closed `safetyContextProvider` (`safety/data/eligibility.dart`, `safety/state/eligibility_providers.dart:38-44`). No mid-session symptom stop path.
- OQ-07 sources re-read on 2026-10-18: `safety/data/eligibility.dart` gates screening, clinician advice, post-surgical restrictions and per-exercise eligibility, and composes existing intensity heuristics. `safety/data/age_policy.dart` adds age-band intensity/day heuristics. `workouts/data/progression.dart` suggests next-session weight from effort/reps; it does not define a hard maximum load/rep safety cap. These existing values are product heuristics, not signed AI Coach limits, and have no clinical-validation claim here.
- Health answers are device-only; Firestore rules strip them (`firestore.rules:209-250`), so a server orchestrator cannot read contraindications.
- Rules: `users/{uid}/{coll}/{document=**}` owner wildcard, `workout_sessions` not excluded, no schema or revision fence (`firestore.rules:83-127`). Patterns to copy: activity `rev` fence (`:989-1007`), `nutrition_plan` `planVersion + 1` (`:714`), closed-schema helpers.
- Conventions: Riverpod 2.6, go_router 16, `features/<name>/{data,state,widgets}`, repositories overridden in `main.dart:434-435`, injectable clocks, callable pattern with injectable `CoachAsk`.

- **`ai_planner`** — `buildPlan` in `mobile/lib/features/ai_planner/data/plan_builder.dart` is a pure synchronous function. Required inputs are a candidate exercise pool, weekly deficit map, `DeloadVerdict` and `SafetyContext`; optional inputs include cycle state/self-report, target minutes, recommendation hints and `TrainingContext`. It returns `PlanReady(GeneratedPlan)` or `PlanRefused`; `GeneratedPlan` is a single session with exercises, intensity factor and typed reasons, not a multi-week plan. `generatedPlanProvider` in `mobile/lib/features/ai_planner/state/ai_planner_providers.dart` resolves auth/profile, safety, deficit, deload, context and equipment repository inputs before calling it.
- **`training_context`** — `mobile/lib/features/training_context/data/training_context.dart` defines gym, outdoor-minimal, home and yoga contexts; pure helpers derive equipment access, narrow candidates, preserve safety fields and apply shared eligibility. `mobile/lib/features/training_context/state/training_context_providers.dart` stores the user's answer in per-UID SharedPreferences and exposes Riverpod providers. This is local context/filtering, not a server or model API.
- **`recovery`** — `detectDeload` in `mobile/lib/features/recovery/data/deload_detector.dart` takes recent workout logs, scheduled sessions and optional HRV averages/time, and returns a typed verdict with signal codes and a volume factor. `deloadVerdictProvider` in `mobile/lib/features/recovery/state/recovery_providers.dart` currently supplies logs and scheduled sessions in a rolling 14-day lookback but no HRV. A separate explicit `acceptNext7Days` action changes eligible pending scheduled sessions; the action is not part of the pure detector. Neither defines projecting a verdict across later weeks.
- **Visual equipment boundary** — `VisualEquipmentService.classifyFile` returns ranked `VisualMatch` values with confidence; the inspected planner provider builds its pool from equipment repository entries, not classifier output. A visual match therefore is not confirmed equipment access under the current interface.
- **`visual_equipment`** — `VisualEquipmentService.classifyFile` in `mobile/lib/features/visual_equipment/data/visual_equipment_service.dart` accepts a file path and optional top-K limit and returns `VisualMatch` values (catalog equipment id, confidence, optional label and source). The controller can combine printed-text recognition, classifier fallback and a separate describer. This is equipment-photo recognition; no current live-coach API or caller was found in the reviewed interfaces.
- **Integration limit** — these are existing mobile seams, not proof of a live-coach integration. A multi-week deterministic composer and its weekly progression/set-rep-rest and projected-volume rules remain new design work; do not assign that selection to the model or infer it from `buildPlan`.

## Risks and gaps

- Two writers (voice and UI tap) race with last-write-wins and no revision; the swallowed timeout means `save()` returning is not confirmation.
- No durable local command journal; a live session written as `completed` would count toward history, streaks and progression at once.
- `asLogEntries()` exposes only the best set to consumers of `WorkoutLogEntry`, while direct session readers can consume all sets; changing repeated-set capture or projections can make history/recovery/export disagree with volume analytics.
- Safety input exists only on the device; either the device approves every model proposal or minimal derived flags are sent (privacy decision needed).
- The voice runtime is a greenfield native build (manifest, foreground service type, permissions, audio focus, Bluetooth, Play declaration, privacy text).
- AI quota is request-count based; a stream needs session-minute cost control.
- Prompt-injection mitigation today is explicitly partial; tool calling on workout state widens the surface.
