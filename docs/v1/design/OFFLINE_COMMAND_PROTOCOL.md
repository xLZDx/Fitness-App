## 1. Scope and non-goals

### 1.1 In scope
- DECISION: exactly three commands use this protocol: CompleteSet (modes APPEND and CORRECT), AddEligibleExercise, SetDifficulty. Touch and voice produce the same command through one local entry point (LOCAL_QUEUE_DECISION criterion 10).
- DECISION: the protocol covers the client queue, the server apply transaction, receipt and fence storage, ordering, conflicts, the writer credential, version compatibility and the legacy-writer migration with preservation of legacy writes.

### 1.2 Non-goals
- FACT: StartSet is not queued and creates no queue entry, no receipt and no completed-set fact (`docs/v1/VOICE_READY_PROMPT_DECISION.md`, section "StartSet is not CompleteSet"; acceptance FU-AC-101 in `package-amendments/ACCEPTANCE_AMENDMENTS.csv`). This document never treats StartSet as a command.
- DECISION: not covered here, each needs its own contract: sign-out sheet, account deletion, export and backup UI (criteria 11 to 14; only the protocol hooks they need are named in 3.9), multi-writer collaboration (ADR-CMD-04 stays one writer), set deletion, ScheduledSession and programme writers, AI intent parsing.
- DECISION: no new online admission step. The package `prepareWorkoutCommand`, `applyWorkoutCommand`, `resolveAndCloseCommand` endpoints, the admission token, the 2-minute `admissibleUntil`, and "birth epoch" closure are withdrawn for these three commands (see 2.4 and 5.1).

### 1.3 Code facts that shape the design
- FACT: today a whole `WorkoutSession` document is written with `doc(id).set(session.toJson())` (no merge) and a 4 second timeout whose `onTimeout` handler returns normally, so a missing server acknowledgement is hidden; the code comment states that "a genuine server rejection after the timeout is not reported to this caller" (`mobile/lib/features/workouts/data/firestore_workout_session_repository.dart`, lines 61 to 71). Delete is a plain `await ...delete()` with no timeout (same file, lines 73 to 76).
- FACT: `WorkoutSession.toJson` emits only the known fields `id`, `title`, `exercises`, `startedAt`, `completedAt`, `status`, `durationMinutes`, `notes`; a session stores `sets` as a list of `{weightKg, reps}` with no set id, no revision and no writer field (`mobile/lib/features/workouts/data/workout_session.dart`, lines 52 and 70 to 81 and 242 to 251). So a legacy whole-document write drops any extra field a server added.
- FACT: the player writes at most one set per exercise per session and a repeat tap overwrites it (`mobile/lib/features/equipment/workout_player_page.dart`, lines 632 to 636). A day session id is deterministic, `day_{dayId}` (same file, lines 81 and 664 to 666); a free session id is `{microsecondsSinceEpoch}_{sessionKey}` and is created on the client (same file, line 666).
- FACT: rest starts only after the save future completes and the error check passes (`workout_player_page.dart`, lines 730 to 736 and 973 to 977). Under this protocol "persist" means the local durable commit of 3.3.
- FACT: `firestore.rules` lines 61 to 83 give the owner read and write on every `users/{uid}/{coll}/...` collection except a named carve-out list; `workout_sessions` is not in the list, so the owner can write it directly today.
- FACT: a search of `functions/src` (excluding test folders) for "workout" found only `abuse_guard.ts`, `account_export.ts`, `scaling.ts`, `video_urls.ts`; no workout command callable was found. Their content was not inspected beyond that. UNKNOWN: whether any of them writes `workout_sessions`.
- UNKNOWN: the local storage engine available in the Flutter app (needs a transactional store with unique indexes); the platform secure storage and its backup behaviour; the deployed Cloud Functions runtime and whether Firestore document triggers with retry are usable there; whether Firestore TTL policies are enabled; whether the app has a minimum-version gate.

## 2. Identity model (canonical)

### 2.1 Identifiers
| Name | Definition | Created by | Mutable |
|---|---|---|---|
| `operationId` | 30 characters: `uidTag` (8 characters, base64url of the first 6 bytes of `SHA-256("u1|" + uid)`) followed by 22 characters, base64url of 16 CSPRNG bytes (128 bit random part). Matches the package id pattern `^[A-Za-z0-9_-]{1,128}$` | client, inside the atomic acceptance commit (3.3), before any network call | never |
| `uid` | Firebase Auth UID active at acceptance | client reads the signed-in UID; the server trusts only the authenticated UID | never |
| `sessionId` | existing scheme: `day_{dayId}` or the client-generated free id | client (FACT, 1.3) | never |
| `sessionGeneration` (hashed) | the generation of the logical session this command belongs to, as the client OBSERVED it. A client that observed nothing uses 1. A client that observed a deletion of generation g (from a server answer or a synced view, 5.5) and starts a new workout on the same id uses g + 1. It is never changed after acceptance and no server answer restamps it | client | never |
| `acceptedEpoch` (hashed) | the writer epoch the client knew when it accepted the record; 0 if it had never synced the session. For ordering and guards 0 is read as 1 | client | never |
| set identity | `(exerciseId, setIndex)` inside a session, written `logicalSetId = {sessionId}:{exerciseId}:{setIndex}`; `setIndex` integer 1..1000 is the index of the player's CURRENT set context for that (session, exercise) (3.3), not "the next free index". Every lookup, precondition and guard key uses the full set identity (M-03) | client | never |
| `setId` in the body | derived display value `set_` plus `setIndex` zero-padded to 4 digits (keeps the shape of `COMMAND_GOLDEN_VECTORS.json` `set_0001`). It is NOT unique across exercises and is never used as a key | client | never |
| `seq` | integer, strictly increasing per (uid, sessionId, originDeviceInstallId), from a persistent counter row that is never derived from remaining records and never pruned with them. It is the accepted ordinal of that device in that session; gaps left by discarded commands are preserved and never renumbered. Used for delivery order, for the exercise order key (6) and for the server guard (4.2 step 6g); NOT for display of sets | client, in the acceptance commit | never |
| `dependsOn` | sorted list of at most 3 `operationId` (canonical; a single predecessor is not enough): the session-creating operation, the AddEligibleExercise operation for this exercise, and (for a CORRECT) the APPEND of the same set, each only while it is not yet `SYNCED` | client | never |

- DECISION: the package `clientIntentId` and the server-minted `commandId` collapse into the single client-generated `operationId`. A retry, a restart and a reconnect reuse the same bytes (LOCAL_QUEUE_DECISION criterion 4).
- DECISION: the `uidTag` makes an `operationId` valid only under the UID it was minted for, statelessly. The server rejects an id whose tag differs from the tag of the authenticated UID (`ID_UID_MISMATCH`, 4.3 I6) without a global id registry.
- DECISION: a user-initiated re-submission after a terminal conflict (7.2) is a new intent with a new `operationId` and a `supersedes` link kept locally. This does not violate criterion 4: criterion 4 forbids changing the id on transport retry, not creating a new intent after the user explicitly resubmits.

### 2.2 Canonical payload and hash (hashVersion 2)
- FACT: version 1 hashes `expectedRevision`, `writerEpoch` and `sessionGeneration` inside the payload (`registers/COMMAND_GOLDEN_VECTORS.json`, payload objects; `registers/API_CONTRACTS.json` schemas `CompleteSet`, `SetDifficulty` require them).
- DECISION: an offline command cannot know the server revision or the current writer epoch at execution time, so version 2 removes `expectedRevision` and `writerEpoch`. `sessionGeneration` stays hashed (it is immutable by 2.1) and `acceptedEpoch` is added. Version 1 vectors stay valid for the withdrawn online endpoints only; new version 2 golden vectors must be generated and checked in Dart and on the server before implementation (NOT_RUN).
- DECISION: hashed canonical object (keys in recursive lexicographic order, UTF-8, no whitespace, integers only, explicit `null` for nullable fixed fields, unknown keys rejected, same rules as `API_CONTRACTS.json` `x-canonicalization`):

```
{ protocolVersion: 2, hashVersion: 2, limitsVersion: 1,
  operationId, uid, sessionId, originDeviceInstallId, sessionGeneration, acceptedEpoch, seq,
  dependsOn: [operationId...],
  exerciseId, operation,
  logicalSetId: string | null,
  sessionInit: { titleKey, dayId | null, startedAtClientMs } | null,
  body: <operation body of API_CONTRACTS.json, see below> }
```
- DECISION: `body` for CompleteSet is the package body (`mode`, `setId`, `performedConfirmed`, `actualReps`, `actualRepsConfirmed`, `targetReps`, `loadGrams`, `source`) plus `performedAtClientMs` (integer, ms since epoch, informational, see 9). AddEligibleExercise and SetDifficulty bodies are unchanged from the package.
- DECISION: `sessionInit` is non-null only on the operation that creates a logical session (the first accepted operation for a session the client has not observed on the server, or the first operation of an explicit new-session intent); it carries what `WorkoutSession` requires on creation (FACT: `title` and `startedAt` are required, `workout_session.dart` lines 193 to 202). PI-M06: the queue never carries free text. `titleKey` is a closed-set key (`day:{dayId}`, `plan:{planId}` or `default`) from which the server derives the stored `title` from the catalogue; a title typed by the user is not one of the three queued operations and stays an ordinary online edit outside this contract. Any other string is `INVALID_PAYLOAD`.
- DECISION: `payloadHash` = lowercase hex SHA-256 of the canonical bytes. The client stores the canonical bytes verbatim in the queue record and always sends those bytes; it never re-serializes (except the rebuild path of 2.5).
- DECISION: binding to identity: the hash covers `operationId`, `uid`, `sessionId` and `originDeviceInstallId` (PI-M02), so a payload cannot be re-labelled to another id, account, session or origin install without changing the hash. The scope label of `seq` in the guard of 4.2 step 6g is the HASHED value; there is no envelope copy to mutate.

### 2.3 Envelope (sent with the payload, not hashed, not stored in the queue record)
`{ payloadBytes, payloadHash, writerProof, writerEpochClaim, deviceInstallId, clientBuild }` - DECISION. The origin install of the record is read from the hashed payload (2.2), never from the envelope.
- `writerProof` is the secret writer token of 8.1, read at send time from platform secure storage keyed by (uid, sessionId). It is NEVER written into the queue record, the canonical bytes, an export or a log.
- `writerEpochClaim` and `deviceInstallId` are informational (display, audit, diagnostics). They carry no authority: the server decides only by `writerProof` (4.2 step 6b).
- The server recomputes the hash from `payloadBytes`; it never trusts a client-supplied hash, role, UID or time.

### 2.4 What the server mints (answer to B-01 of the package review)
- DECISION: the server mints no identity before the effect. It mints only: `serverTime`, `revisionBefore`/`revisionAfter`, the receipt (whose id equals `operationId`) and the writer token at takeover (8.1). Nothing in this list gates local acceptance, so the package conflict (an online `prepare` that mints id, token and 2-minute expiry before the effect) no longer exists for these commands.
- DECISION: what the package token bound (UID, device session, account epoch, session writer epoch, session generation, payload digest) is instead checked inside the apply transaction at apply time (4.2). The authority is the authenticated caller plus the writer credential plus current server state, not a pre-issued admission token. This is not weaker than today: FACT, the owner can already write `workout_sessions` directly (`firestore.rules` lines 61 to 83); the new path adds validation.
- DECISION: there is no server-side maximum command age. A command accepted 30 days ago (LOCAL_QUEUE_DECISION criterion 3) is applied if the session state allows it. Age never makes a command inadmissible; only a fence hit (5.2) or a session rule (7) can refuse it (see the outcome table 3.7).

### 2.5 Version compatibility of queued commands
A queue entry can outlive the app build that wrote it (criterion 3: no eviction by age). DECISION rules:
1. The queue record stores, besides `canonicalBytes`, the structured fields of the command (`payloadFields`, the typed values before canonicalization) and `protocolVersion`, `hashVersion`, `limitsVersion`.
2. The server accepts every shipped `(protocolVersion, hashVersion, limitsVersion)` triple. A triple may be retired only after the minimum-version gate (8.6, P1) forces all clients to a build that can rebuild records; until then it is supported.
3. After retirement, the server resolves the fence first (the hash is computed over the received bytes, no parsing of the old schema is needed). A fence hit returns I2/I3 as usual. A fence miss proves the command was never applied (F1), so the server returns non-terminal `VERSION_RETIRED`.
4. On `VERSION_RETIRED`, and on app start after an upgrade, the client rebuilds every record with `maybeSent = false` or `VERSION_RETIRED` from `payloadFields` under the current version, keeping the same `operationId`, `sessionGeneration`, `acceptedEpoch`, `seq` and `dependsOn` (safe because a miss in the fence proves no effect exists). A record with `maybeSent = true` keeps its original bytes and is sent unchanged; the server must answer it from the fence even if the version is retired.
5. All limits (1000 reps, 1,000,000 grams, setIndex 1..1000, 500 queue cap, batch 25, `dependsOn` 3, session limit 2,000 resolved operations) are frozen in a `limitsVersion` table before release; changing one needs a new `limitsVersion`, and the old one stays accepted.
6. CI obligation: a golden queued payload produced by the oldest shipped client build is replayed against the current server on every release; the build fails if the answer is not the one in the golden file (FU-AC-095 (f)).

### 2.6 Privacy note on the uidTag
DECISION: the 48-bit `uidTag` inside every `operationId` is a pseudonym of the UID (a truncated hash that can be recomputed by anyone who knows a candidate UID). Therefore `operationId` is pseudonymous personal data: it is allowed in the UID-scoped Firestore documents and in the device queue; it must not be used as a metric label (4.6), must not be written to shared logs above debug level, and must be included in the data export and deleted with the account like the fence and receipts. The random 128-bit part carries no user information. The writer token (8.1) is a secret, not an identifier, and is never exported.

## 3. Local queue (canonical contract)

### 3.1 Record schema
One record per command, keyed by `(uid, operationId)`. DECISION; this is the only queue schema, and the export entry, the sender, the local store and the server protocol layer all use these field names:

| Field | Meaning | Mutable |
|---|---|---|
| `uid`, `operationId`, `sessionId`, `exerciseId`, `operation` | identity | no |
| `sessionGeneration`, `acceptedEpoch`, `seq`, `dependsOn[0..3]`, `logicalSetId` | ordering and dependency, part of the hash | no |
| `canonicalBytes`, `payloadHash`, `payloadFields`, `protocolVersion`, `hashVersion`, `limitsVersion` | payload; `canonicalBytes` and `payloadFields` are erased at acknowledgement (3.6) | rebuild of 2.5 only |
| `state` | one of the seven states of 3.2 | yes |
| `heldReason` | when `state = HELD`: `PREDECESSOR_UNRESOLVED` or `PREDECESSOR_CONFLICTED` | yes |
| `conflictKind`, `conflictTerminal` | when `state = CONFLICTED`: the code of 7.1, and whether it is terminal | yes |
| `maybeSent` | true from the commit that moves the record to `SENDING`, never reset | yes |
| `attempts`, `lastAttemptLocalMs`, `lastResultCode` | diagnostics | yes |
| `originDeviceInstallId` | the install that accepted the record; part of the hash and the scope of `seq`; informational after a restore, never a transport identity or authority | no |
| `intentKey` | opaque id of the user event that produced the record: the UI event id of a tap, or the id of a final recognition result. Required on every CompleteSet record | no |
| `ackSummary` | revisionAfter, serverTime, `detailExpired`, `superseded`; set when `SYNCED` | yes |
| `supersedes` | `operationId` of a record this one replaces after an explicit user resubmission (2.1), or null | no |
| `discardSource` | set when `state = DISCARDED`: `USER_DISCARD` (explicit discard, T14 or T17), `SIGNOUT_REMOVE` (the sign-out "remove" outcome, T17: after a snapshot-confirmed export, or, after the explicit confirmation naming the count, without any file, in which case `exportedAt` is null) or `SUPERSEDED_RESUBMIT` (replaced by the user's resubmission, T5). Also stored: `exportedAt` (null if never exported), the final `maybeSent` and `serverStateUnknown` (true when `maybeSent` is true and no server answer for this record was ever received; this is the only place the field lives on a record, and the `effective_set` marker mirrors it) | yes (once) |
| `acceptedAtLocalWallMs`, `acceptedAtMonotonic` | informational only (aging uses 3.8) | no |

Secrets (the writer token) are not fields of the record (2.3).

Local unique indexes (DECISION), enforced by the store: `(uid, operationId)`; `(uid, sessionId, originDeviceInstallId, seq)`; `(uid, intentKey)` for CompleteSet records; and `(uid, logicalSetId)` for `operation = CompleteSet` and `mode = APPEND` and `state` not `DISCARDED`. The `logicalSetId` and `intentKey` indexes are the last line of defence; the primary protection against a second APPEND is the set-context rule of 3.3, because "next free index" would never collide with the index.

Separate local tables (DECISION), none of them pruned with records:
- `session_seq(uid, sessionId, originDeviceInstallId, nextSeq)`;
- `set_context(uid, sessionId, exerciseId, currentSetIndex)`;
- `effective_set(uid, sessionId, exerciseId, setIndex, appendExists, syncedValues, effectiveValues, anchorOperationId)`: one row per set the device has ever logged. `syncedValues` are the values of the last acknowledged APPEND/CORRECT; `effectiveValues` are the values of the newest non-discarded, non-terminal-conflicted pending CORRECT or APPEND, else `syncedValues`. The row is updated in the same local transaction as every acceptance, acknowledgement, discard and terminal conflict. The row has two parts (3.6): the identity marker survives pruning of the records AND the discard or sign-out "remove" of records (T17) and is deleted only with the account, so the set-context rule can never create an APPEND for a set the server already holds; `syncedValues` and `effectiveValues` are workout values and are erased when a record of that set is discarded or removed;
- `intent_keys(uid, intentKey, operationId, acceptedAt)`: kept for at least 30 days, independent of record pruning;
- `session_sender_state(uid, sessionId, hold, nextProbeAt)` (3.5);
- `observed_generation(uid, sessionId, generation, deletedGeneration)`: the last generation and deletion the client observed from server answers or synced views (5.5).

### 3.2 States and transitions
Canonical state names (DECISION). `ACCEPTED`, `SENDING`, `UNKNOWN_EFFECT`, `HELD`, `SYNCED`, `CONFLICTED`, `DISCARDED`. The first, second, third, fifth and sixth correspond to the names PENDING, SENDING, UNKNOWN_EFFECT, HELD_BY_PREDECESSOR and CONFLICT used by the queue lifecycle document draft; the mapping is in 3.11.

| State | Meaning | Counts toward the 500 cap |
|---|---|---|
| `ACCEPTED` | committed locally, eligible to send, no send attempt yet in progress | yes |
| `SENDING` | a send attempt is in flight | yes |
| `UNKNOWN_EFFECT` | a send attempt ended without an answer (timeout, transport error, process death): the server may or may not have applied it; resend the same bytes | yes |
| `HELD` | not sent because a command in `dependsOn` is not `SYNCED` (3.4) | yes |
| `SYNCED` | server answered `COMMITTED`, `ALREADY_COMMITTED`, `ALREADY_COMMITTED_DETAIL_EXPIRED` or `SUPERSEDED` | no |
| `CONFLICTED` | the server refused it (terminal), or a non-terminal hold needs user action (7) | yes |
| `DISCARDED` | the user explicitly discarded it after export, or confirmed discard naming the count | no |

| T16 | `SYNCED`, `DISCARDED` | 7 days after acknowledgement or after the discard | (stub removed) | 3.6 |
| T17 | `ACCEPTED`, `SENDING`, `UNKNOWN_EFFECT`, `HELD`, `CONFLICTED` (non-terminal) | user discard (explicit confirmation naming the number of commands, criterion 12), or the sign-out "remove" outcome | `DISCARDED` | the payload is erased and a stub kept (3.6). Preconditions per source state: `ACCEPTED`, `HELD`, non-terminal `CONFLICTED`: a snapshot-confirmed export of the record first (criterion 12: export then discard), unless the explicit discard confirmation of criterion 12 is given; `SENDING`: only after the send lease fence has cancelled the in-flight send, and if the cancellation cannot be proven (the request may be on the wire) the record first moves to `UNKNOWN_EFFECT` by T10 and is treated as such; `UNKNOWN_EFFECT` (M-05 of round 2, one rule): the default path exports the record first and tries to resolve its outcome (`getWorkoutCommandOutcomes`) when the network allows; if the outcome is resolved, the record is treated by its real result and the question is moot. Removal WITHOUT an export is allowed only through the explicit confirmation naming the count and carrying the distinct warning "this entry may already be saved on the server; removing it deletes only the copy on this phone and does not undo anything the server did; the server result stays unknown"; the stub keeps `maybeSent = true` and `serverStateUnknown = true`, so the UI never claims that nothing was saved anywhere |

Sources of `DISCARDED` (DECISION): the stub records the source in `discardSource` so that the three origins are distinguishable: `USER_DISCARD` (T14 and T17 by an explicit discard), `SIGNOUT_REMOVE` (T17 by the sign-out "remove" outcome, with a snapshot-confirmed export or, for the no-file path with the explicit count confirmation, with `exportedAt = null`), `SUPERSEDED_RESUBMIT` (T5). Discard of a terminal `CONFLICTED` record is T14; discard of a non-terminal one is T17. A discarded record is never sent again and is not counted toward the 500 cap.

`UNKNOWN_EFFECT` records count as eligible for sending exactly like `ACCEPTED`. `ACCEPTED`, `SENDING`, `UNKNOWN_EFFECT`, `HELD` and `CONFLICTED` are never removed by age or size (criterion 3).

### 3.3 Atomic durable acceptance and the set-context rule (criterion 2, criterion 5)
DECISION: acceptance first ensures the writer token for the session exists in secure storage (generated locally, 32 random bytes, only if none exists for (uid, sessionId); if secure storage fails the acceptance fails with "not saved"), then runs ONE transaction of the local store that does all of the following or nothing:
1. read the count of records in `ACCEPTED`, `SENDING`, `UNKNOWN_EFFECT`, `HELD`, `CONFLICTED` for the UID; refuse with a visible message if it is 500 (criterion 3); raise the warnings of 3.8;
2. for a CompleteSet intent, apply the set-context rule:
   - intent dedupe first: if `intent_keys` already holds the intent's `intentKey`, create nothing and return the existing record. This holds across context changes: a late duplicate of the same recognition result or the same tap event, delivered after the user pressed "next set", cannot create a phantom APPEND at the next index;
   - otherwise let `i = set_context.currentSetIndex` for (session, exercise) (default 1) and read `effective_set` for index `i`:
     - no row: create an APPEND at `i` and insert the row;
     - row exists with `appendExists = false` (the discarded APPEND had `maybeSent = false`, so the server cannot hold the set): treat as no row, create a new APPEND at `i`, subject to the intent dedupe above, and set `appendExists = true`; a marker with `appendExists = true` (including `serverStateUnknown = true`) never permits an APPEND, only a CORRECT;
     - row exists with `appendExists` but its values were erased (3.6): create a CORRECT for set `i` and store the new values; no comparison is possible;
     - row exists with `appendExists` and the APPEND is not terminal-conflicted: compare the new values (all body fields except `performedAtClientMs` and `source`) with `effectiveValues`, the LATEST effective values (newest non-discarded CORRECT, else the APPEND, else `syncedValues`, never the first APPEND):
       - equal: create nothing and return the record that holds those values; the rest timer is not restarted;
       - different: create a CORRECT for set `i` (dependsOn the APPEND only while that is not `SYNCED`) and set `effectiveValues` to the new values. So X, then Y, then X again produces APPEND(X), CORRECT(Y), CORRECT(X): last intent wins and the set ends as X;
     - the anchoring APPEND is terminal-conflicted: create nothing; the UI offers the resolution of 7.2.
   - `intent_keys` gets the new key in the same transaction (also when the result was a no-op).
   A synced APPEND that was pruned after 7 days leaves its `effective_set` marker (and, unless a discard erased them, its values), so a later tap with new values produces a CORRECT, never `DUPLICATE_LOGICAL_SET`.
   The index advances only through the explicit "next set" action, which updates `set_context` in its own local transaction. DECISION: when the "next set" UI is absent, which is v1 behaviour today because the player has one set per exercise (FACT 1.3), the context stays at the current set: a repeat tap with identical values is a no-op and with different values a CORRECT; a genuine second identical set needs the explicit action. UNKNOWN: the UI for "next set". Every multi-set test below is gated on that UI existing;
3. allocate `seq` from `session_seq`; compute `sessionGeneration` (from `observed_generation`: the observed current generation, or observed deletedGeneration + 1 only for an explicit new-session intent of 7.2, else 1) and `acceptedEpoch`; compute `dependsOn`; generate `operationId` (with `uidTag`); build and store the canonical bytes, `payloadFields` and the hash;
4. insert the record in state `ACCEPTED`, or `HELD` if any dependency is not `SYNCED` (T1/T2).
Only after the transaction reports commit may the UI show "pending sync" or start the rest timer. A failed or interrupted transaction leaves nothing and the UI reports "not saved". No network call happens before the commit. Because the whole rule runs inside one store transaction, two taps 100 ms apart, or the same voice recognition result delivered twice, are serialized and the second sees the first. UNKNOWN: the storage engine and its durability setting must be chosen and shown by FU-AC-093.

### 3.4 Dependencies and HELD (M-04, criterion 6 literally)
DECISION: one rule, applied identically on the client (here), on the server (4.2 step 6d) and in section 6.
- Representation: `dependsOn` is a list of at most 3 `operationId`, immutable, part of the hash. The longest legitimate chain is session-creating operation, AddEligibleExercise, APPEND (for a CORRECT).
- A record is `HELD` while any record in its `dependsOn` is not `SYNCED`. It is released automatically only when ALL of them are `SYNCED` (T3).
- If a dependency becomes terminal `CONFLICTED` or `DISCARDED`, the dependent stays `HELD` with reason `PREDECESSOR_CONFLICTED` and is NEVER sent and never applied, until the user resolves the chain (T5, 7.2). This is the literal reading of LOCAL_QUEUE_DECISION criterion 6: the dependents of a conflicted predecessor are held as "could not sync" and not applied.
- A predecessor that is a legitimate no-op is not a conflict: an AddEligibleExercise for an exercise that already exists with identical content is answered `COMMITTED` with `effect: NOOP_IDENTICAL` (I11), the record becomes `SYNCED`, and its dependents are released. Only a different-content re-add is the terminal `EXERCISE_ALREADY_IN_SESSION`, which holds its dependents.
- The server enforces the same rule as defence in depth: a dependency absent from the fence gives non-terminal `DEPENDENCY_PENDING`; a dependency with fence code `R` or `S` gives terminal `DEPENDENCY_REJECTED` and the dependent is not applied (the server never evaluates a dependent against "what happens to exist anyway").
- Records that do not list a failed command in `dependsOn` are independent and keep syncing.

### 3.5 Sender, holds and probes
- DECISION: one sender per UID. Per session, at most one request in flight (concurrency limit, not a blocking rule). Different sessions may run in parallel. A batch call carries up to 25 consecutive eligible records (state `ACCEPTED` or `UNKNOWN_EFFECT`) of one session in `seq` order (4.5).
- DECISION: what blocks what. A terminal conflict, a C4 client-defect result (including `INVALID_PAYLOAD`) or any record-level hold blocks ONLY the records that list it in `dependsOn` (they become `HELD`); independent later records are still sent. Only a session-level hold (`NOT_WRITER`, `MIGRATION_HOLD`, `AUTH_REVOKED`, `ACCOUNT_DELETING`, `RATE_LIMITED`, `SESSION_COMMAND_LIMIT`) stops the session's send loop, recorded in `session_sender_state`, because every further record would get the same answer.
- DECISION: backoff on retryable errors is exponential from 2 seconds with jitter, capped at 5 minutes, reset on connectivity change and on app foreground; it never changes the bytes and never gives up (no attempt limit).
- DECISION (hold exit): a session-level hold is never permanent. While a hold is active the sender probes by sending the first eligible record of the session (no separate probe message), with backoff starting at 30 seconds, doubling to a cap of 15 minutes, with full jitter, and honouring a server `retryAfter` when it is larger. The backoff resets on app foreground, connectivity change and sign-in. The first answer that is not a hold clears the hold and every record of the session returns to normal sending automatically, with no user action. Per code: `MIGRATION_HOLD`, `RATE_LIMITED`, `ACCOUNT_DELETING` probe as above; `AUTH_REVOKED` does not probe until sign-in; `NOT_WRITER` probes only on foreground to read `sessionState` and exits by takeover (7.2); `SESSION_COMMAND_LIMIT` exits only by the user action of 7.2.
- DECISION (unknown codes): any result code the client does not know (a newer server or protocol) is treated as a retryable session hold: the record stays `ACCEPTED`, is never marked `SYNCED` and never terminal, a local counter is raised and the alert of 4.6 fires.

### 3.6 Acknowledgement and pruning
DECISION (reconciles "removed after durable ack" with "kept 7 days"):
- At acknowledgement (T7) the record's `canonicalBytes` and `payloadFields` are erased in the same local transaction that sets `SYNCED` (data minimisation; the content is now on the server). The remaining stub holds identity, state, `sessionId`, `exerciseId`, `operation`, `logicalSetId`, `seq`, `dependsOn`, `ackSummary`.
- The stub is kept 7 days for display and support (so a dependent's `dependsOn` can still be resolved), then removed (T16). A `dependsOn` entry that is no longer found in the queue is treated as `SYNCED`: dependents are released at the moment of the acknowledgement, long before pruning.
- `DISCARDED` stub (DECISION): at T14/T17/T5 the record's `canonicalBytes` and `payloadFields` are erased in the same local transaction (the content lives in the confirmed export, or on the server, or in the superseding records). The stub keeps identity, `sessionId`, `exerciseId`, `operation`, `logicalSetId`, `seq`, `dependsOn`, `discardSource`, `exportedAt`, final `maybeSent`, `serverStateUnknown`. Its lifetime is the same 7 days as the `SYNCED` stub (T16). The `operationId` (and the `intentKey` of a CompleteSet) stays in `intent_keys` for the `intent_keys` retention window (at least 30 days), so a late duplicate of the same user event cannot resurrect a discarded command as a new one.
- `effective_set` is split in two parts (M-01 of round 2, one schema for protocol, lifecycle, FU-AC-125 and FU-AC-128). IDENTITY MARKER: `(sessionId, exerciseId, setIndex)`, `appendExists`, `serverStateUnknown`; it holds no workout value and is kept after discard and sign-out "remove" so that a later tap can never create a second APPEND for a set the server may already hold. VALUES: `syncedValues` and `effectiveValues` (workout payload); they are ERASED, in the same local transaction, whenever a queue record of that set is discarded (T5, T14, T17) or removed by sign-out, and with the account (8.7). Remove and discard delete queue RECORDS and the values, never the markers; markers are deleted only with the account. Refinement so that a marker never claims more than the device knows: if a discarded APPEND had `maybeSent = false` (the server cannot hold it) its marker reverts to `appendExists = false`; if it had `maybeSent = true` or was `SYNCED`, the marker keeps `appendExists = true` with `serverStateUnknown = true` when the outcome was never resolved. With the values erased, the set-context rule of 3.3 cannot compare values: a tap on a set whose marker has `appendExists = true` and no values always creates a CORRECT (never an APPEND, never a silent no-op); if the server turns out not to hold the set, the CORRECT ends as the visible terminal conflict `SET_NOT_FOUND` (7.2). Markers are UID-keyed device data, excluded from backup (3.9), and contain no workout value.
- Pruning never touches `session_seq`, `set_context`, the `effective_set` markers, `intent_keys` or `observed_generation`, and never touches any record in a non-`SYNCED`, non-`DISCARDED` state.

### 3.7 Outcome of an old command (single table)
No outcome depends on a client-side or server-side "too old" rule. DECISION:

| Situation | Outcome |
|---|---|
| Never sent, any age (1 day, 31 days, 100 days) | stays eligible (or `HELD`); sent when the session hold allows; the server applies it once if the session rules allow (7.1). There is no "too old" conflict |
| Aging warning at 25 days and the 400-record warning | UI warning only (3.8); never an eviction or a state change |
| Sent, answer lost, replay while the detail receipt exists (90 days) | `ALREADY_COMMITTED` -> `SYNCED` |
| Sent, answer lost, replay after the detail receipt expired | `ALREADY_COMMITTED_DETAIL_EXPIRED` -> `SYNCED` (this is the case the lifecycle draft calls `OUTCOME_EXPIRED` for a committed command) |
| Earlier terminally refused, replay after expiry | `ALREADY_REJECTED` with `reason: UNAVAILABLE` -> `CONFLICTED` (terminal) |
| Earlier superseded, replay after expiry | `SUPERSEDED` -> `SYNCED` with `superseded` flag |
| No fence entry but the server cannot prove the command was never applied (operations from before this protocol, partial restore) | `OUTCOME_UNKNOWN_REPLAY_CLOSED` -> `CONFLICTED` (terminal); never applied |

### 3.8 Honest status and warnings (criterion 8)
- DECISION: UI states map as: `ACCEPTED`/`SENDING`/`UNKNOWN_EFFECT`/`HELD` = "saved on this device, waiting to sync" (HELD adds the reason); `SYNCED` = "synced", except `superseded` which shows "replaced by a newer change"; `CONFLICTED` = "could not sync". "Synced" is shown only from a server answer of classes C1 or C2 (4.4). Local pending data is excluded from history, progress, coach replies and exports as canonical fact until `SYNCED` (FU-AC-099), but is included in the device-only part of the export snapshot (criterion 14). Any record held (CONFLICTED non-terminal, or a session-level hold) for more than 24 hours shows a persistent banner.
- DECISION (aging warning): the 400-record warning is computed in the acceptance transaction. The 25-day warning uses an age computed as `max(wallNow - acceptedAtLocalWallMs, monotonicAge)`, where `wallNow` is replaced by a persisted non-decreasing wall-clock high-water mark `wallHigh = max(wallHigh, wallNow)` written at every app start and every acceptance. Once raised the warning is latched in persistent storage (`ageWarningRaisedAt`) and cleared only when no non-`SYNCED` record older than 25 days remains. A clock moved backwards, a reboot or a process restart cannot hide or reset it. The stronger warning copy shown at 30 days (the lifecycle document's LQ-3, from LOCAL_QUEUE_DECISION criterion 3) is a UI-only addition on top of this latched 25-day warning: it has no state, no field, no transition and no eviction effect, and the protocol, the queue and the fixture do not know about it.

### 3.9 Hooks for lifecycle criteria (11 to 14), protocol part only
- DECISION: the queue store is keyed by UID; the sender takes a per-UID send lease before each attempt and releases it after the answer or cancellation. Sign-out and account deletion must acquire the lease exclusively (waiting for or cancelling the in-flight call) before releasing the UID binding or deleting data. A send never starts without the lease.
- DECISION: the queue file and the writer tokens are excluded from OS backup and device-to-device restore (see 9, device restore).
- DECISION: on the server, an apply for a UID in deletion is refused (8.7), so a send racing with deletion cannot recreate data.

## 4. Server apply

### 4.1 Interface
DECISION (names are proposals): callable `submitWorkoutCommands({ sessionId, items: Envelope[<=25] })` returning one result per item in order; read-only `getWorkoutCommandOutcomes({ operationIds[<=50] })` for status after restart (reads the fence and receipts of the caller, applies nothing); read-only `getSessionState({ sessionId })` returning `{ exists, sessionGeneration, deletedGeneration, writerEpoch, writerDeviceInstallId, quarantineCount }` (never the token hash); `takeOverWorkoutWriter({ sessionId, deviceInstallId })` returning the new `writerToken` once; `deleteWorkoutSession({ sessionId, expectedSessionGeneration, expectedRevision })`; `ackLegacyDrain({ deviceInstallId, migrationEpoch })`; `getLegacyQuarantine({ sessionId? })` (without `sessionId` it lists every unresolved entry of the caller, paginated, including entries whose session no longer exists). Authentication is required on all; the UID is the authenticated UID only.

Every per-item answer, including non-terminal ones, carries `sessionState = { exists, sessionGeneration, deletedGeneration, writerEpoch, writerDeviceInstallId }`, so a client can OBSERVE the generation and the writer (updating `observed_generation`) but a server answer never changes the generation of an already accepted operation (5.5). The same fields (without any token hash) are mirrored on the client-readable `workout_sessions` document.

### 4.2 One Firestore transaction per item
All reads first, then all writes, in one `runTransaction` (the package already requires one atomic effect, `04_CORE_TDD.md` section 4). Storage used by the apply (8.3): the server-only canonical typed session `workout_typed_sessions/{sessionId}` (session content plus controls: `sessionGeneration`, `writerEpoch`, `writerDeviceInstallId`, `writerTokenHash`, `lastSeqByTarget`, `maxSeqSeen`, `resolvedOps`, `revision`, `quarantineCount`), the client-readable projection `workout_sessions/{sessionId}`, and the tombstone `workout_session_tombstones/{sessionId}`. Steps:

1. Parse and validate: schema for the received `(protocolVersion, hashVersion, limitsVersion)`, ASCII ids, integer ranges (limits of 2.5, whose reps and grams values are the package proposals, FACT in `API_CONTRACTS.json` `x-boundaries.existing_domain`, labelled there as new schema limits needing domain review). Recompute `payloadHash`. Reject `payload.uid != auth.uid` with `UID_MISMATCH` and an `operationId` whose `uidTag` differs from the tag of `auth.uid` with `ID_UID_MISMATCH`, in both cases before reading any receipt or fence (nothing is exposed). Invalid shape -> `INVALID_PAYLOAD` (client defect, nothing recorded). Retired version -> see 2.5 (after step 3).
2. Read `AccountCommandPolicy` (`users/{uid}/workout_command_policy/current`, package name, FACT in `05_DATA_MODEL.md` section 2). Absent, or account deleting, or `sendingPaused`, or the device not drain-acknowledged in state `DRAIN`: non-terminal `MIGRATION_HOLD` / `ACCOUNT_DELETING` (nothing recorded). Per-user rate limit (DECISION), ORDER FIXED in gate round 1 (PI-M03): the limit is NOT evaluated in this step but at step 3b, after the permanent fence lookup of step 3 and only for an item that lookup found nothing for, so a replay of an already applied operation always receives its stored outcome (`ALREADY_COMMITTED` class) even when the day's counter is at the limit. For a new item, more than 2,000 applied commands in the current UTC day, or more than 50 session creations in the current UTC day, returns non-terminal `RATE_LIMITED` with a retry-after time. It bounds fence growth under abuse; the 500-record backlog drain is below it. Counter location: one document per user per day, `users/{uid}/workout_command_counters/{utcDay}` with `applied` and `sessionsCreated`, read and incremented INSIDE the per-item transaction of step 8 (PI-M03), so an applied command and its count commit or fail together: no crash can leave an applied command uncounted and concurrent batches serialize on the counter document of that user (acceptable contention: one user, one day, at most 25 items per call). The limit is therefore exact, not a soft bound, and a batch near the limit may be refused item by item with `RATE_LIMITED`. The counter is an abuse and capacity bound, not a correctness mechanism. The collection is carved out of the wildcard like the other command collections (5.3).
3. Read the fence shard (and its spill documents, 5.2) for the item. If an entry exists for the operation digest, go to the idempotency table 4.3 and return; no effect. 3b. (R2-M03) For an item with no fence entry, read the daily counter document `users/{uid}/workout_command_counters/{utcDay}` and evaluate the limit of step 2 now, before any write of the transaction (every read of a Firestore transaction must precede its first write); on excess return non-terminal `RATE_LIMITED` (nothing recorded). The increment of the counter is written at commit together with the effect, the fence entry and the receipt of steps 7 and 8.
4. Read device/account revocation state (UNKNOWN: the existing server representation of device sessions; the package assumes one, `04_CORE_TDD.md` section 6). Revoked: non-terminal `AUTH_REVOKED`.
5. Read the typed session document, the projection (only for the conversion case of 8.3), the tombstone, and the fence entries of each `dependsOn` id.
6. Decide, in this order. Let `T` = tombstone `deletedGeneration` (0 if none), `G` = typed document `sessionGeneration` (if it exists), `g` = the item's hashed `sessionGeneration`.
   a. Existence and generation (B-01; no restamping, ever). The tombstone is evaluated BEFORE any create or legacy-conversion branch: a legacy-shaped document that reappears after a deletion (an old client writing a stored copy) is never a source of a new canonical session:
      - The item creates a session (`sessionInit` non-null):
        - typed document exists: `g == G` -> continue (the init data is ignored, nothing is overwritten; the writer check decides); `g < G` -> terminal `SESSION_DELETED_ELSEWHERE`; `g > G` -> terminal `GENERATION_MISMATCH`.
        - typed document absent and the projection is a legacy-shaped document: tombstone first: if `T >= g` (any tombstone at or above the item's generation) -> terminal `SESSION_DELETED_ELSEWHERE`, the legacy document is NOT converted and is left to the trigger (8.3 item 9); otherwise conversion case (8.3), which requires `g == 1` and `T == 0`.
        - typed document absent and no legacy document: `g <= T` -> terminal `SESSION_DELETED_ELSEWHERE` (kept with its data, never recreated, never moved to another generation); `g == T + 1` -> create at generation `g`; `g > T + 1` -> terminal `GENERATION_MISMATCH`.
      - The item does not create a session:
        - typed document absent and no legacy document: if a `dependsOn` init operation is not in the fence -> non-terminal `DEPENDENCY_PENDING`; otherwise terminal `SESSION_DELETED_ELSEWHERE` (covers the case "init applied, session since deleted" and a legacy-era client delete that left no tombstone).
        - typed document absent and a legacy document exists: tombstone first: if `T >= g` -> terminal `SESSION_DELETED_ELSEWHERE`, no conversion (8.3 item 9); otherwise conversion case (8.3), which requires `g == 1` and `T == 0`.
        - typed document exists: `g < G` -> terminal `SESSION_DELETED_ELSEWHERE`; `g > G` -> terminal `GENERATION_MISMATCH`; `g == G` -> continue.
   b. Writer check (B-02): if the typed document is absent (a new session, or a legacy conversion) the item's `writerProof` must be present and becomes the session writer: the server stores `SHA-256(writerProof)` as `writerTokenHash`, `writerEpoch = 1`, `writerDeviceInstallId` = the envelope value (informational). If the typed document exists and is writerless (`writerTokenHash = null`, created by the backfill or the trigger, 8.3 item 5), the first item with a `writerProof` claims it in this transaction: `writerTokenHash = SHA-256(writerProof)`, `writerEpoch = 1`. If the typed document exists with a hash, `SHA-256(writerProof)` must equal `writerTokenHash` (constant-time comparison). A missing or wrong proof -> non-terminal `NOT_WRITER` with `sessionState`, no effect. `writerEpochClaim` and `deviceInstallId` are never used for the decision. A `sessionInit` against an existing typed document never overwrites its fields.
   c. Session status `abandoned` -> terminal `SESSION_CLOSED`.
   d. Dependencies (the rule of 3.4): a `dependsOn` entry absent from the fence -> non-terminal `DEPENDENCY_PENDING`; any `dependsOn` entry with code `R` or `S` -> terminal `DEPENDENCY_REJECTED` (not applied; no evaluation of the item's own preconditions).
   e. Session size: if `resolvedOps >= 2000` -> non-terminal `SESSION_COMMAND_LIMIT`. `resolvedOps` is a field of the typed document, incremented in step 8 by every committed fence entry for the session (including `R` and `S`). Order: this check runs only after the fence read of step 3 missed, so a replay of an already-resolved operation is still answered by I2 to I4 even when the session is at the limit; it runs after the existence and writer checks, so a deleted session or a non-writer gets the more specific answer.
   f. Operation preconditions of 7.1 -> terminal reasons. Sets are addressed by the full set identity `(exerciseId, setIndex)` in every precondition (APPEND slot occupied, CORRECT target missing).
   g. Epoch bound and monotonic guard (F3, M-03; PI-M02): an item whose hashed `acceptedEpoch` is greater than the session's current `writerEpoch` (read as 1 when the typed document is absent or 0) is terminal `INVALID_PAYLOAD` (an honest client can only have observed an epoch that already exists, because epochs only increase), so a future epoch cannot outrank later genuine takeovers. Guard: for SetDifficulty the target is `d:{exerciseId}`; for CORRECT it is `c:{exerciseId}:{setIndex}` (the full set identity within the session; two exercises with set index 1 never share a key). `lastSeqByTarget[target]` stores `(e, originDeviceInstallId, seq)` of the last applied command, where `e` is that command's `acceptedEpoch` read as 1 when 0. The item (with `e'` = its `acceptedEpoch` read as 1 when 0) is terminal `SUPERSEDED` (not applied) when `e' < e`, or when `e' == e` and the stored origin install equals the item's hashed `originDeviceInstallId` and the stored `seq` is greater than or equal to the item's `seq`. Otherwise it applies. `seq` is never compared between different origin installs (R5); a record restored onto a new install keeps its origin install as the scope of its `seq`, so it cannot collide with the new install's own counter. Example A/B/A: A accepts `d:E` seq 5 under epoch 1 offline; B takes over (epoch 2) and applies a newer `d:E`; A takes over again (epoch 3, new token) and sends its seq-5 command: it carries `acceptedEpoch` 1, so `1 < 2` and the answer is `SUPERSEDED`; B's value remains.
7. Apply the one targeted mutation to the typed document: create it if the item creates a session (or convert a legacy document, 8.3), increment `revision`, update `lastSeqByTarget` and `maxSeqSeen`; for an AddEligibleExercise store the exercise with its `orderKey = [e', seq, operationId]` and keep the exercise list sorted by `orderKey` (6). Then write the projection `workout_sessions/{sessionId}` as a full regeneration from the typed document, including the mirrors (`sessionGeneration`, `writerEpoch`, `writerDeviceInstallId`, `quarantineCount`) and `projectionRevision = revision`, and `projectionSeal` (8.3 item 2), and the head document `users/{uid}/workout_session_heads/{sessionId}` with `{ revision, sessionGeneration, contentHash, quarantineCount }` (8.3 item 11). The projection never contains the token hash.
8. Write the fence entry (code `C` for an applied command, `R` for terminal refusals, `S` for `SUPERSEDED`), increment `resolvedOps`, write the detail receipt, and the outbox record if the package requires one for this operation (`04_CORE_TDD.md` section 4). Steps 7 and 8 commit together or not at all.

DECISION: non-terminal results write nothing (no receipt, no fence entry). Terminal refusals write a fence entry with code `R` and a detail receipt with the reason, so a replay returns the same refusal even if preconditions later change (this keeps FU-AC-059 semantics). A transaction that loses a contention race is retried by the Firestore transaction loop and re-reads steps 3 to 6, so a paused or delayed request observes any newer fence entry or `lastSeqByTarget`.

### 4.5 Batch semantics
DECISION: items of one call are processed in order, each in its own transaction. Processing continues after any C1 to C4 and C5a result; it stops at the first C5b or C6 result and the remaining items are returned as `NOT_ATTEMPTED`. Therefore a batch `[invalid, good1, good2]` returns `INVALID_PAYLOAD, COMMITTED, COMMITTED`.

### 4.6 Observability
DECISION: the server emits counters by result code per UTC hour (no payload fields, no UID or `operationId` in the metric labels) and an alert when `NOT_WRITER`, `MIGRATION_HOLD`, `VERSION_RETIRED` or `RATE_LIMITED` exceed 1% of answers in an hour, when any C4 code occurs (client defect), when a client reports an unknown result code (C8, a newer server or protocol than the client), when any fence shard passes 50% fill (5.2), and when the legacy quarantine trigger fails or its backlog is older than 15 minutes (8.3), and when a legacy trigger event is older than 7 days at delivery (8.3 item 2). The client keeps local counters (oldest non-`SYNCED` age in days, count by `lastResultCode`) and shows the banner of 3.8. UNKNOWN: whether any client telemetry may leave the device is a privacy decision of the privacy review; this document requires only the local counters.

## 5. Receipt retention and the replay fence

### 5.1 Why the package model cannot hold with a queue (B-02 of the package review)
- FACT: the package makes admission last 2 minutes and requires, before the 90-day detail TTL, that every birth epoch is durably closed and replay "permanently inadmissible" (`04_CORE_TDD.md` sections 3 and 4; `05_DATA_MODEL.md` retention row). A command first sent after more than 2 minutes, or after the epoch close, is inadmissible there.
- FACT: the queue forbids eviction by age (LOCAL_QUEUE_DECISION criterion 3: the 30-day mark is a warning, not a deadline). A command accepted offline and unsent for 100 days must still be applied once.
- DECISION: so the fence must distinguish "never seen by the server" (apply) from "seen, applied or refused" (never apply again). A time-based or epoch-based inadmissibility cannot make this distinction and is dropped. Instead the fence records every operation the server has ever resolved, permanently, written in the same transaction as the effect.
- DECISION (invariant F1): a fence entry exists for an `operationId` if and only if the apply transaction for it committed (as `C`, `R` or `S`). Because the entry and the effect are one transaction, a fence miss proves "this operation was never applied", for any command age.

### 5.2 The compact fence (kept for the life of the account)
- DECISION: `users/{uid}/workout_command_fence/{shard}` with 256 primary documents at most, `shard` = two lowercase hex characters = first byte of `D = SHA-256("op1|" + operationId)`. Each document has one map field `e`: key = base64url of the first 16 bytes of `D` (22 characters), value = one string of 23 characters: 1 code character (`C` applied, `R` refused, `S` superseded), 11 characters base64url of the first 8 bytes of `SHA-256("s1|" + sessionId)`, 11 characters base64url of the first 8 bytes of the payload hash. A primary document also holds `spill` (integer 0..3).
- DECISION: size bound. One entry is about 45 bytes of payload (about 55 with field overhead). A user who logs 15 sets a day for 10 years makes about 55,000 entries, about 3 MB over 256 documents (about 12 KB each). The per-document guard is 12,000 entries (about 700 KB, below the 1 MiB document limit).
- DECISION (spill): when a shard document reaches 12,000 entries the server creates `{shard}-1` (up to `{shard}-3`) and increments `spill` in the primary document; writes go to the newest spill document; a lookup reads the primary document and its `spill` documents (at most 4 reads). Only when all four are full does the server return non-terminal retryable `FENCE_SHARD_FULL` (fails closed, never evicts). Capacity per user is about 12 million operations. The server raises an alert when any primary shard passes 6,000 entries (50%, 4.6).
- DECISION: relation to the queue cap. The queue holds at most 500 unacknowledged commands (criterion 3); the fence has no count-based eviction at all, so it holds at least the 500 plus every earlier operation. This satisfies criterion 7 ("at least as many receipts per user as the queue can hold plus the retention window"). The 256-receipt proposal of the AI-Coach design is not adopted anywhere in this protocol. The per-user daily limits of 4.2 step 2 bound abusive growth.
- DECISION: the map field `e` is exempt from Firestore single-field indexing, to avoid the write cost of maintaining index entries. UNKNOWN, reviewer-stated and to be confirmed against the Firestore limits of the pinned platform: each map leaf creates 2 index entries (ascending and descending), so 12,000 entries make 24,000 index entries, which is under the 40,000 per-document limit. UNKNOWN: confirm in the emulator and in a staging project that a write to the map key is atomic with the session write in one transaction.
- DECISION: the fence is deleted only with the account (the deletion framework, 8.7). It has no TTL.
- DECISION (collision, stated honestly): a fence hit for an operation that was never applied would silently lose that command. This needs the 128-bit key to collide with an existing key in the same shard (probability about n times 2 to the power -128 for n entries) and, for the answer to be I2/I3 instead of I5, also the 64-bit session digest and 64-bit hash prefix to agree. The probability is negligible; the design relies on that and does not claim the failure direction is harmless.

### 5.3 Detail receipt (cleanup only, not the correctness boundary)
- DECISION: `users/{uid}/workout_command_receipts/{operationId}` holds: `payloadHash` (full), `status` (`COMMITTED`, `REJECTED` or `SUPERSEDED`), `reasonCode`, `effect`, `sessionId`, `exerciseId`, `operation`, `logicalSetId`, `seq`, `originDeviceInstallId`, `revisionBefore`, `revisionAfter`, `serverTime`, `performedAtClientMs`, `clockSuspect`, and `expireAt = serverTime + 90 days`. It is deleted by a Firestore TTL policy (UNKNOWN: TTL policy availability; a scheduled sweep is the fallback). Package retention of 90 days is kept as the proposal (FACT: `05_DATA_MODEL.md` retention row); the closure precondition for deleting it is replaced by invariant F1, because the fence already outlives it.
- DECISION: collections `workout_command_fence`, `workout_command_receipts`, `workout_typed_sessions`, `workout_session_tombstones`, `workout_command_policy`, `workout_command_counters`, `workout_legacy_quarantine`, `workout_legacy_events`, `workout_gaps`, `deleted_accounts`, `audit_coverage_incidents`, `system_flags` are carved out of the wildcard rule (FACT that carve-outs are by name in `firestore.rules` lines 61 to 83) with `allow read, write: if false` for clients; `workout_quarantine_summary` and `workout_session_heads` are carved out of the wildcard in the same change and get a dedicated match with `allow read: if` owner and `allow write: if false` (no overlapping permissive match, so an owner client or a buggy legacy client cannot create, change or delete them; FU-AC-063 and FU-AC-119 test every write form). PI-M01: these rules and their negative tests are a DEPLOY PREREQUISITE of the first callable that writes any of these collections, not a later hardening step. The operator's deferral of the rules gaps until the queue is implemented stays: the carve-out change is the FIRST item of the queue sprint and the callables stay undeployed (or their flag off) until FU-AC-063 passes on the deployed rules; clients obtain outcomes through the callables. The data a client needs to observe (generation, writer epoch, quarantine count) is exposed through the per-answer `sessionState` of 4.1, the projection mirror for display, and the server-only-written head document (8.3 item 11) for trust decisions.

### 5.4 What is answered for an expired detail
- DECISION: with the fence the historical outcome is known in coarse form. Fence `C` with no receipt -> `ALREADY_COMMITTED_DETAIL_EXPIRED` (I3). Fence `R` with no receipt -> `ALREADY_REJECTED` with `reason: UNAVAILABLE` (I4). Fence `S` with no receipt -> `SUPERSEDED` (I4b). None of these re-applies. The client treats I3 as `SYNCED`.
- DECISION: the package status `OUTCOME_EXPIRED` (FACT: `04_CORE_TDD.md` section 10 FC-01 and `API_CONTRACTS.json` `ExpiredHistoricalOutcome`) is kept only for the case where the server has no fence entry and cannot prove a miss means "never applied": operations accepted before this protocol existed, or after a restore of fence data that is older than the session data (not expected inside one Firestore database, since both are in the same database). In that case the server returns `OUTCOME_UNKNOWN_REPLAY_CLOSED`, never applies, and the client shows current canonical history and keeps the record `CONFLICTED` terminal for export. UNKNOWN: whether a point-in-time restore of only some collections is ever performed; the runbook must forbid partial restores of these collections.
- This closes B-02 of the package review for the stated case: an acked-but-lost command replayed after 90 days hits the fence (I3), so no set is duplicated; a command unsent for 100 days misses the fence and is applied exactly once; a replay fence never claims an outcome it does not hold.

### 5.5 Session tombstones and observed generation (B-01)
- DECISION: `users/{uid}/workout_session_tombstones/{sessionId}` = `{deletedGeneration, deletedAtServer, deleteEventTime, deletes[]}`, written ONLY by `deleteWorkoutSession` (8.5) in the same transaction that deletes the typed document and the projection; `deleteEventTime` is the Firestore commit time of that deletion and `deletes[]` appends one `{ generation, deletedIncarnationCreateTime }` per server deletion and is never pruned (no payload). `deletedIncarnationCreateTime` is the `createTime` metadata of the projection document that the deletion transaction itself read and deleted; it identifies that exact incarnation of the document (a deleted and recreated document gets a new `createTime`) and is the durable identity of a server-originated DELETE event (8.3 item 11). It is a value read from the snapshot, not a server timestamp transform, so it can be stored inside the array; `deleteEventTime` is used only to order a later WRITE against the deletion (item 10) and is never used to classify a DELETE event. A legacy client delete never writes a tombstone (8.3 item 10), kept for the life of the account, no workout payload. Size: one tiny document per deleted session. It is what prevents a late command from recreating a deleted session (criterion 9).
- DECISION: a deletion never moves an accepted operation to another generation. `GENERATION_STALE` and any server-side restamping do not exist. A command whose hashed `sessionGeneration` is at or below the deleted generation ends `SESSION_DELETED_ELSEWHERE`, kept with its data.
- DECISION (starting a fresh workout on a reused deterministic id such as `day_X`): before accepting the first command of a day session the client reads the current generation, in this order: its synced view of the projection mirror, `observed_generation`, and when online `getSessionState`. If a deletion of generation g is observed, the new workout uses `sessionGeneration = g + 1` with `sessionInit` (it is a new logical session). If the client is offline and has observed nothing it uses 1; on arrival that command is checked like any other: if a tombstone covers generation 1 it ends `SESSION_DELETED_ELSEWHERE` as a visible conflict, never silently migrated, and the user may start a new session with the "log into a new session" action of 7.2.

## 6. Ordering and dependencies per session

- DECISION: `seq` is the accepted ordinal of one install in one session. It orders delivery from that install and feeds the server guard of 4.2 step 6g. It is not comparable across installs and is not a display order for sets. Gaps left by discarded commands are preserved. The server does not require `seq` to be contiguous and does not require `seq` order across independent commands; it records `seq` in the receipt and stores `maxSeqSeen` in the typed document.
- DECISION (M-05, exercise order): the authoritative ordering key of an exercise is `orderKey = [e', seq, operationId]` where `e'` is the `acceptedEpoch` of the AddEligibleExercise (0 read as 1) and `seq` its accepted ordinal. It is carried in the command (both fields are hashed), stored with the exercise in the typed document, and the exercise list is kept sorted by `orderKey` (ties by `operationId`, lexicographic). Exercises that existed before the first typed command keep their position with `orderKey = [0, position, ""]` and so sort first. Therefore the final exercise order is independent of arrival order and of replays: Add A (seq 1) and Add B (seq 2) delivered B then A, or replayed, end A, B. A takeover is an ordering barrier: commands accepted under an older epoch sort before those accepted under a newer epoch, even if they were accepted later in wall-clock time; this is deliberate because there is no shared clock between devices.
- DECISION: sets inside an exercise are ordered by `setIndex`, never by arrival, so reordered delivery of independent CompleteSet commands yields the same document (FU-AC-097).
- DECISION: correctness comes from explicit `dependsOn` (the literal rule of 3.4), identity rules and the per-target guard, not from contiguity:
  - the first operation of a logical session carries `sessionInit`; every later operation of that session carries it in `dependsOn` until the creating operation is `SYNCED`;
  - CompleteSet or SetDifficulty on an exercise added by a not-yet-`SYNCED` AddEligibleExercise carries that operation in `dependsOn`;
  - a CORRECT carries the APPEND of the same set in `dependsOn` while that APPEND is not `SYNCED`. The longest chain (init, add, APPEND) is why the cap is 3. The server checks every listed dependency directly; transitive sufficiency is not assumed.
- DECISION: last-writer semantics for SetDifficulty and CORRECT is enforced by the server guard, not by delivery order. A request that was abandoned by the client after a timeout may still be alive on the network; if a newer command from the same install and epoch has already been applied to the same target, the late older command is answered `SUPERSEDED` and changes nothing. Final value therefore equals the newest command of the newest writer epoch, and within one epoch and one install the one with the highest `seq`; a command accepted under an older epoch never overwrites a newer-epoch value.
- DECISION: to recover a chain after a terminal predecessor conflict the user resolves it with one of the actions of 7.2; the client creates new ids, new `seq` and new `dependsOn` links and keeps `supersedes` links to the old records.

### 7.3 Terminal rule
DECISION: every refusal caused by data state is terminal and recorded (fence `R`), and a replay returns the same refusal even if the state later changes. Refusals caused by who is asking or when (writer proof, migration, auth, rate, version, dependency pending) are non-terminal and record nothing. This keeps every outcome of a given `operationId` unique over time.

## 8. Writer credential and legacy-writer migration

### 8.1 Writer credential bound to a secret (B-02)
- FACT: ADR-CMD-04 keeps one active writer per workout; an explicit takeover increments a session writer epoch that the commit transaction reads (`04_CORE_TDD.md` section 5; `15_DECISIONS_AND_RISKS.md` ADR-CMD-04).
- Problem fixed: in version 1.2 the writer was a client-supplied string (`deviceInstallId`) plus an epoch that was also readable, so a second device of the same account could present the writer's values. Authority now rests on a secret that only the writing device holds.
- DECISION: the writer token is 32 random bytes. The server stores only `SHA-256(token)` as `writerTokenHash` in the server-only typed document; it is never mirrored on the projection and never returned by any callable except `takeOverWorkoutWriter`, which returns the freshly minted token ONCE, to the calling device. The device keeps it in platform secure storage keyed by (uid, sessionId), never in the queue record, the canonical bytes, an export or a log.
- DECISION: every command envelope carries `writerProof = token` (bearer, over TLS; the server compares `SHA-256(proof)` with `writerTokenHash` in constant time). `writerEpoch`, `writerDeviceInstallId` and `writerEpochClaim` are informational: they are shown in the UI, mirrored for display and used as `acceptedEpoch` for ordering; they never authorise anything. An HMAC proof is not used because it would require the server to store the key rather than a hash.
- DECISION: first claim. A device that creates a session (or is first to touch a legacy session) generates its own token locally at first acceptance (3.3) and sends it as `writerProof`; the server stores its hash and sets `writerEpoch = 1`. Another device that created the same deterministic `day_{dayId}` offline has a different token: its commands get `NOT_WRITER` and its `sessionInit` never overwrites the first device's document; its user may take over.
- DECISION: `takeOverWorkoutWriter` increments `writerEpoch`, replaces `writerTokenHash` with the hash of a new server-minted token, sets `writerDeviceInstallId`, and returns the token once. The previous token is invalid immediately; the previous writer's queued commands are not lost and not applied; they end as `NOT_WRITER` and the user chooses takeover (then the same ids go out with the new proof) or export. UID binding is separate from writer role.
- DECISION: reinstall or restore means no token (secure storage is not restored, or is discarded on an install mismatch, 9): the session needs an explicit takeover before any command is sent.
- Test requirement: B submits A's `deviceInstallId` and A's epoch without A's token: refused with no effect; B's explicit takeover then succeeds; A's later stale operation neither overwrites B's data (guard of 4.2 step 6g and the token check) nor is silently lost.

### 8.2 Migration states
AccountCommandPolicy (`users/{uid}/workout_command_policy/current`, server-only) holds `migrationState`, `migrationEpoch`, `drainedDevices` (map `deviceInstallId` to `lastAckMs`, at most 50 entries; only entries whose device was not seen in the last 90 days may be evicted), `sendingPaused` (boolean), `drainPhase` (`BACKFILL` or `OPEN`, meaningful in `DRAIN`), `backfillStartedAtMs`, `drainStartedAtMs`, `pausedSinceMs`, `pausedTotalMs`. DECISION: exact states:

| State | Client writes to the projection `workout_sessions` | Typed commands | Entered by |
|---|---|---|---|
| `LEGACY_OPEN` (also: policy document absent) | allowed, as today | refused `MIGRATION_HOLD`; the app queue feature flag is off for the account, so the old code path runs | default |
| `DRAIN` | allowed, as today (no denial); the trigger works in its DRAIN mode (8.3 item 10) from the first moment of phase `BACKFILL`; a write that hits a session already owned by typed commands is preserved by the quarantine of 8.3, never dropped | phase `BACKFILL`: `MIGRATION_HOLD` for every device; phase `OPEN`: accepted only from a device present in `drainedDevices` | server cohort enrollment (operator action), only if the preconditions of 8.6 hold |
| `SERVER_ONLY` | allowed and quarantined exactly as in `DRAIN` (the name means that typed commands are the only writer of canonical state) | accepted from any device of the new protocol | server, when ALL conditions of 8.6 hold |
| `SEALED` | denied by rules for create, update and delete of every `workout_sessions` id | as `SERVER_ONLY` | OPERATOR ACTION ONLY, never automatic, see 8.6 and the risk O-R1 |
| `DELETING` | denied | refused `ACCOUNT_DELETING` | account deletion (8.7), reachable from any state, never left |

- DECISION: transitions are forward-only: `LEGACY_OPEN` -> `DRAIN` -> `SERVER_ONLY` -> `SEALED` (optional); an attempted regression is refused. Any state may move to `DELETING`, which is terminal. `sendingPaused` is the rollback lever: it makes the server return `MIGRATION_HOLD`, queues keep accumulating on devices (nothing lost, bounded by the 500 cap), and voice and touch keep working locally. Reopening whole-document writers after typed commands have committed is not needed and is not done: legacy writers are never refused before `SEALED`.
- DECISION: while `sendingPaused` is true the DRAIN clock is frozen: `drainStartedAtMs` is set when phase `OPEN` starts (the 30 days count only after the backfill is proved complete), and elapsed drain time is `now - drainStartedAtMs - pausedTotalMs - (now - pausedSinceMs if paused)`, and the cutover of 8.6 is forbidden.
- FACT: the package FC-02 requires `SERVER_ONLY` to deny client create, update and delete of every `workout_sessions` id (`04_CORE_TDD.md` section 10). This document does not meet that before `SEALED`, on purpose: denial would silently destroy legacy work (operator decision of 2026-10-22: no silent loss). See 11.3 item 11.

### 8.3 Coexistence and preservation without overwrite, duplication or loss (B-03)
DECISION: canonical state of a converted session lives in the server-only typed document `workout_typed_sessions/{sessionId}` (same session content as `WorkoutSession` plus the controls of 4.2). The client-readable document `workout_sessions/{sessionId}` is a PROJECTION that the server regenerates in full at every apply (4.2 step 7) and that carries `projectionRevision`. Existing readers and exports keep reading the projection unchanged. Consequences:
1. No overwrite: a legacy whole-document `.set` can only replace the projection. It cannot touch the typed document, so typed sets are never erased by a late legacy write.
2. Detection, provenance and repair: a Firestore document trigger on `workout_sessions/{sessionId}` (UNKNOWN: runtime and retry support) looks at every write event. Provenance (M-02 of round 3): the server seals every projection it writes: `projectionRevision` and `projectionSeal = kid + HMAC-SHA256(key[kid], canonical form of the document without projectionSeal)`, with the key held server-side only (UNKNOWN: secret store and key rotation; verification accepts every non-retired `kid`). An event is a SERVER write when its `after` carries a valid seal. This is independent of order and repetition: a delayed or repeated event of an OLDER server revision still verifies, so it is never mistaken for a legacy write, and a repair-generated projection is sealed like any other. A legacy whole-document `.set` drops the seal; a partial client `update` that keeps an old seal but changes any content fails verification; a client cannot forge a valid seal without the key (rules additionally deny client-created or client-changed `projectionRevision`, `projectionSeal`, `sessionGeneration`, `writerEpoch`, `writerDeviceInstallId` and `quarantineCount`; absence after a whole-document `.set` is allowed, because that is what an old client does and rejecting it would lose its write; FU-AC-119 tests the rules and the seal separately). Every other event is classified by the class of the session (item 10). For class (A), a typed document exists: the trigger runs ONE transaction (M-03 of round 3) that reads the processed-event marker of this event (`users/{uid}/workout_legacy_events/{sessionId}~{eventKey}` = `{ outcome, expireAt }`, server-only, created by EVERY trigger run in its transaction; `expireAt` is the event commit time plus 30 days, UNKNOWN: TTL availability; deleted with the account. Durable idempotence does not rest on this marker alone (R7-M02 of round 7): quarantine entry ids are permanent and a resolved entry is never deleted, the typed document keeps `convertedFromEventId` permanently, and the deployment invariant is that the trigger's retry window and message retention are at most 24 hours (checked at deploy; UNKNOWN: the platform limit), so an event is never delivered after its marker expired. If the invariant were ever broken, an old `NOOP` or `CONVERTED` event could only produce an extra, visible, resolvable quarantine entry, never a loss; the alert of 4.6 fires on any event older than 7 days at delivery. The no-op rule of item 10(c) is evaluated BEFORE a quarantine entry is created; an event whose id equals `convertedFromEventId` is also a no-op), the typed document and the current projection, and (a) the checks run in this fixed order inside the one transaction (R8-M01 of round 8): (i) the marker exists -> do nothing, whichever outcome it recorded (`CONVERTED`, `QUARANTINED`, `NOOP`, `IGNORED_SERVER`), with ONE exception (R4-B01): the audit marker `{sessionId}~a-{auditKey}` of outcome `GAP` (item 12), found by a processor that holds the event's own snapshot (the trigger computes the auditKey of its write from the path, `after.updateTime` and WRITE). That processor treats the marker as absent and runs the class-specific handling on its snapshot (class A: (ii) to (iv); class B: the `POST_DELETE_WRITE` or no-op outcome of item 10; class C: conversion of item 10), so the exception is a shared step 0 for EVERY session class, and in the SAME transaction it writes the actual outcome marker under the eventKey, flips the audit marker from `GAP` to `RESOLVED_BY_EVENT`, moves the gap record from OPEN to RESOLVED and decrements `gapTotal`, each step guarded by the current status read in that transaction (compare-and-set), so concurrent or duplicate deliveries serialize on those documents, only the first changes anything, and a later delivery finds the eventKey marker and does nothing; (ii) no marker, but the permanent quarantine entry `workout_legacy_quarantine/{sessionId}~{eventKey}` exists in ANY status (unresolved or resolved) -> write the marker with outcome `QUARANTINED` and change nothing else (not the entry, its resolution, its payload or any counter); (iii) the event id equals `convertedFromEventId` of the typed document -> write the marker with outcome `CONVERTED`; (iv) only when none of the three evidence items exists, continue to the no-op rule and the classification below; the entry is written with a create that fails if it exists, never with an unconditional set; (b) otherwise it writes the marker and creates the quarantine document `users/{uid}/workout_legacy_quarantine/{sessionId}~{eventKey}` (a copy of the incoming document, server-only) and increments `quarantineCount` on the typed document and `unresolvedTotal` on the account summary (8.4); (c) in both cases, if the CURRENT projection does not carry a valid seal for the latest typed `revision` and count, it rewrites the projection and the head document from the typed document as read in this same transaction. A concurrent typed apply writes the same typed document, so Firestore serializes the two transactions and the loser retries and re-reads; a repair can therefore never write a projection derived from an older typed revision, and an event whose current projection is already valid changes nothing. `quarantineCount` equals the number of unresolved entries of the session under any retry, resolving an entry (8.4) decrements it in the transaction that marks the entry resolved, and the repair events are sealed and therefore are not themselves quarantined.
3. Visible, not silent: a session with `quarantineCount > 0` shows "data saved by an older app version is waiting for review" (8.4). The quarantine copy is kept until the user resolves it, is included in the export, and is deleted with the account. It is never aged out.
4. Legacy delete (B-02 of rounds 2 and 3): for class (A) a delete event on the projection is NOT honoured automatically, because an old device may deliver it long after other devices wrote newer typed sets. The trigger quarantines it as a `DELETE_INTENT` entry in the same transaction as item 2 and regenerates the projection. The session shows "an older app version asked to delete this workout" with the number of sets that would be lost. Only an explicit user action deletes it, through `deleteWorkoutSession({ sessionId, expectedSessionGeneration, expectedRevision })`. One transaction compares BOTH values with the current typed document: a mismatch of the generation OR of the revision returns `STALE_DELETE` with the current `sessionState` and changes nothing (revision numbers restart with a new generation, so revision alone cannot identify the content the user saw); the client then shows the current content and the user must confirm against it. A delete event caused by the server's own deletion finds no typed document and does nothing. In `LEGACY_OPEN` there is no typed document; an old client delete leaves no tombstone, which is why 4.2 step 6a treats "absent, no pending init" as `SESSION_DELETED_ELSEWHERE`.
5. Conversion: when a typed command meets a session that exists only as a legacy-shaped projection (no typed document), the apply transaction reads that projection (the transaction detects a concurrent legacy write and retries) and creates the typed document: set ids are positional, each existing set is marked `source = LEGACY_UNVERIFIED` (package label, `05_DATA_MODEL.md` section 8), `revision = 1`, `sessionGeneration = 1`, exercises get `orderKey = [0, position, ""]` (6). Writer authority (R6-M02 of round 6): a session created by the typed apply gets `writerEpoch = 1` and the hash of the claimant's proof; a session created by the backfill or by the trigger is WRITERLESS (`writerTokenHash = null`, `writerEpoch = 0`) because no device is present; the first typed item from the authenticated owner claims it atomically (4.2 step 6b), a later device gets `NOT_WRITER` and uses `takeOverWorkoutWriter`, which also works on a writerless session (result `writerEpoch = 1`). Authentication of the UID is always required; there is no unauthenticated claim. The same routine is used by the typed apply (4.2 step 6a), by the server backfill and by the trigger (item 10); it first checks that no typed document exists in its own transaction, so whichever transaction commits first creates the typed document and the others find it.
6. Duplication: a typed CompleteSet APPEND whose set identity slot is already occupied by a `LEGACY_UNVERIFIED` set (FACT: the legacy player holds one set per exercise, so index 1 is the same physical set) is refused as `DUPLICATE_LOGICAL_SET` (I8); the user may fix it with a CORRECT command (new id). No value is guessed and no set is added twice.
7. Write amplification: each apply writes the typed document, the projection, the head, the fence entry and the receipt (five documents); each legacy write after conversion adds one quarantine write and one projection regeneration. UNKNOWN: cost and trigger latency; the alert of 4.6 covers a trigger backlog older than 15 minutes.
8. A legacy write that races with the typed apply between two projection regenerations is overwritten on the projection, but its trigger event still carries the legacy `after` snapshot, so it is still quarantined.
9. Late legacy write after deletion (class (B), B-01 of rounds 2 and 3, B-02 of round 4): while a tombstone exists and no typed document exists, a client write to the projection is copied by the trigger, in one transaction, to the quarantine (kind `POST_DELETE_WRITE`) with `unresolvedTotal` incremented, and the projection document is removed so that it can never be read as a conversion source (4.2 step 6a). The entry is owner-discoverable WITHOUT the session id through the account-level inventory of 8.4. A typed command of the same generation gets `SESSION_DELETED_ELSEWHERE`; a new session needs the explicit new-session intent of 7.2, or the owner's "restore as a new workout" choice on the quarantine entry (8.4). Readers do not show a restored projection as a workout: it fails the trust check of item 11.
10. Eager conversion and the legacy delete rule (replaces the class-C ledger and fence of 1.3.4). Principle: once an account is in `DRAIN` or later there is no long-lived "legacy-only" session, and a legacy delete is never authoritative. (a) At entry to `DRAIN` a server backfill converts every existing `workout_sessions` document of the account by item 5 (typed document with `LEGACY_UNVERIFIED` sets, sealed projection, head); `DRAIN` may start only when the backfill reports complete (P5 of 8.6). (b) Every later legacy event (create, update, delete) is handled by the trigger in one transaction whose first step is the processed-event marker of item 2 together with the shared GAP resolution of item 2 (R5-M02: it applies to classes A, B and C alike, before and after the class-specific outcome in the same transaction) (so a redelivered event, including the first event that converted a session, changes nothing: no second quarantine entry, no counter change, one head), by what exists: a typed document exists -> class (A), items 2 and 4; no typed document and a tombstone exists -> class (B): a write committed after `deleteEventTime` is quarantined as `POST_DELETE_WRITE` and the projection removed (item 9), a delete event is a no-op (the server wrote the tombstone before its own deletion); no typed document and no tombstone (a never-seen id created by an old client, or an event that overtook the backfill) -> the trigger converts the event's own snapshot (`after` for a write, `before` for a delete) into a typed document by item 5, regenerates the sealed projection and head (for a delete this RECREATES the document) records the marker with outcome `CONVERTED` and sets `convertedFromEventId` on the typed document and, for a delete, records a `DELETE_INTENT` entry. Every later or reordered event for the session then finds the typed document and is class (A), so a divergent snapshot is quarantined and never overwritten, in whatever order events are processed. (c) No-op rule (R6-B01 of round 6): an event is ignored (marker outcome `NOOP`) only when the full normalized legacy model of its snapshot equals the legacy image of the typed state field by field: `id`, `title`, `exercises`, `startedAt`, `completedAt`, `status`, `durationMinutes`, `notes` and every set (`weightKg`, `reps`) at its position, with no set or exercise of the typed state missing from the snapshot. Any difference, including a changed note or status, or a set or exercise that the snapshot no longer contains (a removal is a user intent), makes the whole snapshot a quarantine entry that records the differing fields. (d) The consequence for users is stated honestly: a workout deleted in an old build reappears with the review prompt of 8.4 until the owner confirms the deletion in a current build; this is the price of the operator decision of 2026-10-22 (no silent loss). Only `SEALED` denies legacy writes.
12. What "no silent loss" means and what backs it (PI-B01; gate round 1 of the pre-implementation fixes). Guarantee, stated exactly: the EXISTENCE of every accepted legacy write is accounted for by an inventory that does not depend on the trigger, so a write can never disappear without a record; the CONTENT of an overwritten snapshot is recovered on a best-effort basis inside a bounded window and, when it cannot be recovered, the loss is recorded and disclosed (never silent). The design does not claim lossless content preservation under every failure. (a) AUTHORITATIVE INVENTORY (the answer to the missing inventory): Firestore data-write audit logs for the database are enabled and exported by a log sink to a store with retention of at least 30 days; each client write to `workout_sessions/{id}` under `users/{uid}` appears there with its document path and commit time. EVENT KEY (R2-M01), the one identity shared by every processor: eventKey = SHA-256 of `path|kind|versionTime`, where kind is WRITE or DELETE and versionTime is, for a create or an update, the `updateTime` of the version that the write produced (trigger: `after.updateTime`; watchdog: the audit commit time, which equals it; UNKNOWN until the deploy check verifies the equality) and, for a DELETE, the `updateTime` of the version that was deleted (trigger: `before.updateTime`; watchdog: the `updateTime` shown by the exact read taken just before the audit commit time). From v1.5.2 the processed-event marker, the quarantine entry id and `convertedFromEventId` use the eventKey wherever this document says eventId; the trigger's own `eventId` survives only as an informational field of the marker. Trigger, watchdog and backfill all compute the key from document versions and apply the checks of item 2 in the same order inside one transaction (marker, permanent quarantine entry, convertedFromEventId), so a delayed trigger finds the marker that the watchdog wrote and the reverse; one accepted write yields one terminal outcome, one entry and one counter change. If the deleted version of a DELETE cannot be established by an exact read, the watchdog writes a gap record and never a guessed key. (b) WATCHDOG, every 10 minutes, per account in `DRAIN` or later: for every audit-log write older than a 15-minute grace period it requires a processed-event marker with the same eventKey; a write with no marker is a MISSING EVENT. Before it is counted, one exact read of the document at that commit time (point-in-time read) decides whether the write created a version (R2-M02): `NOOP_WRITE` is recorded only when the read shows an `updateTime` EARLIER than the audit commit time, which proves that no new version was produced (Firestore does not change `updateTime` for a write that changes nothing). A read showing `updateTime` equal to the commit time proves a new version exists, so the write is an event to process by the item-2 rules (even when a later write restored the earlier value); the content is never compared with the current canonical state to decide a no-op. If the exact read is unavailable the write is not a `NOOP_WRITE`: it is a recoverable event or a gap record. For a missing event the watchdog runs the item-2 conversion/quarantine logic itself on the document version read at the commit time (so the content is quarantined by the same transaction as the trigger would have used, with the same idempotent ids) and writes the marker; it also quarantines a projection that is not a verified server write and has no marker. (c) GAP RECORD: if the version at a commit time cannot be read exactly (the point-in-time read is unavailable or older than one hour and a second write fell in the same minute), the watchdog writes `users/{uid}/workout_gaps/{auditKey}` = `{ auditKey, sessionId, statusUnknown, commitTime (null when keySource is INSERT_ID), keySource, observedAt, kind, lossProven, status, detectedAt, contentRecoverable: false }` (server-only, 5.3), raises the alert of 4.6 and counts it in the account-level summary of 8.4; the owner sees "some changes made with an older app version may be missing" in the review inventory and the export lists the gap records, so the loss is disclosed. (d) WHY THE WINDOW IS MET IN NORMAL OPERATION: Firestore point-in-time reads are exact to the microsecond for the last hour and keep one version per minute for the rest of the retention (7 days), so two snapshots committed in the same minute can be told apart only inside that hour. The watchdog detects and recovers within about 25 minutes (10-minute interval plus 15-minute grace), inside the exact window. Only a watchdog outage longer than one hour combined with multiple writes in one minute can make a snapshot's content unrecoverable; a watchdog heartbeat older than 30 minutes raises the alert, and the loss is still recorded by (c) because the inventory (a) still lists the write. (e) DEPLOY GATE (fail closed): no account enters `DRAIN` until the checks P3 pass: trigger retries enabled, data-write audit logs enabled with the sink and the 30-day retention, point-in-time recovery enabled, and a replay test of the inventory comparison (below). UNKNOWN until verified: audit-log coverage of client SDK writes to Firestore; if the audit log does not list them, this inventory does not exist and the legacy path stays closed to `DRAIN` (the product then needs the stronger option of the operator: deny legacy writes after the minimum-version gate, which is the O-R1 trade-off). AUDIT KEY AND TERMINAL ACCOUNTING (R3-B01, R3-M04): every audit record has a stable identity auditKey = SHA-256 of `path|commitTime|op` (op is WRITE or DELETE and is taken per successful mutation as defined in AUDIT EXTRACTION below, never from the method name; one document has at most one commit at a given commit time), independent of the eventKey, so it survives repeated passes, concurrent watchdogs and restarts. An audit record is ACCOUNTED, and later passes skip it, when ONE of these exists: (1) the marker of its eventKey; (2) the marker `{sessionId}~a-{auditKey}` (outcomes `DELETE_NOOP`, `WRITE_NOOP`, `GAP` and `RESOLVED_BY_EVENT`); (3) the gap record `workout_gaps/{auditKey}`. A gap record = `{ auditKey, sessionId, commitTime, kind, lossProven, status, detectedAt }` with kind `WRITE_CONTENT_LOST` (lossProven true: independent evidence proves that a version existed, either an exact read showing `updateTime` equal to the commit time or a delivered trigger event naming that version, and its content cannot be recovered), `WRITE_UNVERIFIED` (lossProven false: the audit record is the only evidence and the version-producing effect of the write cannot be established, so an identical no-op write can end here) or `DELETE_UNVERIFIED` (lossProven false: the effect of a delete could not be established) and status OPEN or RESOLVED; it is created with create-if-absent in the SAME transaction that increments `gapTotal` (so two watchdogs, a retry or a restart give one record and one increment) and, for a WRITE, writes the audit marker `{sessionId}~a-{auditKey}` with outcome `GAP`. WRITE_NOOP rule (R4-M02): an exact read at the commit time that shows an `updateTime` EARLIER than the commit time proves that no version was produced; the watchdog writes the audit marker `{sessionId}~a-{auditKey}` with outcome `WRITE_NOOP` (no eventKey exists for it), creates no gap, no entry and no counter change, and repeated or concurrent passes find the marker. AUDIT EXTRACTION (R4-M01, R5-M01): the audit processor expands every SUPPORTED audit record into one item per SUCCESSFUL document mutation and skips failed mutations. The supported shapes and the source of the per-mutation commit time are: (1) a single `Commit` (including a transaction commit and a client batch): the `commitTime` of the commit response applies to every write of the commit, update or delete, and a write that contains only field transforms is a WRITE; (2) the streaming `Write` call used by the mobile SDK listen-and-write channel: the `commitTime` of each write response applies to the writes it acknowledges, with the same rules; (3) `BatchWrite` (a server-side bulk API, non-atomic, with no commit time in its response): UNSUPPORTED for updates and deletes alike (R6-M01, R6-M02): the `updateTime` of the write result of a write that changed nothing is the PREVIOUS update time and so cannot identify the operation, and a delete result carries none; no independently verified commit time exists. STATUS VALIDATION AND COVERAGE INCIDENTS (R8-M01, R9-M01, R9-M02): validation is method-specific. (1) The per-write `status` list exists ONLY in the non-atomic `BatchWrite` response, so the check "present, parseable, index-aligned with the writes list (entry i describes write i)" applies to BatchWrite only; a BatchWrite mutation is OK only when its status is explicitly OK, FAILED only when explicitly non-OK, and UNKNOWN in every other case (absent, truncated, extra, misaligned or unreadable, which includes an export that omits response elements); only FAILED takes the skip path. (2) A single `Commit` and the streaming `Write` have NO status list (the commit is atomic): they are validated by their own required fields, namely the commit time and a write-result list whose length equals the writes list; a record that carries them is OK and creates nothing, and a record that lacks a required field is UNKNOWN. (3) UNKNOWN fails closed: when the path and the operation of the item are readable, the item is accounted at once as a per-account gap of kind `WRITE_UNVERIFIED` or `DELETE_UNVERIFIED` (the neutral kind `UNVERIFIED` when the path is readable and the operation is not) with `statusUnknown` true and `lossProven` false, keyed by SHA-256 of `path|logInsertId|op|itemIndex`; it never claims that the write succeeded. (4) When the affected account cannot be established (the path is unreadable) the item cannot be written under any account: it creates a DATABASE-LEVEL coverage incident `audit_coverage_incidents/{incidentKey}`, incidentKey = SHA-256 of `logInsertId|itemIndex`, fields `{ incidentKey, observedAt, reason, affectedUidTags (the uidTags of 2.6 that ARE known, possibly empty), status }` with status OPEN, neutral by design (no WRITE or DELETE provenance is invented) and server-only (5.3). A record that lists writes for several accounts creates the per-account gaps of (3) for every account whose path is readable and one incident for every unreadable item. When the exported record has no enumerable writes list at all (absent, empty although the method requires writes, or unreadable), no item index exists: the record creates ONE record-level incident keyed by SHA-256 of `logInsertId|RECORD`, with the same neutral kind and the same global hold (R10-M01). (5) While any incident is OPEN the cutover to `SERVER_ONLY` is refused for EVERY account and entry to `DRAIN` is refused for every account (a global hold held in `system_flags/audit_coverage`), because no account can be proven unaffected. An incident is closed ONLY by reconciliation (R10-M02): the affected accounts are established from verified evidence, their per-account gaps are created (so the owners see them in the inventory and the export) and the incident is then marked closed; an incident is never deleted and an operator acceptance NEVER closes it, because a closure without attribution would leave an owner without a disclosure. A broader business waiver for incidents that cannot be attributed is a separate operator decision (O-R3, not taken), with its own release criterion and a database-wide user notice, and it never inherits the acceptance of O-R2. (5b) Atomic fence (R10-M03): `system_flags/audit_coverage` holds `openCount`, equal to the number of OPEN incidents; creating an incident and incrementing `openCount` is ONE transaction; every entry to `DRAIN` and every cutover to `SERVER_ONLY` is a transaction that READS this document and requires `openCount` equal to 0 in that same transaction (a concurrent incident creation writes the same document, so one transaction retries and sees the other, and no phase change commits against a stale flag); closing an incident is a transaction that decrements `openCount` together with the status change and refuses to go below 0; the watchdog checks the count against the OPEN incidents and alerts on any mismatch. (6) In every UNKNOWN case the alert fires and the per-account flag `unsupportedAuditShapeSeen` is set for the accounts that are known. UNSUPPORTED ITEMS (R6-M01, R6-M02): a SUCCESSFUL item (its status evaluated first; failed items are skipped as in the extraction rule above and never reach this rule, never create a gap and never set the flag) of a BatchWrite, or of any record whose commit-time source is absent, is never given a key built from an invented time. It is accounted at once as a gap of kind `DELETE_UNVERIFIED` or `WRITE_UNVERIFIED` with `keySource` INSERT_ID, keyed by SHA-256 of `path|logInsertId|op` (the unique insert id of the log entry), with `commitTime` null and `observedAt` set to the log timestamp, and the alert is raised. No 24-hour waiting applies and no correlation with a later trigger event is attempted (no proximity matching exists anywhere in this design): a trigger event for the same operation, if one arrives, is processed normally by its own eventKey and holds the content, and the gap stays as a disclosed over-report until the owner acknowledges it. Lifecycle: BEFORE `DRAIN` an unsupported shape in the deploy sample or in the account's audit window refuses entry to `DRAIN` (fail closed); AFTER `DRAIN` has begun the phase never regresses: the account policy document gets the flag `unsupportedAuditShapeSeen`, the alert fires and the cutover to `SERVER_ONLY` is refused while the flag is set, until the operator clears it after reviewing the gaps. UNKNOWN until the deploy check captures them: which of these shapes the audit log actually contains for client SDK traffic and which request and response fields it retains; the auditKey is computed per mutation. The deploy check feeds ordinary writes, mixed update-and-delete batches, streaming writes and failed mutations through the processor and fails when any required field is absent or a key is not deterministic; the fail-closed `DRAIN` gate of (e) then applies. DELETE rules: an exact read just before the delete commit that shows the document ABSENT proves a no-op delete (a delete of an already deleted document): the watchdog writes the marker `~a-{auditKey}` with outcome `DELETE_NOOP`, creates no gap, no entry and no counter change, and repeated passes find the marker. A delete whose deleted version cannot be established (no exact read) is NOT guessed: while the trigger can still deliver (the audit record is younger than the 24-hour retry window) nothing is written and the pending item raises the alert after one hour; after the window a gap record of kind `DELETE_UNVERIFIED` is created, whose copy says the change could not be verified and never claims lost content. A late trigger finding the audit marker with outcome `GAP` follows the exception of item 2 (R4-B01): it processes its event from its own snapshot (it holds the content) and resolves the gap atomically and exactly once; a gap is never deleted by anyone. Residual risk O-R2 (operator-visible, not hidden, not yet accepted): the CONTENT of a snapshot is lost, and disclosed through a gap record, when the trigger failed permanently, the watchdog was down for more than an hour and two writes fell in one minute. Existence is never lost. the verdict still counts it as a disclosed gap, while an unaccounted audit record always FAILS; (xiv) audit extraction: ordinary writes, mixed update-and-delete batches, streaming writes and failed mutations each yield exactly one deterministic auditKey per successful document mutation, and any missing metadata keeps the account out of `DRAIN`; 11. Reader trust boundary and DELETE events (M-02 and M-03 of round 4, M-02 of round 5). Reader trust: the head document `users/{uid}/workout_session_heads/{sessionId}` is written only by the server, in the same transaction as every projection write (apply, repair, backfill, trigger conversion), and holds `revision` and `contentHash` = SHA-256 of the canonical JSON of the projection without `projectionSeal`. A new client in an account in `DRAIN` or later treats a projection as authoritative for history, progress, coach context and export only when `projection.projectionRevision == head.revision` AND the SHA-256 of the projection it read, computed the same way, equals `head.contentHash`; otherwise the session is shown as "verifying" and is excluded from aggregates and from the export until the repair or conversion converges (bounded by the 15-minute alert of 4.6). Because the backfill converts every existing session before `DRAIN` and the trigger converts any new legacy document, every real session has a head, so existing workouts never disappear from history (they appear with provenance `LEGACY_UNVERIFIED`, not as verified typed facts). A projection with no head and a tombstone (class B) is not a workout. Before `DRAIN` (`LEGACY_OPEN`) clients do not use heads. The HMAC key is never needed by a client, and a copied seal does not help a forger because the check is against the server-only head. Server-side readers (export function, coach) read the typed document, not the projection. DELETE events carry no `after`, so classification uses, in this order (R6-M04 of round 6, R7-M03 of round 7): (1) the processed-event marker (item 2); (2) SERVER ORIGIN (R8-M02 of round 8): the `createTime` of the event's `before` document equals the `deletedIncarnationCreateTime` of an entry of `deletes[]` -> the event deletes an incarnation that the server itself deleted and is a no-op, even when a newer typed session exists and even when the `before` image lost its server fields to an old whole-document `.set` (a `.set` on an existing document keeps its `createTime`). The match is exact equality of the document's own metadata; no proximity of times, no time window and no fallback by closeness is used anywhere. A legacy DELETE of the generation 2 document has a different `createTime` (the document was recreated), so it never matches. UNKNOWN: that the pinned trigger SDK exposes `before.createTime`; if it does not, this step cannot match and classification continues to (3) and (4) unchanged (the trigger path is NOT disabled; a deploy check only records whether the pinned SDK exposes it). COMPLETE MATRIX (gate round 1, PI-M05), exactly one outcome per combination: createTime available and equal to a `deletes[]` entry -> NOOP (server origin), whatever the before generation; createTime available without a match, or createTime unavailable: before generation present and lower than the current typed generation or at or below the tombstone `deletedGeneration` -> NOOP (stale older generation); before generation equal to the current generation, or absent (stripped by a legacy whole-document `.set`) -> deletion intent. With createTime unavailable, a server DELETE that still has an intact generation-1 before-image is therefore a NOOP by generation, and only a delete without generation evidence yields the conservative visible intent; (3) otherwise, by the generation of the `before` image (the projection mirrors `sessionGeneration`): lower than the current typed generation, or at or below the tombstone `deletedGeneration`, is a stale event of an older generation and a no-op; (4) otherwise a typed document exists -> deletion intent (item 4), including a `before` with no generation (an unsealed legacy document), which stays non-authoritative; no typed document and a tombstone -> no-op; neither -> conversion of `before` plus a deletion intent. Duplicate and reordered delivery change nothing because every action is keyed by `eventId` or creates a document only if absent.

### 8.4 Quarantine review flow
DECISION: discovery is account-level first (M-01 of round 3). The server keeps the client-readable summary `users/{uid}/workout_quarantine_summary/current = { unresolvedTotal, gapTotal }`, changed only inside the trigger, watchdog and resolve transactions that create or resolve an entry or a gap record (once per entry, same rule as item 2; `gapTotal` counts the records of 8.3 item 12 written by the watchdog in the same transaction as the record). A client that sees `unresolvedTotal > 0` OR `gapTotal > 0` (R2-B01) shows a persistent entry in the history area: "data from an older app version is waiting for review" for quarantine entries and, as separate copy, "some changes made with an older app version could not be recovered" for gap records with `lossProven` true and "some changes made with an older app version could not be verified" for the others (a gap-only account therefore shows the warning); acknowledging a gap hides the prompt but never deletes or alters the record and the copy never claims recovery; opens `getLegacyQuarantine()` for the full list (any session id, including sessions that no longer exist; the same call returns the gap records of 8.3 item 12 without needing a session id, and a gap can be acknowledged but never deleted by a client), and shows the legacy sets next to the current ones where the session exists. For each legacy set the user chooses "use this value" (the client creates a CompleteSet CORRECT, or an APPEND if the slot is free, through the normal accept path with `source = LEGACY_QUARANTINE`, new ids; it is never applied by the server on its own) or "keep current". For a `POST_DELETE_WRITE` entry the choices are "export", "dismiss" and "restore as a new workout" (an explicit new-session intent of 7.2 with a new generation; the deleted session is never recreated by the quarantine on its own).  For a `DELETE_INTENT` entry the choices are "delete the workout" (the confirmed `deleteWorkoutSession` of item 4) or "keep it". "Export and dismiss" marks the entry resolved but does not delete it. The account export (QUEUE_LIFECYCLE_DATA_PRIVACY.md) includes every unresolved quarantine entry with its kind and every gap record, so the export is never silently incomplete (FU-AC-049, FU-AC-119 scenario 18). Nothing in the quarantine changes canonical state without an explicit user command.

### 8.5 Drain barrier on the device and ack
- DECISION: a new-protocol client in a `DRAIN` account (a) stops issuing `.set` for the three operations (no direct fallback), (b) obtains a verified flush of its legacy write queue, (c) then calls `ackLegacyDrain({deviceInstallId, migrationEpoch})`, which records the device in `drainedDevices`. Until the ack, typed sends return `MIGRATION_HOLD`; local acceptance continues unaffected. The barrier is no longer what prevents loss (the quarantine is); it reduces quarantine events and gives the cutover its evidence.
- DECISION (flush mechanism and fallback): the primary mechanism is the SDK `waitForPendingWrites`. UNKNOWN: its availability in the pinned `cloud_firestore` version and its behaviour offline are not verified, and the package warns that the SDK queue cannot be enumerated (`04_CORE_TDD.md` section 7). Fallback: write a marker document (`users/{uid}/sync_markers/{deviceInstallId}`, ordinary client collection) through the normal SDK path and wait for its server acknowledgement; UNKNOWN: this relies on the SDK acknowledging writes in submission order, to be verified in a test with an old-build stub. If neither can be verified, the new client does NOT enter `DRAIN`: it never sends `ackLegacyDrain`, typed sends stay `MIGRATION_HOLD`, the queue accumulates (bounded by 500) and the account cannot reach `SERVER_ONLY` (8.6). A fresh install with an empty persistence cache acks immediately (nothing can be pending).
- DECISION: a device that is not in `drainedDevices` shows "finishing update" and retries the barrier on each app start. Reinstalls get a new `deviceInstallId` and ack immediately, so they cannot be stuck by the size of the set.
- DECISION: session deletion is the server operation `deleteWorkoutSession(sessionId, expectedSessionGeneration, expectedRevision)`, available from `DRAIN` on: in one transaction that first compares the typed `sessionGeneration` and `revision` with the expected values (8.3 item 4), reads the `createTime` of the projection it is about to delete and records it in the tombstone `deletes[]` (5.5), it deletes the typed document and the projection and writes the tombstone with `deletedGeneration = generation of the deleted session`. FACT: today delete is a plain client delete (`firestore_workout_session_repository.dart` lines 73 to 76); new builds switch to the callable when the account is in `DRAIN` or later; an old build's direct delete is quarantined as a deletion intent and is NOT applied without the owner's explicit confirmation (8.3 item 4).

### 8.6 Preconditions, cutover and sealing
Preconditions to enter `DRAIN` (fail closed: if any is not true the account stays `LEGACY_OPEN`):
- P1 (mandatory): a minimum-version gate is live and has been live for at least 30 days. UNKNOWN: the app has no verified gate; if none exists, building one (a remotely set minimum build number checked at app start and on resume, which blocks the logging UI of older builds with an update prompt) is a deliverable of the rollout that precedes the first `DRAIN`. It limits new legacy writes; it is not what prevents loss.
- P2: the verified flush of 8.5 exists in the new client (either mechanism).
- P3: the trigger, the quarantine collection and the carve-outs of 5.3 are deployed and covered by FU-AC-119.
- P4: a registry of devices seen on the account exists (UNKNOWN: the device-session registry the package assumes). Without it the account cannot leave `DRAIN` (fail closed).
- P5 (R6-M01 of round 6, R7-M01 of round 7; what the scan proves and what it does not): entering `DRAIN` sets `drainPhase = BACKFILL` and `backfillStartedAtMs`, and from that instant the trigger runs in its DRAIN mode for every event it processes for the account (8.3 item 10). The safety argument is a partition in time, not a claim that nothing is in flight: events whose documents existed before `backfillStartedAtMs` are covered by the scan, which converts every existing `workout_sessions` document (item 5); every event that arrives after `backfillStartedAtMs` is converted or quarantined by the trigger, and a typed command that meets a document not yet converted converts it with the same routine (4.2 step 6a), so no accepted write is ever left outside typed state or quarantine whatever the trigger lag. The scan is repeated as a CLEAN SCAN: a full pass started after `backfillStartedAtMs` that finds, for every document, a typed document and a head whose `contentHash` matches the projection or a processed-event marker of its latest event. The server sets `drainPhase = OPEN` by compare-and-set on `migrationEpoch` and on the identifier of the clean scan that is being committed. `OPEN` therefore certifies exactly this: every document that existed at the start of the clean scan was converted and verified; it does NOT certify that no later legacy event is awaiting its trigger. Such an event is covered by the trigger (its backlog alert is 15 minutes, 4.6), by the "verifying" reader state of 8.3 item 11 and by typed-command conversion; the `SERVER_ONLY` cutover (8.6) additionally requires a quiet trigger backlog. A failed or unclean scan is repeated; the account never leaves phase `BACKFILL` on a time basis. Without the backfill the account stays in `LEGACY_OPEN` (fail closed).

`DRAIN` -> `SERVER_ONLY` (operator decision of 2026-10-22: the 30 days is a MINIMUM, not a deadline). It happens only when ALL hold: (a) unpaused `DRAIN` time is at least 30 days; (b) every device seen in the last 90 days has acknowledged a verified flush (is in `drainedDevices`); (c) `sendingPaused` is false; (d) the trigger backlog alert of 4.6 has not fired during the last 24 hours. `DRAIN` is open-ended per account: if (b) is not met because a device is dormant or unknown, the account stays in `DRAIN`, legacy writes keep being accepted into the projection, typed commands are accepted from drained devices only, and nothing is denied. No calendar deadline moves an account forward.

`SERVER_ONLY` -> `SEALED` is an operator action, never automatic, and optional. Proposed preconditions (checked by the tool that performs it): at least 180 days in `SERVER_ONLY`, zero legacy quarantine events for the last 90 days, and the registry shows no device on a build older than the gate within 180 days. Effect: rules deny client writes to `workout_sessions`.
- Residual risk O-R1 (operator-visible, NOT accepted by this document): after `SEALED`, a write held in the persistence cache of a device that was last seen more than 180 days before the sealing (or was never registered), on a build older than the gate, that reconnects without updating, is denied by the rules and the old build shows nothing (FACT 1.3: it swallows the rejection). That cohort and only that cohort can lose a legacy write. Sealing is therefore a separate decision; not sealing loses nothing, at the price of a client-writable projection that the trigger keeps repairing. See 11.1.

### 8.7 Account deletion and fence
DECISION (PI-B02; ordering fixed in gate round 1): the deletion fence outlives the policy document and is created in the SAME transaction as the irreversible state. Order: (1) all reversible pre-checks of the existing deletion flow (including the payment-provider checks) run first; a failure here changes nothing on the server, the local sending fence of the lifecycle document (state FENCED) may be cancelled by the user and the account stays fully usable; (2) ONE Firestore transaction creates `deleted_accounts/{uid}` = `{ deletingSince, expireAt: null }` (server-only write, no payload) AND sets `migrationState = DELETING` in the policy document; from this commit on the deletion is irreversible and cancellation is no longer offered (the client button is removed once the begin call returns success; a begin call whose answer was lost is retried idempotently and answers `ALREADY_DELETING`; R3-M01: the checkpoint carries a client-generated `deletionRequestId` that makes every retry of the begin call the same logical request, and ONLY an explicit server answer that nothing started (a typed pre-check refusal or `NOT_STARTED`) removes the local fence; a timeout, a transport error or a missing answer is ambiguous: the checkpoint and fence are kept, the app shows "verifying", retries the idempotent call with backoff and resumes normal operation only after `NOT_STARTED`; R2-M04: the client writes `beginAttempted` into its local checkpoint BEFORE the call, and a recovered `FENCED` checkpoint with `beginAttempted` reconciles the server state through that idempotent call before Cancel is offered: `ALREADY_DELETING` means committed and recovery is forward-only, `NOT_STARTED` means cancellation is still possible, and an unreachable or ambiguous server keeps the fence and shows "verifying" with no Cancel; see the lifecycle document 4.3); (3) after the commit the server revokes the user's refresh tokens (idempotent, retried until it succeeds; the fence already blocks every write, so a failed revocation cannot reopen a path); (4) a deletion job completes forward only: it is idempotent and is retried until it ends, a crash at any point resumes at the step it had reached, and the fence stays in force the whole time; (5) when the deletion completes the job sets `expireAt = completionTime + 24 hours` on the fence document; the TTL policy on `expireAt` removes it (a document whose `expireAt` is null or absent is never expired, so an incomplete or delayed deletion keeps its fence however long it takes; UNKNOWN: the TTL policy availability, fallback a scheduled sweep of documents with a past `expireAt`). The fence is checked by the security rules and by every server writer: EVERY rule match that grants a client write under `users/{uid}/**` or to `workout_sessions` (the wildcard and each dedicated match, since overlapping permissive grants combine) carries the same `!exists(/databases/$(database)/documents/deleted_accounts/$(uid))` condition, one `exists()` per write, within the rules call budget; every server writer (apply, trigger, watchdog, backfill, callables) refuses with `ACCOUNT_DELETING`. The fence document is NOT deleted with the account data; a new sign-up always gets a new uid, so no legitimate writer is blocked. The absence of the policy document therefore means `LEGACY_OPEN` ONLY when no fence exists. Then client sends are cancelled and the queue cleared, then server data including fence entries, receipts, typed documents, projections, tombstones, quarantine, processed-event markers, quarantine summary, session heads, gap records and counters is deleted, the policy document last, the fence last of all (by TTL). An apply for a missing policy document is refused (`MIGRATION_HOLD`) and a write under a fence is refused, so nothing is recreated after deletion completes (criterion 13). The legacy trigger and the watchdog must ignore events for a UID under a fence. Test (FU-AC-119 scenario S25): force a payment pre-check failure (cancellation works, no fence, writes accepted); crash immediately before and immediately after the fence transaction (both or neither of fence and DELETING); crash before token revocation (forward recovery revokes, writes denied meanwhile); delay the final deletion beyond 24 hours (the fence persists, `expireAt` is null); complete it (`expireAt` set, expiry only afterwards); then attempt direct SDK create, update and delete through the wildcard and through EVERY dedicated match, with a previously issued token and delayed writes: all refused, no document recreated. The account deletion also deletes the device-side `effective_set` rows (markers and values), `intent_keys` and all stubs. UNKNOWN (shared with the lifecycle document, see 11.2 item 5b): how the existing deletion framework (referenced as an extension point in `05_DATA_MODEL.md` section 2, row DeletionTombstone) and the deployed deletion function with its Stripe pre-checks would host this state; their code was not read.

| Device restore or new phone | The queue file and the writer tokens are excluded from OS backup. The client binds the queue to a `deviceInstallId` stored outside backup. DECISION: on a mismatch every record keeps its `operationId`, bytes, `seq`, `acceptedEpoch` and `sessionGeneration`; `originDeviceInstallId` stays as informational history; the records go to `CONFLICTED` non-terminal "restored from backup, review before sending" (T15) and nothing is sent automatically; any restored token is discarded. The server seq guard never compares `seq` across different origin installs, so a restored `seq` cannot collide with the new install's own counter; duplicates of already-applied commands are removed by the fence. | Fence shard full | Spill documents first; only after 4 full documents a retryable hold with an alert, nothing evicted | 5.2 |
| Legacy write races a typed command, or arrives after conversion | Accepted into the projection, quarantined by the trigger, projection repaired, typed state intact, user sees the review prompt | 8.3, 8.4 |
| Dormant old build with a queued legacy write reconnects | Same as above while the account is not `SEALED`; after `SEALED` see the cohort of O-R1 | 8.6 |
| App upgrade with a queue | Unsent records are rebuilt under the current version with the same ids; sent records keep their bytes | 2.5 |
| Migration paused | Records stay eligible, the DRAIN clock is frozen, cutover is forbidden | 8.2 |
| Server rejects as `INVALID_PAYLOAD` | Client defect; record kept `CONFLICTED`, independent records keep syncing; release blocked in test (FU-AC-095 vectors) | 4.4 |

## 11. Open questions and unknowns

### 11.1 Operator-visible risks and decisions
- O-1 (DECIDED by the operator on 2026-10-22): the 30 days of `DRAIN` is a MINIMUM period, not a deadline; cutover to `SERVER_ONLY` additionally requires that every device seen in the last 90 days has acknowledged a verified flush; dormant or unknown devices keep the account in an open-ended `DRAIN` in which legacy writes keep being accepted; and a legacy write is never silently dropped (8.3 preservation). Correction to earlier versions: the old build shows no error when a write is rejected (FACT 1.3), so preservation, not an error message, is the protection.
- O-R1 (risk, not accepted by this document, new): sealing the rules (`SEALED`, 8.6) would silently lose a legacy write only for a device last seen more than 180 days before the sealing (or never registered), on a build older than the gate, holding an unflushed write and reconnecting without updating. Recommendation: do not seal in v1; keep `SERVER_ONLY` with the quarantine. This is a deferrable operator decision; nothing in v1 depends on it.
- Q-1 (new, operator decision recommended before implementation): the preservation design (8.3) moves canonical state to a server-only typed document and turns `workout_sessions` into a server-regenerated projection that old clients may still overwrite (and the trigger repairs). This departs from the package's "one canonical WorkoutSession document" and from FC-02's "SERVER_ONLY denies client writes". Recommendation: accept; it is the only design found that keeps old-client writes without loss. Alternative: deny legacy writes after the minimum-version gate and accept the O-R1-style loss earlier, which contradicts the operator decision on silent loss.

### 11.3 Contradictions found in the inputs
1. Package v1 canonical payload includes `expectedRevision` and `writerEpoch` (`COMMAND_GOLDEN_VECTORS.json`, `API_CONTRACTS.json`), which an offline-accepted command cannot know or keep stable across retries. Resolved by hashVersion 2 (2.2); `sessionGeneration` stays hashed.
